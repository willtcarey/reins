# ADR-039: Node processes: one primitive that outlives its link; git and `nodes.run` run on it to their end; extensions' keyed processes are the host's

- **Status:** Accepted
- **Date:** 2026-11-08, revised 2026-11-11 (processes outlive their link, protocol 18; keyed processes)
- **Author:** Will (with Claude)
- **Amends:** [ADR-018](018-process-run-and-fs-methods.md) (`process.run` goes: git runs on `process.start`), [ADR-013](013-server-holds-credentials.md) (secrets reach a node as a process's environment), [ADR-029](029-sessions-on-the-server-nodes-host-tools.md) (`pi.exec` is the agent's bash only)

## Context

Stdio MCP servers are to run on the session's node, the server staying the MCP client. That needs a process on a node that the server writes to (stdin) and reads from (stdout, newline-delimited JSON-RPC) for as long as it is in use, not tied to a tool call. The node had two ways to run things: `process.run` (git: argv, raw stdout on a stream, stderr's tail at the end, no stdin, killed with its stream) and `pi.exec` (the agent's bash: Pi's bounded, merged and sanitized output view, kept 60 s after a dropped link and reattached by offset, waited for by a node reload). `nodes.run` was on `pi.exec`, with a spill file read back past 1 MiB.

An app reload (every save of server code in dev) or a server restart drops every node link. A process that ended with its link would stop every MCP server at each of them, to be started and initialized again, losing its state; dev servers per project, a language server per checkout and a tunnel have the same need. And the extension that started a process is reloaded too, keeping nothing in memory: something must keep track of the process across the reload.

## Decision

**One process primitive on the node: `process.start`**, with `process.attach`, `process.write` (stdin, base64 chunks, answered once the pipe took them) and `process.stop`. Its stdout and stderr come in one stream, as tagged frames in the order the node read them, ending with the exit once both pipes have closed: so the exit never arrives before the output, and stderr needs no stream or tail of its own. `process.run` is removed. A run to completion is a wrapper on the server: `NodeDirClient.spawner` starts with `stdin: false`, reads stdout and takes the exit from the stream's end, and stops the process (`process.stop`) when its stdout is cancelled. Git and `nodes.run` (`bash -c` with stderr joined to stdout) use it. `pi.exec` stays, for the agent's bash only: its view, spill and reattachment are what a tool call needs, and Pi's `exec` takes no input.

**A process outlives its stream** (protocol 18). The node keeps each process's output frames with byte offsets in a bounded tail (`PROCESS_TAIL_BYTES`, 8 MiB: a reader of whole messages that misses part of a line must start again); what the open stream has not sent is never dropped, so a slow reader loses nothing. A stream's end (`stream.cancel`, the connection closing, another stream attaching) leaves the process running: with no stream open it runs on for `PROCESS_GRACE_MS` (60 s, as `pi.exec`'s), then is stopped. Only `process.stop` stops it at once. `process.attach {streamId, processId, offset}` → `{pid, offset, lost, input}` reopens its output from a frame boundary, stopping any older stream; from an offset older than the tail it starts at the oldest frame kept and says how many bytes were `lost`; unknown is `not_found`. `processId` stays separate from `streamId`: a process has a stream per link (ADR-017: resuming is the method's, not the transport's). `process.write` takes an input `offset`, so a write resent after a dropped link is not taken twice (as `fs.write` chunks), and `input` in the attach's answer is where a new attacher's writes start. The tail, the grace period and attaching are one helper (`OutputBuffer`, `packages/node/src/output-buffer.ts`) that `pi.exec` uses too. A node reload or shutdown stops its processes, so they are lost; a pause does not wait for them.

**The server's `NodeProcess` attaches again** from the offset it had read to on the node's next link, within the grace period, and resends its writes and stop meanwhile. `exited` resolves only for a real end: its exit, a stop, or the node no longer having it (`not_found`: it restarted, or the server stayed away past the grace period). An app has one handle per process.

**Stopping reaches the process group**: each process is started detached (its own group); stopping closes stdin, sends SIGTERM to the group, then SIGKILL after `PROCESS_STOP_GRACE_MS` (3 s). When the process exits by itself, what is left of its group is stopped too, so an `npx`/`uvx` wrapper's server and a stray background child do not outlive it.

**Bounded both ways.** Stdout: the server's stream buffer (`MAX_STREAM_BUFFER_BYTES`), so a process whose stdout nobody reads fails, and a line length (`maxLineBytes`, 8 MiB by default) enforced where lines are split, on the server, which must join a line's chunks anyway. Stdin: writes are serialized and answered once the pipe has the bytes, and the server holds at most `MAX_PENDING_INPUT_BYTES` (16 MiB) not yet taken. Stderr: the server keeps its last 64 KiB characters. On the node, output a stream has not sent yet is kept whole: Bun (1.3.9) reads a child's pipes as fast as they fill, paused or not (measured: 200 MB read into memory), so while a stream is open the server's limit, which stops the process, is the bound; with none open, the tail. At most `MAX_NODE_PROCESSES` (64) run at once on a node, git's included (an exited one kept for an attach does not count); one more is refused `unavailable`, retryable (it certainly did not start). The spawner waits that out, for up to its retry window even when its client does not wait for the node, so git calls in parallel queue rather than fail. A long-running caller gets the refusal.

**Environment values may be secrets** (ADR-013 keeps credentials on the server; an extension may still choose to give a value to a process, as `nodes.run`'s `env` already did). They cross the link once, in `process.start`, and the node keeps nothing of them after it spawned the process; neither side logs call parameters. They are in the process's environment on the node (`/proc/<pid>/environ`, readable by the node's user), never in its arguments. The host's records (below) keep only an HMAC-SHA256 of the command, `cwd` and environment under the server's key (`crypto.ts`), so they can be compared without being guessed off the server.

**Extensions only.** `reins.nodes.spawn` is not a `ScriptMethod`: a process outlives the call that starts it, and a script's work ends with the script. A session's own background processes need a lifecycle the session owns (its deadline, its close, a lost process told to the session; docs/TODO.md), which is not built.

**An extension's processes across a reload are the host's, by a key the extension gives**; the extension keeps no process IDs. `reins.nodes.spawn(node, command, { key, ifRunning })`: a key is unique per extension and node. The host records (extension, node, key, process ID, pid, output offset, the keyed hash, how it ended) in a table of the main database, `processes` (`models/processes.ts`, `AppState.processes`), under an owner (`extension:<name>`), not in the extension's database: the host must find an extension's records when its code does not load, to stop them, and its database is the extension's own. **Reattaching is opt-in:** by default (`ifRunning: "replace"`) a spawn with a key stops a live process under it (once it has ended: a dev server must free its port) and starts a fresh one, so code that knows nothing of reattaching is never handed one; `ifRunning: "attach"` gives a handle on the live process (`reattached: true`), else starts one. Calls on one key are taken one at a time, so concurrent attaches share one process; a call that finds the process an earlier call of the app started gets that call's handle. A recorded hash that differs from the one given replaces the process. **Without a key** nothing is recorded: the process is the extension's, stopped when it is unloaded (a disposer, a reload, turning it off) and when the `signal` it gave aborts.

**Lifecycle of keyed processes.** An app's stop (a reload, a restart) first, while its node links are open, stops the extensions' processes without a key and lets go of the keyed ones, recording where their output was read to (`AppState.processes.release()`, from `server.ts`). An extension unloaded in a running app (its own reload, turning it off, removal) has its keyed processes let go before its disposer runs, so a disposer that stops its handles stops none of them. Once an extension is not loaded (turned off, removed, or its code did not load, after a reload or a restart included), the host stops its recorded processes and forgets them (`Processes.stopOwners`, after `Extensions.start`'s loads and after each operation on one extension). One on a node not connected, as every node is just after a restart, is stopped when its node connects within the grace period; past it, the node has stopped it itself.

**Also:** `reins.nodes.processes()` lists the extension's records (key, node, pid, state: `running` in this app, `detached`, or `ended` with how), before any spawn; `reins.nodes.stop(node, key)` stops one without a handle and forgets the key; a spawn that finds its key's process gone says how it ended (`previous`: its exit, or lost with its node); output lost past the tail is a count of bytes on the handle (`lostBytes`); a handle let go resolves `exited` with `detached: true`. **Records do not expire:** one whose node stays offline is kept, as the host cannot tell whether its process still runs; it goes when its key is used again, `stop(node, key)` forgets it, or its extension is not loaded. Records are a few per extension, bounded by its keys.

**Tool providers know their caller.** `ToolProvider.search` and `call` get `sessionId: string | null`, the calling session's ID; null for an extension's own `reins.tools`. Only the ID: the provider reads the session's project, task and node with `reins.sessions.get` (a session cannot move while its script runs), so the core passes no copy of its row. A script method's `ScriptContext` is the same, `{ sessionId, signal? }` (its `projectId` and `taskId` went: no extension read them). A provider can then run a tool on the session's node, or hide one from a session.

## Options considered

- **Extending `pi.exec` with stdin.** Rejected: Pi's `exec` has no input, and its output view (merged, sanitized, cut at 1 MiB) breaks JSON-RPC.
- **`process.start` beside `process.run`.** Rejected: the same spawn, stderr tail and stream ownership twice; git gains process groups and the stop sequence by sharing it.
- **A process owned by the connection that started it** (a dropped link stops it; no reattaching): the decision of protocol 17, as MCP restarts on a lost connection. Replaced in protocol 18: every reload and restart would stop every MCP server.
- **Making only keyed processes outlive their link** (a start flag). Rejected: a network blip would still stop a keyless MCP server mid-session; git's processes run on for at most the grace period after a dropped link, and its spawner stops one whose stdout it cancels.
- **The extension keeps its process IDs** (in its database) and attaches by ID. Rejected: every extension would repeat the bookkeeping, and an extension whose code does not load could not have its processes stopped.
- **Records in the extension's database.** Rejected: the host must read them when the extension's code does not load, and the extension's database is its own.
- **Reattaching by default.** Rejected: code that knows nothing of it (a log tail, one-off work) would be handed a process in a state it did not expect.
- **A host-side keeper that attaches every recorded process at an app's start**, so that none expires before its extension attaches. Not done: the extension attaches at its load, well within the grace period, and one that does not want a process lets it go.
- **A handle per caller**, each reading from where it attached (agreed first). Dropped: it took a shared reader on the server fanning output out to every handle, with a buffer and listeners each, for callers that can share one handle (an MCP client owns its server). Likewise listeners for lost output: `lostBytes` is read after a `spawn`.
- **A record expiry** for nodes that stay away. Left out: a record costs a row, and dropping it would lose the reason a later spawn reports.
- **Stderr on a stream of its own** (`process.stderr`, the node's tail then what follows). Replaced: its end and the exit came on separate streams, so the exit could arrive before the last of stderr.
- **Line framing on the node.** Rejected: the stream splits lines into chunks again, so the server would join them anyway; one place splits and bounds them.
- **Exempting one-shot runs from the process limit.** Rejected: a mode flag; waiting on a retryable refusal costs nothing.
- **`spawn` for scripts.** Not yet (above).

## Consequences

- Protocol 18: a server and node must restart together; an older node from source is refused with "the node is too old: update it", a node bundle is told to update.
- Git's stdout always crosses as base64 (a third larger than text on the wire); the bytes are the same as before.
- `nodes.run`'s output is no longer limited by Pi's view, and no spill file is written or removed; it is bash (`bash` on the node's `PATH`).
- Stdio MCP servers can survive reloads: an MCP client spawns its server with `key: "mcp:<server>"` and `ifRunning: "attach"`; reattached, it resumes without initializing again, keeping the server's capabilities and tool list, and starts again when `lostBytes` is not 0.
- After a server crash, the recorded output offset is the one of the last let-go or start: output since then is read again by the next attach.
- A git process whose link dropped runs on for up to the grace period on its node.
