# ADR-031: Session Run State from Pi and the Live Runtime

- **Status:** Accepted
- **Date:** 2026-10-18
- **Amends:** [ADR-029](029-sessions-on-the-server-nodes-host-tools.md) (a runtime no longer applies `runStarted`; recovery finds pending runs from Pi; a child's report is keyed by Pi's operation ID, not the settlement's count) and [ADR-021](021-explicit-node-reload.md) (the server resumes the runs Pi has in progress, not those it "still sees `running`")
- **Plan:** [session-run-state-from-pi.md](../plans/completed/session-run-state-from-pi.md)

## Context

Reins kept its own copy of each run on the `sessions` row: `run_id`, `run_started_at`, `activity_state = 'running'`, `settlement_count`, `settlement_json` and `settlement_next_seq`. The copy dates from when runs lived on nodes and the server learned of them only through lifecycle reports: ADR-010's per-session report watermark (`node_session_watermarks`, migration 035, with `settlement_count`/`settlement_json` for waits and later `settlement_next_seq`), moved onto the session row with `run_id` when ADR-015 made the node stateless. ADR-021's recovery resumed every session the server "still sees `running`", trusting that row because the node delivered a run's reports before letting it go, and ADR-029 kept all of it when runs moved to the server, keying a child's report to its parent by the settlement's count (`child-report:<childId>:<n>`).

Since ADR-029, Pi's storage and the runtime that drives it are both in the server process, and the copy only drifts. In this checkout's database, 3 sessions had Pi's result `completed` and the row `failed: "The run was interrupted"`: the settlement was lost when the process exited while applying it, recovery found "nothing pending" and stamped the run interrupted, and a child in that state reported a false failure to its parent. Recovery and node removal patched the copy when it drifted, and a standalone compaction (reported started through `compaction_start`, never ended by `run_end`) would have left a row `running` for good.

What Pi 0.85 stores (plan §1): the lane state (`pi.lane.state`: the current operation, set from its accept to its terminal commit, the last one and the inbox), each operation's meta while it is in progress, and one `pi.result` per finished operation, never deleted, written with the lane state's change in one atomic terminal commit. Nothing durable says whether anyone is driving an operation: one an exit cut off looks the same as one being driven now.

## Decision

**Running is the live state of this process; Pi's storage records unfinished work and how operations ended; the row records only what Reins decided or what the user did.**

- **Running is derived, in the session store.** A session runs while the process has it busy: a submission in progress, a live runtime that `isBusy()` (streaming, or a run's end still being applied: its record, a child's report), or an opening of a session Pi has an operation in progress for (recovery's resume before it drives). The store gets the process's open sessions with its database at each app's start (`injectProcessState`) and returns `activity_state` with its three values as before, so the views, scripting and the frontend are unchanged. Nothing writes `'running'`; the stored column holds only the unread flag (`finished`) or null. The runtime announces its busy edges (`session_updated`) and offers `whenIdle()`, which waits use.
- **The row keeps three things Pi cannot hold:** the unread flag, the automatic resume budget (`auto_resumes`) and one record of the last run end Reins applied (`settlement_json`: `{operationId, source, status, error?}`). `source: "pi"` is Pi's `run_end` (with the runtime's `checkout_unavailable` override, which Pi records as `aborted`); `source: "reins"` is an end Pi cannot express: a run given up as interrupted (budget spent, resume failed, node removed) or a storage fault. "Given up" needs no flag: Pi's current operation named by the record with `source: "reins"`.
- **`run_id`, `run_started_at`, `settlement_count` and `settlement_next_seq` go.** When a run started is Pi's (`startedAt` of its result, or of its meta for a run given up while in progress), which task-close quieting uses.
- **A child's report is keyed by Pi's operation ID:** `child-report:<childId>:<operationId>` for Pi's end, `…:<operationId>:interrupted` for Reins' give-up (the same operation may still end in Pi after a manual resume: another report). Both are deterministic from durable state, so a replay after a crash between the steer and the settlement forms the same key, which Pi recognises.
- **Recovery finds pending runs from Pi.** At process start the first app resumes every session whose main lane has a current operation that the record does not name with `source: "reins"` (a partial index over the lane states, migration 056), within the resume budget; it gives up (records `source: "reins"`) when the budget is spent or the resume fails. A run given up is left alone at later starts: it reads idle with its operation pending (the Resume button). Node removal gives up the same pending runs of its sessions without a live runtime.
- **Waits** rest on the live state plus the inputs the caller named still queued in Pi; their outcome is the record when it names Pi's newest run result or the current operation, else Pi's newest run result (an end whose settlement an exit cut off). They sleep on `whenIdle`, the submission chain and the opening, with a slow fallback poll.
- **Reads of Pi's storage go through one module** (`pi/run-state.ts`), with Pi's exported address helpers and types: its published storage contract for `Storage` implementers, versioned with the package. A Pi upgrade that changes the format fails typechecking there; pi-durable replaces that module.

**Rollout across hot reloads.** New app code duck-types the runtime (`isBusy?`, `whenIdle?`): a live runtime built before `isBusy` still stores `'running'`, which counts while it is the session's live runtime, and a wait falls back to polling it. A give-up checks the old count-keyed report before steering, so a crash straddling the key change does not report twice. Existing records were backfilled with their operation and source (migration 056). Dropping the four columns and clearing leftover stored `running` is a migration of its own (057), applied with a restart: an old runtime still live after it would fail its lifecycle writes. With it go the fallback for runtimes built before `isBusy` (both `isBusy` and `whenIdle` become required) and the count-keyed report check.

## Consequences

- The drift class goes: a lost settlement no longer leaves a stale `running` row blocking task deletion and moves, nor gets reported to a parent as an interruption. A wait reads its real outcome from Pi.
- **A lost run end's effects are lost:** a run Pi ended whose settlement the exit cut off has nothing pending, so recovery does not see it; its unread flag and a child's report are not applied. Rarer and less wrong than the false failure. A catch-up at process start is possible (the plan's *Later*); not built.
- **Steers stranded by a crash** (committed to an idle lane's inbox before the runtime started a run from them) stay in the inbox: nothing is current, so recovery does not see them, as before (*Later*; not built). A wait naming one keeps waiting until its deadline.
- A run interrupted before its task closed and resumed after it keeps its original start, so it stays quiet; before, the resume re-stamped `run_started_at`.
- Reins reads Pi 0.85's storage format behind its API, confined to one module. No list query reads Pi's JSON: "is it running" is the live state (an opening alone looks up its lane), and the readers are point lookups (the detail view's `pendingOperation`, a wait's outcome, task-close quieting) plus recovery once at start and node removal, over the partial index.
- A faulted runtime may read idle just before its storage fault's settlement is recorded (it is applied outside the runtime); accepted, since a faulted runtime is reopened at its next use.
