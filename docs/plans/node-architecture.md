# Node Architecture

Status: **local process split done; server-canonical storage done ([ADR-015](../adr/015-server-canonical-storage-stateless-node.md)); remote nodes done: pairing and authentication ([ADR-023](../adr/023-node-pairing-and-challenge-authentication.md)), the WebSocket transport ([ADR-024](../adr/024-node-link-origin-from-the-upgrade-request.md)), server-managed sources on remote nodes ([ADR-026](../adr/026-sources-managed-on-the-server.md)), and code delivery with self-update ([ADR-025](../adr/025-node-version-handshake.md)); sessions on the server, nodes host tools, done ([ADR-029](../adr/029-sessions-on-the-server-nodes-host-tools.md)). Open: the local node on the bundle, node management, choosing a session's node and the items below.** Every session runs on the server: AgentHarness over its storage in the server's database, the server's model runtime and credentials, kept across reloads in a process-owned runtime map ([session-runtime.md](../dev/session-runtime.md)). Every node is a tool and file host: it runs the agent's file operations and commands, git and the file browser's reads on its checkouts, runs no Pi and holds nothing durable. The local node is a separate process linked over a Unix socket, run from source by the supervisor; a remote node is installed from the server with one command, runs the server's node bundle and links over a WebSocket. The completed phases are recorded in [completed/node-local-process-split.md](completed/node-local-process-split.md), [completed/server-canonical-storage.md](completed/server-canonical-storage.md), [completed/node-pairing.md](completed/node-pairing.md) and [completed/remote-nodes.md](completed/remote-nodes.md), and the move of sessions to the server in [ADR-029](../adr/029-sessions-on-the-server-nodes-host-tools.md); the current design is in [node-transport.md](../dev/node-transport.md), [node-contract.md](../dev/node-contract.md), [session-runtime.md](../dev/session-runtime.md) and [node-bundle.md](../dev/node-bundle.md).

## Motivation

Support multiple machines (e.g. a Mac and a Linux box, or disposable cloud machines), each with their own checkouts, connected to one Reins server, and eventually a hosted server with users connecting their own machines as nodes. Browser traffic, including agent events, stays routed through the server.

```mermaid
graph LR
    Browser[Browser] <-->|HTTP + WS| Server
    subgraph Server host
        Server[Reins server\nproduct DB, session storage,\nsession runtimes, models, credentials]
        Local[Local node\ntool host, git, checkouts,\nno durable state]
        Server <-->|JSON-RPC over\nUnix socket| Local
    end
    Remote[Remote node\ntool host, git, checkouts] <-->|JSON-RPC over\nWebSocket /nodes/link| Server
```

## Server-canonical storage (done)

The server's SQLite is the only session storage and the node holds nothing durable ([ADR-015](../adr/015-server-canonical-storage-stateless-node.md)). How it was delivered, the storage-traffic measurements behind the decision and the deferred write-behind decorator for high-latency links (not built, and moot since sessions run on the server: storage no longer crosses the link, ADR-029) are in [completed/server-canonical-storage.md](completed/server-canonical-storage.md).

## Remaining work

- [x] **Explicit node reload and automatic resume:** a CLI or an agent's `execute` script reloads the node; runs are held at clean pause points, the node restarts and the server resumes them. The server resumes every run a node lost, within a limit against crash loops; SIGTERM pauses runs instead of aborting them ([ADR-021](../adr/021-explicit-node-reload.md), [completed/node-reload.md](completed/node-reload.md)). The same path serves *Code delivery* below.
- [x] **Idle runtime eviction:** done on the server with *Sessions on the server; nodes host tools*: the process's sweep closes a runtime idle 3 minutes and not streaming, and a new app closes idle runtimes at once and running ones once idle, so the next prompt opens on the new code (session-runtime.md *What the process keeps*).
- [x] **Chunked storage calls:** a storage read result, commit or commit result longer than the link's storage chunk (`STORAGE_CHUNK_CHARS`, 1 Mi characters, or a quarter of a smaller frame cap) crosses in slices of its serialized JSON: a held reply fetched by offset (`storage.readPart`), writes uploaded slice by slice and applied with the last (`storage.commitPart`), all on one connection (protocol 9). Streams did not fit (they run node→server and are opened by the server). A resent commit is uploaded again and answered from its `commitId` record. Partial payloads are bounded per connection and freed on close. Deleted with protocol 12: storage no longer crosses the link (ADR-029).
- [x] **Reconnect-safe node calls:** a dropped link should cost only a reconnect. Remote links will drop on their own, so they need this anyway. Then make the hub reloadable. Since ADR-029 the link carries no storage, reports or session commands: what rides a drop is a session's tool calls (a file operation sent again, a command picked up again by its ID and output offset; node-contract.md *Files*, *Shell commands*), and the retry-safe commits and reports below went with the node's session path. In order:
  - [x] **Retry-safe commits:** an unanswered `storage.commit` was resent under its `commitId` on the next connection; the session row kept the last applied commit's ID and result (protocol 7, [ADR-010](../adr/010-state-derived-idempotency.md); removed with protocol 12, migration 054).
  - [x] **Retry-safe reports:** an unanswered `session.started`/`session.settled` was resent; a repeated start applies nothing and a settlement is recognised by its `reportId` (the run ID cannot tell a resend from a resumed run). The reports no longer cross the link: the server's runtimes create each settlement in-process and apply it once, so the `reportId` check went too (migration 055).
  - [x] **Reloadable hub:** a dev reload builds a new app state (`createAppState`: a new hub) and node socket listener and closes the previous ones; the node redials and in-flight work recovers through the paths above ([ADR-020](../adr/020-reloadable-node-hub.md), [hot-reload.md](../dev/hot-reload.md)). Deleted: the `restartRequired` rules and process-owned module list, the import rewriting in dev bundles, the `NodeHubServices` port and its per-call lookup (the hub calls product code directly; a connection resolves its handlers once, at hello), `DeliveryDeferred` in the protocol package (back in the dispatcher); submission failure recipients moved onto the browser client; `node-link/` folded into `nodes/`. Only process startup code warns restart-required. `execute` stays non-retryable: a reload stopping the app that runs a script fails that one tool call with "may have run" (it now runs on the server, not over the link).
- [x] **Node bundle spike:** a single-file `bun build --target bun` of `packages/node/src/main.ts` (11 MB at the time, ~150 ms to build, ~215 ms to start, deterministic) ran real sessions from a directory outside the repository with no `node_modules`. It covered AGENTS.md and skill discovery in the session cwd, slash expansion, `read`/`bash`, an image attachment, git and `fs.*` through the node, and a clean SIGTERM. The fixes it found shipped with *Code delivery* ([completed/remote-nodes.md](completed/remote-nodes.md) *Decisions*, [node-bundle.md](../dev/node-bundle.md)).
- [x] **Pairing and node authentication:** settings-page pairing codes, `reins node pair`, Ed25519 node keys, the server-first challenge (`node.authenticate`, before `node.hello`) and revocation ([ADR-023](../adr/023-node-pairing-and-challenge-authentication.md), [completed/node-pairing.md](completed/node-pairing.md), node-contract.md *Pairing and authentication*). The transport decides whether a connection authenticates (`accept(socket, {authenticate: {origin}})`); the local socket does not, so the local node needs no pairing. A revoked node is refused at hello on every transport. Every refusal (unknown, revoked or removed node, failed challenge, a hello for another node) is `NODE_REFUSED` (`-32005`): the dialer stops instead of redialing, and the supervised node exits with a code the supervisor does not restart (node-contract.md *Process model*). Tested: stolen, expired and competing codes, challenge replay, a wrong node ID in the hello, reconnect fencing, revocation, CLI re-run safety, and CLI → endpoint → challenge end to end. What it left (the install command, the WebSocket route's origin, accepting from `open`, the pairing step waiting for the first connection) shipped with *Remote transport* and *Code delivery*. Deferred: key rotation (revoke and re-pair for now), fingerprint confirmation, an audit log.
- [x] **Remote transport** ([completed/remote-nodes.md](completed/remote-nodes.md)): JSON-RPC over WebSocket at `/nodes/link` on the HTTP server (`nodes/node-link.ts`), behind the same `LinkSocket` seam, accepted from `open` so the challenge is the first frame. The process owner drives any socket whose upgrade data carries handlers with them, so node-link sockets belong to the app that upgraded them. The origin the signature is checked against comes from the upgrade request (`X-Forwarded-Proto`/`X-Forwarded-Host`, else the request; [ADR-024](../adr/024-node-link-origin-from-the-upgrade-request.md)). Frame cap 16 MiB (`REMOTE_MAX_FRAME_BYTES`) both ways. Prompt content was bounded to 8 MiB of JSON at submission and the system prompt to 1 Mi characters so an opening command would fit; since protocol 12 prompts do not cross the link ([ADR-029](../adr/029-sessions-on-the-server-nodes-host-tools.md)), the system prompt bound is gone and the content bound (`MAX_PROMPT_CONTENT_BYTES`) stays only as a sanity bound on a submission. The node dials `ws://`/`wss://` from its paired config (`webSocketTransport`; `reins node run`), sharing `connectNode` with the local link. Until the outbox went ([ADR-029](../adr/029-sessions-on-the-server-nodes-host-tools.md)), its dispatcher bounded deliveries per node so a slow node could not hold the slots of others; nothing is queued for a node now. The settings page's pairing step waits for the new node's first connection. Known gap: Bun 1.3.9's client WebSocket reports `bufferedAmount` 0, so node-side stream pacing does nothing on the remote link (node-transport.md *1b*). Process test: `remote-node.process-test.ts`.
- [x] **Bundle-safe node source fixes:** `createPiResources` passed `noExtensions: true`; the REINS docs come from `REINS_DOCS_DIR`, falling back to the checkout's `docs/`, and the developer docs are named only where `<docs>/dev` exists (a bundle ships only `features/`). Since ADR-029 the node runs no Pi, so `PI_OFFLINE` and the other Pi workarounds are gone; the node reports its docs directory (in its hello since protocol 13) and the server's runtime names it.
- [x] **Code delivery** ([ADR-025](../adr/025-node-version-handshake.md), [completed/remote-nodes.md](completed/remote-nodes.md), [node-bundle.md](../dev/node-bundle.md)): the server builds the node bundle (`reins.js`: the `reins` CLI and all of the node, with `docs/features` embedded; build ID its sha256) at each app's start and serves it with its manifest and the install script (`/nodes/*`). Settings shows the one-line install command with the pairing code; the script fetches the pinned Bun and the bundle into `~/.reins` and runs `reins node setup` (pair, declare `--source`s, start in the background, wait for the connection). `reins node start|stop|status` and the launcher's restart loop run it. The hello carries `buildId` and is answered `ready`, `update` or `error` (protocol 10); a node on another build installs the server's (and its Bun), flips `current` and restarts through its launcher (since ADR-029 this interrupts only the commands it was running). Acceptance: `node-install.process-test.ts`.
- [ ] **Local node on the bundle, and no restart for protocol changes:** the local node still runs from source under the supervisor, and a `@reins/node-protocol` edit still needs `bun run dev` restarted: dev reloads keep the protocol external so the server cannot move ahead of the node. With the `update` reply that rule can go. Bundle the protocol into every app, so the server always reloads. The hello carries a fingerprint of the node's protocol code (a hash of its sources, or the build ID). On a mismatch the server answers `update`, which for the local node means reload from the checkout through the existing `node.reload` path. A node whose new code does not build stays on its old code and is told again at each redial. With the hub per app, every reload drops the links and each node redials at once, so the hello's fingerprint check happens at once after any reload. Costs: every saved protocol edit restarts the local node, cutting off the commands it runs (runs are on the server and are not affected otherwise). Amends ADR-020 and ADR-021. Deferred (2026-10-12): protocol edits are rare now that nodes only host tools, and this trades a manual restart for about as much code as it removes. If built, treat the local node like a remote one rather than adding a separate fingerprint: it announces a build ID (a hash of its sources), and a build that differs from the server's gets `update`, meaning install the bundle on a remote node and reload from the checkout on the local one; that removes the from-source exception (no build announced, never told to update).
  - [x] The dev supervisor restarts the server process itself on process-owner edits (2026-10-12): the server exits with `SERVER_RESTART_EXIT_CODE` after suspending its runs, once its new code builds, and the supervisor starts it again alone, the node and its commands running on (hot-reload.md *Restarting the server*; `kill -HUP <server pid>` by hand). Only `supervisor.ts` and protocol edits still need `bun run dev` restarted; after a protocol edit the watcher warns instead of restarting the server alone, until that full restart. The rest of this item (the protocol bundled into the app, the fingerprint, the local node told to reload) is open. Running the local node through the `reins` launcher is optional beyond that.

  - **Scripting:** `nodes.list()` and `nodes.get(nodeId?)` are done (2026-10-12, scripting.md): the list gives each node's ID, name, hostname, whether it is connected, revoked or the caller's, and its source count; `get` adds its sources with their paths. Node file and command access is done (2026-10-19, scripting.md *Files and commands on any node*, node-contract.md *Shell commands*): `nodes.readFile`, `nodes.writeFile` and `nodes.run` on any connected node (by ID, name or `"current"`), any path, over the operations under the agent's tools, no protocol change; bounded to 16 MiB and to the script's 30 s, failing at once for a node not connected. Still to come: `projects.addSource(projectId, nodeId, path)` over `createSource`, and `sessions.start` in another project or source (it starts only in the caller's).

## Remote nodes: direction for open work

Remote nodes are built ([completed/remote-nodes.md](completed/remote-nodes.md)); the connection, server-managed sources, the bundle and its updates are current design in [node-transport.md](../dev/node-transport.md), [node-contract.md](../dev/node-contract.md) and [node-bundle.md](../dev/node-bundle.md), the version handshake in [ADR-025](../adr/025-node-version-handshake.md). What still directs open work:

### Trust model (decided)

- **Private network only.** Reins is exposed only on a private network (e.g. Tailscale). This is a deployment assumption, not something code checks or enforces. Anyone who can reach the server is effectively an administrator: the browser API is unauthenticated, so they can create pairing grants, change settings and run scripts. Frontend authentication is a prerequisite for any wider exposure and is out of scope here.
- **Nodes get no credentials.** Sessions run on the server ([ADR-029](../adr/029-sessions-on-the-server-nodes-host-tools.md)): credentials and model configuration never leave the server's machine. (Until then, under [ADR-013](../adr/013-server-holds-credentials.md), any authenticated node was served every provider's credentials.)
- **Nodes authenticate anyway** ([ADR-023](../adr/023-node-pairing-and-challenge-authentication.md)). Not to defend against the network: a node's stored identity can only be replaced by re-pairing that machine, and a stale or mistaken node (or a copy of the database) must not be able to pose as another node. Hence a keypair per node rather than a shared token.
- The server can already run arbitrary bash on a node through prompts, so the server delivering the node's code adds no new trust. The bundle and install script are public on the private network: code with no secrets, so downloading them grants nothing. Joining requires redeeming a pairing code; connecting requires the registered node key.

### Upgrades

An upgrade restarts the server, which pauses its runs at clean points and resumes them when it starts (session-runtime.md *Recovery*); each node redials, is told `update` and restarts on the new bundle, which cuts off only the commands it was running (their tool calls come back "outcome unknown"; ADR-025, ADR-029). **Later, if that proves costly:** the server could drain its nodes' commands before restarting for an upgrade (`node.reload`'s drain over the old protocol, bounded); and push a node-only build to connected nodes over the live link instead of waiting for a redial. The bootstrap surface ADR-025 lists changes only additively.

### Sessions on the server; nodes host tools (done)

Decided and built 2026-10-11: [ADR-029](../adr/029-sessions-on-the-server-nodes-host-tools.md) has the reasons (a model set up only on the server, and an endpoint on the server's `127.0.0.1`, could not work on a remote node), the options rejected (copying model configuration to nodes; the server as model gateway; the node's runtime in the server process over an in-memory link; a separate package), and the decision as built: running sessions in a process-owned runtime map with 3-minute idle eviction and a process-owned database connection, the outbox replaced by Pi's admission, every node a tool and file host whose commands survive a dropped link, the environment from the server's `~/.agents` plus the checkout's (since 2026-10-18, the node's `~/.agents` plus the checkout's), and no compatibility path. Current design: [session-runtime.md](../dev/session-runtime.md), [node-contract.md](../dev/node-contract.md) *Tool host*.

How a remote session reads the server's skills: resolved 2026-10-18 (ADR-029 *The environment comes from the node*): the environment comes from the node (its `~/.agents` and the checkout's); skills shared across nodes will come from Reins. Adopting pi-durable moved to [TODO.md](../TODO.md).

**Later:**

- A package or process of its own for the session code (not a node), supervised beside the server, if keeping runtimes on old code across reloads proves costly.
- A model only one node can reach (none today): a node could offer an endpoint back through the server.

## Cloud nodes (future)

Disposable cloud machines (e.g. Fly Sprites, which resume from checkpoint in about a second) are natural nodes, and a stateless node suits them: there is nothing on the machine to back up or re-hydrate. Reins would manage only a sleep/wake lifecycle: track nodes as online, sleeping or offline; on a prompt for a sleeping wakeable node, trigger a wake (a run already waits for its node at its first request, and its tool calls wait for it); show "Starting…" for a waking cloud node and "Offline" for an unreachable personal machine. Provisioning the machine (tools, clones, CLI auth) stays outside Reins.

## Open questions

- **Where inference runs:** decided 2026-10-11: on the server side, with nodes as tool hosts (*Sessions on the server; nodes host tools*).
- **Frontend authentication:** not needed while Reins is exposed only on a private network (see *Trust model*); required before any wider exposure. Account authentication and user-scoped authorization are separate from node identity; passkeys are a candidate.
- **Privacy and trust:** a node lets the server route prompts that execute on the user's machine, and the server receives all events and transcripts. Fine for self-hosting; for a hosted multi-user service, explore node-side tool permissions and approval gates, audit logging of server-initiated commands, scoped node permissions and end-to-end encrypted storage. Self-hosted remains the primary model.
- **Latency:** every tool call on a remote node is a round trip from the server (a file operation, a command and its streamed output); events no longer cross the link. Batching a tool's file operations, or a larger remote environment (pi-durable's), is a possible later optimization.
- **Multiple sources per project:** the model allows it; decide the default-source policy and UX once it is real.
- **Protocol standards:** whether ACP could carry the server–node command/event channel (see [ADR-006](../adr/006-acpx-as-runtime-replacement.md) for the runtime-level evaluation).
