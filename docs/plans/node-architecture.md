# Node Architecture

Status: **local process split done; server-canonical storage done ([ADR-015](../adr/015-server-canonical-storage-stateless-node.md)); remote nodes done: pairing and authentication ([ADR-023](../adr/023-node-pairing-and-challenge-authentication.md)), the WebSocket transport ([ADR-024](../adr/024-node-link-origin-from-the-upgrade-request.md)), server-managed sources on remote nodes ([ADR-026](../adr/026-sources-managed-on-the-server.md)), and code delivery with self-update ([ADR-025](../adr/025-node-version-handshake.md)). Open: moving running sessions to the server with nodes as tool hosts (decided 2026-10-11, *Sessions on the server; nodes host tools*), the local node on the bundle, node management, idle eviction and the items below.** Today every session runs on a node; the server stores every session, dispatches work through a durable queue and serves the UI. The node holds nothing durable: its Pi runtime reads and commits each session on the server over the link. The local node is a separate process linked over a Unix socket, run from source by the supervisor; a remote node is installed from the server with one command, runs the server's node bundle and links over a WebSocket. The completed phases are recorded in [completed/node-local-process-split.md](completed/node-local-process-split.md), [completed/server-canonical-storage.md](completed/server-canonical-storage.md), [completed/node-pairing.md](completed/node-pairing.md) and [completed/remote-nodes.md](completed/remote-nodes.md); the current design is in [node-transport.md](../dev/node-transport.md), [node-contract.md](../dev/node-contract.md), [node-runtime.md](../dev/node-runtime.md) and [node-bundle.md](../dev/node-bundle.md).

## Motivation

Support multiple machines (e.g. a Mac and a Linux box, or disposable cloud machines), each with their own checkouts, connected to one Reins server, and eventually a hosted server with users connecting their own machines as nodes. Browser traffic, including agent events, stays routed through the server.

```mermaid
graph LR
    Browser[Browser] <-->|HTTP + WS| Server
    subgraph Server host
        Server[Reins server\nproduct DB, canonical session storage,\ncommand queue, credentials]
        Local[Local node\nPi, tools, checkouts,\nno durable session state]
        Server <-->|JSON-RPC over\nUnix socket| Local
    end
    Remote[Remote node\nPi, tools, checkouts] <-->|JSON-RPC over\nWebSocket /nodes/link| Server
```

The server's SQLite is the only session storage and the node holds nothing durable ([ADR-015](../adr/015-server-canonical-storage-stateless-node.md)). ## Remaining work

- [x] **Explicit node reload and automatic resume:** a CLI or an agent's `execute` script reloads the node; runs are held at clean pause points, the node restarts and the server resumes them. The server resumes every run a node lost, within a limit against crash loops; SIGTERM pauses runs instead of aborting them ([ADR-021](../adr/021-explicit-node-reload.md), [completed/node-reload.md](completed/node-reload.md)). The same path serves *Code delivery* below.
- [ ] **Idle runtime eviction:** close runtimes idle for a fixed period (they hold nothing durable), which also bounds node memory and picks up new node code between turns. Once sessions run on the server (*Sessions on the server; nodes host tools*) this applies to the server's session layer instead.
- [x] **Chunked storage calls:** a storage read result, commit or commit result longer than the link's storage chunk (`STORAGE_CHUNK_CHARS`, 1 Mi characters, or a quarter of a smaller frame cap) crosses in slices of its serialized JSON: a held reply fetched by offset (`storage.readPart`), writes uploaded slice by slice and applied with the last (`storage.commitPart`), all on one connection (protocol 9). Streams did not fit (they run node→server and are opened by the server). A resent commit is uploaded again and answered from its `commitId` record. Partial payloads are bounded per connection and freed on close (node-contract.md *Session storage*). Left: fencing and the commit record are checked only at a long commit's last slice.
- [ ] **Reconnect-safe node calls:** a dropped link should cost only a reconnect. Remote links will drop on their own, so they need this anyway. Then make the hub reloadable. In order:
  - [x] **Retry-safe commits:** an unanswered `storage.commit` is resent under its `commitId` on the next connection; the session row keeps the last applied commit's ID and result, and a repeat is answered with it (protocol 7; node-contract.md *Session storage*, [ADR-010](../adr/010-state-derived-idempotency.md)).
  - [x] **Retry-safe reports:** an unanswered `session.started`/`session.settled` is resent; a repeated start applies nothing and a settlement is recognised by its `reportId` (the run ID cannot tell a resend from a resumed run). A session with a report still to deliver is listed live in the hello, so crash recovery leaves it alone.
  - [x] **Reloadable hub:** a dev handler reload builds a new state (`createServerState`: a new hub) and node socket listener and closes the previous ones; the node redials and in-flight work recovers through the paths above ([ADR-020](../adr/020-reloadable-node-hub.md), [hot-reload.md](../dev/hot-reload.md)). Deleted: the `restartRequired` rules and process-owned module list, the import rewriting in dev bundles, the `NodeHubServices` port and its per-call lookup (the hub calls product code directly; a connection resolves its handlers once, at hello), `DeliveryDeferred` in the protocol package (back in the dispatcher); submission failure recipients moved onto the browser client; `node-link/` folded into `nodes/`. Only process startup code warns restart-required. `script.execute` stays non-retryable: a drop still fails that one tool call with "may have run". A `storage.read` in flight at a drop still fails its run (reads are not resent).
- [x] **Node bundle spike:** a single-file `bun build --target bun` of `packages/node/src/main.ts` (11 MB at the time, ~150 ms to build, ~215 ms to start, deterministic) ran real sessions from a directory outside the repository with no `node_modules`. It covered AGENTS.md and skill discovery in the session cwd, slash expansion, `read`/`bash`, an image attachment, git and `fs.*` through the node, and a clean SIGTERM. The fixes it found shipped with *Code delivery* ([completed/remote-nodes.md](completed/remote-nodes.md) *Decisions*, [node-bundle.md](../dev/node-bundle.md)).
- [x] **Pairing and node authentication:** settings-page pairing codes, `reins node pair`, Ed25519 node keys, the server-first challenge (`node.authenticate`, before `node.hello`) and revocation ([ADR-023](../adr/023-node-pairing-and-challenge-authentication.md), [completed/node-pairing.md](completed/node-pairing.md), node-contract.md *Pairing and authentication*). The transport decides whether a connection authenticates (`accept(socket, {authenticate: {origin}})`); the local socket does not, so the local node needs no pairing. A revoked node is refused at hello on every transport. Every refusal (unknown, revoked or removed node, failed challenge, a hello for another node) is `NODE_REFUSED` (`-32005`): the dialer stops instead of redialing, and the supervised node exits with a code the supervisor does not restart (node-contract.md *Process model*). Tested: stolen, expired and competing codes, challenge replay, a wrong node ID in the hello, reconnect fencing, revocation, CLI re-run safety, and CLI → endpoint → challenge end to end. What it left (the install command, the WebSocket route's origin, accepting from `open`, the pairing step waiting for the first connection) shipped with *Remote transport* and *Code delivery*. Deferred: key rotation (revoke and re-pair for now), fingerprint confirmation, an audit log.
- [x] **Remote transport** ([completed/remote-nodes.md](completed/remote-nodes.md)): JSON-RPC over WebSocket at `/nodes/link` on the HTTP server (`nodes/node-link.ts`), behind the same `LinkSocket` seam, accepted from `open` so the challenge is the first frame. The process owner drives any socket whose upgrade data carries handlers with them, so node-link sockets belong to the handler load that upgraded them. The origin the signature is checked against comes from the upgrade request (`X-Forwarded-Proto`/`X-Forwarded-Host`, else the request; [ADR-024](../adr/024-node-link-origin-from-the-upgrade-request.md)). Frame cap 16 MiB (`REMOTE_MAX_FRAME_BYTES`) both ways; prompt content is bounded to 8 MiB of JSON at submission and the system prompt to 1 Mi characters, so an opening command fits. The node dials `ws://`/`wss://` from its paired config (`webSocketTransport`; `reins node run`), sharing `connectNode` with the local link. The dispatcher bounds deliveries per node (`MAX_SESSIONS_PER_NODE`), so a slow node cannot hold the slots of others. The settings page's pairing step waits for the new node's first connection. Known gap: Bun 1.3.9's client WebSocket reports `bufferedAmount` 0, so node-side stream pacing does nothing on the remote link (node-transport.md *1b*). Process test: `remote-node.process-test.ts`.

- [x] **Code delivery** ([ADR-025](../adr/025-node-version-handshake.md), [completed/remote-nodes.md](completed/remote-nodes.md), [node-bundle.md](../dev/node-bundle.md)): the server builds the node bundle (`reins.js`: the `reins` CLI and all of the node, with `docs/features` embedded; build ID its sha256) at each handler load and serves it with its manifest and the install script (`/nodes/*`). - [ ] **Local node on the bundle, and no restart for protocol changes:** the local node still runs from source under the supervisor, and a `@reins/node-protocol` edit still needs `bun run dev` restarted: dev reloads keep the protocol external so the server cannot move ahead of the node. With the `update` reply that rule can go. Bundle the protocol into every handler load, so the server always reloads. The hello carries a fingerprint of the node's protocol code (a hash of its sources, or the build ID). On a mismatch the server answers `update`, which for the local node means reload from the checkout through the existing `node.reload` path. A node whose new code does not build stays on its old code and is told again at each redial. Costs: every saved protocol edit restarts the local node, and its runs are cut off (and resumed) rather than paused at clean points, because the node cannot commit to the new server before it restarts. Have the dev supervisor restart the server process itself on process-owner edits, so only `supervisor.ts` edits still need a manual restart. Amends ADR-020 and ADR-021. Running the local node through the `reins` launcher is optional beyond that.

## Remote nodes: direction for open work

Remote nodes are built ([completed/remote-nodes.md](completed/remote-nodes.md)); the connection, server-managed sources, the bundle and its updates are current design in [node-transport.md](../dev/node-transport.md), [node-contract.md](../dev/node-contract.md) and [node-bundle.md](../dev/node-bundle.md), the version handshake in [ADR-025](../adr/025-node-version-handshake.md). What still directs open work:

### Trust model (decided)

- **Private network only.** Reins is exposed only on a private network (e.g. Tailscale). This is a deployment assumption, not something code checks or enforces. Anyone who can reach the server is effectively an administrator: the browser API is unauthenticated, so they can create pairing grants, change settings and run scripts. Frontend authentication is a prerequisite for any wider exposure and is out of scope here.
- **Nodes get every credential.** [ADR-013](../adr/013-server-holds-credentials.md) stands as is: any authenticated node is served `credentials.*` for every provider. No per-node scoping. Once sessions run on the server (below), nodes get no credentials at all.
- **Nodes authenticate anyway** ([ADR-023](../adr/023-node-pairing-and-challenge-authentication.md)). Not to defend against the network: a node's stored identity can only be replaced by re-pairing that machine, and a stale or mistaken node (or a copy of the database) must not be able to pose as another node. Hence a keypair per node rather than a shared token.
- The server can already run arbitrary bash on a node through prompts, so the server delivering the node's code adds no new trust. The bundle and install script are public on the private network: code with no secrets, so downloading them grants nothing. Joining requires redeeming a pairing code; connecting requires the registered node key.

### Upgrades

An upgrade cuts off what was in flight on a remote node: the server restarts on a new build, the node redials, is told `update`, restarts on the new bundle, and the server resumes the runs it lost (a model request is asked again, a tool call comes back "outcome unknown"; ADR-025). **Later, if that proves costly:** the server could drain its nodes before restarting for an upgrade (`Node.pause` over the old protocol, bounded, then restart), so runs wait at clean points instead; and push a node-only build to connected nodes over the live link instead of waiting for a redial. The bootstrap surface ADR-025 lists changes only additively.

### Sessions on the server; nodes host tools (decided 2026-10-11)

**Why.** Opus 5.5 did not work on a Mac paired as a remote node. Two failures, both hidden on the server's machine because the server and the local node read the same `~/.pi/agent`:

- *The catalog.* Pi 0.85.1's built-in catalog stops at `claude-opus-5`. `claude-opus-5-5` is only in the server's `~/.pi/agent/models-store.json`, which `GET /api/models` refreshes from the network (`allowModelNetwork: true`, `pi/model-catalog.ts`). The node never refreshes it: `buildNodeRuntime` does not allow model network, and the bundle sets `PI_OFFLINE=1`, which turns Pi's model network off. So the node refuses a model the picker offered (`Model not found`).
- *The endpoint.* The server's `~/.pi/agent/models.json` points `anthropic` at a local proxy (`127.0.0.1:3456`, Meridian) with its key in that file. That is provider configuration, not a credential, so the ADR-013 path never sends it, and `127.0.0.1` on the Mac is the Mac.

Custom models will keep being set up on the server, and every node should be able to use them. Options considered:

1. *Loop and inference on the node* (until now): copy `models.json` and the model store to every node and rewrite endpoints a node cannot reach. Rejected: an uphill battle with every new custom model.
2. *The server as model gateway; loop and tools on the node.* An HTTP proxy that adds credentials does not work for OAuth logins, because Pi builds the request from the credential (an `sk-ant-oat` token switches on the Claude Code system prompt, tool renames and beta headers in pi-ai's `anthropic-messages.js`; Codex and Copilot also build requests from their token). Cutting at Pi's `Models` interface instead (the harness calls only `getModel`, `streamSimple`, `completeSimple`, `streamDeferred` and `cancelDeferred`; relay them to the server's `ModelRuntime`) works, but each turn would read the context from the server's storage and upload it straight back to the server's gateway, and the server is in the path of every call anyway. Rejected.
3. *The loop on the server side; nodes host tools.* Chosen.

Pi points the same way. Pi 1.x removed AgentHarness (`@earendil-works/pi-agent-core` 1.1.0 has only `agent`, `agent-loop` and `proxy`) for `@earendil-works/pi-durable`: one process owns a storage ("no cross-process locking"), and tools touch files and processes only through a per-call `ExecutionEnv` built for remote hosts (`FileSystem.id` per container or remote host, `ShellExecOptions.window` so remote environments need not transfer output the caller drops, `registerEnvConformance`). pi-durable is experimental (its README: the API changes without notice; 1.0.3 and 1.1.0 broke it) and its `read` tool does not read images yet, so Reins stays on AgentHarness 0.85 for now. Running the loop on the server with tools behind an `ExecutionEnv` adopts pi-durable's shape, so the later switch happens in the session layer and nodes do not change.

**Decision.**

- **Running sessions live on the server side:** AgentHarness, its storage on the server's database (`PiStorageAdapter`, `pi-storage.ts`) and the server's model runtime (`pi/factory.ts`: its catalog, `models.json`, model store and credentials). Credentials and model configuration never leave the server's machine.
- **Kept across handler reloads**, as Reins kept running sessions before the node split: in state the server process owns, not in a separate process for now. Edits to that layer need a `bun run dev` restart. It is not a node: it holds no source and has no `nodes` row.
- **Every node is a tool and file host**, the server machine's included, none special. It serves the operations of Pi's tools (a remote `ExecutionEnv`) and, as now, `process.run`/`fs.*` for git and the UI. No Pi, session storage, credentials, events or lifecycle reports on nodes. The server machine's node still links over the Unix socket without pairing.
- **Skills and context** come from the server's `~/.agents` (user skills, `~/.agents/AGENTS.md`) plus the checkout's (`.agents/skills`, AGENTS.md in the checkout and its ancestors), read from the source's node. A node's own `~/.agents` is no longer seen.
- **Node links stay per handler load** (ADR-020). A tool call in flight survives a dropped link instead (below), which also covers remote links that drop on their own (a Mac sleeping, Wi-Fi).

**What it needs** (code pointers as of 2026-10-11):

- *The session layer.* Today the node's runtime drives sessions (`packages/node/src/runtime/`: `buildNodeRuntime` in `build.ts`, `pi-runtime.ts`, the pause gate, tool images, the Reins tools); it moves to the server side. Two ways to build it, to decide in the task: **(a)** run the node's session runtime in the server process, attached to each handler load's hub through an in-memory link (the shape of `@reins/node-protocol/testing`'s loopback pair), so a reload looks like today's redial and the existing resend paths (a commit's `commitId`, a report's `reportId`, outbox replay) carry runs across it; storage still goes through `storage.*`, in memory. **(b)** A process-owned layer calling product code through a narrow interface, with storage direct; it then needs a database connection across reloads, since each handler load opens and closes its own (ADR-020). (a) looks like the smaller change. Either way the import boundaries change (`reins/node-import-boundary` forbids backend production code importing `@reins/node`; node-contract.md *Packages and import boundaries*) and the process-owned modules become restart-only (hot-reload.md). Outbox commands for a moved session are delivered to the session layer, not a node.
- *A remote `ExecutionEnv`.* Pi's four tools touch the machine only through `ExecutionEnv` (`createHostTools` in `runtime/tools.ts` builds a `NodeExecutionEnv`). Together they use `readTextFile`, `readBinaryFile`, `writeFile`, `exec`, `fileInfo`, `exists`, `absolutePath` and `canonicalPath`, plus `cleanup`. Serve them as node methods on the session's source (its binding's `cwd`). bash's environment (`PI_SESSION_ID`, `PI_PROVIDER`, `PI_MODEL`, `PI_REASONING_LEVEL`) goes with each `exec`; its output streams back as `process.run`'s does. `read`'s images arrive as bytes and become attachments on the server. pi-durable's environment is larger (`openBinaryReader`, `openDirReader`, `watch`, argv `exec`); nodes update themselves, so adding methods later is cheap.
- *Tool calls survive a dropped link.* Every reload drops every node link, so without this a save would cut every tool call in flight on every node, the server machine's included. Short calls wait for the node to reconnect (as node calls wait today, `RECONNECT_WAIT_MS`) and are sent again: they are safe to repeat. An `exec` has an ID: the node keeps the process and the tail of its output across the drop for a grace period (e.g. 60 s, then kills it), and the remote environment picks it up again on the new link by ID and output offset and keeps piping its output into the same tool call. The model sees nothing. A node that restarted does not know the ID: "outcome unknown", as today. Keep it simple; details when built.
- *The environment from the server plus the checkout.* `ReinsResourceLoader` (`resources/loader.ts`) and slash expansion (`expandLocalPrompt`, `resources/prompt.ts`) read the filesystem directly. The checkout's part (context files and skills, with content) should come from its node in one call and be merged with the server's `~/.agents`. `skills.list` goes; `GET /api/projects/:id/skills` merges the same way. The REINS docs path in the environment prompt must be the node's (the model reads it with `read`, which runs there): the node reports its docs directory (`REINS_DOCS_DIR`; a bundle ships `docs/features`). The task branch checkout moves to the server's `Git` over `process.run` (today node-local git in `buildNodeRuntime`).
- *Direct calls instead of link calls.* Lifecycle reports (`runStarted`/`runSettled`, `sessions/session-runs.ts`), events (the browser broadcast, `sessionEventFrame`), attachments and the Reins tools (`script.execute`, `script.search`, `project.createTask`) no longer cross a node link. Fencing (`nodeOwnsSession`) changes: nodes make no session calls; the server calls a node for a session's source.
- *Removed from nodes* once every node is a tool host: `session.*` commands, `RemoteStorage` and `storage.*` over node links (slicing included), `credentials.*` and `RemoteCredentialStore`, `session.event`, attachment fetch and store, lifecycle reports, `skills.list`, and Pi in the bundle with its workarounds (`PI_OFFLINE`, `PI_PACKAGE_DIR`, `registerBundledPiModules`).
- *The ADR* amends ADR-013 (nodes get no credentials), ADR-015 (storage stops crossing to nodes), ADR-019 (the environment is no longer all machine-local) and ADR-020/021 (running sessions are kept across reloads; what pauses and resumes them).

**Switching over without breaking sessions.** Session state is all on the server already (ADR-015), and both sides run Pi 0.85.1 over the same storage, so no data migrates: only where a session is driven changes. Do not upgrade Pi in the same change.

- Transcripts, lanes and model selections are read as they are. Queued prompts stay in the outbox and go to the session layer instead of a node.
- Runs in flight at the switch are lost runs, as at any node restart: Pi left them pending and the server resumes them (ADR-021), now on its side. A model request in flight is asked again; a tool call in flight comes back "outcome unknown".
- The system prompt and skills are rebuilt at every runtime open, so a session gets the new environment at its next open (one prompt-cache miss).
- Gradually, by capability: a node on the new build advertises the tool-host methods in its hello; sessions on such a node run on the server, sessions on other nodes on the node as today. Nodes update themselves on connect, and the update restarts them, closing their runtimes; the server resumes those runs on its side, so a session is never driven in two places. Delete the node-side path once every node has moved. The hello's capability list is capped at 16 (`negotiation.ts`) and a node already advertises 14 (`CAPABILITIES` in `node-connection.ts`): raise the cap, or advertise one tool-host capability, before a node lists both sets.
- Reins is developed with Reins: try the build on a second dev instance against a copy of the database (`REINS_DATA_DIR`) before switching the main one, and back up `reins.db`. The previous build reads the same data, so going back is possible.

**Later:**

- Split the session layer into its own process, supervised beside the server (not a node), reloadable with pause and resume as the node is now, if keeping it across reloads proves costly.
- pi-durable once it is stable: in the session layer only; storage moves into its process.
- A model only one node can reach (none today): a node could offer an endpoint back through the server.

## Cloud nodes (future)

Disposable cloud machines (e.g. Fly Sprites, which resume from checkpoint in about a second) are natural nodes, and a stateless node suits them: there is nothing on the machine to back up or re-hydrate. Reins would manage only a sleep/wake lifecycle: track nodes as online, sleeping or offline; on a prompt for a sleeping wakeable node, trigger a wake and let the queued command deliver on reconnect (the command queue already holds work for disconnected nodes); show "Starting…" for a waking cloud node and "Offline" for an unreachable personal machine. Provisioning the machine (tools, clones, CLI auth) stays outside Reins. A distant cloud node is the case most likely to want the deferred write-behind decorator.

## Open questions

- **Where inference runs:** decided 2026-10-11: on the server side, with nodes as tool hosts (*Sessions on the server; nodes host tools*).
- **The server's skills on a remote node** (revisit; ADR-029 *Later*): sessions list the server's `~/.agents` skills by their server paths, and `read` runs on the node, so for now the server serves `read` itself for paths under its own `~/.agents`. Decide on something less special-cased (skill content sent with the environment, or a virtual path).
- **Frontend authentication:** not needed while Reins is exposed only on a private network (see *Trust model*); required before any wider exposure. Account authentication and user-scoped authorization are separate from node identity; passkeys are a candidate.
- **Privacy and trust:** a node lets the server route prompts that execute on the user's machine, and the server receives all events and transcripts. Fine for self-hosting; for a hosted multi-user service, explore node-side tool permissions and approval gates, audit logging of server-initiated commands, scoped node permissions and end-to-end encrypted storage. Self-hosted remains the primary model.
- **Latency:** server-relayed events add a hop for remote nodes. Direct browser–node streaming (e.g. WebRTC data channels with the server as signaling) is a possible later optimization with fallback to the relay.
- **Multiple sources per project:** the model allows it; decide the default-source policy and UX once it is real.
- **Protocol standards:** whether ACP could carry the server–node command/event channel (see [ADR-006](../adr/006-acpx-as-runtime-replacement.md) for the runtime-level evaluation).
