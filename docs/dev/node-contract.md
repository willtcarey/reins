# Internal node seam

`packages/node/src/contract.ts` is the isolated `@reins/node/contract` export of a separately buildable node package. It contains a versioned semantic vocabulary for session provision, prompt, steer, abort, pending resume, typed results and observations. It imports no server, Pi or browser modules; Oxlint restricts the contract's imports to `zod` and backend imports to declared node package exports. Future daemon implementation belongs elsewhere in `packages/node/src/`, not in this export. `deliveryPolicy()` classifies provision, prompt, steer and setModel as `submit-work`, matching server outbox admission; abort and pending resume remain immediate controls. The classifier does not itself deliver commands. The semantic contract alone does not guarantee delivery or offline execution. Future read-only workspace/git commands should use `request-now` and return unavailable when offline. `node-command-store.ts` owns SQLite outbox rows and transitions; `models/node-command-projection.ts` owns submission/projection and a wake hint; `models/node-command-dispatcher.ts` resolves the session's current source and owns the sole delivery path. Session creation atomically stores the session and provision command, then signals a dedicated dispatcher after commit. The signal carries no command payload; startup, node availability/reconnect wake, and a 30-second poll rescan SQLite. The dispatcher resolves the session's current source before claim and uses the internal adapter to admit provisioning without constructing Pi. Creation returns a persisted ID and scheduling projection without awaiting the dispatcher or returning a live runtime. Browser HTTP creation returns a session view immediately; validated prompt/steer and scripting child starts persist their input without waiting for Pi admission (unsupported remote sources still reject input). The node adapter lazily opens/reopens Pi when an addressed input or explicit pending resume arrives. Session views distinguish provision scheduling from runtime activity; negative admission and delivery exceptions are `failed`; failures are notified and removed rather than automatically retried. The start signal is a hint; the periodic scan recovers missed hints. Existing process-startup handling still marks interrupted dispatches `unknown`; this slice does not change startup. Handler hot reload must not reinterpret previous in-flight work. Live delivery failures are notified and removed. `stop()` clears the timer. Prompt and steer now persist validated input in `node_command_outbox` before acknowledgement, keyed uniquely by `(session_id, command_json.clientId)` via a SQLite expression index (the clientId travels only inside the command payload); a replay with the same operation/content/source returns the prior admission acknowledgement. A different payload with that key is rejected. The single command dispatcher scans `node_command_outbox` in insertion order across all persisted operations. Queued and dispatching predecessors order work only within their session; a queued offline provision cannot stall unrelated sessions. Failed commands are removed after notification so later queued work can proceed. Provision must be admitted before its inputs; the internal node adapter interprets the command and owns readiness, lazy runtime opening and Pi admission; the transport claims and settles the command without knowing its operation. There is no input-only scan or claim lifecycle. The dispatcher scans, checks predecessor/source availability and sends one validated `NodeCommand` through the selected adapter. `node-command-transport.ts` alone claims and settles generic delivery, recording explicit negative results and exceptions as failed; a stored command that no longer parses (e.g. a provision stored before it carried its configuration) reads as failed work and is failed, never sent, when the dispatcher reaches it. The dispatcher fences inputs behind provision, while `@reins/node/node` interprets node-owned commands and lazily assembles/reopens Pi with node-local canonical storage and injected product policy; server-side `node-command-notifications.ts` handles scheduling/input-failure notifications after delivery. The adapter does not read the outbox or broadcast product events. Legacy persisted open/reopen is unsupported. Provision's node-side receipt is recorded after its binding and Pi lane, so a replay converges; prompt/steer receipts follow Pi admission non-atomically, so absence of a receipt does not prove Pi did not admit the input. Provision scheduling changes notify through `Sessions.notifyScheduling()`, not a dispatcher-level broadcast. Eventual input failures use `node-command-notifications.ts`: only the currently connected submitting WS client registered for `(sessionId, clientId)` receives the existing error shape. Disconnected clients are not notified; failed commands are deleted after settlement, with no replay-to-UI mechanism yet. Scripting sends and child reports return on enqueue rather than Pi admission; explicit wait still observes runtime settlement. Process startup discards interrupted dispatches rather than replaying them; prompt/steer receipts remain non-atomic with Pi admission. Explicit abort and resume remain immediate controls rather than queued behind input. Errors after enqueue surface asynchronously on the existing WS error path, not as a retraction of the acknowledgement. Queued inputs survive process loss and are recovered by the shared dispatcher scan; remote execution and automatic retries remain unsupported. Provision establishes source admission and stores the session's frozen configuration (see *Session configuration*); the node validates a provisioned model against its registry when Pi creates the lane, so an unknown configured model fails the provision (the session shows "Session open failed"). A durable node-side receipt for safe replay is still missing. The outbox stores a session ID and operation, not a source. Without Pi-side durable admission keyed by command ID, dispatch failures and interrupted dispatches are reported as failures and never retried automatically. Queued commands are retained when no adapter is available; the dispatcher polls for eligible commands. No external node adapter is implemented. Semantic contract v4 uses a single durable `session.provision` carrying the session's frozen `configuration` (no open/reopen commands), a queued `session.setModel`, attachment references and `sourceSessionId`; it is **not** a network protocol: no handshake, framing, correlation, ordering, delivery guarantee or serialized runtime event payload is promised. Change schema meaning with a version bump; negotiate incompatible versions closed when transport exists. For existing installations from the in-progress internal-node spike, reconcile schema changes on the affected development database before using the new code; the fresh schema defines `storage_owner` in `032_node_replica_receipts` and a provision index in `030_node_command_outbox`. Delivery failures are removed after notification, never automatically retried. Schema changes take effect only when the backend starts with a new database connection.

**Execution targets:** `runtimes/execution-target.ts` is a leaf seam: `SessionExecutionTarget.send(command, commandId?)` delivers one semantic command, with the outbox row ID as the idempotency receipt (required for provision, which may throw `DeliveryDeferred`). `executionTargetFor(state, session)` selects the target by `storage_owner`; `installRuntimeHooks` registers the internal-node target (`runtimes/internal-node-execution.ts`: provision over the JSON-RPC link, other commands to the in-process node) and the legacy target (`runtimes/legacy-session-execution.ts`: server-owned `SessionManager` runtime). The dispatcher and `executeSessionCommand` call only the resolver, so they import neither `SessionManager` nor a target implementation. Callers still validate the current source themselves. The interface exposes no live runtime and no `open`: `ensureSessionOpen` remains the explicit (owner-branching) open path for callers that still drive a runtime directly (code-review submission). Owner checks that remain are storage/view semantics, not execution: a node-owned session with no outbox work is a failed open (`waitForAdmission`, `SessionInstance.wait`, session views), and live-runtime observation for waits/abort/active lists.

`handler.install()` acquires the `@reins/node/node` instance via `startNode()` (releasing its lease on uninstall) before the dispatcher drains work. Overlapping handler installs on the same node SQLite connection reuse a live node/runtime cache; old in-flight server-handler work can finish without closing an active Pi run. `runtimes/internal-node.ts` is the in-process server adapter: it injects the credential store and serves node→server calls (below); the node package opens and owns its SQLite connection. It resolves and passes the source/path/created-at/parent binding from product rows. The node itself never imports backend state or tables. `startNode()` runs node-owned versioned SQLite migrations once per new node instance and returns a running node; `getNodeDb()` runs them when opening the default connection, while binding never runs schema setup. The node's own `migrations` table records `001_canonical_node_storage` (canonical lane/binding/outbox/receipts, including the provisioned task snapshot on the session binding row), `002_node_attachments` (image cache), `003_session_outbox` (moves pending commits into the ordered per-session outbox shared with lifecycle reports), `004_session_task` (task snapshot), `005_attachment_uploads` (rebuilds the outbox, keeping rows, IDs and its AUTOINCREMENT sequence, so it can hold `attachment` upload rows) and `006_node_attachment_content` (content index for reusing cached attachments). New versions append named migrations; startup applies missing SQL and ledger inserts transactionally without reconstructing or comparing the full schema. Nonempty DBs without the ledger (including the earlier `user_version` experiment) and unknown migration names fail closed. Migration errors throw synchronously during node initialization before commands are accepted; no reset or automatic deletion occurs. Migrations are atomic, node-local, restart-required and do not import backend migrations. Test against in-memory or temporary files, never the user's default DB; back up node storage before deployment because discarding an old node DB makes node-owned sessions unresumable (server history/images remain readable). See [node-migrations.md](node-migrations.md) for the append-only migration workflow. `send()` binds and checks provisioned sessions, opens node canonical storage with ordered outbox delivery, and executes addressed commands. The dispatcher retains server scheduling, source lookup, claim/settle, failure notification and UI projection. `runtimes/node-execution.ts` routes immediate controls through the same instance. **Loopback JSON-RPC provision:** the dispatcher sends node-owned `session.provision` (wire method and capability of the same name) through `provisionInternal()` in `runtimes/internal-node.ts`, which pairs `createServerTransport` (`node-transport/server-peer.ts`) with the node half `connectNode()` (`@reins/node/node-connection`) over `createLoopbackPair()` (`@reins/node/protocol`: string frames, microtask delivery, close seen by both ends, queued frames dropped). The same hello/ready negotiation, zod wire schemas and epoch checks as a remote node apply, so values that do not survive JSON fail as `-32602` instead of leaking in-process. The wire params carry `configuration` beside the binding; the node reconstructs `{op, sessionId, sourceId: binding.sourceId, configuration: {model, thinkingLevel, task}}` in the stored command's key order, so the receipt payload equals `JSON.stringify` of the stored outbox command byte-for-byte and a replay (which re-sends the stored bytes) matches it; node rejections return application error `-32000` whose JSON-RPC `error.data` is the NodeResult error `{code, message, retryable}` (`nodeError` in `@reins/node/protocol`); exceptions thrown by node code use the same code with `{code: "internal", retryable: false}`. The peer validates `error.data` against a per-call schema, bounds it to 8 KiB and error messages to 2048 chars (senders truncate messages and replace oversized data with `-32603`), and treats malformed or oversized error responses as a non-deferred `-32603` that closes the connection. `node-transport/provision.ts` maps the wire outcome to a `NodeResult`, so the dispatcher records the node's own code (e.g. `invalid_request`) and never sees RPC codes; other protocol failures (e.g. `-32602`) are terminal `internal` failures. Connection loss, send failure, failed negotiation, call timeout (30s default for provision; outcome unknown, late reply dropped), busy (`-32002`) or stale epoch (`-32003`) throw `DeliveryDeferred`: `deliverCommand` returns the row to `queued` (never `failed`) and the dispatcher replays it on the next wake/poll, safe because provision is idempotent by ordering and receipted by command ID (see *Session configuration*). Only provision may use this; prompt/steer receipts are not atomic with Pi. `stopInternalNode()` closes the link; each handler install creates its own link (handlers are per connection, never registered on the shared `Node`), and a closed link is recreated on the next provision. Negotiation (`node.hello`) has no timeout. Prompt, steer, setModel, abort, pending resume and `open()` still call `Node` directly. Legacy server-owned sessions continue through `legacy-session-execution.ts` and server SQLite. The server applies node committed writes and receipts in `node-replica.ts`; `runtimes/internal-node.ts` serves `session.committed` into it and supplies product policy; `startNode()` selects the node-owned database internally. The node deletes outbox batches only after the server acknowledges them. Pi storage SQL is shared in `@reins/node/pi-storage`, with a server-only writer guard in `runtimes/pi/storage-adapter.ts`.

**Intermediate seam:** `packages/node/src/runtime/build.ts` constructs Pi for new node-owned sessions from node-local storage/resources/native tools and owns the runtime map; backend `SessionManager.open()` now rejects node-owned sessions. Its old builder/registry path still serves existing server-owned sessions. The node receives its session configuration (model, thinking level, task) with `session.provision` (see *Session configuration* below), renders the system prompt and checks out the task branch itself, so opening a runtime makes no server call; only the credential store is still an in-process JS object (see *Agent tools* below for tools); browser events cross the link as `session.event` and run lifecycle as durable `session.started`/`session.settled` reports (below). For node-owned sessions, the node fetches attachment bytes with `attachment.fetch` (below); the node verifies their checksum and declared MIME/size once when fetched and materializes them in its SQLite attachment cache (`node_attachments`) before prompt admission, then hydrates provider input synchronously from cached bytes. The same table holds node-created tool-result images, whose rows are the only copy until their outbox upload is acknowledged, so the cache must not be evicted while an upload row names it (nothing evicts it today; rows go only with the session). Opening a runtime does not fetch historical image bytes; an uncached historical reference becomes a provider placeholder. Native Pi drive/reopen code now lives in `@reins/node/pi-runtime`; `@reins/node/runtime` creates Pi model/resource context with an injected credential store, `@reins/node/host-tools` creates cwd-scoped native tools and execution environment, and `@reins/node/resources` / `@reins/node/prompt` own local discovery and slash expansion. The server still invokes these modules in-process and passes the product credential store; it holds only legacy server-owned live runtime instances in `ServerState.sessions`. Slash expansion now uses the session's bound source cwd rather than the project's current path. The node builder takes the immutable node session binding (created-at, parent ID and cwd) and canonical storage directly. The legacy server builder resolves those fields from the product row. The node verifies each command's binding against the binding stored at provision; the server resolves that binding from product rows on every send. This is not independently runnable node Pi: product credentials cross an in-process seam, not a serializable protocol. The node process is still the server process, so agent file/git work and the open-time branch checkout share its checkout and unsupported remote sources remain queued or fail closed. Node provision receipts are durable, but prompt/steer admission receipts are not atomic with Pi; delivery errors are reported as failures without automatic replay. If a session binding is missing from node storage, the node returns an explicit `not_found` with "This session's node data is missing. Start a new session." before Pi admission: the server marks that input `failed` and notifies its submitting WS client; the frontend refreshes authoritative activity after the error so optimistic streaming ends. A binding mismatch still throws and is reported as a failure. No remote daemon or network transport exists. See `docs/plans/node-architecture.md` for ownership and recovery limits.

**Node→server calls:** the node reports commits and fetches attachment bytes over the same JSON-RPC link, as a remote node would; `startNode()` takes only `credentials`. Method names live in `methods` (`@reins/node/protocol`; see *Wire method naming* below): `session.committed` `{epoch, sessionId, startSeq, writesJson}` → `{acknowledged: true}` is a durable report the node replays until acknowledged and the server dedupes by `(sessionId, startSeq)` in `node_replica_receipts`. `writesJson` crosses as a string, byte-for-byte, because a replay is compared by exact string (a different string for the same `startSeq` is rejected as divergence and stays pending). `attachment.fetch` `{epoch, sessionId, attachmentId, offset}` → `{attachment: {data, mimeType, byteSize, sha256, filename?, width?, height?} | null}` returns base64 of raw bytes `[offset, offset + 512 KiB)` so a 10 MiB upload fits 1 MiB frames; the node loops over offsets, requires consistent metadata and exact chunk lengths, then verifies total size and sha256 before caching. `attachment.store` `{epoch, sessionId, attachmentId, mimeType, sha256, byteSize, filename?, width?, height?, offset, data}` → `{stored: true} | {nextOffset}` is the reverse direction, for node-created image bytes (tool results; see *Images* under *Session events*). **The node assigns `attachmentId`** (`att_<uuid>`; the schema allows `[A-Za-z0-9_.-]`, 1–128 chars) when it references the image, and the node delivers the upload from its session outbox (below), so it is a durable report like `session.committed`, replayed until acknowledged. `data` is base64 of raw bytes `[offset, offset + 512 KiB)`, symmetric with fetch, so it fits capped frames. On every chunk the server first looks up the session's attachment under that ID with its data held: the same sha256, MIME type and size answers `{stored: true}` at once without buffering (a replay after a lost reply is idempotent), and different content under that ID is rejected (`-32000` "Attachment <id> is already stored with different content": divergence, left pending on the node like a divergent commit). Otherwise it keeps one partial upload per connection keyed by `(sessionId, attachmentId)` (at most 8; the oldest is evicted; cleared on close) holding the contiguous prefix received; a chunk whose offset is not that prefix length gets `{nextOffset: received}` (so a retried chunk is not appended twice, and an evicted or unknown upload restarts at 0), every chunk must be exactly `min(512 KiB, byteSize - offset)` bytes, and changed metadata for the key rejects. After the last chunk the server verifies the sha256, then stores through the session attachment store under exactly the node's ID (the upload MIME allowlist and 10 MiB limit apply; an ID another session holds rejects with "Attachment ID already in use"; a pruned row with the same content has its bytes restored). Identical bytes already held under another ID are stored again under the new ID, never remapped, so every transcript reference resolves as written; backend migration `034_session_attachment_node_ids` replaced the per-session `(sha256, mime_type)` uniqueness with an index for this (server-assigned uploads still dedupe by content). Mismatches and store rejections are `-32000`, `byteSize` over 10 MiB is `-32602`. Each chunk call has the 30s timeout; the node loops from `nextOffset`, bounded to twice the chunk count plus one. Frames: `createRpcPeer(socket, handlers, { maxFrameBytes })` caps each frame (default 1 MiB, `DEFAULT_MAX_FRAME_BYTES`); `createServerTransport` and `connectNode` pass the option through, and the internal loopback link uses `Infinity`, so a committed batch of any size crosses in one frame. `writesJson` has no size limit; a remote (capped) transport will need chunked commits, since an oversized batch would otherwise never deliver and would block that session's later outbox rows, including lifecycle reports. Attachments ≤ 10 MiB (`MAX_ATTACHMENT_BYTES`, the upload limit; larger rejects with an explicit `-32000`). The upload MIME allowlist (`ATTACHMENT_IMAGE_MIME_TYPES`) and size limit are exported by `@reins/node/protocol` and used by both the node and the server attachment store. These methods are base protocol v1, not capabilities: the server accepts them only after `node.hello` and only with the epoch it issued (`-32003` otherwise). Handlers are injected into `createServerTransport(socket, handlers)`; `internal-node.ts` supplies them with the storage-owner check (session must be `internal-node`-owned), so the transport imports no product stores. Server application errors use `-32000` with a message only. Node side: `connectNode()` attaches its connection to the `Node` immediately (calls await negotiation) and detaches on close or failed negotiation; the newest attached connection serves calls, and attaching replays every session's pending outbox. With no attached connection, calls reject: commits, attachment uploads and lifecycle reports stay pending, and a prompt/steer needing an uncached attachment returns `unavailable`/retryable (explicit server rejections return `invalid_request`). `internalNodeFor()` recreates a closed link so server calls do not depend on a provision. Calls time out after 30s with unknown outcome; all are safe to retry.

## Wire method naming

Wire methods are named for what is happening, not for what the receiver does or which side serves them. All names live in `methods` (`@reins/node/protocol`).

- Commands sent to the node are imperatives on the resource: `session.provision` (later `session.prompt`, `session.setModel`, …, which today are semantic contract ops delivered in-process).
- Requests name the resource: `attachment.fetch`, `script.execute`.
- Durable reports are past tense: `session.committed`, `session.started`, `session.settled`.
- Live notifications: `session.event`.
- Only connection-level methods use the `node.` prefix: `node.hello`. Per-session queries are `session.*` (`session.status`).

Server→node methods are negotiated capabilities named after the method (`capability` enum); node→server methods are base protocol.

**Session configuration (in `session.provision`):** the server resolves a session's configuration once, at creation (`createManagedSession`), and freezes it into the provision command stored in `node_command_outbox`: `configuration: {model: {provider, modelId} | null, thinkingLevel: string | null, task: {title, description, branchName} | null}`. Model: the creation override, else the `default_model` setting (its runtime type must match); thinking: the override's level, else the default's, with the row's `off` sent as null. The same model and thinking level are persisted on the server session row; a later `default_model` change never reaches an existing session, and a session created with no resolvable model stays at null (it cannot open until `session.setModel`). The task is a snapshot: task title/description edits after creation are **not** propagated to the node (the branch name is immutable). On the node (`send` in `node.ts`), provision is idempotent by **ordering**, not by one transaction:

1. When a model was resolved, it is looked up in the node's model registry first; a model the registry does not know rejects the provision with `invalid_request` (`Model not found: <provider>/<model>`) before anything is stored (no binding, lane or receipt). The dispatcher records the failure, logs it and broadcasts `{type: "error", sessionId, error: "Session open failed: …"}` to connected clients, then removes it; the session shows "Session open failed", and opening it reports its node data missing.
2. `provisionNodeSession` (`storage.ts`) stores the binding and, on first bind, the task snapshot (`sessions.task_json`, node migration `004_session_task`; NULL is a scratch session). An equal binding is a no-op (the first provision's task stands); a different one rejects. The configuration is not part of the binding: binding equality (`verify`) still compares only source, cwd, created-at and parent.
3. Unless the main lane already exists, Pi creates it (`createMainLane` in `runtime/lane.ts`): an `AgentHarness` over a `StorageBackedSession` on the node's `PiStorageAdapter`, created with just the registry model, `thinkingLevel` and no active tools, then `harness.lane("main")` and `harness.close()`. Pi writes its own lane records through the adapter, so they replicate like any Pi commit; the runtime sets its registered tools at first open. No resolved model: no lane (open fails "requires an explicit model" until `session.setModel`).
4. The admission receipt is recorded **last**. A crash before it leaves no receipt, so the server replays the same command and each step converges (the binding matches, the lane exists and is not written again); a replay after the receipt is a no-op (identical bytes; different bytes: `Node admission receipt mismatch`). A replay whose lane exists converges even if its model has since left the registry. Provision's lane creation and runtime opening are serialized per session, because Pi's storage has no cross-harness conflict detection.

From then on Pi's lane is the **only** durable copy of the node's model selection: the node keeps no other. Opening reads the stored selection through Pi's `laneConfig` address (`storedLaneModel`), because building a harness needs a registry model first and an unknown stored model must still be reported by name.

Pi does not persist the system prompt (the harness takes it from options at every open; only model, thinking level and active tools are lane state), which is why the task snapshot lives with the binding. At every open the node, with no server call:

- checks out `task.branchName` in the binding cwd with node-local git (`runtime/git.ts`) only if the current branch differs; a git failure fails the open;
- renders the system prompt itself with `buildReinsSystemPrompt` (`@reins/node/system-prompt`, the single copy, also used by the legacy server builder, the Claude adapter and `print-reins-system-prompt.ts`); a null task is a scratch session. Fixture tests (`runtime/system-prompt.test.ts`) pin its output byte-for-byte to the pre-move server rendering;
- reads the model from Pi's lane and validates it against its model registry before building Pi: an unknown model throws `NodeModelNotFoundError`; no lane (no model was ever resolved) fails with `AgentHarness Pi runtime requires an explicit model`. Pi restores the lane's model and thinking level.

`NodeDependencies` holds only `credentials`: the DB-backed credential store is the last in-process dependency, pending a credentials RPC (OAuth refresh coordination is unsettled). Runtime errors log node-locally (`console.error`).

**Model changes (`session.setModel`):** `{op: "session.setModel", sessionId, provider, modelId, thinkingLevel?}` → `{kind: "modelSet"}`. `Sessions.setModel` (the HTTP session model route and scripting `sessions.setModel`) keeps its server-side provider/model validation against the catalog, then for a node-owned session updates the row and enqueues the command in `node_command_outbox` in one transaction, wakes the dispatcher and returns the updated row without waiting: the node applies it asynchronously. It is `submit-work` and delivered in outbox order like prompt/steer: after earlier queued commands of the session are admitted (a prompt's run may still be going; the lane change applies from Pi's next LLM turn) and before later ones; a request is never deduplicated, so the last delivered change wins. Omitting `thinkingLevel` keeps Pi's current level. The node applies it to the open runtime, or opens one if needed (validating the new model and seeding a lane Pi has not created, so a lane whose stored model is gone can be repaired), and calls the runtime's `setModel`, which persists through Pi's lane. A receipt is recorded after the lane write (non-atomic, like prompt/steer); a replay with the same command ID returns `modelSet` without applying again. A model the node's registry does not know returns `invalid_request` (`Model not found: <provider>/<model>`): the command fails, is logged, and every connected client gets `{type: "error", sessionId, error: "Model change failed: …"}` plus `session_updated` (there is no single submitting client), then the failed command is removed. The row keeps the requested model until the next settlement reports Pi's actual selection. Legacy server-owned sessions keep the direct path: a live in-memory runtime gets `setModel` immediately and nothing is queued. The server no longer reaches into the node's live runtime to change a model.

**Durable run lifecycle (node→server reports):** `session.started` `{epoch, sessionId, runId}` and `session.settled` `{epoch, sessionId, runId, status, error?, metadata: {model, thinkingLevel}, reply, replyError?}` → `{acknowledged: true}` are base-protocol requests, like `session.committed`. They drive durable server effects (activity `running`/`finished`, runtime model metadata, a child's report to its parent), so they are never lost with a notification.

- *Node persistence and ordering:* commits, attachment uploads and lifecycle reports share one node table, `session_outbox` (migration `003_session_outbox`; `attachment` rows since `005_attachment_uploads`), ordered by row ID and drained per session serially (`deliverNodeOutbox`); a row is deleted only after the awaited acknowledgement, and a failure stops that session's drain until the next commit, report, provision or attach. A commit row is inserted inside its Pi commit transaction and the harness emits `run_start`/`run_end` after that commit, so a settlement is always delivered after the transcript commits it summarizes, and run N's `settled` before run N+1's `started`. An `attachment` row (payload `{"attachmentId"}`; the bytes stay in `node_attachments` and are read at delivery, never copied into the outbox) is inserted in the same SQLite transaction that writes the cached bytes, which is the transaction that creates the reference: either the `after_tool` hook's own transaction, before Pi can commit or stage the result carrying it, or the Pi commit transaction itself (storage-adapter safety net), before that commit's row. Row IDs are AUTOINCREMENT, so every upload is delivered, and acknowledged, before any commit that can contain its reference, and the server holds the bytes under that ID before its replica applies the transcript entry. For a child session (binding `parentSessionId`) the settlement needs the final reply from an async transcript read: the node inserts the settlement at once with `ready = 0`, which holds it **and every later row of that session** in place, then fills in `reply` (or `replyError`) and marks it ready. A new node instance (`startNode()`) releases rows left unready by a crash as `replyError: "The node restarted before the final reply was read"`. Pi emits `started` again with the same runId on `run_resume` and in-run compaction; each is recorded and the server treats it as a replay.
- *Server idempotency:* `node_lifecycle_receipts` (backend migration `033_node_lifecycle_receipts`) is keyed by `(session_id, run_id, kind)` and stores the report JSON (without epoch/sessionId). `runtimes/node-session-events.ts` applies each report through `SessionInstance.startedWith()`/`settledWith()` with a receipt callback (`recordNodeLifecycle` in `node-replica.ts`) that runs **inside the same server transaction** as the activity update, metadata write and the parent steer's `node_command_outbox` insert (`enqueueSessionInput`, synchronous). An identical replay (e.g. after a lost ack) applies nothing and is acknowledged, so it cannot re-steer the parent or re-flip state; a different payload for an existing key is divergence: rejected with `-32000`, left pending on the node, and applied nowhere. Broadcasts and the dispatcher wake happen after commit. Because the node delivers a session's reports in order and only after the previous acknowledgement, no per-session `SessionInstance` is retained for node sessions: each report uses a fresh instance, and the stale-settlement guard (`activeRunId`) only matters for legacy in-process runtimes, where a child's async reply read can overlap the next run.
- *Reply failure:* if the node cannot read a child's transcript, `reply` is null and `replyError` carries the message; the server logs it and marks the child `finished` without reporting to the parent (the pre-protocol behaviour; no misleading "Session completed."). A parent that cannot receive the report (out of scope, source unavailable) is likewise logged and leaves the child `finished`. Legacy server-owned sessions reach the same `settledWith()` through `settled(runtime, outcome)`, reading the reply in-process and applying without a receipt.
- *Limits:* a run that never settles because the node died mid-run leaves the session `running` until a later run (crash recovery is open). Receipts are not pruned. Without installed services (`subscribeInternalNodeServices`), lifecycle reports are rejected and stay pending.

**Session events (node→server notification):** `session.event` `{epoch, sessionId, seq, event}` is a JSON-RPC notification (no `id`, never answered) carrying live UI deltas only. The peer (`createRpcPeer`) takes notification handlers (`{params, notify}`) alongside call handlers and offers `notify(method, params)`. Notifications are best effort: an unknown method, invalid params, a failing handler, a stale epoch or an out-of-order seq drops that one notification with a `console.warn` and never closes the connection (closing would fail durable in-flight calls for a lossy message); a call to a notification-only method gets `-32601`. `notify()` returns false and drops locally when closed or when the frame exceeds the peer cap; a socket failure still closes the peer. `event` is a runtime event, relayed to browsers as the node runtime projected it; the schema checks its `type` and that every image block in any `content` array (messages, tool results, partial tool results) is an attachment reference (`{type: "image", attachmentId, mimeType, byteSize, sha256?, filename?, width?, height?}`, strict), so an event carrying inline image bytes is dropped at the wire; run lifecycle is not a session event. `seq` is per session and node instance, starts at 1 and increments for every event the node emits, including ones dropped because no connection is attached (then the event is discarded without error). The node emits a session's events in occurrence order. The server transport accepts only the issued epoch, drops seqs at or below the last one seen on that connection, and passes `missed` (skipped seqs since the previous event, 0 for the first on a connection) to its `event` handler, which logs gaps; there is no replay or resync, and seqs are not compared across reconnects or node restarts. A lost event only affects live browser rendering; the transcript remains `session.committed`. `internal-node.ts` authorizes the storage owner and forwards to the services injected per `ServerState` by `installRuntimeHooks()` (`runtimes/node-session-events.ts`), which broadcasts the event as received: the server no longer externalizes node event images. `onError` stays node-local.

*Images:* session events never carry image bytes. Pi holds user prompt images as references (hydrated only for providers), and tool-result images are turned into references where Pi produces them, synchronously and without the network: the node registers Pi's `after_tool` hook (`referenceToolImages` in `createAgentHarnessPiRuntime`, implemented by `runtime/tool-images.ts`), which runs after a tool executes and before Pi stages and commits its result. For each inline image block it first looks for a cached `node_attachments` row of the session with the same sha256 and MIME type (index `node_attachments_content`, migration `006_node_attachment_content`) and, if one exists, reuses its ID and writes nothing, so an image read or checkpointed repeatedly, or met again by the storage-adapter safety net, is cached and uploaded once. Reuse keeps the outbox ordering: a node-created row's upload row was appended in an earlier (or the same) transaction, so it precedes any commit that now references it, or was already acknowledged; a prompt attachment materialized by `attachment.fetch` is cached under the server's ID and has no upload row because the server already holds it. The reference then carries the cached row's metadata, which is what the server holds for that ID (filename and dimensions are hints, so the first occurrence's win and a later block's differing hints are dropped). The same bytes under another MIME type, or in another session, get their own attachment. Otherwise it assigns a new ID (`att_<uuid>`) and, in one node SQLite transaction, writes the bytes into `node_attachments` under that ID and appends an `attachment` upload row to the session outbox; it returns the reference of the prompt-image shape (`{type: "image", attachmentId, mimeType, byteSize, sha256, filename?, width?, height?}`) at once. The hook never waits on the server and never keeps bytes inline: with no connection the run proceeds normally and the upload waits in the outbox with the commits. Pi then stages and commits the reference, so the tool-result message, `tool_execution_end`, message/entry/turn/agent events and `session.committed` (hence the server replica and transcript reload) all carry it. Pi does not validate or strip image blocks on commit or replay (its `ImageContent` type requires `data`, so the hook's return is cast in that one place, as prompt references already are); compaction only serializes text. `toProviderMessagesForSession` hydrates references inside `toolResult` messages from the node cache, as it does for `reinsInput`, so the provider still receives the bytes (an uncached reference becomes the `[Image attachment missing]` text).

- *Rejection policy:* before referencing an image the node applies the server's upload rules: a MIME type outside `ATTACHMENT_IMAGE_MIME_TYPES`, empty bytes or more than 10 MiB replace the block with a text note (`[Image omitted: unsupported type <mime>]`, `[Image omitted: empty]`, `[Image omitted: larger than 10 MiB]`), with nothing cached or queued, so the model sees the note rather than the image. Every queued upload is therefore one the server accepts, and a server rejection of a queued upload (different content under the ID, an ID another session holds, a missing cache row) is a real divergence or corruption: it stays pending and, like a divergent commit, holds back that session's later outbox rows until resolved. Nothing retries it past the normal drain triggers.
- *Storage-adapter safety net:* Pi can commit a tool result without running `after_tool` (a checkpointed result it republishes for an interrupted tool on recovery; a hook cut short by abort). The node's `PiStorageAdapter` (opened by `openNodeStorage`) takes a `prepare` step that rewrites the prepared writes inside the commit transaction, before they are stored and before the commit row is recorded: `referenceInlineImages` (the hook's conversion, shared) replaces every inline image in any `content` array of any write (message entries, `retainedTail` messages, Pi's staged `pi.pending.entry` values and `pi.pending.tool_output` checkpoints) with a reference, its bytes and upload row written in the same transaction. No inline image reaches node storage or `session.committed`. A commit that fails rolls back its conversion with it; a retried Pi commit converts afresh (reusing any cached ID for the same content, otherwise new IDs; nothing orphaned), and outbox replays resend the stored, already converted `writesJson` bytes, never converting again. Reads return the stored references, which providers hydrate from the cache; Pi's in-memory copy of that one result may still hold the bytes until it is re-read, and live events built from it get the placeholder below. The legacy server-owned adapter has no `prepare` step.
- *Stray inline images in live events* (a partial result in `tool_execution_update`, sent before `after_tool` runs; Pi's in-memory copy of a result the safety net converted) are replaced in the live event only by the text block `[Image attachment unavailable]` (`sendableEvent` in `node.ts`), synchronously, so ordering and seqs are unchanged.

*Legacy server-owned sessions* are unchanged: their tool results keep inline images in the transcript and `runtime-broadcast-observer.ts` externalizes live event images on the server (`externalizeRuntimeEventImages`); image blocks that are already references (user prompt images, which previously made externalization throw and broke those events) pass through.

**Agent tools (node→server requests):** the server does not execute agent tools. Every tool definition lives on the node: native read/write/edit/bash (`@reins/node/host-tools`) and the Reins application tools `create_task`, `search` and `execute` (`@reins/node/reins-tools`), assembled by `buildNodeRuntime`; `NodeRuntimePolicy` has no tools field. Their names, descriptions, parameter schemas and order are the model-visible contract, pinned by a snapshot test (`runtime/reins-tools.test.ts`). Each Reins tool forwards exactly one base-protocol request, named per *Wire method naming*:

- `script.execute` `{epoch, sessionId, callId, code}` → `{ok: true, text} | {ok: false, error}`: the server runs the script in its `node:vm` sandbox against the Reins scripting API (`tools/execute.ts`). A script that throws is a completed call (`ok: false`), so its full message reaches the model as `Error: <message>` exactly as before; the tool keeps its `{success}` details.
- `script.search` `{epoch, sessionId, query}` → `{text, matchCount}`: the formatted scripting API documentation (`tools/search.ts`).
- `project.createTask` `{epoch, sessionId, title, description, branchName?, prompt?}` → `{task, sessionStarting}`: creates the task through the task model (branch, broadcast) and, with a prompt, starts a session on it fire-and-forget as before (`tools/create-task.ts`). Not folded into execute.
- `script.cancel` `{epoch, sessionId, callId}` (notification): aborts the `AbortSignal` of that in-flight script, if it belongs to the same session.

*Scope and authorization:* params name only the calling session; strict schemas reject any project/task field (`-32602`), so a node cannot widen scope. `internal-node.ts` runs the same storage-owner check as the other node→server methods (unknown session, or one not `internal-node`-owned, is rejected with `-32000` before product code runs), then `runtimes/node-tool-calls.ts` (injected with the report services by `installRuntimeHooks()` as `subscribeInternalNodeServices`) derives project/task from the server's session row and builds the server-side `SessionInstance` for `sessions.*` scripts and task session starts. `internal-node.ts` therefore imports no session manager/instance. Rejections are `-32000` with a message (truncated to 2048 chars); the tool reports them as `Error: <message>`.

*Timeouts, abort and retries:* per-call timeouts are 5 min for `script.execute` (the vm bounds synchronous code to 30s, but a script may await several `sessions.wait` calls of up to 30s each), 30s for `script.search` and 60s for `project.createTask` (git branch creation). The tool's `AbortSignal` is passed to the peer call: aborting stops the node waiting immediately (late reply dropped). On abort or timeout of `script.execute` the node also sends `script.cancel`; the server aborts the script's signal, which API calls that honour it (`sessions.wait`) observe; synchronous script code and already-started effects are not interrupted. Closing the link aborts every in-flight script. `project.createTask` and `script.search` have no server-side cancellation. None of the calls is retried automatically. Transport failures become tool results, never exceptions: a timeout, abort, connection loss after sending or `-32603` means the outcome is unknown, and `execute`/`create_task` say so ("may have run, with side effects" / "the task may have been created"); no attached connection, busy, invalid params or stale epoch mean the call did not run. Results are unbounded on the uncapped internal link; over a capped transport an oversized result fails with `-32603` (unknown outcome).

*Legacy server-owned sessions* build the same `@reins/node/reins-tools` definitions through `createCustomTools()` (`tools/index.ts`), whose `serverToolCalls()` calls the same server functions in-process; there is one copy of the tool definitions and of each server operation.
