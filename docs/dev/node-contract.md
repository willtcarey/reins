# Internal node seam

`packages/node/src/contract.ts` is the isolated `@reins/node/contract` export of a separately buildable node package. It contains a versioned semantic vocabulary for session provision, prompt, steer, abort, pending resume, typed results and observations. It imports no server, Pi or browser modules; Oxlint restricts the contract's imports to `zod` and backend imports to declared node package exports. Future daemon implementation belongs elsewhere in `packages/node/src/`, not in this export. `deliveryPolicy()` classifies provision, prompt and steer as `submit-work`, matching server outbox admission; abort and pending resume remain immediate controls. The classifier does not itself deliver commands. The semantic contract alone does not guarantee delivery or offline execution. Future read-only workspace/git commands should use `request-now` and return unavailable when offline. `node-command-store.ts` owns SQLite outbox rows and transitions; `models/node-command-projection.ts` owns submission/projection and a wake hint; `models/node-command-dispatcher.ts` resolves the session's current source and owns the sole delivery path. Session creation atomically stores the session and provision command, then signals a dedicated dispatcher after commit. The signal carries no command payload; startup, node availability/reconnect wake, and a 30-second poll rescan SQLite. The dispatcher resolves the session's current source before claim and uses the internal adapter to admit provisioning without constructing Pi. Creation returns a persisted ID and scheduling projection without awaiting the dispatcher or returning a live runtime. Browser HTTP creation returns a session view immediately; validated prompt/steer and scripting child starts persist their input without waiting for Pi admission (unsupported remote sources still reject input). The node adapter lazily opens/reopens Pi when an addressed input or explicit pending resume arrives. Session views distinguish provision scheduling from runtime activity; negative admission and delivery exceptions are `failed`; failures are notified and removed rather than automatically retried. The start signal is a hint; the periodic scan recovers missed hints. Existing process-startup handling still marks interrupted dispatches `unknown`; this slice does not change startup. Handler hot reload must not reinterpret previous in-flight work. Live delivery failures are notified and removed. `stop()` clears the timer. Prompt and steer now persist validated input in `node_command_outbox` before acknowledgement, keyed uniquely by `(session_id, command_json.clientId)` via a SQLite expression index (the clientId travels only inside the command payload); a replay with the same operation/content/source returns the prior admission acknowledgement. A different payload with that key is rejected. The single command dispatcher scans `node_command_outbox` in insertion order across all persisted operations. Queued and dispatching predecessors order work only within their session; a queued offline provision cannot stall unrelated sessions. Failed commands are removed after notification so later queued work can proceed. Provision must be admitted before its inputs; the internal node adapter interprets the command and owns readiness, lazy runtime opening and Pi admission; the transport claims and settles the command without knowing its operation. There is no input-only scan or claim lifecycle. The dispatcher scans, checks predecessor/source availability and sends one validated `NodeCommand` through the selected adapter. `node-command-transport.ts` alone claims and settles generic delivery, recording explicit negative results and exceptions (including malformed stored commands) as failed. The dispatcher fences inputs behind provision, while `@reins/node/node` interprets node-owned commands and lazily assembles/reopens Pi with node-local canonical storage and injected product policy; server-side `node-command-notifications.ts` handles scheduling/input-failure notifications after delivery. The adapter does not read the outbox or broadcast product events. Legacy persisted open/reopen is unsupported. Provision has an atomic node-side receipt; prompt/steer receipts follow Pi admission non-atomically, so absence of a receipt does not prove Pi did not admit the input. Provision scheduling changes notify through `Sessions.notifyScheduling()`, not a dispatcher-level broadcast. Eventual input failures use `node-command-notifications.ts`: only the currently connected submitting WS client registered for `(sessionId, clientId)` receives the existing error shape. Disconnected clients are not notified; failed commands are deleted after settlement, with no replay-to-UI mechanism yet. Scripting sends and child reports return on enqueue rather than Pi admission; explicit wait still observes runtime settlement. Process startup discards interrupted dispatches rather than replaying them; prompt/steer receipts remain non-atomic with Pi admission. Explicit abort and resume remain immediate controls rather than queued behind input. Errors after enqueue surface asynchronously on the existing WS error path, not as a retraction of the acknowledgement. Queued inputs survive process loss and are recovered by the shared dispatcher scan; remote execution and automatic retries remain unsupported. Provision only establishes source admission: model validation and Pi construction happen on the first addressed command, so an invalid configured model leaves provision admitted but the input failed and the failed command removed. A durable node-side receipt for safe replay is still missing. The outbox stores a session ID and operation, not a source. Without Pi-side durable admission keyed by command ID, dispatch failures and interrupted dispatches are reported as failures and never retried automatically. Queued commands are retained when no adapter is available; the dispatcher polls for eligible commands. No external node adapter is implemented. Semantic contract v3 uses a single durable `session.provision` (no open/reopen commands), attachment references and `sourceSessionId`; it is **not** a network protocol: no handshake, framing, correlation, ordering, delivery guarantee or serialized runtime event payload is promised. Change schema meaning with a version bump; negotiate incompatible versions closed when transport exists. For existing installations from the in-progress internal-node spike, reconcile schema changes on the affected development database before using the new code; the fresh schema defines `storage_owner` in `032_node_replica_receipts` and a provision index in `030_node_command_outbox`. Delivery failures are removed after notification, never automatically retried. Schema changes take effect only when the backend starts with a new database connection.

**Execution targets:** `runtimes/execution-target.ts` is a leaf seam: `SessionExecutionTarget.send(command, commandId?)` delivers one semantic command, with the outbox row ID as the idempotency receipt (required for provision, which may throw `DeliveryDeferred`). `executionTargetFor(state, session)` selects the target by `storage_owner`; `installRuntimeHooks` registers the internal-node target (`runtimes/internal-node-execution.ts`: provision over the JSON-RPC link, other commands to the in-process node) and the legacy target (`runtimes/legacy-session-execution.ts`: server-owned `SessionManager` runtime). The dispatcher and `executeSessionCommand` call only the resolver, so they import neither `SessionManager` nor a target implementation. Callers still validate the current source themselves. The interface exposes no live runtime and no `open`: `ensureSessionOpen` remains the explicit (owner-branching) open path for callers that still drive a runtime directly (code-review submission). Owner checks that remain are storage/view semantics, not execution: a node-owned session with no outbox work is a failed open (`waitForAdmission`, `SessionInstance.wait`, session views), and live-runtime observation for waits/abort/active lists.

`handler.install()` acquires the `@reins/node/node` instance via `startNode()` (releasing its lease on uninstall) before the dispatcher drains work. Overlapping handler installs on the same node SQLite connection reuse a live node/runtime cache; old in-flight server-handler work can finish without closing an active Pi run. `runtimes/internal-node.ts` is the in-process server adapter: it injects the credential store and serves node→server calls (below), including the session configuration the node fetches at open; the node package opens and owns its SQLite connection. It resolves and passes the source/path/created-at/parent binding from product rows. The node itself never imports backend state or tables. `startNode()` runs node-owned versioned SQLite migrations once per new node instance and returns a running node; `getNodeDb()` runs them when opening the default connection, while binding never runs schema setup. The node's own `migrations` table records `001_canonical_node_storage` (canonical lane/binding/outbox/receipts), `002_node_attachments` (disposable image cache) and `003_session_outbox` (moves pending commits into the ordered per-session outbox shared with lifecycle reports). New versions append named migrations; startup applies missing SQL and ledger inserts transactionally without reconstructing or comparing the full schema. Nonempty DBs without the ledger (including the earlier `user_version` experiment) and unknown migration names fail closed. Migration errors throw synchronously during node initialization before commands are accepted; no reset or automatic deletion occurs. Migrations are atomic, node-local, restart-required and do not import backend migrations. Test against in-memory or temporary files, never the user's default DB; back up node storage before deployment because discarding an old node DB makes node-owned sessions unresumable (server history/images remain readable). See [node-migrations.md](node-migrations.md) for the append-only migration workflow. `send()` binds and checks provisioned sessions, opens node canonical storage with ordered outbox delivery, and executes addressed commands. The dispatcher retains server scheduling, source lookup, claim/settle, failure notification and UI projection. `runtimes/node-execution.ts` routes immediate controls through the same instance. **Loopback JSON-RPC provision:** the dispatcher sends node-owned `session.provision` (wire method and capability of the same name) through `provisionInternal()` in `runtimes/internal-node.ts`, which pairs `createServerTransport` (`node-transport/server-peer.ts`) with the node half `connectNode()` (`@reins/node/node-connection`) over `createLoopbackPair()` (`@reins/node/protocol`: string frames, microtask delivery, close seen by both ends, queued frames dropped). The same hello/ready negotiation, zod wire schemas and epoch checks as a remote node apply, so values that do not survive JSON fail as `-32602` instead of leaking in-process. The node reconstructs `{op, sessionId, sourceId: binding.sourceId}` so the receipt payload matches the stored command; node rejections return application error `-32000` whose JSON-RPC `error.data` is the NodeResult error `{code, message, retryable}` (`nodeError` in `@reins/node/protocol`); exceptions thrown by node code use the same code with `{code: "internal", retryable: false}`. The peer validates `error.data` against a per-call schema, bounds it to 8 KiB and error messages to 2048 chars (senders truncate messages and replace oversized data with `-32603`), and treats malformed or oversized error responses as a non-deferred `-32603` that closes the connection. `node-transport/provision.ts` maps the wire outcome to a `NodeResult`, so the dispatcher records the node's own code (e.g. `invalid_request`) and never sees RPC codes; other protocol failures (e.g. `-32602`) are terminal `internal` failures. Connection loss, send failure, failed negotiation, call timeout (30s default for provision; outcome unknown, late reply dropped), busy (`-32002`) or stale epoch (`-32003`) throw `DeliveryDeferred`: `deliverCommand` returns the row to `queued` (never `failed`) and the dispatcher replays it on the next wake/poll, safe because provision admission is receipted atomically by command ID. Only provision may use this; prompt/steer receipts are not atomic with Pi. `stopInternalNode()` closes the link; each handler install creates its own link (handlers are per connection, never registered on the shared `Node`), and a closed link is recreated on the next provision. Negotiation (`node.hello`) has no timeout. Prompt, steer, abort, pending resume and `open()` still call `Node` directly. Legacy server-owned sessions continue through `legacy-session-execution.ts` and server SQLite. The server applies node committed writes and receipts in `node-replica.ts`; `runtimes/internal-node.ts` serves `session.committed` into it and supplies product policy; `startNode()` selects the node-owned database internally. The node deletes outbox batches only after the server acknowledges them. Pi storage SQL is shared in `@reins/node/pi-storage`, with a server-only writer guard in `runtimes/pi/storage-adapter.ts`.

**Intermediate seam:** `packages/node/src/runtime/build.ts` constructs Pi for new node-owned sessions from node-local storage/resources/native tools and owns the runtime map; backend `SessionManager.open()` now rejects node-owned sessions. Its old builder/registry path still serves existing server-owned sessions. The node fetches its session configuration (model, thinking level, task) with `session.configuration` (see *Session configuration* below), renders the system prompt and checks out the task branch itself; only the credential store is still an in-process JS object (see *Agent tools* below for tools); browser events cross the link as `session.event` and run lifecycle as durable `session.started`/`session.settled` reports (below). For node-owned sessions, the node fetches attachment bytes with `attachment.fetch` (below); the node verifies their checksum and declared MIME/size once when fetched and materializes them in its disposable SQLite cache before prompt admission, then hydrates provider input synchronously from cached bytes. Opening a runtime does not fetch historical image bytes; an uncached historical reference becomes a provider placeholder. Native Pi drive/reopen code now lives in `@reins/node/pi-runtime`; `@reins/node/runtime` creates Pi model/resource context with an injected credential store, `@reins/node/host-tools` creates cwd-scoped native tools and execution environment, and `@reins/node/resources` / `@reins/node/prompt` own local discovery and slash expansion. The server still invokes these modules in-process and passes the product credential store; it holds only legacy server-owned live runtime instances in `ServerState.sessions`. Slash expansion now uses the session's bound source cwd rather than the project's current path. The node builder takes the immutable node session binding (created-at, parent ID and cwd) and canonical storage directly. The legacy server builder resolves those fields from the product row. The server still verifies the binding against product identity (in `session.configuration`) before the node opens the runtime. This is not independently runnable node Pi: product credentials cross an in-process seam, not a serializable protocol. The node process is still the server process, so agent file/git work and the open-time branch checkout share its checkout and unsupported remote sources remain queued or fail closed. Node provision receipts are durable, but prompt/steer admission receipts are not atomic with Pi; delivery errors are reported as failures without automatic replay. If a session binding is missing from node storage, the node returns an explicit `not_found` with "This session's node data is missing. Start a new session." before Pi admission: the server marks that input `failed` and notifies its submitting WS client; the frontend refreshes authoritative activity after the error so optimistic streaming ends. A binding mismatch still throws and is reported as a failure. No remote daemon or network transport exists. See `docs/plans/node-architecture.md` for ownership and recovery limits.

**Node→server calls:** the node reports commits and fetches attachment bytes over the same JSON-RPC link, as a remote node would; `startNode()` takes only `credentials`. Method names live in `methods` (`@reins/node/protocol`; see *Wire method naming* below): `session.committed` `{epoch, sessionId, startSeq, writesJson}` → `{acknowledged: true}` is a durable report the node replays until acknowledged and the server dedupes by `(sessionId, startSeq)` in `node_replica_receipts`. `writesJson` crosses as a string, byte-for-byte, because a replay is compared by exact string (a different string for the same `startSeq` is rejected as divergence and stays pending). `attachment.fetch` `{epoch, sessionId, attachmentId, offset}` → `{attachment: {data, mimeType, byteSize, sha256, filename?, width?, height?} | null}` returns base64 of raw bytes `[offset, offset + 512 KiB)` so a 10 MiB upload fits 1 MiB frames; the node loops over offsets, requires consistent metadata and exact chunk lengths, then verifies total size and sha256 before caching. Frames: `createRpcPeer(socket, handlers, { maxFrameBytes })` caps each frame (default 1 MiB, `DEFAULT_MAX_FRAME_BYTES`); `createServerTransport` and `connectNode` pass the option through, and the internal loopback link uses `Infinity`, so a committed batch of any size crosses in one frame. `writesJson` has no size limit; a remote (capped) transport will need chunked commits, since an oversized batch would otherwise never deliver and would block that session's later outbox rows, including lifecycle reports. Attachments ≤ 10 MiB (`MAX_ATTACHMENT_BYTES`, the upload limit; larger rejects with an explicit `-32000`). These methods are base protocol v1, not capabilities: the server accepts them only after `node.hello` and only with the epoch it issued (`-32003` otherwise). Handlers are injected into `createServerTransport(socket, handlers)`; `internal-node.ts` supplies them with the storage-owner check (session must be `internal-node`-owned), so the transport imports no product stores. Server application errors use `-32000` with a message only. Node side: `connectNode()` attaches its connection to the `Node` immediately (calls await negotiation) and detaches on close or failed negotiation; the newest attached connection serves calls, and attaching replays every session's pending outbox. With no attached connection, calls reject: commits and lifecycle reports stay pending, and a prompt/steer needing an uncached attachment returns `unavailable`/retryable (explicit server rejections return `invalid_request`). `internalNodeFor()` recreates a closed link so server calls do not depend on a provision. Calls time out after 30s with unknown outcome; all are safe to retry.

## Wire method naming

Wire methods are named for what is happening, not for what the receiver does or which side serves them. All names live in `methods` (`@reins/node/protocol`).

- Commands sent to the node are imperatives on the resource: `session.provision` (later `session.prompt`, …).
- Requests name the resource: `attachment.fetch`, `session.configuration`.
- Durable reports are past tense: `session.committed`, `session.started`, `session.settled`.
- Live notifications: `session.event`.
- Only connection-level methods use the `node.` prefix: `node.hello`. Per-session queries are `session.*` (`session.status`).

Server→node methods are negotiated capabilities named after the method (`capability` enum); node→server methods are base protocol.

**Session configuration (node→server request):** when the node opens a session's runtime (first addressed input, resume or reopen) it calls `session.configuration` `{epoch, sessionId, binding}` → `{model: {provider, modelId} | null, thinkingLevel: string | null, task: {title, description, branchName} | null}`. The server rejects (`-32000`, message only) an unknown session (`Session not found: <id>`) and a session that is not `internal-node`-owned or whose current binding (source, cwd, created-at, parent) differs from the node's (`Node session binding mismatch: <id>`). Model: the session's stored provider/model, else the `default_model` setting when its `runtimeType` matches the session's; thinking: stored `off` is null, another stored level is used, an unset level falls back to the matching default's. A task ID whose task is gone is rejected. The result is plain data; the node then, before building Pi:

- checks out `task.branchName` in the binding cwd with node-local git (`runtime/git.ts`) only if the current branch differs; a git failure fails the open;
- renders the system prompt itself with `buildReinsSystemPrompt` (`@reins/node/system-prompt`, the single copy, also used by the legacy server builder, the Claude adapter and `print-reins-system-prompt.ts`); a null task is a scratch session. Fixture tests (`runtime/system-prompt.test.ts`) pin its output byte-for-byte to the pre-move server rendering;
- builds Pi; an unknown model still throws `NodeModelNotFoundError`.

Read-only and safe to retry, but not retried automatically: timeout 30s (`SESSION_CONFIGURATION_TIMEOUT_MS`). A server rejection fails the open with the server's message; no attached connection, timeout or another transport failure fails it with `Session configuration unavailable: <reason>`. Nothing is cached, so the next addressed input asks again. `NodeDependencies` holds only `credentials`: the DB-backed credential store is the last in-process dependency, pending a credentials RPC (OAuth refresh coordination is unsettled). Runtime errors log node-locally (`console.error`).

**Durable run lifecycle (node→server reports):** `session.started` `{epoch, sessionId, runId}` and `session.settled` `{epoch, sessionId, runId, status, error?, metadata: {model, thinkingLevel}, reply, replyError?}` → `{acknowledged: true}` are base-protocol requests, like `session.committed`. They drive durable server effects (activity `running`/`finished`, runtime model metadata, a child's report to its parent), so they are never lost with a notification.

- *Node persistence and ordering:* commits and lifecycle reports share one node table, `session_outbox` (migration `003_session_outbox`), ordered by row ID and drained per session serially (`deliverNodeOutbox`); a row is deleted only after the awaited acknowledgement, and a failure stops that session's drain until the next commit, report, provision or attach. A commit row is inserted inside its Pi commit transaction and the harness emits `run_start`/`run_end` after that commit, so a settlement is always delivered after the transcript commits it summarizes, and run N's `settled` before run N+1's `started`. For a child session (binding `parentSessionId`) the settlement needs the final reply from an async transcript read: the node inserts the settlement at once with `ready = 0`, which holds it **and every later row of that session** in place, then fills in `reply` (or `replyError`) and marks it ready. A new node instance (`startNode()`) releases rows left unready by a crash as `replyError: "The node restarted before the final reply was read"`. Pi emits `started` again with the same runId on `run_resume` and in-run compaction; each is recorded and the server treats it as a replay.
- *Server idempotency:* `node_lifecycle_receipts` (backend migration `033_node_lifecycle_receipts`) is keyed by `(session_id, run_id, kind)` and stores the report JSON (without epoch/sessionId). `runtimes/node-session-events.ts` applies each report through `SessionInstance.startedWith()`/`settledWith()` with a receipt callback (`recordNodeLifecycle` in `node-replica.ts`) that runs **inside the same server transaction** as the activity update, metadata write and the parent steer's `node_command_outbox` insert (`enqueueSessionInput`, synchronous). An identical replay (e.g. after a lost ack) applies nothing and is acknowledged, so it cannot re-steer the parent or re-flip state; a different payload for an existing key is divergence: rejected with `-32000`, left pending on the node, and applied nowhere. Broadcasts and the dispatcher wake happen after commit. Because the node delivers a session's reports in order and only after the previous acknowledgement, no per-session `SessionInstance` is retained for node sessions: each report uses a fresh instance, and the stale-settlement guard (`activeRunId`) only matters for legacy in-process runtimes, where a child's async reply read can overlap the next run.
- *Reply failure:* if the node cannot read a child's transcript, `reply` is null and `replyError` carries the message; the server logs it and marks the child `finished` without reporting to the parent (the pre-protocol behaviour; no misleading "Session completed."). A parent that cannot receive the report (out of scope, source unavailable) is likewise logged and leaves the child `finished`. Legacy server-owned sessions reach the same `settledWith()` through `settled(runtime, outcome)`, reading the reply in-process and applying without a receipt.
- *Limits:* a run that never settles because the node died mid-run leaves the session `running` until a later run (crash recovery is open). Receipts are not pruned. Without installed services (`subscribeInternalNodeServices`), lifecycle reports are rejected and stay pending.

**Session events (node→server notification):** `session.event` `{epoch, sessionId, seq, event}` is a JSON-RPC notification (no `id`, never answered) carrying live UI deltas only. The peer (`createRpcPeer`) takes notification handlers (`{params, notify}`) alongside call handlers and offers `notify(method, params)`. Notifications are best effort: an unknown method, invalid params, a failing handler, a stale epoch or an out-of-order seq drops that one notification with a `console.warn` and never closes the connection (closing would fail durable in-flight calls for a lossy message); a call to a notification-only method gets `-32601`. `notify()` returns false and drops locally when closed or when the frame exceeds the peer cap; a socket failure still closes the peer. `event` is a runtime event, relayed to browsers as the node runtime projected it (the schema checks only its `type`); run lifecycle is not a session event. `seq` is per session and node instance, starts at 1 and increments for every event the node emits, including ones dropped because no connection is attached (then the event is discarded without error). The node emits a session's events in occurrence order. The server transport accepts only the issued epoch, drops seqs at or below the last one seen on that connection, and passes `missed` (skipped seqs since the previous event, 0 for the first on a connection) to its `event` handler, which logs gaps; there is no replay or resync, and seqs are not compared across reconnects or node restarts. A lost event only affects live browser rendering; the transcript remains `session.committed`. `internal-node.ts` authorizes the storage owner and forwards to the services injected per `ServerState` by `installRuntimeHooks()` (`runtimes/node-session-events.ts`), which image-externalizes and broadcasts runtime events. `onError` stays node-local.

**Agent tools (node→server requests):** the server does not execute agent tools. Every tool definition lives on the node: native read/write/edit/bash (`@reins/node/host-tools`) and the Reins application tools `create_task`, `search` and `execute` (`@reins/node/reins-tools`), assembled by `buildNodeRuntime`; `NodeRuntimePolicy` has no tools field. Their names, descriptions, parameter schemas and order are the model-visible contract, pinned by a snapshot test (`runtime/reins-tools.test.ts`). Each Reins tool forwards exactly one base-protocol request, named per *Wire method naming*:

- `script.execute` `{epoch, sessionId, callId, code}` → `{ok: true, text} | {ok: false, error}`: the server runs the script in its `node:vm` sandbox against the Reins scripting API (`tools/execute.ts`). A script that throws is a completed call (`ok: false`), so its full message reaches the model as `Error: <message>` exactly as before; the tool keeps its `{success}` details.
- `script.search` `{epoch, sessionId, query}` → `{text, matchCount}`: the formatted scripting API documentation (`tools/search.ts`).
- `project.createTask` `{epoch, sessionId, title, description, branchName?, prompt?}` → `{task, sessionStarting}`: creates the task through the task model (branch, broadcast) and, with a prompt, starts a session on it fire-and-forget as before (`tools/create-task.ts`). Not folded into execute.
- `script.cancel` `{epoch, sessionId, callId}` (notification): aborts the `AbortSignal` of that in-flight script, if it belongs to the same session.

*Scope and authorization:* params name only the calling session; strict schemas reject any project/task field (`-32602`), so a node cannot widen scope. `internal-node.ts` runs the same storage-owner check as the other node→server methods (unknown session, or one not `internal-node`-owned, is rejected with `-32000` before product code runs), then `runtimes/node-tool-calls.ts` (injected with the report services by `installRuntimeHooks()` as `subscribeInternalNodeServices`) derives project/task from the server's session row and builds the server-side `SessionInstance` for `sessions.*` scripts and task session starts. `internal-node.ts` therefore imports no session manager/instance. Rejections are `-32000` with a message (truncated to 2048 chars); the tool reports them as `Error: <message>`.

*Timeouts, abort and retries:* per-call timeouts are 5 min for `script.execute` (the vm bounds synchronous code to 30s, but a script may await several `sessions.wait` calls of up to 30s each), 30s for `script.search` and 60s for `project.createTask` (git branch creation). The tool's `AbortSignal` is passed to the peer call: aborting stops the node waiting immediately (late reply dropped). On abort or timeout of `script.execute` the node also sends `script.cancel`; the server aborts the script's signal, which API calls that honour it (`sessions.wait`) observe; synchronous script code and already-started effects are not interrupted. Closing the link aborts every in-flight script. `project.createTask` and `script.search` have no server-side cancellation. None of the calls is retried automatically. Transport failures become tool results, never exceptions: a timeout, abort, connection loss after sending or `-32603` means the outcome is unknown, and `execute`/`create_task` say so ("may have run, with side effects" / "the task may have been created"); no attached connection, busy, invalid params or stale epoch mean the call did not run. Results are unbounded on the uncapped internal link; over a capped transport an oversized result fails with `-32603` (unknown outcome).

*Legacy server-owned sessions* build the same `@reins/node/reins-tools` definitions through `createCustomTools()` (`tools/index.ts`), whose `serverToolCalls()` calls the same server functions in-process; there is one copy of the tool definitions and of each server operation.
