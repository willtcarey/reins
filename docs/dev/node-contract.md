# Node contract

A **node** runs agent sessions: it owns the Pi runtime and the checkout the agent works in, and holds nothing durable ([ADR-015](../adr/015-server-canonical-storage-stateless-node.md)). The **server** never runs a session. It owns product state (projects, tasks, sessions, settings, credentials), **the only copy of every session's AgentHarness storage** and the browser UI/API. The node's Pi runtime reads and commits a session's storage on the server over the link.

**Sessions run on the server now** ([ADR-029](../adr/029-sessions-on-the-server-nodes-host-tools.md), step 2b of the node architecture plan): submitted work goes to the session's runtime on the server (*Submitted work*), whose tools run on its source's node (*Tool host*). The server sends no `session.*` command any more; the node's session path this doc still describes (its runtimes, `storage.*`, lifecycle reports, `session.event`, attachments, credentials, `script.*`) stays in the protocol until step 3 removes it, and step 4 rewrites this doc.

This doc covers what the server and node say to each other and what each is responsible for. How the link itself works (socket, framing, JSON-RPC, negotiation, streams) is in [node-transport.md](node-transport.md); read it first.

A node is a process running `packages/node`: the local node on the server's machine, linked over a Unix socket, or a remote node on another machine, paired with the server (*Pairing and authentication*) and linked over a WebSocket at `/nodes/link` (`reins node run`, *Process model*). See [the node architecture plan](../plans/node-architecture.md) for what is open. Decisions behind this design are recorded in ADRs [010](../adr/010-state-derived-idempotency.md), [012](../adr/012-ndjson-unix-socket-local-link.md)–[015](../adr/015-server-canonical-storage-stateless-node.md).

| Concern | Server (`packages/backend`) | Node (`packages/node`) |
|---|---|---|
| Session storage | The only copy: Pi tables in the server database, served over `storage.*` | None: every Pi read and commit crosses the link (`RemoteStorage`) |
| Execution | None | Pi runtime, native tools, Reins tools (which call the server), skill/resource discovery, task branch checkout |
| Submitted work | Admitted by the session's runtime on the server, one chain per session (*Submitted work*) | None: tools and files only (*Tool host*) |
| Credentials | Sole holder and sole OAuth refresher | Reads them over the link; caches in memory only |
| Attachments | Durable bytes for the browser and for providers | In-memory cache of bytes the server holds |

## Process model

The server and the local node are separate processes that meet only on the node socket ([node-transport.md](node-transport.md)).

- **Server-only** (`bun run start:server`, `packages/backend/src/index.ts` → `server-process.ts`): opens the product database under `REINS_DATA_DIR`, listens on HTTP (remote nodes connect there, at `/nodes/link`) and on the node socket. It never starts a node.
- **Node-only** (`bun run start:node`, `packages/node/src/main.ts`): starts the node and dials the socket. Its lifecycle (the signals, pausing, refusal and reload below) is `runNodeProcess` (`node-process.ts`), which resolves with why the node stopped; `main.ts` gives it the transport (`unixTransport`) and picks the exit code. It keeps no state on disk: its data directory (`REINS_NODE_DATA_DIR`, default `~/.reins`) holds no session state: the bytes of unfinished `fs.write`s (`partial-writes/`), which it removes when it starts, and, on a paired machine, the node's pairing and key (*Pairing and authentication*), which the local node does not read. Logs go to stdout/stderr with a `[node]` prefix. It announces `REINS_NODE_ID`, by default `DEFAULT_LOCAL_NODE_ID` (`"internal"`, the node row the server's migrations seed). `REINS_DOCS_DIR` is where the REINS docs named in its sessions' environment prompt are (a delivered bundle's `builds/<buildId>/docs`, holding only `features/`); unset, they are the checkout's `docs/` ([node-runtime.md](node-runtime.md) *Assembly*). `REINS_NODE_TEST_FAUX_PROVIDER` is a **test-only** hook (`src/testing/faux-provider.ts`) registering a scripted model for process-level tests; never set it in production. A production node bundle leaves its code out (`REINS_TEST_HOOKS`, [node-bundle.md](node-bundle.md)).
- **Remote node** (`reins node run`, `packages/cli/src/node/run.ts`, which runs `runInstalledNode` in `node-process.ts` and prints how it ended, `report`): runs this machine's paired node in the foreground. On a remote machine `reins` is the node bundle, `bun --no-install <dir>/reins.js`, which an installed node runs through its launcher, `~/.reins/bin/reins` ([node-bundle.md](node-bundle.md)), which sets `PI_PACKAGE_DIR` (`<dir>`), `PI_OFFLINE=1` and `REINS_DOCS_DIR` (`<dir>/docs`, where it writes the docs/features it carries) where they are unset, before Pi loads; from source it is `bun run reins`. It reads `node.json` and the key from the node home (`REINS_NODE_DATA_DIR`, default `~/.reins`; *Pairing and authentication*), which is also its data directory, and runs `runNodeProcess` over `webSocketTransport`: it dials `node.json`'s server at `/nodes/link` (`ws://` or `wss://`), answers the challenge with its key and announces its paired node ID. Like the local node, it works in whatever checkout the server sends (*Checkout operations*). Same lifecycle as the node-only process, `REINS_NODE_TEST_FAUX_PROVIDER` included, but nothing restarts it, so it serves no `node.reload`. It refuses to run while another node of the same home runs (by the status file below). Exit 0 stopped by SIGTERM/SIGINT (last line `[node] stopped`), 1 not paired, already running or an unexpected failure (a broken config or key), 4 refused by the server (the last line names the server and its reason, and says to re-pair with `reins node pair --force <server URL> <code>`), 75 (`RESTART_EXIT_CODE`) updated (below).
- **Updates** ([ADR-025](../adr/025-node-version-handshake.md)): run from a bundle, `reins node run` announces its build (`buildId`, the sha256 of the `reins.js` it runs) in every hello. A server on another build answers `update {buildId, sha256, bunVersion}` (node-transport.md *Details: builds and updates*); the node logs `[node] the server runs build <id>; updating to it`, dials nothing meanwhile and installs the build in its home (`NodeInstall.installUpdate`, `packages/node/src/install.ts`, which `runInstalledNode` gives `runNodeProcess` as its `installUpdate`; node-bundle.md *Updates*): the bundle from the server it is paired with, checked against `sha256`; Bun's official release `bunVersion` if that is not the Bun it runs; then `current` flipped and the launcher written again. A failure (an HTTP error, a checksum, a Bun that will not run) leaves `current` as it was and is logged, and the node asks the server again after a backoff of 5 s doubling to 5 min (node-transport.md *Details: reconnecting*). Installed, it logs `[node] build <id> installed; restarting on it` and stops without pausing its runs (it cannot reach the new server to bring them to a pause point): `Node.shutdown` closes its runtimes without aborting their runs, and the server resumes them when the new build connects (*Crash recovery*). Under its launcher (which sets `REINS_NODE_RESTART_EXIT_CODE`: the bundle is `restartable`) it records `updating` in the status file and exits with that code, and the launcher starts the new `current`. Run without one (a bundle run directly) it does the same install, records `stopped`, says nothing restarts it here and how to start it (`<home>/bin/reins node start`), and exits 75 all the same. From source it announces no build and is never told to update; a node without an updater (`runNodeProcess` without `installUpdate`) that is told to treats it as a refusal.
- **Status file** (`NodeInstall.recorder`, `packages/node/src/install.ts`): `reins node run` (`runInstalledNode`, which claims it before it dials and records the link's state as `runNodeProcess` reports it, `onState`) records itself in `<home>/run/node-status.json`, `{pid, started, state, buildId?, serverUrl, since, message?}`, rewritten (temp file and rename) on each transition: `connecting` when it starts and whenever it redials, `connected`, `refused` (with the server's `message`), `updating` (it installed a new build and exited for its launcher to start it), and `stopped` when it exits, unless refused or updating, which stay the final state. `buildId` is the sha256 of the bundle it runs from (absent from source); `since` is when it entered the state. `started` is the process's start time as the OS reports it (`/proc/<pid>/stat` on Linux, `ps -o lstart=` elsewhere): a status file outlives a killed node and its pid may since be another process's, so a pid is trusted, or signalled, only while its start time is still the recorded one; a zombie counts as gone. A file left by a crash just reads as not running. `reins node start` also records the launcher it runs in `<home>/run/launcher.json` (`{pid, started, since}`): until the node records itself, and while the launcher restarts it on a new build (the status file says `updating` with the old node's pid), the launcher is what runs (`NodeInstall.status()` is then `starting` or `updating` and running, with the launcher's pid), so `start` and `setup` start no second node then, and `stop` stops the launcher.
- **In the background** (an installed node: the launcher, `bin/reins`, [node-bundle.md](node-bundle.md) *The node home*): `reins node start` (`packages/cli/src/node/control.ts`, `NodeInstall.start`) runs `<home>/bin/reins node run` as a plain detached process (a session and process group of its own, stdin closed, stdout and stderr appended to `<home>/logs/node.log`, cwd the home, without the `PI_PACKAGE_DIR`/`REINS_DOCS_DIR` of the bundle starting it), after removing the previous status file, and records it, unless the node (or its launcher) already runs; then waits until the status file says `connected` or `refused`, the node and its launcher have exited, or 30 s pass, and prints the outcome as its last line (`report`, `node/outcome.ts`, as for `run`, `setup`, `stop` and `status`). Exit 0 connected, 1 not paired, not installed (no launcher: from source, use `reins node run`), exited or still not connected (it keeps trying), 4 refused. Not a service: nothing starts it after a reboot. `reins node stop` sends SIGTERM to the recorded node (only while its pid's start time is the recorded one), or, while its launcher runs no node (starting one, or restarting it on a new build), to the launcher's process group, and waits up to 15 s for the node and its launcher to exit (the node pauses its runs first, *Shutdown*); exit 0 stopped or not running, 1 still running. `reins node status` prints the pairing (server, node ID), the build (the running node's, and `current` if that differs), the log path and, last, whether it runs (pid) and is connected, or is restarting on a new build (`updating`); exit 0 connected, 1 not paired, 3 not running (stopped, refused or never started), 4 running but not connected, or restarting. A node started in the background that updates itself is started again by its launcher, so `start`'s and `setup`'s wait goes on through the restart until the new build connects.
- **Combined** (`bun run start`, `bun run dev`; `packages/backend/src/supervisor.ts start|dev`): spawns the server (in dev, `packages/backend/dev.ts` with handler hot reload), the node and, in dev, the frontend watchers. Both inherit the environment, so they agree on `REINS_NODE_SOCKET`. The server exiting stops everything. A node that exits is restarted with exponential backoff (1 s doubling to 30 s, reset after 30 s of uptime), except that one exiting with `NODE_RELOAD_EXIT_CODE` (75, which the supervisor gives it as `REINS_NODE_RELOAD_EXIT_CODE`) is restarted at once: an explicit reload (*Reloading a node*), and one exiting with `NODE_REFUSED_EXIT_CODE` (77, given as `REINS_NODE_REFUSED_EXIT_CODE`) is not restarted at all ("node refused by the server; not restarting"): the server refused it (*Refused nodes* below). The server keeps running either way. Nothing watches node code, in `dev` either (see [hot-reload.md](hot-reload.md)). SIGTERM/SIGINT: SIGTERM to every child, SIGKILL after 10 s, exit 0. The Docker image runs `supervisor.ts start`.

**Startup ordering:** either may start first. A node started before the server redials with backoff (100 ms to 5 s; node-transport.md *Details: reconnecting*); a server started before the node admits submitted work; a run waits for the node at its first request, and its tool calls wait for it.

**Shutdown:** the server on SIGTERM/SIGINT pauses the runs of its sessions at their pause points (bounded by 3 s, then forced) and suspends them, leaving them pending for its next start to resume (`suspendSessions` in `process-state.ts`; *Crash recovery*), then exits through `exit`, removing its socket file. The node on SIGTERM/SIGINT **pauses its runs rather than aborting them** ([ADR-021](../adr/021-explicit-node-reload.md)): `Node.pause` holds every run at its next pause point and waits for the tool host's commands to exit (*Pausing runs*), bounded by 3 s, after which whatever is still in flight is cut off (shutting down kills the commands); then it stops redialing and closes its connection, `Node.shutdown()` closes every runtime without aborting its run (bounded by 5 s), and it exits 0. It does not wait for runs to finish: runs can last longer than a supervisor would wait. (Sessions run on the server now: it is the server's SIGTERM that pauses and suspends them, and its next start that resumes them, *Crash recovery*.)

**Refused nodes:** a server that answers the hello with `NODE_REFUSED` will not serve this node (its ID is unknown, it was revoked or removed, or it failed authentication), so the dialer stops instead of redialing. The node logs `[node] refused by the server: <reason>; not reconnecting`, shuts down as on SIGTERM (its runs are paused and left pending, as on any offline node) and exits with `REINS_NODE_REFUSED_EXIT_CODE` (1 when run on its own). Dropped connections and failed dials (the server down, a reload, the network) and a hello with no common protocol version are still redialed. `reins node run` stops the same way and exits 4, with a hint to re-pair (`reins node pair --force`).

### Pausing runs

A node goes away without losing work by holding every run at a **pause point**, where nothing has started that a restart would cut off: the assistant step's `before_request` (the run is `assistant.ready`, its request not yet recorded) and `before_tool` (the call is still `planned`). A run cut off there resumes into a fresh request, or runs its tool normally; one cut off mid-request asks again (one retry attempt), and one cut off mid-tool is run again if the tool is safe to repeat (`read`, `search`) and otherwise gets "outcome unknown" (node-runtime.md *Pause points*). `Node.pause({timeoutMs, force})` closes the node's `PauseGate`, so every run waits at its next pause point, and resolves `{paused, blocking}` once every runtime is paused (`isPaused`: no admission or tool call in flight, every run it drives held), no lifecycle report is left to deliver and **no command of the tool host is running** (`env.exec`, *Tool host*; `busy` in `host-env.ts`): a command counts until it has exited and its output stream has sent its exit, so the server gets the result before the node goes. One that exited while no stream was open (its link dropped) does not count. Commands are still served meanwhile: input is admitted and its run held before its first request, and every other tool host call is served, `env.execAttach` and `env.execKill` included. **A new `env.exec` is refused** `unavailable` (retryable) while the pause lasts, not held: a command started during the drain would hold it up in turn, so a busy node could put a reload off for ever; refused, it was certainly not run, and the server sends it again (`RemoteExecutionEnv`, for up to `EXEC_START_WINDOW_MS`, 90 s), to this node once the pause ends or to the restarted one. At `timeoutMs` it resolves anyway with `force`; without, it releases the runs, accepts commands again and resolves `paused: false`, `blocking` naming the sessions and commands (`exec <execId>: <command>`, the command cut to 100 characters) it waited for. An abort releases a held run as usual.

### Reloading a node

`node.reload {force?}` → `{scheduled: true}` restarts the node on its current code ([ADR-021](../adr/021-explicit-node-reload.md)). The server sends it for `POST /api/nodes/:nodeId/reload {force?}` (404 unknown node, 409 the node's refusal, 503 offline), the scripting call `api.nodes.reload(nodeId?, force?)` (the calling session's node by default) and `reins node reload [nodeId] [--force] [--server <url>] [--local]` (`packages/cli/src/node/reload.ts`, through `@reins/client`'s `nodes.reload`; exit 1 on a refusal, 5 when no Reins server answers). It reloads the node it names, or by default this machine's paired node (`node.json`) on its server, else the local server's (`http://localhost:<REINS_PORT or 3100>`) local node (`REINS_NODE_ID`, default `internal`); `--server` names the server (the paired node is then the default only on its own server) and `--local` ignores `node.json`. `bun run node:reload` is `reins node reload --local`, so it means the local node on a paired machine too, all through `NodeModel.reload` (`models/node.ts`). The node refuses it `unavailable` when nothing would restart it (`startNode` was given no `reload`: `main.ts` gives one only under the supervisor) and `invalid_request` when its new code does not build (`main.ts` bundles its entrypoint with `Bun.build`, packages external). Otherwise it answers at once, before the reload, because the caller's own tool call may be one of the things the reload waits for. It then pauses (*Pausing runs*: it waits for the commands it runs to exit, bounded by `RELOAD_DRAIN_TIMEOUT_MS`, 60 s) and exits with the reload code; the supervisor starts it again at once. Sessions run on the server, so a node reload pauses no run: a command running on it finishes and is answered first, a new one waits for the restarted node, and so does any other tool call (*Tool host*). A pause that times out without `force` cancels the reload: the commands run on, new ones are accepted again, and the node logs the commands (and sessions) that held it up; with `force` the node restarts all the same, killing them (their calls come back "outcome unknown"). A second request while one is pending joins it. **Nothing is exempt from the drain**: `api.nodes.reload()` in an `execute` script runs on the server and is no command, but a bash call running `bun run node:reload` is one, on the node it reloads. It ends as soon as the reload answers, so it holds the reload up only as long as the rest of that command runs (a `bun run node:reload && sleep 120` holds it to the timeout).

## Pairing and authentication

A remote node gets its identity by pairing, and proves it on every connection that authenticates ([ADR-023](../adr/023-node-pairing-and-challenge-authentication.md); user-facing: [settings.md](../features/settings.md) *Nodes*, [nodes.md](../features/nodes.md)). The local node is never paired: the local socket's file permissions are its authentication.

- **Codes** (`NodePairing.createCode` in `models/node-pairing.ts`, reached as `Nodes.pairing()`; `POST /api/nodes/pairing-codes {name?}` → 201 `{id, code, expiresAt}`; `id` is not secret and names the code in the `node_updated` its redemption sends): 32 random bytes, base64url, never starting with `-` (drawn again if it would: the CLI would read it as an option), redeemable once within 10 minutes (`PAIRING_CODE_TTL_MS`). `node_pairing_grants` keeps only the code's SHA-256, its expiry, when it was consumed and the node it paired. The code appears in no log line or error message. Times are computed in JS, so tests move them with `setSystemTime`.
- **Redemption** (`NodePairing.redeem`; `POST /api/nodes/pair {code, publicKey, hostname}` → 201 `{nodeId, name}`): `publicKey` is the canonical base64url of a raw 32-byte Ed25519 key. One conditional `UPDATE` consumes the grant inside the transaction that inserts the `nodes` row (a new UUID, named by the code or else the hostname, with `public_key`, `hostname`, `paired_at`), so of competing redemptions exactly one pairs and a failed one consumes nothing. Unknown, used and expired codes are all 403 "Invalid or expired pairing code"; a malformed body or key 400; a key another node holds 409. Browsers are told `node_updated {node, pairingCodeId}` (the node view and the grant's ID).
- **`reins node pair <server URL> <code> [--force]`** (`packages/cli/src/node/pair.ts`; the files are written by `NodeInstall.savePairing`; `bun run reins …` from source; an installed node runs it as `~/.reins/bin/reins`, and the install command pairs through `reins node setup`, below): generates the keypair, redeems the code through `@reins/client` with the machine's name (`machineName`: on macOS `scutil --get LocalHostName`, the name set in System Settings, since `os.hostname()` there is the network's name for the machine, such as `Mac.lan`; `os.hostname()` elsewhere, or when that fails or is empty), writes the private key to `<home>/keys/<nodeId>.pem` (PKCS#8, 0600; home `REINS_NODE_DATA_DIR` or `~/.reins`, 0700) and then the config `<home>/node.json` (`{version: 1, serverUrl, nodeId, keyPath}`, 0600) by rename, its commit point (the new key is removed if that fails). An existing config refuses the run before the code is sent, unless `--force`, which removes the previous key once the new config is in place. Non-interactive: exit 0 paired, 1 another Reins error answer (a 400 or 409: `requestFailure`, as for `reins node reload`) or an unexpected failure, 2 usage (an argument count or a server URL that is not http(s)), 3 already paired, 4 code refused (403), 5 server unreachable or not answering as Reins (an unexpected body included); the last line says which. An argument that starts with `-` would go after `--`; codes never do. `NodeInstall.pairing` (version-checked; it keeps fields it does not know, written by a newer CLI of the same version) and `NodeInstall.key` (→ `{origin, privateKey}`, `connectNode`'s `key` for dialing the pairing's `serverUrl` as its `nodeId`) are what `reins node run` starts from.
- **`reins node setup <server URL> <code>`** (`packages/cli/src/node/setup.ts`): what the install script (`/nodes/install`, [node-bundle.md](node-bundle.md)) runs from the bundle it downloaded. In order: it refuses to run from source (exit 1: it installs the bundle it runs from); refuses a home paired with another server (exit 3, with the hint `reins node pair --force <server URL> <code>`, then the install command again), all before anything changes or the code is sent. Then it makes its build current and writes the launcher (node-bundle.md *The node home*); pairs as `reins node pair` does unless the home is already paired with this server (then the code is not sent: "the code was not used"); and starts the node as `reins node start` does (*Process model*), except that a node already running another build is stopped first and one running this build is left running; and waits for it to connect. Its last line is the outcome (`Node "<name>" (<id>) connected to <server> (pid N).`, or what failed and where the log is). Exit 0 connected; 1 as above, or the node exited or did not connect within 30 s; 2 usage; 3 paired with another server; 4 the code refused (as `pair`) or the node refused; 5 the server unreachable (as `pair`). Run again with the same, already used code it pairs nothing and keeps the running node: safe to repeat. **Recovery:** when the home was already paired with this server (so this run did not use the code) and the server refuses the node it starts (it was removed or revoked there), setup says so (`<server> refused node <id> (<reason>); pairing this machine again with the code given`) and pairs again with the code given, as `pair --force`, then starts the node again. So re-running the install command with a fresh code from Settings repairs a node removed on the server. A code this run has just used to pair is not tried again.
- **A project's sources from the command line** (`reins source add <path> --project <id> [--node <nodeId>] [--server <url>] [--local]`, `reins source list [--project <id>] [--node <nodeId>]`, `packages/cli/src/source.ts`): through the server's API (`POST /api/projects/:id/sources`, `GET /api/nodes`; which server and which node is "this node": `server.ts`, as for `reins node reload`). Without `--node`, add means this machine's node and resolves a relative path against the working directory; with `--node` the path must be absolute (exit 2 otherwise). `list` prints `<node ID>\t<path>\t<project> (project <id>)` per source, or `No sources.`; add prints `Source added to project <id> on node <nodeId>: <path>`. Exit 0, 1 the server's refusal (*Node hub*, default source), 2 usage (no `--project` for add, a project ID that is not one), 5 no server answering. A node keeps no list of its own (*Checkout operations*).
- **Authentication on the link:** a connection the hub accepts with `authenticate: {origin}` is challenged (`node.authenticate`) and must sign it with the paired key before its hello, which must name that node, is answered (node-transport.md *Details: authentication*). The local socket accepts without it. The WebSocket route (`/nodes/link`, `routes/nodes.ts`) accepts every connection with it, from the socket's `open` (the challenge is the first frame), for the origin of the upgrade request: its forwarded headers (`X-Forwarded-Proto`, `X-Forwarded-Host`) else the request's own scheme and `Host` ([ADR-024](../adr/024-node-link-origin-from-the-upgrade-request.md); node-transport.md *1b. The WebSocket link*).
- **Renaming** (`NodeModel.rename` in `models/node.ts`; `PATCH /api/nodes/:nodeId {name}` → the node view; `@reins/client`'s `nodes.rename`): any node, the never-paired local node included, paired or revoked; the name is trimmed and must then have 1 to 100 characters (`MAX_NODE_NAME_LENGTH`; `InvalidNodeNameError`, 400); an unknown node 404. Tells browsers (`Nodes.publish`). Nothing else stores the name: views that show it (session placement's `nodeName`, a source's view, the move targets) read the node's row each time they are built, so they show the new name from their next build; a browser's cached session view keeps the old one until the session's next `session_updated`.
- **Revocation** (`NodeModel.revoke` in `models/node.ts`; `POST /api/nodes/:nodeId/revoke` → the node view): sets `revoked_at`, closes the node's link (`state.nodes.disconnect`) and tells browsers (`Nodes.publish`). A revoked node keeps its key, so it still passes the challenge, and its hello is refused (`NODE_REFUSED` "Node revoked: <id>", `NodeRevokedError` from `NodeModel.assertMayConnect`) on every transport, so the node stops rather than redialing (*Process model*, *Refused nodes*). Its rows stay: its sessions' work waits as for any offline node. A never-paired node is 409; revoking again changes nothing. Key rotation is revoke and re-pair.
- **Removal** (`NodeModel.remove` in `models/node.ts`; `DELETE /api/nodes/:nodeId` → 204) **abandons** a paired node, revoked or not, whatever it holds: it sets `removed_at` (migration 051), closes the node's link and tells browsers (`Nodes.publish`, `node_removed`). The row stays, key included (sessions hang off its sources, which stay too), so the node still passes the challenge and its hello is refused, `NODE_REFUSED` "Node removed: <id>" (`NodeRemovedError` from `NodeModel.assertMayConnect`), on every transport, and the node stops (*Process model*, *Refused nodes*). Its pairing grant keeps the record (`node_id`). From then on the node is not listed (`GET /api/nodes`, `Nodes.list`), not offered (the project form's node selector, Add source: `createSource` answers 400 "Node not found: <id>"; move targets) and its sources are no project's default (*Node hub*, default source); renaming, revoking or reloading it is 404 ("Node removed: <id>"). **Its sessions** stay readable (their history is the server's) and movable to a node holding a source of the project (*Moving a session*), and their placement says `removed: true`. Work for them is refused at once: `Sessions.submit` (prompt, steer, child reports, code-review prompts), `Sessions.setModel` and `Sessions.resume` throw `SessionNodeRemovedError` ("This session's node was removed; move it to another node to continue"; HTTP 409, the browser socket's `{type: "error", sessionId, clientId, error: "prompt failed: …"}`, a script's thrown error; a child's report to such a parent is logged and the child left `finished`, as for any parent that cannot receive it). The removal closes the live runtimes of its sessions, aborting their runs (a tool call waiting for the node fails), and a run the server still sees in progress there without a live runtime is settled as interrupted ("The run was interrupted: its node was removed"; `SessionRuns.interruptRunsOn`), since the node will never report it, so its session can be moved. Removing it again changes nothing (204); the never-paired local node 409; an unknown node 404. A machine whose node was removed pairs again as a new node (setup's recovery, above); its sessions are moved to it like any.
- **Browser messages** (`ServerMessage` in `models/broadcast.ts`): one method sends them, `Nodes.publish(nodeId, {pairingCodeId?})` in `models/nodes.ts`, which reads the node's row: `node_updated {node, pairingCodeId?}` with its view (`NodeView`, `models/node.ts`: `paired` says whether it has a key, which the view never carries) while the node exists and is not removed, else `node_removed {nodeId}`. It is called on a redemption (with the grant's ID, so the browser showing that code sees it paired), on renaming, revocation and removal, by the hub when it gives a node a link or loses its only one (not when one link replaces another; where it logs "Node X connected/disconnected") or it tells a node to update (and when that node comes back), and when a node's project sources change (*Node hub*, nodes and sources). Each message carries the node's whole state, so a repeat changes nothing: revoking or removing a connected node sends a second one when its link has closed.
- `GET /api/nodes` lists every node not removed as `{id, name, connected, paired, hostname, pairedAt, revokedAt, sources, build}` (`sources`: *Node hub*, nodes and sources; `build`: `{id, status}`, the node bundle it announced at its last hello to this server load, `current`, `outdated` or `updating`, null from source or when it has not said hello since it disconnected; `RemoteNode.build`, node-transport.md *Details: builds and updates*); the settings page's Nodes section shows it (kept current by the messages above; a build that is not `current` is labelled), creates codes and follows their pairing (until the node connects, or is removed), renames nodes (a dialog), removes nodes (after a confirmation dialog; revocation has no UI until node detail pages) and shows how many sources each node holds; the project form leaves revoked nodes out (removed ones are not listed at all).

## The link

How the server and node exchange messages is in [node-transport.md](node-transport.md): the socket and its permissions, framing, JSON-RPC, `node.hello` and epochs, the heartbeat, frame caps, wire error codes, the method tables and naming, streams, reconnecting, hot reload and test links. This doc covers what is sent over it.

## Checkout operations

The server reads and writes a source's checkout through the node holding it, never on its own disk ([ADR-018](../adr/018-process-run-and-fs-methods.md)): **git runs on the node through one generic method, `process.run`, while the git logic (which commands, how their output is read) stays on the server**, where it hot reloads. The file browser's filesystem reads and uploads, which are not git and whose shell equivalents differ between Linux and macOS, are typed `fs.*` methods. All are negotiated, request-now node capabilities: never queued, failing at once when the node is offline. Like `skills.list`, all name the source and send the path the server resolves for it (`cwd`).

**The server's sources are the record** ([ADR-026](../adr/026-sources-managed-on-the-server.md)). A node keeps no list of sources: it works in the path each call sends (`cwd`, a binding's `cwd`), as the local node always has, refusing only what its operations refuse anyway (a missing checkout, `not_found`; a path escaping the checkout, `invalid_request`). Which sources a node has is the `sources` table, managed on the server only (the project form, `POST /api/projects/:id/sources`, `reins source add`): `createSource` and `moveSource` refuse a relative path (`CheckoutNotFoundError`, 400: "A source's path must be absolute: <path>") and check the path with `fs.list` of `.` on the node, so one that is not a directory there is `CheckoutNotFoundError` (400: "Directory does not exist: <path>"). Under the trust model the server can already run anything on a node, so a node-side allowlist would protect nothing.

- `process.run {sourceId, cwd, streamId, argv, env?, binary?}` → `{}`, and opens a stream (node-transport.md *Streams*) of the process's stdout. `argv` is run directly, never through a shell (the server builds arguments from browser input such as paths and branch names); `env` is merged over the node's environment. The node refuses a missing checkout (`not_found`) or a program it cannot find on `PATH` (`invalid_request`, "Program not found: <name>") before answering, and spawns the process when the stream starts. The stream's end frame carries the exit (`{code, signal, stderr}`); cancelling the stream (or losing the link) kills the process. No stdin yet: no server git call writes to one.
- `fs.list {sourceId, cwd, path}` → `{entries: [{name, type}]}`: one directory, files and directories only (no symlinks), directories first, then by name case-insensitively, at most `MAX_DIRECTORY_ENTRIES`. A `path` resolving outside the checkout is `invalid_request` ("Path traversal not allowed"); a missing directory `not_found`.
- `fs.read {sourceId, cwd, streamId, path, maxBytes?}` → `{size}`, then the file's bytes (the first `maxBytes`) as a binary stream. `path` is checked as for `fs.list`; anything but a file is `not_found` ("File not found"). The node reads with `createReadStream`: a sliced `Bun.file` stream never ends for a large file in Bun 1.3.9.
- `fs.write {sourceId, cwd, path, offset, data, last}` → `{size}`: one chunk of a file (`data` base64 of at most `ATTACHMENT_CHUNK_BYTES`, so it fits a frame). `path` is checked as for `fs.list`, and naming a directory is `invalid_request`. Chunks come in order: offset 0 starts the file (creating its directories), each later chunk must start where the written bytes end (`invalid_request` otherwise), and `last` renames the file into place, replacing one there. Until then its bytes are kept in the node's data directory (`<dataDir>/partial-writes/`, named by a hash of the file's path), so an upload that never finishes leaves nothing in the checkout, not even its directories (they are created with the last chunk). The node clears `partial-writes/` when it starts: an upload cut off by a node restart cannot continue (its next chunk is out of order) and is refused. The move into the checkout is a rename, or a copy when the data directory is on another filesystem. Any other filesystem failure (a path through a file) is `invalid_request`. Uploads (`SourceModel.writeFiles`) send each file this way, one chunk at a time.

On the server, a node runs a process through `RemoteNode.spawn(argv, {sourceId, cwd, env?, binary?})`: it opens the `process.run` stream (bounded by a 10 s timeout on the node accepting it) and returns `{stdout, exited}` (`SpawnedProcess`, `spawn.ts`). Git is a `Git` (`git.ts`) built on an injected `Spawn`, so the git logic stays on the server whichever checkout it reads; the server runs no git of its own (tests use `localGit` from `__tests__/helpers/local-git.ts`). Creating a project without a base branch detects it in the project's first source on its node (`createProject`): with that node unreachable the project is not created (503).

**Which checkout a call works in** is the call's source, resolved where the call enters and handed to `ProjectModel` as a `SourceModel` (`resolveSource` in `models/sources.ts`): an agent tool's or script's calling session (`sessions.source_id`, from `sessionToolScope`); a project HTTP request works in the project's default source until the frontend picks among several (node architecture plan). Tasks have no source: a task's sessions may run in several. The source model (`models/sources.ts`) owns what reads or changes its checkout: its `git` runs on its node (`node.spawn` bound to it), as do `listFiles()` (two `git ls-files` runs merged), `listDirectory(path)` (`fs.list`, 10 s timeout), `workspace(baseBranch)` (files and diffs), `sync(baseBranch)` (fetch and fast-forward) and `listSkills()`. Tasks are not closed from git state: whether a branch looks merged depends on which checkout looks. `listDirectory` turns the node's refusals into the domain errors routes already map (`PathTraversalError` → 400, `FileNotFoundError` → 404). An unreachable node (not connected, no answer, link dropped: `RemoteNode`'s `RpcFailure` with code `"unavailable"`, from a call, a process's start, its stdout or its exit alike) reaches the router as it is, which answers 503 (`isNodeUnavailable` in `errors.ts`); models do not translate it. Task creation, reopen and deletion, task diff stats (`null` while the node is offline), spread, push, rebase, the current branch, a file at a ref (`GitTreeFileSystem`) and the diffs (`Workspace`) all go through the source's `git`. A working-tree diff shows untracked files as Git-native new files by marking them intent-to-add in a temporary copy of the index: `Git` runs that as one `sh -c` script through `process.run` (`WITH_UNTRACKED_AS_INTENT_TO_ADD` in `git.ts`: copy the index, `git add -N` each readable untracked file, run the diff, remove the copy on exit or `TERM`), so the index lives on the node and a diff costs one round trip. Patches cross as binary, byte for byte. Working-tree file content (`WorkingTreeFileSystem`, `/files/content` without a ref) reads through `fs.read` (`openStream`, 10 s timeout) in two steps, as a file at a ref does through git: the first 8 KiB for the size and the MIME type (`detectMimeTypeFromBytes`), then the whole file only if the route sends it (a binary file without `download=1` gets a placeholder). Its refusals become `WorkspaceFileNotFoundError` (404) and `InvalidWorkspacePathError` (400) (`nodeRefusal` in `errors.ts`).

### Tool host

Every node is a tool and file host for the sessions on its sources ([ADR-029](../adr/029-sessions-on-the-server-nodes-host-tools.md)): it serves the operations of Pi's tools (read, write, edit, bash) as a remote `ExecutionEnv` on a source's checkout, and what of a session's environment comes from the checkout. The server's `RemoteExecutionEnv` (`sessions/remote-env.ts`) is what the server's session runtime (`session-runtime/`, backend-architecture.md) runs Pi's tools on. Node code: `host-env.ts` (`createHostEnv`), served through `NodeCommands`.

- `env.fs {sourceId, cwd, streamId, op, args}` → Pi's `Result` (`{ok: true, value}` or `{ok: false, error: {code, message, path?}}`, Pi's `FileError` codes), from Pi's own `NodeExecutionEnv` for `cwd` on the node. `op` is one of the operations Pi's tools use: `absolutePath`, `canonicalPath`, `exists`, `fileInfo` (`args: {path}`), `readTextFile`, `readBinaryFile` and `writeFile`. `cwd` only resolves relative paths (`~` is the node's home): nothing is confined to the checkout, as in Pi's local environment. Every call opens a binary stream: a read's value is `{size}` and its bytes follow on the stream; every other answer's stream ends at once, empty. `writeFile`'s `args` are `{path, writeId, offset, data, last}`, `data` base64 of at most `ATTACHMENT_CHUNK_BYTES`: a write in one chunk is written at once; a longer one is kept under its `writeId` in the node's data directory (`partial-writes/`, as `fs.write`'s) until its last chunk writes the whole file with Pi's `writeFile`. Every call is safe to send again: a chunk replaces what was kept from its offset, and a last chunk sent again after its write is answered as written (the node remembers the last 1024 writes). A chunk past what was kept is `invalid_request`.
- `env.exec {sourceId, cwd, streamId, execId, command, options: {cwd?, env?, inheritEnv?, timeout?, capture?}}` → `{}`, and a text stream of the command's **output records** (NDJSON, `execRecord`): `{update}`, Pi's `ShellOutputUpdate`s in order, then `{exit}`, Pi's `exec` result (`{ok: true, value: {exitCode, truncation, spillPath?, lastLineBytes?}}` or `{ok: false, error: {code, message}}`), the last line. The node runs it with Pi's `NodeExecutionEnv.exec`: its shell, environment merge (`env` over the node's; bash's `PI_SESSION_ID`, `PI_PROVIDER`, `PI_MODEL`, `PI_REASONING_LEVEL` come in `env`), timeout, bounded capture (`capture.limits.maxBytes` at most `MAX_EXEC_VIEW_BYTES`) and spill file (on the node, where `read` finds it). `execId` is the server's; one the node already has is `invalid_request`.
- **Commands outlive their stream.** The node keeps each command under its ID with the last `EXEC_TAIL_BYTES` (1 MiB) of its output records and the output's current view. A command with no stream open (its link dropped, or its output was all sent) is kept for `EXEC_GRACE_MS` (60 s; `startNode({execGraceMs})`); then a running one is killed and either is forgotten. `env.execAttach {streamId, execId, offset}` → `{offset, view?}` reopens its output stream from `offset` (the end of the last record the server took): from the same offset, or, when that output is no longer kept, from where the records end, with the current view in `view` (the server replaces its view with it, so nothing the tool would show is lost). Attaching stops any stream still open for it. An offset that is not the start of a record is `invalid_request`; an unknown `execId` (the node restarted, or forgot it) is `not_found`.
- `env.execKill {execId}` → `{killed}` (whether it was running) kills the command's process tree, as aborting Pi's `exec` does; its stream still ends with its exit (`aborted`). Unknown: `not_found`. Shutting the node down kills every command it runs.
- `checkout.environment {sourceId, cwd}` → `{contextFiles: [{path, content}], skills: [{name, description, path, content, disableModelInvocation}], docs: {dir, devDocs}}`: the AGENTS.md files of the checkout and its ancestors (root first) and the checkout's skills (`.agents/skills`, with SKILL.md's content), discovered as `ReinsResourceLoader` does but without the node's own `~/.agents`; and this node's REINS docs (`REINS_DOCS_DIR`, else the checkout's `docs/` it runs from, as the environment prompt names them; `devDocs`: whether `<dir>/dev` exists). A missing checkout is `not_found`; a result over `MAX_CHECKOUT_ENVIRONMENT_BYTES` (12 MiB as JSON) `invalid_request`.

**On the server**, `RemoteExecutionEnv` (`sessions/remote-env.ts`) is Pi's `ExecutionEnv` over these. It holds no hub: each call asks `nodeFor(signal)` for the session's node, from the handler load serving now (it may wait for one). A file operation that fails `unavailable` (node unreachable, the outcome unknown, or the node's retryable `unavailable` refusal) is sent again with a backoff for up to `ENV_RETRY_WINDOW_MS` (30 s); any other failure is a `FileError` `unknown`. `exec` sends `env.exec` again only while it was certainly not run (not sent, or refused `unavailable` by a node pausing to restart, *Pausing runs*), for up to `EXEC_START_WINDOW_MS` (90 s, longer than a reload's drain); when its stream drops (or its outcome was unknown) it calls `env.execAttach` from the last record it took, on whichever link the node has then, for up to `EXEC_REATTACH_WINDOW_MS` (60 s, the node's grace period), feeding the same `onUpdate`. A node that answers `not_found` (it restarted) makes the call fail `unknown` ("The command's outcome is unknown"). Aborting the call sends `env.execKill` and returns `aborted` once the command's exit arrives (at once, if the kill cannot reach the node); `cleanup` kills the commands it still runs. Operations Pi's tools do not use (`readTextLines`, `appendFile`, `renameFile`, `listDir`, `createDir`, `remove`, `createTempDir`, `createTempFile`) answer `not_supported`; `joinPath` joins POSIX paths on the server. Tested against Pi's local environment in `__tests__/sessions/remote-env.test.ts`.

## Node API

`@reins/node/node` is the node's in-process API; `connectNode` (`@reins/node/node-connection`) links it to its server over a transport and serves it there, and nothing else calls it outside tests. Tests that script a node pass a stand-in `Node` (`scriptedNode`, `@reins/node/testing`) to the same `connectNode`.

- **Lifecycle.** `startNode()` starts a new, independent node (its runtimes, caches, event seqs, credential cache and connections are its own; no module globals) and takes no in-process server dependency. `attach(server)` adds a connection (the newest serves the node's server calls). `liveSessions()` lists the sessions with a run in progress, for `node.hello`. `pause({timeoutMs, force})` holds every run at its next pause point and waits for the tool host's commands to exit (*Pausing runs*). `shutdown()` is the one teardown: refuses new commands (`Node stopped`) and closes every live runtime without aborting its run; pause and close the connection before it.
- **Commands** (`NodeCommands`). One method per server→node wire method, taking its params (without `epoch`) and returning its wire result: `prompt`/`steer → {inputId}`, `setModel → {modelSet}`, `abort → {aborted}`, `resumePending → {started}`, `close → {closed}`, `reload → {scheduled}` (*Reloading a node*), `listSkills → {skills}` (see *Skills*), `listDirectory → {entries}`; `runProcess` returns the source of the stream `process.run` opens (see *Checkout operations*). The tool host's commands (*Tool host*): `envFs → {result, source}` (the stream's bytes), `envExec` → the source of its output stream, `envExecAttach → {result, source}`, `envExecKill → {killed}`, `checkoutEnvironment` → the checkout's environment. `connectNode` serves each and advertises it as a capability, with `stream.cancel`; `credentialsChanged` (the `credentials.changed` notification) drops what the node cached for the provider (see *Credentials*).
- **Errors.** A definite rejection throws `NodeRejection` carrying a `NodeError`: `invalid_request` (bad attachment, unknown model, a path escaping its checkout: *Checkout operations*), `busy` (a runtime running under another binding), `not_found` (a skills checkout that does not exist), `unavailable` (retryable: an attachment fetch with no server). Any other exception (a storage failure) is sent as `internal`, non-retryable.
- **Test seam.** `nodeRuntimesForTesting(node)` (`has`/`open`/`close`) reaches a node's live runtimes; production code must not import it.

**Runtimes.** The node opens a session's runtime on the first prompt, steer, setModel or resumePending from what that command carries (binding, task branch, lane seed, runtime configuration; see *Session commands on the wire*) and keeps it in memory; opening and closing are serialized per session. A runtime open under another binding (the session moved to another source on this node) is closed and reopened when idle and refused `busy` while it runs. `close` aborts a run and closes the runtime; nothing else closes an idle one yet (idle eviction is a follow-up in the plan).

**Link loss.** Runtimes outlive a connection: a run keeps going through a redial (a server handler reload or restart). Every node→server call a run makes follows the newest connection, and **a call that was never sent waits for one**: no connection attached, or one that closed or never negotiated (`NotConnected` in `@reins/node-protocol`: the peer refuses to send on a closed connection, and a call waiting for a negotiation that fails was never sent). It waits for another connection to attach and is sent there, for up to `RECONNECT_WAIT_MS` (30 s, `startNode({reconnectWaitMs})`) in all, then fails. This applies to `storage.*`, lifecycle reports, `credentials.*` and attachment fetches and uploads (an upload restarted on a new connection resends chunks an old one may have received, which is safe: the same ID and content is acknowledged as stored). **A call that was sent is sent again only when the server recognises a repeat:** a `storage.commit` (under its `commitId`) or a lifecycle report (`session.started`, or `session.settled` under its `reportId`) whose reply was lost (outcome unknown: its connection closed or it timed out) is resent on the next connection to attach, within the same wait. Any other call in flight at a drop, and any refused call, fails as it came. A storage call that fails (past the wait, a read in flight at a drop, or refused) fails the run: Pi faults its harness on any storage error and never ends the run itself, so the node sends its `session.settled` (failed, "Session storage failed: …"; lost like any report that cannot be delivered) and ignores any later report from that runtime. The node then marks the runtime **stale**, never reuses it (nor lists it as live), and closes and reopens it from the server's copy before the session's next command; a command whose runtime went stale under it (e.g. a delivery racing a dropped link) runs once more on a fresh runtime, which is safe because every command converges on replay (*Replay idempotency*).

## Node hub (server side)

One hub per handler load (`nodes/node-hub.ts`, built by `createServerState` in `state.ts`, which each handler load's `start` (`server.ts`) calls; closed on a dev reload or process exit, after which the node redials the next load's hub; tests create one with the `createServerState()` helper). It is `state.nodes` (the `NodeHub` interface in `state.ts`) and owns the node links by node ID. It calls product code directly, with the state it belongs to: `nodeHandlers` (`nodes/node-handlers.ts`) serves a node's calls (storage, reports, events, tool calls, credentials, attachments; resolved once per connection, at hello). Interface: `accept(socket)`, `get(nodeId)` (a `RemoteNode`: `connected`, `request(method, input, options)` for any request-now node method, `openStream(method, input, options)`; see node-transport.md *5. Hub and node API*), `disconnect(nodeId)`, `credentialsChanged(providerId)` (*Credentials*), `close()`. Callers of `request` choose their own timeout. The stream buffer cap is a hub option (`NodeHubOptions`).

**Default source:** a new session is placed on the source its caller names (child and task sessions inherit the caller's), else on its project's **default source: the project's first (lowest-ID) source on a node that was not removed** (`defaultSource` in `node-store.ts`, `resolveSource` in `models/sources.ts`); a project whose every source is on a removed node has none ("Project has no source", as for a project with no source). A source named explicitly is resolved even on a removed node (a session's own source: so it can be read and moved), and work for it is refused there (*Pairing and authentication*, Removal). A project has no path of its own: paths live on sources, and a node and path belong to one project's source (a unique index; `DuplicateSourceError`, 409: "That path is already a source of another project"). A project's first source is created with it, on the node its creator chose (`createProject` in `models/projects.ts`, through `createSource` in `models/sources.ts`; the browser form's node selector, or for a `projects.create` script the calling session's node unless it names one), after the path is checked on that node (`fs.list` of `.`: a missing directory refuses the project, an unreachable node is a 503, and the project is not kept either way). `POST /api/projects/:id/sources {nodeId, path}` adds a source of an existing project on a node (the project form's Add source, `reins source add`), checked the same way (`createSource`: 201 with the source's view; 400 for an unknown node, a relative path or one that is not a directory there; 409 for a path another project's source has, or a second source of the project on that node ("The project already has a source on <node>"): a session moved to a node works in its project's source there, so a project has at most one per node; 503 when the node is offline); `PATCH /api/projects/:id/sources/:sourceId` moves a source's path, checked the same way (`moveSource`); `GET /api/projects/:id/sources` lists them for the edit form. Selection is policy, not a connectivity check: a session placed on a node that is not connected is created and its work waits.

**Nodes and sources:** `nodes` identifies execution hosts; `sources` binds a project to a host-local path. Sessions persist `source_id` beside `project_id` (triggers enforce agreement). **A session runs on its source's node**; that is the whole of placement. The node runs a session in its bound source path, not the project's current path.

**A node's sources are the server's sources on it** (*Checkout operations*). The node's view (`NodeView.sources`, `GET /api/nodes` and `node_updated`) lists them by path (`NodeSourceView`: `{path, project: {id, name, sourceId}}`), so they are known while it is offline; Settings → Nodes shows how many there are, and `reins source list` lists them. Creating and moving a source and deleting a project publish the nodes concerned (`Nodes.publish`); renaming a project does not, so a node's view shows the old name until its next update.

## Submitted work

Submitted session work goes straight to the session's runtime on the server ([ADR-029](../adr/029-sessions-on-the-server-nodes-host-tools.md)); Pi's durable admission is its record. `Sessions.submit(sessionId, {op, content, clientId, sourceSessionId?})` (`models/sessions.ts`; the browser socket's prompt and steer, scripting sends, child reports, code-review prompts, task generation) opens the session's live runtime (`openSessionRuntime`, `session-runtime/live.ts`) and admits the input with `prompt` or `steer` under `reinsId` = `clientId` (with `metadata.sourceSessionId` for an addressed steer), resolving once Pi committed it. A session's submissions and model changes apply one at a time in arrival order: each enters the session's chain (`ProcessSessions.submissions`, process-owned) synchronously when called. A replay under the same `clientId` converges on the admitted input and resolves again. A failure is the submission's own answer: the HTTP error, the browser socket's `{type: "error", sessionId, clientId, error: "prompt failed: …"}`, a script's thrown error. Refused before anything is submitted: an unknown session, content over `MAX_PROMPT_CONTENT_BYTES` (`PromptTooLargeError`) and a removed node (`SessionNodeRemovedError`). A node that is offline does not hold admission up (a run waits for it at its first request), except to expand a skill only the checkout has. A prompt to a session whose lane is running fails ("Lane "main" already has an active operation"): running sessions take steers.

## Abort and resume

`Sessions.abort(sessionId)` (the WS `abort` message) acts on the session's live runtime at once, not ordered behind submissions: `{aborted}` says whether it was busy; with no live runtime it answers `{aborted: false}` and opens nothing. `Sessions.resume(sessionId)` (`POST /api/sessions/:id/resume`) drives the operation an interruption left pending in its live runtime (opened if needed): `{started: true}` while it is being driven (also when an input joined it first), `{started: false}` with nothing to resume (409 from the route). Neither calls the node. Deleting a session closes its runtime before its row goes; moving it closes its runtime (*Moving a session*).

## Session commands on the wire

**The server no longer sends these** (sessions run on the server, *Submitted work*); the node still serves them until step 3. Each session method crosses the link as `RemoteNode.request` (handlers in `connectNode`). Each is a capability checked against the connection's epoch before the node runs anything. The server resolves what each carries from its rows on every send: the `binding` (`{sourceId, cwd, createdAt, parentSessionId}`: where the session runs and Pi's session identity), and for the methods that may open the runtime (**opening commands**: prompt, steer, setModel and resumePending; `SessionModel.context`, `models/session.ts`) the `branch` the node checks out before it opens Pi (resolved by the session's kind: an `agent` task session's task branch; null for a scratch session or a utility kind, which the node checks nothing out for), the `lane` seed (`{model: {provider, modelId} | null, thinkingLevel: string | null}`: the row's model and thinking level, else the current `default_model` setting's; `off` is sent as null) and the `runtime` configuration (`{systemPrompt, tools?, environment}`, resolved from the session's kind; see *Session kinds*). All three are read from the rows at send time, so task edits and prompt changes reach the node the next time it opens the runtime: **a runtime already open keeps the prompt and tools it was opened with** until it is closed (a move, a node restart, a stale runtime) and reopened.

| Method | Params (besides `epoch`, `sessionId`) | Result | Delivery | Timeout |
|---|---|---|---|---|
| `session.prompt`, `session.steer` | `binding`, `branch`, `lane`, `runtime`, `clientId`, `content`, `sourceSessionId` (nullable) | `{inputId}` | not sent | 120 s |
| `session.setModel` | `binding`, `branch`, `lane`, `runtime`, `provider`, `modelId`, `thinkingLevel?` | `{modelSet: true}` | not sent | 60 s |
| `session.abort` | `binding` | `{aborted}` | not sent | 30 s |
| `session.resumePending` | `binding`, `branch`, `lane`, `runtime` | `{started}` | not sent | 60 s |
| `session.close` | none | `{closed}` | not sent | 30 s |
| `node.reload` (not a session method) | `force?` | `{scheduled: true}` | direct (`NodeModel.reload`) | 30 s |

`content` is text blocks and image **references** only (at most 64 blocks, text up to 4 Mi characters, at most 8 MiB as JSON in all (`MAX_PROMPT_CONTENT_BYTES`), allowed image MIME types, `byteSize` ≤ 10 MiB); inline bytes or other block types are `-32602`. The 8 MiB bound, with the system prompt's 1 Mi characters, keeps an opening command within one remote frame (node-transport.md *Details: frame caps*); `Sessions.submit` refuses longer content before submitting it (`PromptTooLargeError`, "Prompt too large: …", which the browser socket answers as the prompt's error and a script gets thrown). The node keeps no per-command state.

**Re-entrancy:** a node serving `session.prompt`/`session.steer` calls `attachment.fetch` and `storage.*` back over the same link before admission; the peer serves inbound requests while its own call is pending.

### Session configuration and the main lane

The server resolves a session's model and thinking level once, at creation (`createSession` in `sessions/create-session.ts`): the creation override, else the `default_model` setting (thinking: the override's level, else the default's). A `default_model` of another runtime is rejected there and when seeding a lane (`piModelSetting` in `models/model-settings.ts`). They are stored on the session row; a later `default_model` change never reaches an existing session. Session creation writes nothing else: **Pi's main lane is created by the node**, through the server's storage, the first time it opens the session's runtime, seeded from the command's `lane` (Pi's harness creates a lane that does not exist with the model it is opened with). The node validates the model against its own registry, so the server never needs to know the node's models; an unknown model rejects the command `invalid_request` (`Model not found: <provider>/<model>`), and a null seed model fails the open ("AgentHarness Pi runtime requires an explicit model") until `session.setModel`. Once the lane exists **it is the only copy of the model selection** and the seed is ignored. Pi does not persist the system prompt, so every runtime open checks out the command's branch (if any) and builds the system prompt from the command's runtime configuration (see *Session kinds* and [node-runtime.md](node-runtime.md)).

### Session kinds

A session's **kind** (`sessions.kind`, migration 046; `"agent"` unless created as another) defines how it runs: its system prompt, its tools and whether the node appends its environment. There is no per-session prompt: it comes from the kind. Kinds live in a registry on the server (`sessions/session-kinds.ts`): a name → a resolver that, given the session's row and its task's, returns what the opening commands carry: the `runtime` configuration `{systemPrompt, tools?, environment}` and the `branch` to check out (absent: none). Defining a kind is one entry (`registerSessionKind(name, kind)`, which returns its removal). Kinds are validated in code, not by the database, so a new kind needs no migration; `createSession(state, projectId, {kind})` rejects an unknown one, as does sending a command for a row whose kind is no longer registered. Only server code creates sessions of a kind; scripts can neither create nor see them.

- **`agent`** (every existing session): the server's Reins prompt (`reinsSystemPrompt` in `sessions/system-prompt.ts`: the persona and editing guidelines, session orchestration when the session is offered `execute`, and the task section for a task session or the project-assistant section for a scratch session, from the session's hierarchy), every tool (`tools` absent), the node's environment appended, and its task's branch checked out (a task session). The prompt text is product code, so it hot reloads on the server ([ADR-019](../adr/019-server-generated-system-prompt-and-session-kinds.md)).
- **Utility kinds**: a fixed system prompt, a chosen tool list (typically `[]`) and `environment: false`, so the model sees exactly the kind's prompt. **A utility kind has no side effects:** no tools, no node environment and no checkout (it names no branch, even on a task session). Background sessions (`background: true`) are the usual home for them.
  - **`task-generator`** (built in): parses freeform intent into a task's `{title, description, branch_name}` JSON, with `tools: []`. `generateTask` (`sessions/task-generator.ts`, for `POST /api/projects/:id/tasks/generate`) creates a background session of it on the request's source with the utility model (the `utility_model` setting, else `default_model`'s; neither: no session, the deterministic task), submits the user's text as a prompt and waits for its settlement (`waitForSettlement` with the submitted `clientId`, 30 s in all). It needs no node: no tools, no environment, no checkout, and no skill expansion. The session exists only for the request: whatever the outcome its runtime is closed (aborting a run) and it is deleted (its row, cascading to its transcript and attachments). A timeout, a failed submission or run, or a reply that is not the expected JSON gives the deterministic task (the prompt as title and description, a slugged branch).

**On the node** (`buildNodeRuntime`): every tool is registered, and the lane's active tools are set to `runtime.tools` (absent: every registered tool), so Pi offers the model only those; a name the node does not have rejects the command `invalid_request` ("Unknown tools: …"). The system prompt is `runtime.systemPrompt`, followed, when `environment` is true, by the node's environment (`environmentPrompt` in `runtime/system-prompt.ts`): the list of the active tools, the REINS docs paths of the node's own install, the checkout's context files (AGENTS.md) and skills. These are machine-local, which is why the node renders them.

### Model changes

`Sessions.setModel` (HTTP `PUT /api/sessions/:id/model` and scripting `sessions.setModel`) enters the session's chain when called (*Submitted work*), validates the provider/model against the server catalog (`findPiModel`), applies it through the live runtime's `setModel` (Pi's lane; opening the runtime with the requested model if needed, which seeds a lane Pi has not created yet or repairs one whose model is gone), then updates the row and broadcasts `session_updated`. A running prompt picks it up from Pi's next request. Omitting `thinkingLevel` keeps Pi's current level. A failure is the request's error (400 over HTTP; a removed node 409) and leaves the row as it was.

### Skills

`GET /api/projects/:id/skills` (`routes/skills.ts`, `SourceModel.listSkills`; the composer's `/name` suggestions) lists the skills a session in the request's source (see *Which checkout a call works in*) can invoke, merged as its runtime merges them: the server's own (`~/.agents/skills`), then the checkout's, which the source's node reports (`checkout.environment`, 5 s), a checkout skill of the same name as a server skill hidden. When the node is not connected, does not answer in time or refuses, it answers the server's skills with `available: false` (200, logged at debug); otherwise `{skills, available: true}`. The frontend keeps its last known suggestions when `available` is false, and takes the partial list only while it knows none (`ProjectStore.fetchSkills`/`fetchLists`). The server no longer calls `skills.list`, which the node still serves until step 3.

## Node→server calls

The node reads and commits session storage, reports run lifecycle, fetches and uploads attachments, runs Reins tools and reads credentials over the same link. Node→server handlers (`nodeHandlers`, `nodes/node-handlers.ts`) are resolved once per connection, at hello, from the node ID it announced, and fenced (see *Fencing*); the transport (`server-peer.ts`) imports no product stores: it is handed the handlers.

### Lifecycle reports

`session.started {epoch, sessionId, runId}` and `session.settled {epoch, sessionId, runId, reportId, status, error?, metadata: {model, thinkingLevel}, tipId}` → `{acknowledged: true}` drive server effects: activity `running`/`finished`, runtime model metadata and a child's report to its parent (`nodes/node-session-events.ts` → `runStarted`/`runSettled` in `sessions/session-runs.ts`, which the server's own runtimes report through too (`LoadServices`); a child's final reply is read there from the report's `tipId` branch).

- The node sends a session's reports one at a time in occurrence order over the newest connection, waiting for one when none is attached (*Link loss*; `sendReport` in `node.ts`). Pi emits `run_start`/`run_end` after the commits they follow, and every commit went to the server first, so a settlement always follows the commits it summarizes. One whose reply was lost is resent on the next connection (*Link loss*), and while a session has a report still to deliver the node lists it in `liveSessions` (which the server no longer reads). A report that cannot be delivered (no connection within the wait, a refusal) is logged and lost; *Crash recovery* resumes or settles its run.
- `tipId` is Pi's committed `run_end.tipId` (null for a storage fault/interruption with no trustworthy completed branch). The server projects child replies directly from that captured ancestry through `loadBranchMessages`; a delayed report cannot read a newer run's main tip. No node transcript read or reply-read promise is needed.
- A settlement is applied in two ordered steps. For a child, its final reply is first steered to its parent (`Sessions.submit`, under `reinsId` `child-report:<childId>:<n>`, `n` the settlement's count, with `metadata.sourceSessionId`), which the parent's runtime commits on its own; then one server transaction records the settlement with the session's run record (`sessions/session-runs.ts`, columns on `sessions`), the activity update and the metadata write. A crash between the two leaves the child running; recovery at process start settles it and steers again under the same key, which Pi recognises as a replay (the parent hears of it once). `started` sets `run_id` (the run in progress); a `started` for the run already in progress applies nothing. `settled` clears `run_id`, increments `settlement_count` and records the latest status/error (`settlement_json`), the storage's `harness_next_seq` at that moment (`settlement_next_seq`) for waits and its `reportId` (`last_settlement_id`); a settlement whose `reportId` is the last applied one is a resend and applies nothing. Broadcasts happen after commit.
- A child whose report reached its parent clears to idle; if the server could not project the completed branch or the parent cannot receive it (out of scope, its node removed, admission failed), the server logs it and marks the child `finished` with no report.
- Pi re-reports `started` with the same run ID in-run (compaction), which the server treats as a repeat. A run the server or node already settled (interrupted, or failed on a storage fault) may be resumed by Pi under the same run ID on the next command; its reports then apply again (a new `started` if Pi emits one, and a new settlement).

### Crash recovery

Runtimes live in the server process, so a handler reload loses no run and recovers nothing. **At process start** the first load resumes every session it sees `running` (`recoverInterruptedRuns` in `sessions/session-runs.ts`, from `start` with `recoverRuns`): a SIGTERM suspended its run (`suspendSessions` in `process-state.ts`: the process's pause gate closed, up to 3 s for every runtime to be paused, then every runtime suspended, not aborted), or a crash cut it off. Pi left its operation pending in storage; the server opens its runtime and resumes it (`Sessions.resume`), and the session stays `running`. It **settles the run as interrupted** instead, as failed ("The run was interrupted: the server restarted") through `runSettled`, under the run ID of its last `started`, when the resume fails, when there is nothing pending (Pi already ended the run), or when the session has used up its automatic resumes: `AUTO_RESUME_LIMIT` (3) within `AUTO_RESUME_WINDOW_MS` (10 min), counted on the session row (`sessions.auto_resumes`, migration 052, `takeAutoResume`), so neither a reload nor a restart resets it: a run that crashes the server does not crash it at every start. A run that settled or restarted while its resume was in flight is left alone. A settled run can still be resumed by hand (`POST /api/sessions/:id/resume`). A node restart interrupts only the tool calls in flight on it (*Tool host*).

### `session.event`

`{epoch, sessionId, seq, emittedAt, event}` is a JSON-RPC notification carrying live UI deltas only. `emittedAt` is the node's wall clock (`Date.now()`) at emission, for latency diagnostics only (see [client-telemetry.md](client-telemetry.md) *Session bus capture*); it is forwarded to browsers and never drives behavior. `event` is a **string**: the node's single `JSON.stringify` of one runtime event, made after `sendableEvent` (`packages/node/src/session-events.ts`) replaced any image that is not an attachment reference. The server validates only the envelope (epoch, sessionId, seq, emittedAt, and `event` a string of at most `MAX_SESSION_EVENT_CHARS`, 32 MiB), fences it (see *Fencing*; the one session-row read also supplies the project) and relays the string to every connected browser without parsing it, as `{"event":<event>,"type":"event","sessionId":…,"projectId":…,"seq":…,"emittedAt":…}` (`sessionEventFrame` in `models/broadcast.ts`). The envelope fields come after the payload, so duplicate keys inside the payload cannot override them. Notifications are best effort: an unknown method, invalid params, a failing handler, a stale epoch or an out-of-order seq drops that one notification with a warning and never closes the connection. `seq` is per session and node instance, starts at 1 and counts every emitted event, including ones dropped because no connection was attached; the server drops seqs at or below the last seen on that connection, logs gaps, and forwards `seq` so browsers detect gaps too. There is no replay or resync: a lost event only affects live rendering (the transcript comes from the session's storage on the server). Event shapes, including thin `message_update`s and their keyframes, are in [node-runtime.md](node-runtime.md) *Events*. Run lifecycle is not a session event.

### Attachments

- `attachment.fetch {epoch, sessionId, attachmentId, offset}` → `{attachment: {data, mimeType, byteSize, sha256, filename?, width?, height?} | null}` returns base64 of bytes `[offset, offset + 512 KiB)`. The node loops over offsets, requires consistent metadata and exact chunk lengths, verifies size and sha256, and caches the bytes in its in-memory `AttachmentCache` (`node-attachments.ts`) before prompt admission. Provider input is hydrated from the cache; a miss (history from before the runtime opened, e.g. after a node restart) is fetched from the server then, and an attachment the server no longer holds becomes a provider placeholder. With no connection, a prompt/steer needing an uncached attachment returns `unavailable`. A session's cache entries go when its runtime closes.
- `attachment.store {epoch, sessionId, attachmentId, mimeType, sha256, byteSize, filename?, width?, height?, offset, data}` → `{stored: true} | {nextOffset}` uploads node-created image bytes. **The node assigns `attachmentId`** (`att_<uuid>`). If the session already holds that ID with the same content the server answers `{stored: true}` at once (idempotent replay); different content under that ID is rejected. Otherwise the server keeps one partial upload per connection and key (at most 8), answers `{nextOffset}` for an out-of-order chunk, verifies the sha256 after the last chunk and stores under exactly the node's ID (the upload MIME allowlist and 10 MiB limit apply; an ID another session holds rejects). Identical bytes under another ID are stored again, never remapped, so every transcript reference resolves as written.
- Limits (`MAX_ATTACHMENT_BYTES` 10 MiB, `ATTACHMENT_IMAGE_MIME_TYPES`) are exported by `fields.ts` and used by both sides. Each chunk call has a 30 s timeout.

**Images never cross in events or commits as bytes.** User prompt images are references from the start. Tool-result images are converted where Pi produces them: the node's `after_tool` hook (`runtime/tool-images.ts`) replaces each inline image with a reference before Pi stages the result, reusing a cached attachment of the session with the same sha256/MIME, else **uploading the bytes now** under a new ID (`attachment.store`) and caching them, so the server holds the bytes before any commit references them. Images outside the allowlist, empty or over 10 MiB, and images whose upload fails, become a text note (`[Image omitted: …]`). `RemoteStorage`'s `prepare` step applies the same conversion to any inline image Pi commits without the hook (recovered checkpoints, hooks cut short by abort). Stray inline images in live events (partial tool results) are replaced by `[Image attachment unavailable]` (`sendableEvent` in `session-events.ts`). It scans only events that can carry images (message snapshots on `message_start`/`message_end`, `turn_end`, `agent_end`, `entry_added`, and tool results in `tool_execution_update`/`tool_execution_end`); streaming assistant updates hold only text, thinking and tool calls and skip it. The server relays events unread, so **this node check is the only guarantee that events carry no image bytes**; a node must not skip it. Providers still receive bytes: `toProviderMessagesForSession` hydrates references through the cache.

### Agent tools

All tool definitions live on the node: native read/write/edit/bash (`@reins/node/host-tools`) and the Reins tools `create_task`, `search` and `execute` (`@reins/node/reins-tools`). Their names, descriptions, schemas and order are pinned by a snapshot test (`runtime/reins-tools.test.ts`). Each Reins tool forwards one request:

- `script.execute {epoch, sessionId, callId, code}` → `{ok: true, text} | {ok: false, error}`: the server runs the script in its `node:vm` sandbox against the scripting API (`tools/execute.ts`). 5 min timeout.
- `script.search {epoch, sessionId, query}` → `{text, matchCount}` (`tools/search.ts`). 30 s.
- `project.createTask {epoch, sessionId, title, description, branchName?, prompt?}` → `{task, sessionStarting}` (`tools/create-task.ts`). 60 s.
- `script.cancel {epoch, sessionId, callId}` (notification): aborts that script's `AbortSignal` on abort or timeout of `script.execute`; closing the link aborts every in-flight script.

Params name only the calling session; strict schemas reject project/task fields, and `nodes/node-tool-calls.ts` derives scope from the server's session row. None is retried. Transport failures become tool results: an unknown outcome says the call "may have run"; no connection, busy, invalid params or stale epoch mean it did not run.

### Credentials

**The server is the sole credential holder and the sole OAuth refresher** ([ADR-013](../adr/013-server-holds-credentials.md)). A node needs no credential configuration: every Pi model runtime it builds reads provider credentials through `RemoteCredentialStore` (`packages/node/src/credentials.ts`). Refresh tokens never leave the server.

- `credentials.get {epoch, providerId}` → `{credential}`: the stored credential or `null` (logged out; Pi then falls back to ambient auth, e.g. provider environment variables in the node's environment).
- `credentials.refresh {epoch, providerId}` → `{credential}`: runs Pi's own refresh (`getAuth`) against the server's `DbCredentialStore`, whose `modify` is serialized per provider for the process and persists the rotated credential, so concurrent nodes and the server refresh a login at most once. Failure is `-32000` with `{code: "unavailable", retryable: true}` and "OAuth refresh failed for <provider>; sign in again on the server if this persists". No message carries token material.
- `credentials.list {epoch}` → `{credentials: [{providerId, type}]}`, no secrets.
- `credentials.changed {epoch, providerId}` (server→node notification, a capability): a credential for the provider was set or deleted on the server. The routes that change credentials send it to every connected node through the hub (`state.nodes.credentialsChanged`): `PUT`/`DELETE /api/auth/api-keys/:provider`, a completed OAuth login (`/api/oauth/start` once Pi stored it) and `DELETE /api/oauth/:providerId`. A routine OAuth refresh does not send it: nodes re-read a token entering the refresh window themselves, and a notification would only discard the refreshed token the asking node is about to cache. Best effort: an offline node, or one that misses the frame, re-reads everything when it next attaches. Any other server-side credential write must send it too: nodes cache logged-out answers (*Node store*), so a credential stored without it reaches a connected node only on its next attach.

These are not per session, so any negotiated connection is served; **a remote node must be paired and its connection authenticated before they are exposed to it** (*Pairing and authentication*). Handlers: `nodes/node-credentials.ts`.

*Wire shape* (`nodeCredential`, strict): `{type: "api_key", key?, env?}` or `{type: "oauth", access, expires, enterpriseUrl?, availableModelIds?, gatewayConfig?}`. `toNodeCredential` copies only `OAUTH_WIRE_FIELDS`, the non-secret fields Pi's providers read at request or catalog time; the schema rejects `refresh` or any other field (`-32603`). On the node an OAuth credential carries `refresh: ""` only because Pi's type requires it.

*Node store:* `read` returns a fresh cached credential or calls `credentials.get` (concurrent reads share one call). `modify(providerId, fn)` is how Pi refreshes and how a login would persist: a function that returns a credential for no prior credential is a login and rejects ("sign in on the server"); otherwise the store returns a fresh cached OAuth credential or calls `credentials.refresh` (shared by concurrent callers). `list` returns the cached list or calls `credentials.list` (shared the same way); `delete` rejects. The cache is memory only, with no TTL: per provider its credential or that it is logged out (`null`), and the list. Logged-out answers are cached because Pi checks every registered provider, several times over, on every model runtime it builds (`ModelRuntime.create`'s model refresh and availability pass): uncached, each runtime open cost hundreds of `credentials.get` calls; cached, the first open after an attach asks once per provider and later opens ask nothing. An API key or logged-out answer stays for the life of the connection; an OAuth entry until it enters Pi's 5-minute refresh window (`OAUTH_MIN_VALIDITY_MS`). Every entry is dropped when a connection attaches; `credentials.changed` drops that provider's entry and the list. A call in flight when its provider (for `list`: any provider, or the whole cache) is invalidated is not cached, and later calls do not join it, so a stale answer never outlives the change. With no connection, a cached answer still serves `read` and `list`; a miss, a token in the refresh window and a refresh wait for a connection (*Link loss*), then reject with "Credentials unavailable: no Reins server connection".

### Session storage (`storage.read`, `storage.commit`)

The node's Pi runtime keeps a session's AgentHarness storage on the server ([ADR-015](../adr/015-server-canonical-storage-stateless-node.md)): `RemoteStorage` (`packages/node/src/remote-storage.ts`, Pi's `Storage`) turns every read and every commit into one of these calls, and the server serves each from a fresh `PiStorageAdapter` on its own database (`SessionModel.readStorage`/`commitStorage` in `models/session.ts`, behind `readStorage`/`commitStorage` in `nodes/node-storage.ts`, which turns Pi's refusals into `invalid_request`). Schemas: `storageReadParams`/`storageReadResult`, `storageCommitParams`/`storageCommitResult` in `server-methods.ts`.

- `storage.read {epoch, sessionId, op, args}` → `{op, …}`: one read method of Pi's `Storage`, its arguments as `args` and its result named by `op`:

  | `op` | `args` | Result |
  |---|---|---|
  | `getEntries` | `{ids}` | `{entries}`: the entries found, in request order (Pi's `Map`) |
  | `getValue` | `{namespace, key}` | `{value: {namespace, key, value, seq} \| null}` (null: Pi's `undefined`) |
  | `scanValues` | `{namespace, key}` (key prefix) | `{values: [{namespace, key, value, seq}]}` |
  | `readList` | `{namespace, key, options?: {cursor?, order?, limit?}}` | `{elements: [{seq, value}]}` |
  | `scanBranch`, `scanBranchStructure` | Pi's `StorageBranchScan` | `{entries}` (entries, or payload-free structures) |
  | `scanEntries` | Pi's `EntryScan` | `{entries}` |
  | `scanUsage` | Pi's `UsageScan` | `{rows}` |
  | `getStats` | `{}` | `{stats: {messageCount, usage}}` |

  The node rebuilds Pi's value addresses (`value(namespace, key)`) and `Map`s from these.
- `storage.commit {epoch, sessionId, commitId, writes}` → `{firstSeq, seqs, timestamp, stats}`: Pi's `Write[]` as the node produced them, applied in one server transaction by the adapter (`PiStorageAdapter.commitOnce`), which runs Pi's `prepareStorageCommit` and `validateCommittedWrites` against the server's copy and assigns the seqs; the result is Pi's `CommitResult`. `commitId` is the node's fresh ID for the commit, kept when it is resent. The session row keeps the last applied commit's ID and result (`last_commit_id`, `last_commit_json`), written in the same transaction; a commit under that ID is answered with that result and writes nothing. Only the last commit can come again, since a session's commits go one at a time.

Reins-owned structure is strict (an unknown `op`, write kind or extra field is `-32602`); Pi's own bodies (an entry's payload, values, list elements, usage) cross as the JSON Pi's storage writes and reads, with only their envelope checked (entry `id`/`parentId`/`type`, plus `seq`/`timestamp` when stored).

**Long payloads cross in slices** (protocol 9), so no read or commit is bounded by the link's frame cap. A payload is long when its serialized JSON is longer than the link's storage chunk, `storageChunkChars(maxFrameBytes)`: `STORAGE_CHUNK_CHARS` (1 Mi characters), or a quarter of the frame cap if that is smaller. A slice's frame is at most about three bytes per character, so it fits whatever the cap; each side slices what it sends by its own cap, and the local link (64 MiB) takes the same path as the remote one (16 MiB) for the same payload. Shorter payloads keep their one round trip. Offsets and lengths count characters of the JSON text (UTF-16 units); a slice may end inside a surrogate pair, which JSON carries escaped and the receiver rejoins. Every slice of one payload goes over one connection, which holds the partial payload (`createServerTransport` in `nodes/server-peer.ts`; on the node, `connectNode` assembles and slices, so `RemoteStorage` and `StorageServer` see whole calls):

- **A long reply** (a read result, or a commit result: Pi returns one seq per write) is held. `storage.read`, `storage.commit` and the last `storage.commitPart` answer `{replyId, length, data}` (the first slice) instead of the result; the node fetches the rest with `storage.readPart {epoch, replyId, offset}` → `{data}` and checks the whole against the result schema. The server serializes the result once and holds it until its last slice is fetched or the connection closes, at most 16 per connection (the oldest is evicted: fetching its next slice is refused, failing that read or commit).
- **Long writes** are uploaded: `storage.commitPart {epoch, sessionId, commitId, length, offset, data}` → `{nextOffset}` until the last slice, with which the server parses the writes, checks them like `storage.commit`'s params (`-32602`) and applies the commit exactly as `storage.commit` does, answering its result. Offset 0 starts the upload over; an upload the server no longer holds answers `nextOffset` 0, and a slice out of place the offset the server expects. At most 8 uploads per connection (the oldest is evicted and restarts) and `MAX_STORAGE_PAYLOAD_CHARS` (64 Mi characters, what one local frame carried before) per payload, either way.
- **Retries.** Each slice is its own call (30 s timeout); one that fails fails the whole read or commit, which the node makes again from the start. That is safe because a read has no effect and a commit keeps its `commitId`: a commit resent on a new connection is uploaded again, since the server's partial uploads went with the old one, and answered from the session row's record when it was already applied. The record is checked only with the last slice, so fencing (`not_owner`) also refuses a long commit only then; memory per connection stays bounded by the limits above. A read whose reply or slice is lost to a drop fails its run, as a short one does.
- **Why not streams.** Streams (node-transport.md *Streams*) run node→server and are opened by a server→node request; a storage read is a node→server request answered by the server, and a commit carries its payload node→server inside the request. A continuation fetched or sent by offset, as attachments do, covers both directions with two methods and keeps each read a snapshot taken once.

**Fencing:** reads and commits are served only when the session's source is on the calling node (see *Fencing*). Otherwise both are refused as `-32000` with `{code: "not_owner", message: "Node session unavailable: <id>", retryable: false}`. **Refusals are definite:** a read or commit Pi's storage refuses (a duplicate entry or usage ID or a missing parent: a stale or concurrent writer; an unknown branch entry; an invalid list limit) is `-32000` with `{code: "invalid_request", retryable: false}` and changes nothing. **Resends:** `RemoteStorage` sends commits one at a time in admission order, each under a fresh `commitId`; the node resends one whose reply was lost on its next connection (*Link loss*), and one still unanswered past the reconnect wait (or that timed out with no new connection) rejects with the connection's `RpcFailure`. `new RemoteStorage(sessionId, server, prepare?)` takes the node's server-call surface (`readStorage`, `commitStorage`, as the connection has them) and an optional `prepare` step that rewrites each commit's writes just before it is sent, in commit order (the node uploads inline images there; see *Attachments*). `close()` seals admission, waits for admitted commits and releases nothing on the server. Proven by Pi's `createStorageConformance` through the hub's loopback link, capped at 4 KiB so its larger reads, commits and commit results cross in slices (`__tests__/nodes/node-storage.test.ts`, which also covers a long read, a long commit, and a long commit whose reply was lost answered from its record on the next connection).

## Fencing

Every node→server call about a session (`storage.read`/`storage.commit`/`storage.commitPart`, `session.started`/`settled`, `session.event`, `attachment.fetch`/`attachment.store`, `script.*`, `project.createTask`) is served only when **the session's source is on the calling node** (`nodeOwnsSession` in `sessions/session-ownership.ts`; `storage.readPart` fetches the rest of a reply whose call was fenced, on the same connection). Otherwise it is refused with `-32000` and `NodeError` `{code: "not_owner", message: "Node session unavailable: <id>", retryable: false}` (events are dropped). An unknown session is refused before any product service runs. Agent tool calls refused with `not_owner` fail as tool results; a refused storage call fails the run. Credentials are not per session: any negotiated connection is served.

## Replay idempotency

There are no receipt tables on either side ([ADR-010](../adr/010-state-derived-idempotency.md)): "already applied" is derived from state, so a replay after a lost acknowledgement or a restart of either side is **acknowledged as success** and applies nothing twice.

**Node → server:** a commit or lifecycle report whose reply was lost is resent (*Link loss*). Commits and reports each go one at a time per session, so only the last applied one can come again, and the session row keeps just its ID: a commit under the last `commitId` is answered with its recorded result (see *Session storage*); otherwise Pi's sequence check refuses a stale or duplicate writer. *Lifecycle reports:* a `started` for the run already in progress (a resend, or Pi's in-run compaction) applies nothing; a settlement under the last applied `reportId` applies nothing, and any other settlement applies (a second settlement for the same run is a resumed run, so the run ID cannot tell a resend). *Attachments:* the same content under the same ID is acknowledged; different content rejects.

**Submissions** converge on Pi's state in the session's storage (*Submitted work*):

- **prompt:** Pi admission is durable (`lane.accept` commits the `reinsInput` keyed by `reinsId` = the submission's `clientId`). A replay finds that input and answers it; an in-flight admission of the same input is joined. A recovered operation is driven again only if not already active.
- **steer:** `lane.steer` commits the queued input and Pi moves it from queue to transcript in one commit, so checking the queue first, then entries, cannot miss it. Residual: an abort discards queued steers, so a steer replayed after an abort discarded it is queued again.
- **model changes:** an absolute selection, re-applied.

Verified by `__tests__/models/sessions.test.ts` (order, replay, failures, model changes, abort and resume), `__tests__/sessions/session-runs.test.ts` (child reports and the crash between their steps, recovery at process start and its budget), `__tests__/server-process.process-test.ts` (real processes, `bun run test:process`: SIGTERM pausing and the next process resuming, a server killed mid-request, a node killed mid-run, a dev reload mid-run), `__tests__/supervisor.process-test.ts` (a node reloaded during a run on the server), `__tests__/nodes/node-hub.test.ts` (a commit reply lost across a hub replacement) and `packages/node/src/node.test.ts`.

## Server reads projections only

Server code reads a node's sessions from its own tables, so it works unchanged with the node in another process:

- **Activity** (`models/session-activity.ts`): `sessionActivity(row, sessions)` is `running` when `activity_state` is `running` (set/cleared by lifecycle reports), or when the session has submissions in progress or its live runtime is admitting or driving input (`isStreaming`) whose start has not been applied yet, else `idle`. `activeSessionIds(sessions)` applies the same rule across sessions. Reading writes nothing. Used by session views (`pendingOperation` only when idle), task deletion (any non-idle session blocks it), moves and `/api/health` (`activeSessions`, `streaming`). Browsers see the row's `activityState` (`running` from the run's `started`, then `finished` or null), as before.
- **Wait** (`waitForSettlement` in `sessions/session-runs.ts`, behind `SessionInstance.wait` and `api.sessions.wait`): polls every 10 ms and resolves once the session is idle (`sessionActivity`) and every input the caller names (`inputs`: clientIds it submitted, as task generation does) that Pi admitted is covered by a settlement: an input still queued as steering awaits a run; a transcript entry is covered once the latest settlement was applied after it (`settlement_next_seq` above its seq). An input Pi never admitted expects no run. The result is the transcript's final reply with the latest settlement's status/error (`completed`/`failed`/`cancelled`, or `idle` with no reply), `timeout` at the deadline; an `AbortSignal` rejects with `AbortError`.

## Moving a session

A session runs on its source's node, so moving it is re-pointing its source (`sessions/session-ownership.ts`). `POST /api/sessions/:sessionId/move {nodeId}` checks the session is idle (`sessionActivity`; otherwise 409) and, in one transaction, sets `source_id` to the target node's source for the project (409 when there is none; 404 for an unknown session). Moving to the node it is on changes nothing. Its runtime is on the server and everything is in storage, so nothing is left behind: `Sessions.move` closes its live runtime (bound to the source it left), and its next submission opens it on the target's source. The response is the session's placement view; the move broadcasts `session_updated`. `GET /api/sessions/:sessionId/move-targets` lists every node not removed as `{nodeId, name, connected, eligible, reason?}`, eligible first, each group by name; `reason` is `"current"` or `"no_source"`. A session on a removed node moves like any other, to a node holding a source of its project (its run, if the server saw one in progress, was aborted or settled as interrupted at the removal, so it is idle); until then it takes no work (*Pairing and authentication*, Removal).

Session views expose `placement: {available, removed, nodeId, nodeName, path}`: the node of the session's source, whether it is connected, whether it was removed, and the checkout's path. A removal does not broadcast `session_updated` for the node's sessions: a browser's cached view marks the node removed from the session's next update, or a reload.

**Session deletion.** Deleting a task or a project deletes its sessions' rows (and their storage) on the server, as task generation deletes its background session (*Session kinds*); their live runtimes are closed first, aborting their runs (`closeSessionRuntimes` in `session-runtime/live.ts`, which closes again any a child's report reopened). The node holds nothing for a session.
