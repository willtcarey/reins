# Node contract

A **node** is a tool and file host ([ADR-029](../adr/029-sessions-on-the-server-nodes-host-tools.md)): it runs, on the checkouts of the sources on its machine, what the server asks of them: git and other processes (`process.run`), the file browser's reads and uploads (`fs.*`), and the file operations and commands of the agent's tools as a remote execution environment (`env.*`), with what of a session's environment comes from the checkout (`checkout.environment`). It runs no Pi, holds no session state and gets no credentials, and keeps nothing durable but unfinished file writes. The **server** owns everything else: product state (projects, tasks, sessions, settings, credentials), every session's storage, the sessions themselves (their runtimes run in the server process, with the server's model runtime and credentials: [session-runtime.md](session-runtime.md)), and the browser UI and API. Every node is alike, the server machine's included.

This doc covers what each side is responsible for and what they say to each other. How the link itself works (socket, framing, JSON-RPC, negotiation, streams) is in [node-transport.md](node-transport.md); read it first. How sessions run is in [session-runtime.md](session-runtime.md).

A node is a process running `packages/node`: the local node on the server's machine, linked over a Unix socket, or a remote node on another machine, paired with the server (*Pairing and authentication*) and linked over a WebSocket at `/nodes/link` (`reins node run`, *Process model*). See [the node architecture plan](../plans/node-architecture.md) for what is open. Decisions behind this design are recorded in ADRs [012](../adr/012-ndjson-unix-socket-local-link.md), [014](../adr/014-shared-protocol-and-storage-packages.md), [018](../adr/018-process-run-and-fs-methods.md), [020](../adr/020-reloadable-node-hub.md)–[029](../adr/029-sessions-on-the-server-nodes-host-tools.md).

| Concern | Server (`packages/backend`) | Node (`packages/node`) |
|---|---|---|
| Sessions | Their runtimes (AgentHarness), storage, submitted work, events, lifecycle, recovery | None |
| Models and credentials | The model runtime and catalog, credentials (sole holder and OAuth refresher) | None |
| Agent tools | Defined and run on the server: Pi's tools over `RemoteExecutionEnv`, the Reins tools in process | Serves the file operations and commands (*Tool host*) |
| Git and files | The git logic (`Git`), which checkout a call works in | Runs `process.run`, `fs.*` in the checkout it is sent |
| Environment | The server's `~/.agents`, merged with the checkout's | The checkout's context files, skills and its REINS docs path (`checkout.environment`) |
| Attachments | The only copy, for browsers and providers | None |

## Process model

The server and the local node are separate processes that meet only on the node socket ([node-transport.md](node-transport.md)).

- **Server-only** (`bun run start:server`, `packages/backend/src/index.ts` → `server-process.ts`): opens the product database under `REINS_DATA_DIR` (once, for every handler load), runs the sessions, listens on HTTP (remote nodes connect there, at `/nodes/link`) and on the node socket. It never starts a node.
- **Node-only** (`bun run start:node`, `packages/node/src/main.ts`): starts the node and dials the socket. Its lifecycle (the signals, pausing, refusal and reload below) is `runNodeProcess` (`node-process.ts`), which resolves with why the node stopped; `main.ts` gives it the transport (`unixTransport`) and picks the exit code. It keeps no state on disk: its data directory (`REINS_NODE_DATA_DIR`, default `~/.reins`) holds the bytes of unfinished `fs.write`s and `env.fs` writes (`partial-writes/`), which it removes when it starts, and, on a paired machine, the node's pairing and key (*Pairing and authentication*), which the local node does not read. Logs go to stdout/stderr with a `[node]` prefix. It announces `REINS_NODE_ID`, by default `DEFAULT_LOCAL_NODE_ID` (`"internal"`, the node row the server's migrations seed). `REINS_DOCS_DIR` is where the REINS docs it reports in `checkout.environment` are (a delivered bundle's `builds/<buildId>/docs`, holding only `features/`); unset, they are the checkout's `docs/` it runs from ([session-runtime.md](session-runtime.md) *The environment*). A node needs no Pi configuration and no credentials.
- **Remote node** (`reins node run`, `packages/cli/src/node/run.ts`, which runs `runInstalledNode` in `node-process.ts` and prints how it ended, `report`): runs this machine's paired node in the foreground. On a remote machine `reins` is the node bundle, `bun --no-install <dir>/reins.js`, which an installed node runs through its launcher, `~/.reins/bin/reins` ([node-bundle.md](node-bundle.md)); the bundle's entry sets `REINS_DOCS_DIR` (`<dir>/docs`, where it writes the docs/features it carries) where it is unset. From source it is `bun run reins`. It reads `node.json` and the key from the node home (`REINS_NODE_DATA_DIR`, default `~/.reins`; *Pairing and authentication*), which is also its data directory, and runs `runNodeProcess` over `webSocketTransport`: it dials `node.json`'s server at `/nodes/link` (`ws://` or `wss://`), answers the challenge with its key and announces its paired node ID. Like the local node, it works in whatever checkout the server sends (*Checkout operations*). Same lifecycle as the node-only process, but nothing restarts it, so it serves no `node.reload`. It refuses to run while another node of the same home runs (by the status file below). Exit 0 stopped by SIGTERM/SIGINT (last line `[node] stopped`), 1 not paired, already running or an unexpected failure (a broken config or key), 4 refused by the server (the last line names the server and its reason, and says to re-pair with `reins node pair --force <server URL> <code>`), 75 (`RESTART_EXIT_CODE`) updated (below).
- **Updates** ([ADR-025](../adr/025-node-version-handshake.md)): run from a bundle, `reins node run` announces its build (`buildId`, the sha256 of the `reins.js` it runs) in every hello. A server on another build answers `update {buildId, sha256, bunVersion}` (node-transport.md *Details: builds and updates*); the node logs `[node] the server runs build <id>; updating to it`, dials nothing meanwhile and installs the build in its home (`NodeInstall.installUpdate`, `packages/node/src/install.ts`, which `runInstalledNode` gives `runNodeProcess` as its `installUpdate`; node-bundle.md *Updates*): the bundle from the server it is paired with, checked against `sha256`; Bun's official release `bunVersion` if that is not the Bun it runs; then `current` flipped and the launcher written again. A failure (an HTTP error, a checksum, a Bun that will not run) leaves `current` as it was and is logged, and the node asks the server again after a backoff of 5 s doubling to 5 min (node-transport.md *Details: reconnecting*). Installed, it logs `[node] build <id> installed; restarting on it` and stops without pausing (it cannot reach the new server meanwhile): `Node.shutdown` kills the commands its tool host still runs, whose tool calls come back "outcome unknown" (*Tool host*). Under its launcher (which sets `REINS_NODE_RESTART_EXIT_CODE`: the bundle is `restartable`) it records `updating` in the status file and exits with that code, and the launcher starts the new `current`. Run without one (a bundle run directly) it does the same install, records `stopped`, says nothing restarts it here and how to start it (`<home>/bin/reins node start`), and exits 75 all the same. From source it announces no build and is never told to update; a node without an updater (`runNodeProcess` without `installUpdate`) that is told to treats it as a refusal.
- **Status file** (`NodeInstall.recorder`, `packages/node/src/install.ts`): `reins node run` (`runInstalledNode`, which claims it before it dials and records the link's state as `runNodeProcess` reports it, `onState`) records itself in `<home>/run/node-status.json`, `{pid, started, state, buildId?, serverUrl, since, message?}`, rewritten (temp file and rename) on each transition: `connecting` when it starts and whenever it redials, `connected`, `refused` (with the server's `message`), `updating` (it installed a new build and exited for its launcher to start it), and `stopped` when it exits, unless refused or updating, which stay the final state. `buildId` is the sha256 of the bundle it runs from (absent from source); `since` is when it entered the state. `started` is the process's start time as the OS reports it (`/proc/<pid>/stat` on Linux, `ps -o lstart=` elsewhere): a status file outlives a killed node and its pid may since be another process's, so a pid is trusted, or signalled, only while its start time is still the recorded one; a zombie counts as gone. A file left by a crash just reads as not running. `reins node start` also records the launcher it runs in `<home>/run/launcher.json` (`{pid, started, since}`): until the node records itself, and while the launcher restarts it on a new build (the status file says `updating` with the old node's pid), the launcher is what runs (`NodeInstall.status()` is then `starting` or `updating` and running, with the launcher's pid), so `start` and `setup` start no second node then, and `stop` stops the launcher.
- **In the background** (an installed node: the launcher, `bin/reins`, [node-bundle.md](node-bundle.md) *The node home*): `reins node start` (`packages/cli/src/node/control.ts`, `NodeInstall.start`) runs `<home>/bin/reins node run` as a plain detached process (a session and process group of its own, stdin closed, stdout and stderr appended to `<home>/logs/node.log`, cwd the home, without the `REINS_DOCS_DIR` of the bundle starting it), after removing the previous status file, and records it, unless the node (or its launcher) already runs; then waits until the status file says `connected` or `refused`, the node and its launcher have exited, or 30 s pass, and prints the outcome as its last line (`report`, `node/outcome.ts`, as for `run`, `setup`, `stop` and `status`). Exit 0 connected, 1 not paired, not installed (no launcher: from source, use `reins node run`), exited or still not connected (it keeps trying), 4 refused. Not a service: nothing starts it after a reboot. `reins node stop` sends SIGTERM to the recorded node (only while its pid's start time is the recorded one), or, while its launcher runs no node (starting one, or restarting it on a new build), to the launcher's process group, and waits up to 15 s for the node and its launcher to exit (the node waits for its commands first, *Shutdown*); exit 0 stopped or not running, 1 still running. `reins node status` prints the pairing (server, node ID), the build (the running node's, and `current` if that differs), the log path and, last, whether it runs (pid) and is connected, or is restarting on a new build (`updating`); exit 0 connected, 1 not paired, 3 not running (stopped, refused or never started), 4 running but not connected, or restarting. A node started in the background that updates itself is started again by its launcher, so `start`'s and `setup`'s wait goes on through the restart until the new build connects.
- **Combined** (`bun run start`, `bun run dev`; `packages/backend/src/supervisor.ts start|dev`): spawns the server (in dev, `packages/backend/dev.ts` with handler hot reload), the node and, in dev, the frontend watchers. Both inherit the environment, so they agree on `REINS_NODE_SOCKET`. The server exiting stops everything. A node that exits is restarted with exponential backoff (1 s doubling to 30 s, reset after 30 s of uptime), except that one exiting with `NODE_RELOAD_EXIT_CODE` (75, which the supervisor gives it as `REINS_NODE_RELOAD_EXIT_CODE`) is restarted at once: an explicit reload (*Reloading a node*), and one exiting with `NODE_REFUSED_EXIT_CODE` (77, given as `REINS_NODE_REFUSED_EXIT_CODE`) is not restarted at all ("node refused by the server; not restarting"): the server refused it (*Refused nodes* below). The server keeps running either way. Nothing watches node code, in `dev` either (see [hot-reload.md](hot-reload.md)). SIGTERM/SIGINT: SIGTERM to every child, SIGKILL after 10 s, exit 0. The Docker image runs `supervisor.ts start`.

**Startup ordering:** either may start first. A node started before the server redials with backoff (100 ms to 5 s; node-transport.md *Details: reconnecting*). A server started before the node admits submitted work: a run waits for the node at its first assistant request, and its tool calls wait for it (session-runtime.md *The environment*).

**Shutdown:** the server on SIGTERM/SIGINT pauses the runs of its sessions at their pause points (bounded by 3 s, then forced) and suspends them, leaving them pending for its next start to resume (`suspendSessions` in `process-state.ts`; session-runtime.md *SIGTERM*, *Recovery*), then exits through `exit`, removing its socket file. The node on SIGTERM/SIGINT pauses (*Pausing a node*): it waits for the commands its tool host runs to exit and their output to be sent, bounded by 3 s (`SHUTDOWN_PAUSE_MS` in `node-process.ts`), after which whatever is still running is cut off; then it stops redialing, closes its connection, `Node.shutdown()` kills any command still running, and it exits 0. A command cut off comes back to its tool call "outcome unknown"; every other tool call waits for the node to come back.

**Refused nodes:** a server that answers the hello with `NODE_REFUSED` will not serve this node (its ID is unknown, it was revoked or removed, or it failed authentication), so the dialer stops instead of redialing. The node logs `[node] refused by the server: <reason>; not reconnecting`, shuts down as on SIGTERM and exits with `REINS_NODE_REFUSED_EXIT_CODE` (1 when run on its own). Dropped connections and failed dials (the server down, a reload, the network) and a hello with no common protocol version are still redialed. `reins node run` stops the same way and exits 4, with a hint to re-pair (`reins node pair --force`).

### Pausing a node

A node goes away without losing work by waiting until **no command of its tool host is running** (`env.exec`, *Tool host*). `Node.pause({timeoutMs, force})` resolves `{paused, blocking}` once no command runs or has output still to send (`busy` in `host-env.ts`): a command counts until it has exited and its output stream has sent its exit, so the server gets the result before the node goes; one that exited while no stream was open (its link dropped) does not count. Every other call is served meanwhile, `env.execAttach` and `env.execKill` included, but **a new `env.exec` is refused** `unavailable` (retryable) while the pause lasts, not held: a command started during the drain would hold it up in turn, so a busy node could put a reload off for ever. Refused, it was certainly not run, and the server sends it again (`RemoteExecutionEnv`, for up to `EXEC_START_WINDOW_MS`, 90 s), to this node once the pause ends or to the restarted one. At `timeoutMs` it resolves anyway with `force`; without, it accepts commands again and resolves `paused: false`, `blocking` naming the commands it waited for (`exec <execId>: <command>`, the command cut to 100 characters). A node pauses no run: runs are on the server, where their tool calls wait for the node.

### Reloading a node

`node.reload {force?}` → `{scheduled: true}` restarts the node on its current code ([ADR-021](../adr/021-explicit-node-reload.md)). The server sends it for `POST /api/nodes/:nodeId/reload {force?}` (404 unknown node, 409 the node's refusal, 503 offline; 30 s), the scripting call `api.nodes.reload(nodeId?, force?)` (the calling session's node by default) and `reins node reload [nodeId] [--force] [--server <url>] [--local]` (`packages/cli/src/node/reload.ts`, through `@reins/client`'s `nodes.reload`; exit 1 on a refusal, 5 when no Reins server answers). It reloads the node it names, or by default this machine's paired node (`node.json`) on its server, else the local server's (`http://localhost:<REINS_PORT or 3100>`) local node (`REINS_NODE_ID`, default `internal`); `--server` names the server (the paired node is then the default only on its own server) and `--local` ignores `node.json`. `bun run node:reload` is `reins node reload --local`, so it means the local node on a paired machine too, all through `NodeModel.reload` (`models/node.ts`). The node refuses it `unavailable` when nothing would restart it (`startNode` was given no `reload`: `main.ts` gives one only under the supervisor) and `invalid_request` when its new code does not build (`main.ts` bundles its entrypoint with `Bun.build`, packages external). Otherwise it answers at once, before the reload, because the caller's own tool call may be one of the things the reload waits for. It then pauses (*Pausing a node*, bounded by `RELOAD_DRAIN_TIMEOUT_MS`, 60 s) and exits with the reload code; the supervisor starts it again at once. A command running on it finishes and is answered first, a new one is sent again to the restarted node, and every other tool call waits for it. A pause that times out without `force` cancels the reload: the commands run on, new ones are accepted again, and the node logs the commands that held it up; with `force` the node restarts all the same, killing them (their calls come back "outcome unknown"). A second request while one is pending joins it. **Nothing is exempt from the drain**: `api.nodes.reload()` in an `execute` script runs on the server and is no command, but a bash call running `bun run node:reload` is one, on the node it reloads. It ends as soon as the reload answers, so it holds the reload up only as long as the rest of that command runs (a `bun run node:reload && sleep 120` holds it to the timeout).

## Pairing and authentication

A remote node gets its identity by pairing, and proves it on every connection that authenticates ([ADR-023](../adr/023-node-pairing-and-challenge-authentication.md); user-facing: [settings.md](../features/settings.md) *Nodes*, [nodes.md](../features/nodes.md)). The local node is never paired: the local socket's file permissions are its authentication.

- **Codes** (`NodePairing.createCode` in `models/node-pairing.ts`, reached as `Nodes.pairing()`; `POST /api/nodes/pairing-codes {name?}` → 201 `{id, code, expiresAt}`; `id` is not secret and names the code in the `node_updated` its redemption sends): 32 random bytes, base64url, never starting with `-` (drawn again if it would: the CLI would read it as an option), redeemable once within 10 minutes (`PAIRING_CODE_TTL_MS`). `node_pairing_grants` keeps only the code's SHA-256, its expiry, when it was consumed and the node it paired. The code appears in no log line or error message. Times are computed in JS, so tests move them with `setSystemTime`.
- **Redemption** (`NodePairing.redeem`; `POST /api/nodes/pair {code, publicKey, hostname}` → 201 `{nodeId, name}`): `publicKey` is the canonical base64url of a raw 32-byte Ed25519 key. One conditional `UPDATE` consumes the grant inside the transaction that inserts the `nodes` row (a new UUID, named by the code or else the hostname, with `public_key`, `hostname`, `paired_at`), so of competing redemptions exactly one pairs and a failed one consumes nothing. Unknown, used and expired codes are all 403 "Invalid or expired pairing code"; a malformed body or key 400; a key another node holds 409. Browsers are told `node_updated {node, pairingCodeId}` (the node view and the grant's ID).
- **`reins node pair <server URL> <code> [--force]`** (`packages/cli/src/node/pair.ts`; the files are written by `NodeInstall.savePairing`; `bun run reins …` from source; an installed node runs it as `~/.reins/bin/reins`, and the install command pairs through `reins node setup`, below): generates the keypair, redeems the code through `@reins/client` with the machine's name (`machineName`: on macOS `scutil --get LocalHostName`, the name set in System Settings, since `os.hostname()` there is the network's name for the machine, such as `Mac.lan`; `os.hostname()` elsewhere, or when that fails or is empty), writes the private key to `<home>/keys/<nodeId>.pem` (PKCS#8, 0600; home `REINS_NODE_DATA_DIR` or `~/.reins`, 0700) and then the config `<home>/node.json` (`{version: 1, serverUrl, nodeId, keyPath}`, 0600) by rename, its commit point (the new key is removed if that fails). An existing config refuses the run before the code is sent, unless `--force`, which removes the previous key once the new config is in place. Non-interactive: exit 0 paired, 1 another Reins error answer (a 400 or 409: `requestFailure`, as for `reins node reload`) or an unexpected failure, 2 usage (an argument count or a server URL that is not http(s)), 3 already paired, 4 code refused (403), 5 server unreachable or not answering as Reins (an unexpected body included); the last line says which. An argument that starts with `-` would go after `--`; codes never do. `NodeInstall.pairing` (version-checked; it keeps fields it does not know, written by a newer CLI of the same version) and `NodeInstall.key` (→ `{origin, privateKey}`, `connectNode`'s `key` for dialing the pairing's `serverUrl` as its `nodeId`) are what `reins node run` starts from.
- **`reins node setup <server URL> <code>`** (`packages/cli/src/node/setup.ts`): what the install script (`/nodes/install`, [node-bundle.md](node-bundle.md)) runs from the bundle it downloaded. In order: it refuses to run from source (exit 1: it installs the bundle it runs from); refuses a home paired with another server (exit 3, with the hint `reins node pair --force <server URL> <code>`, then the install command again), all before anything changes or the code is sent. Then it makes its build current and writes the launcher (node-bundle.md *The node home*); pairs as `reins node pair` does unless the home is already paired with this server (then the code is not sent: "the code was not used"); and starts the node as `reins node start` does (*Process model*), except that a node already running another build is stopped first and one running this build is left running; and waits for it to connect. Its last line is the outcome (`Node "<name>" (<id>) connected to <server> (pid N).`, or what failed and where the log is). Exit 0 connected; 1 as above, or the node exited or did not connect within 30 s; 2 usage; 3 paired with another server; 4 the code refused (as `pair`) or the node refused; 5 the server unreachable (as `pair`). Run again with the same, already used code it pairs nothing and keeps the running node: safe to repeat. **Recovery:** when the home was already paired with this server (so this run did not use the code) and the server refuses the node it starts (it was removed or revoked there), setup says so (`<server> refused node <id> (<reason>); pairing this machine again with the code given`) and pairs again with the code given, as `pair --force`, then starts the node again. So re-running the install command with a fresh code from Settings repairs a node removed on the server. A code this run has just used to pair is not tried again.
- **A project's sources from the command line** (`reins source add <path> --project <id> [--node <nodeId>] [--server <url>] [--local]`, `reins source list [--project <id>] [--node <nodeId>]`, `packages/cli/src/source.ts`): through the server's API (`POST /api/projects/:id/sources`, `GET /api/nodes`; which server and which node is "this node": `server.ts`, as for `reins node reload`). Without `--node`, add means this machine's node and resolves a relative path against the working directory; with `--node` the path must be absolute (exit 2 otherwise). `list` prints `<node ID>\t<path>\t<project> (project <id>)` per source, or `No sources.`; add prints `Source added to project <id> on node <nodeId>: <path>`. Exit 0, 1 the server's refusal (*Node hub*, default source), 2 usage (no `--project` for add, a project ID that is not one), 5 no server answering. A node keeps no list of its own (*Checkout operations*).
- **Authentication on the link:** a connection the hub accepts with `authenticate: {origin}` is challenged (`node.authenticate`) and must sign it with the paired key before its hello, which must name that node, is answered (node-transport.md *Details: authentication*). The local socket accepts without it. The WebSocket route (`/nodes/link`, `routes/nodes.ts`) accepts every connection with it, from the socket's `open` (the challenge is the first frame), for the origin of the upgrade request: its forwarded headers (`X-Forwarded-Proto`, `X-Forwarded-Host`) else the request's own scheme and `Host` ([ADR-024](../adr/024-node-link-origin-from-the-upgrade-request.md); node-transport.md *1b. The WebSocket link*).
- **Renaming** (`NodeModel.rename` in `models/node.ts`; `PATCH /api/nodes/:nodeId {name}` → the node view; `@reins/client`'s `nodes.rename`): any node, the never-paired local node included, paired or revoked; the name is trimmed and must then have 1 to 100 characters (`MAX_NODE_NAME_LENGTH`; `InvalidNodeNameError`, 400); an unknown node 404. Tells browsers (`Nodes.publish`). Nothing else stores the name: views that show it (session placement's `nodeName`, a source's view, the move targets) read the node's row each time they are built, so they show the new name from their next build; a browser's cached session view keeps the old one until the session's next `session_updated`.
- **Revocation** (`NodeModel.revoke` in `models/node.ts`; `POST /api/nodes/:nodeId/revoke` → the node view): sets `revoked_at`, closes the node's link (`state.nodes.disconnect`) and tells browsers (`Nodes.publish`). A revoked node keeps its key, so it still passes the challenge, and its hello is refused (`NODE_REFUSED` "Node revoked: <id>", `NodeRevokedError` from `NodeModel.assertMayConnect`) on every transport, so the node stops rather than redialing (*Process model*, *Refused nodes*). Its rows stay: its sessions' runs wait for it at their first request and tool calls, as for any offline node. A never-paired node is 409; revoking again changes nothing. Key rotation is revoke and re-pair.
- **Removal** (`NodeModel.remove` in `models/node.ts`; `DELETE /api/nodes/:nodeId` → 204) **abandons** a paired node, revoked or not, whatever it holds: it sets `removed_at` (migration 051), closes the node's link and tells browsers (`Nodes.publish`, `node_removed`). The row stays, key included (sessions hang off its sources, which stay too), so the node still passes the challenge and its hello is refused, `NODE_REFUSED` "Node removed: <id>" (`NodeRemovedError` from `NodeModel.assertMayConnect`), on every transport, and the node stops (*Process model*, *Refused nodes*). Its pairing grant keeps the record (`node_id`). From then on the node is not listed (`GET /api/nodes`, `Nodes.list`), not offered (the project form's node selector, Add source: `createSource` answers 400 "Node not found: <id>"; move targets) and its sources are no project's default (*Node hub*, default source); renaming, revoking or reloading it is 404 ("Node removed: <id>"). **Its sessions** stay readable (their history is the server's) and movable to a node holding a source of the project (*Moving a session*), and their placement says `removed: true`. Work for them is refused at once: `Sessions.submit` (prompt, steer, child reports, code-review prompts), `Sessions.setModel` and `Sessions.resume` throw `SessionNodeRemovedError` ("This session's node was removed; move it to another node to continue"; HTTP 409, the browser socket's `{type: "error", sessionId, clientId, error: "prompt failed: …"}`, a script's thrown error; a child's report to such a parent is logged and the child left `finished`, as for any parent that cannot receive it). The removal closes the live runtimes of its sessions, aborting their runs (a tool call waiting for the node fails), and a run the server still sees in progress there without a live runtime is settled as interrupted ("The run was interrupted: its node was removed"; `SessionRuns.interruptRunsOn`), since the node will never report it, so its session can be moved. Removing it again changes nothing (204); the never-paired local node 409; an unknown node 404. A machine whose node was removed pairs again as a new node (setup's recovery, above); its sessions are moved to it like any.
- **Browser messages** (`ServerMessage` in `models/broadcast.ts`): one method sends them, `Nodes.publish(nodeId, {pairingCodeId?})` in `models/nodes.ts`, which reads the node's row: `node_updated {node, pairingCodeId?}` with its view (`NodeView`, `models/node.ts`: `paired` says whether it has a key, which the view never carries) while the node exists and is not removed, else `node_removed {nodeId}`. It is called on a redemption (with the grant's ID, so the browser showing that code sees it paired), on renaming, revocation and removal, by the hub when it gives a node a link or loses its only one (not when one link replaces another; where it logs "Node X connected/disconnected") or it tells a node to update (and when that node comes back), and when a node's project sources change (*Node hub*, nodes and sources). Each message carries the node's whole state, so a repeat changes nothing: revoking or removing a connected node sends a second one when its link has closed.
- `GET /api/nodes` lists every node not removed as `{id, name, connected, paired, hostname, pairedAt, revokedAt, sources, build}` (`sources`: *Node hub*, nodes and sources; `build`: `{id, status}`, the node bundle it announced at its last hello to this server load, `current`, `outdated` or `updating`, null from source or when it has not said hello since it disconnected; `RemoteNode.build`, node-transport.md *Details: builds and updates*); the settings page's Nodes section shows it (kept current by the messages above; a build that is not `current` is labelled), creates codes and follows their pairing (until the node connects, or is removed), renames nodes (a dialog), removes nodes (after a confirmation dialog; revocation has no UI until node detail pages) and shows how many sources each node holds; the project form leaves revoked nodes out (removed ones are not listed at all).

## The link

How the server and node exchange messages is in [node-transport.md](node-transport.md): the socket and its permissions, framing, JSON-RPC, `node.hello` and epochs, the heartbeat, frame caps, wire error codes, the method tables and naming, streams, reconnecting, hot reload and test links. This doc covers what is sent over it.

## Checkout operations

The server reads and writes a source's checkout through the node holding it, never on its own disk ([ADR-018](../adr/018-process-run-and-fs-methods.md)): **git runs on the node through one generic method, `process.run`, while the git logic (which commands, how their output is read) stays on the server**, where it hot reloads. The file browser's filesystem reads and uploads, which are not git and whose shell equivalents differ between Linux and macOS, are typed `fs.*` methods. All are negotiated, request-now node capabilities: never queued, failing at once when the node is offline. All name the source and send the path the server resolves for it (`cwd`).

**The server's sources are the record** ([ADR-026](../adr/026-sources-managed-on-the-server.md)). A node keeps no list of sources: it works in the path each call sends (`cwd`, a session binding's `cwd` for the tool host), as the local node always has, refusing only what its operations refuse anyway (a missing checkout, `not_found`; a path escaping the checkout, `invalid_request`). Which sources a node has is the `sources` table, managed on the server only (the project form, `POST /api/projects/:id/sources`, `reins source add`): `createSource` and `moveSource` refuse a relative path (`CheckoutNotFoundError`, 400: "A source's path must be absolute: <path>") and check the path with `fs.list` of `.` on the node, so one that is not a directory there is `CheckoutNotFoundError` (400: "Directory does not exist: <path>"). Under the trust model the server can already run anything on a node, so a node-side allowlist would protect nothing.

- `process.run {sourceId, cwd, streamId, argv, env?, binary?}` → `{}`, and opens a stream (node-transport.md *Streams*) of the process's stdout. `argv` is run directly, never through a shell (the server builds arguments from browser input such as paths and branch names); `env` is merged over the node's environment. The node refuses a missing checkout (`not_found`) or a program it cannot find on `PATH` (`invalid_request`, "Program not found: <name>") before answering, and spawns the process when the stream starts. The stream's end frame carries the exit (`{code, signal, stderr}`); cancelling the stream (or losing the link) kills the process. No stdin yet: no server git call writes to one.
- `fs.list {sourceId, cwd, path}` → `{entries: [{name, type}]}`: one directory, files and directories only (no symlinks), directories first, then by name case-insensitively, at most `MAX_DIRECTORY_ENTRIES`. A `path` resolving outside the checkout is `invalid_request` ("Path traversal not allowed"); a missing directory `not_found`.
- `fs.read {sourceId, cwd, streamId, path, maxBytes?}` → `{size}`, then the file's bytes (the first `maxBytes`) as a binary stream. `path` is checked as for `fs.list`; anything but a file is `not_found` ("File not found"). The node reads with `createReadStream`: a sliced `Bun.file` stream never ends for a large file in Bun 1.3.9.
- `fs.write {sourceId, cwd, path, offset, data, last}` → `{size}`: one chunk of a file (`data` base64 of at most `WRITE_CHUNK_BYTES`, 512 KiB, so it fits a frame). `path` is checked as for `fs.list`, and naming a directory is `invalid_request`. Chunks come in order: offset 0 starts the file (creating its directories), each later chunk must start where the written bytes end (`invalid_request` otherwise), and `last` renames the file into place, replacing one there. Until then its bytes are kept in the node's data directory (`<dataDir>/partial-writes/`, named by a hash of the file's path), so an upload that never finishes leaves nothing in the checkout, not even its directories (they are created with the last chunk). The node clears `partial-writes/` when it starts: an upload cut off by a node restart cannot continue (its next chunk is out of order) and is refused. The move into the checkout is a rename, or a copy when the data directory is on another filesystem. Any other filesystem failure (a path through a file) is `invalid_request`. Uploads (`SourceModel.writeFiles`) send each file this way, one chunk at a time.

On the server, a node runs a process through `RemoteNode.spawn(argv, {sourceId, cwd, env?, binary?})`: it opens the `process.run` stream (bounded by a 10 s timeout on the node accepting it) and returns `{stdout, exited}` (`SpawnedProcess`, `spawn.ts`). Git is a `Git` (`git.ts`) built on an injected `Spawn`, so the git logic stays on the server whichever checkout it reads; the server runs no git of its own (tests use `localGit` from `__tests__/helpers/local-git.ts`). Creating a project without a base branch detects it in the project's first source on its node (`createProject`): with that node unreachable the project is not created (503).

**Which checkout a call works in** is the call's source, resolved where the call enters and handed to `ProjectModel` as a `SourceModel` (`resolveSource` in `models/sources.ts`): an agent tool's or script's calling session (`sessions.source_id`, from `sessionToolScope`); a project HTTP request works in the project's default source until the frontend picks among several (node architecture plan). Tasks have no source: a task's sessions may run in several. The source model (`models/sources.ts`) owns what reads or changes its checkout: its `git` runs on its node (`node.spawn` bound to it), as do `listFiles()` (two `git ls-files` runs merged), `listDirectory(path)` (`fs.list`, 10 s timeout), `workspace(baseBranch)` (files and diffs), `sync(baseBranch)` (fetch and fast-forward) and `listSkills()`. Tasks are not closed from git state: whether a branch looks merged depends on which checkout looks. `listDirectory` turns the node's refusals into the domain errors routes already map (`PathTraversalError` → 400, `FileNotFoundError` → 404). An unreachable node (not connected, no answer, link dropped: `RemoteNode`'s `RpcFailure` with code `"unavailable"`, from a call, a process's start, its stdout or its exit alike) reaches the router as it is, which answers 503 (`isNodeUnavailable` in `errors.ts`); models do not translate it. Task creation, reopen and deletion, task diff stats (`null` while the node is offline), spread, push, rebase, the current branch, a file at a ref (`GitTreeFileSystem`) and the diffs (`Workspace`) all go through the source's `git`. A working-tree diff shows untracked files as Git-native new files by marking them intent-to-add in a temporary copy of the index: `Git` runs that as one `sh -c` script through `process.run` (`WITH_UNTRACKED_AS_INTENT_TO_ADD` in `git.ts`: copy the index, `git add -N` each readable untracked file, run the diff, remove the copy on exit or `TERM`), so the index lives on the node and a diff costs one round trip. Patches cross as binary, byte for byte. Working-tree file content (`WorkingTreeFileSystem`, `/files/content` without a ref) reads through `fs.read` (`openStream`, 10 s timeout) in two steps, as a file at a ref does through git: the first 8 KiB for the size and the MIME type (`detectMimeTypeFromBytes`), then the whole file only if the route sends it (a binary file without `download=1` gets a placeholder). Its refusals become `WorkspaceFileNotFoundError` (404) and `InvalidWorkspacePathError` (400) (`nodeRefusal` in `errors.ts`).

### Tool host

Every node is a tool and file host for the sessions on its sources ([ADR-029](../adr/029-sessions-on-the-server-nodes-host-tools.md)): it serves the operations of Pi's tools (read, write, edit, bash) as a remote `ExecutionEnv` on a source's checkout, and what of a session's environment comes from the checkout. The server's `RemoteExecutionEnv` (`sessions/remote-env.ts`) is what a session's runtime runs Pi's tools on ([session-runtime.md](session-runtime.md) *Assembly*). Node code: `host-env.ts` (`createHostEnv`) and `checkout-environment.ts`, served through `NodeCommands`.

- `env.fs {sourceId, cwd, streamId, op, args}` → Pi's `Result` (`{ok: true, value}` or `{ok: false, error: {code, message, path?}}`, Pi's `FileError` codes), from Pi's own `NodeExecutionEnv` for `cwd` on the node. `op` is one of the operations Pi's tools use: `absolutePath`, `canonicalPath`, `exists`, `fileInfo` (`args: {path}`), `readTextFile`, `readBinaryFile` and `writeFile`. `cwd` only resolves relative paths (`~` is the node's home): nothing is confined to the checkout, as in Pi's local environment. Every call opens a binary stream: a read's value is `{size}` and its bytes follow on the stream; every other answer's stream ends at once, empty. `writeFile`'s `args` are `{path, writeId, offset, data, last}`, `data` base64 of at most `WRITE_CHUNK_BYTES`: a write in one chunk is written at once; a longer one is kept under its `writeId` in the node's data directory (`partial-writes/`, as `fs.write`'s) until its last chunk writes the whole file with Pi's `writeFile`. Every call is safe to send again: a chunk replaces what was kept from its offset, and a last chunk sent again after its write is answered as written (the node remembers the last 1024 writes). A chunk past what was kept is `invalid_request`.
- `env.exec {sourceId, cwd, streamId, execId, command, options: {cwd?, env?, inheritEnv?, timeout?, capture?}}` → `{}`, and a text stream of the command's **output records** (NDJSON, `execRecord`): `{update}`, Pi's `ShellOutputUpdate`s in order, then `{exit}`, Pi's `exec` result (`{ok: true, value: {exitCode, truncation, spillPath?, lastLineBytes?}}` or `{ok: false, error: {code, message}}`), the last line. The node runs it with Pi's `NodeExecutionEnv.exec`: its shell, environment merge (`env` over the node's; bash's `PI_SESSION_ID`, `PI_PROVIDER`, `PI_MODEL`, `PI_REASONING_LEVEL` come in `env`), timeout, bounded capture (`capture.limits.maxBytes` at most `MAX_EXEC_VIEW_BYTES`) and spill file (on the node, where `read` finds it). `execId` is the server's; one the node already has is `invalid_request`.
- **Commands outlive their stream.** The node keeps each command under its ID with the last `EXEC_TAIL_BYTES` (1 MiB) of its output records and the output's current view. A command with no stream open (its link dropped, or its output was all sent) is kept for `EXEC_GRACE_MS` (60 s; `startNode({execGraceMs})`); then a running one is killed and either is forgotten. `env.execAttach {streamId, execId, offset}` → `{offset, view?}` reopens its output stream from `offset` (the end of the last record the server took): from the same offset, or, when that output is no longer kept, from where the records end, with the current view in `view` (the server replaces its view with it, so nothing the tool would show is lost). Attaching stops any stream still open for it. An offset that is not the start of a record is `invalid_request`; an unknown `execId` (the node restarted, or forgot it) is `not_found`.
- `env.execKill {execId}` → `{killed}` (whether it was running) kills the command's process tree, as aborting Pi's `exec` does; its stream still ends with its exit (`aborted`). Unknown: `not_found`. Shutting the node down kills every command it runs.
- `checkout.environment {sourceId, cwd}` → `{contextFiles: [{path, content}], skills: [{name, description, path, content, disableModelInvocation}], docs: {dir, devDocs}}`: the AGENTS.md files of the checkout and its ancestors (root first) and the checkout's skills (`.agents/skills`, with SKILL.md's content), discovered on the node (a directory with a `SKILL.md` is a skill, a skill without a description is not listed, the first of a name wins), never the node's own `~/.agents`, at most `MAX_LISTED_SKILLS`; and this node's REINS docs (`REINS_DOCS_DIR`, else the `docs/` of the checkout it runs from, which the environment prompt names; `devDocs`: whether `<dir>/dev` exists). A missing checkout is `not_found`; a result over `MAX_CHECKOUT_ENVIRONMENT_BYTES` (12 MiB as JSON) `invalid_request`.

**On the server**, `RemoteExecutionEnv` (`sessions/remote-env.ts`) is Pi's `ExecutionEnv` over these. It holds no hub: each call asks `nodeFor(signal)` for the session's node, from the handler load serving now (it may wait for one). A file operation that fails `unavailable` (node unreachable, the outcome unknown, or the node's retryable `unavailable` refusal) is sent again with a backoff for up to `ENV_RETRY_WINDOW_MS` (30 s); any other failure is a `FileError` `unknown`. `exec` sends `env.exec` again only while it was certainly not run (not sent, or refused `unavailable` by a node pausing to restart, *Pausing a node*), for up to `EXEC_START_WINDOW_MS` (90 s, longer than a reload's drain); when its stream drops (or its outcome was unknown) it calls `env.execAttach` from the last record it took, on whichever link the node has then, for up to `EXEC_REATTACH_WINDOW_MS` (60 s, the node's grace period), feeding the same `onUpdate`. A node that answers `not_found` (it restarted) makes the call fail `unknown` ("The command's outcome is unknown"). Aborting the call sends `env.execKill` and returns `aborted` once the command's exit arrives (at once, if the kill cannot reach the node); `cleanup` kills the commands it still runs. Operations Pi's tools do not use (`readTextLines`, `appendFile`, `renameFile`, `listDir`, `createDir`, `remove`, `createTempDir`, `createTempFile`) answer `not_supported`; `joinPath` joins POSIX paths on the server. Tested against Pi's local environment in `__tests__/sessions/remote-env.test.ts`.


## Node hub (server side)

One hub per handler load (`nodes/node-hub.ts`, built by `createServerState` in `state.ts`, which each handler load's `start` (`server.ts`) calls; closed on a dev reload or process exit, after which the node redials the next load's hub; tests create one with the `createServerState()` helper). It is `state.nodes` (the `NodeHub` interface in `state.ts`) and owns the node links by node ID. It calls product code directly, through one `Models` built from the state it belongs to: at a connection's challenge the node's key (`NodeModel.publicKey`), at its hello whether the node may connect (`NodeModel.assertMayConnect`) and which build it must run (`offerUpdate`, ADR-025), and `Nodes.publish` when a node gets or loses its link. A node calls nothing on the server but the frames of the streams the server opened (`stream.data`, `stream.end`; `nodes/server-peer.ts` serves them). Interface: `accept(socket, options?)`, `get(nodeId)` (a `RemoteNode`: `connected`, `build`, `request(method, input, options)` for any request-now node method, `openStream(method, input, options)`, `spawn(argv, options)`; see node-transport.md *5. Hub and node API*), `disconnect(nodeId)`, `close()`. Callers of `request` choose their own timeout. The stream buffer cap is a hub option (`NodeHubOptions`). A session runtime reaches the hub of the load serving now, never the one that built it (`LoadServices.node`, session-runtime.md *Reaching the load serving now*).

**Default source:** a new session is placed on the source its caller names (child and task sessions inherit the caller's), else on its project's **default source: the project's first (lowest-ID) source on a node that was not removed** (`defaultSource` in `node-store.ts`, `resolveSource` in `models/sources.ts`); a project whose every source is on a removed node has none ("Project has no source", as for a project with no source). A source named explicitly is resolved even on a removed node (a session's own source: so it can be read and moved), and work for it is refused there (*Pairing and authentication*, Removal). A project has no path of its own: paths live on sources, and a node and path belong to one project's source (a unique index; `DuplicateSourceError`, 409: "That path is already a source of another project"). A project's first source is created with it, on the node its creator chose (`createProject` in `models/projects.ts`, through `createSource` in `models/sources.ts`; the browser form's node selector, or for a `projects.create` script the calling session's node unless it names one), after the path is checked on that node (`fs.list` of `.`: a missing directory refuses the project, an unreachable node is a 503, and the project is not kept either way). `POST /api/projects/:id/sources {nodeId, path}` adds a source of an existing project on a node (the project form's Add source, `reins source add`), checked the same way (`createSource`: 201 with the source's view; 400 for an unknown node, a relative path or one that is not a directory there; 409 for a path another project's source has, or a second source of the project on that node ("The project already has a source on <node>"): a session moved to a node works in its project's source there, so a project has at most one per node; 503 when the node is offline); `PATCH /api/projects/:id/sources/:sourceId` moves a source's path, checked the same way (`moveSource`); `GET /api/projects/:id/sources` lists them for the edit form. Selection is policy, not a connectivity check: a session placed on a node that is not connected is created, takes prompts, and its run waits for the node.

**Nodes and sources:** `nodes` identifies execution hosts; `sources` binds a project to a host-local path. Sessions persist `source_id` beside `project_id` (triggers enforce agreement). **A session's tools run on its source's node**; that is the whole of placement. They run in the session's bound source path, not the project's current path.

**A node's sources are the server's sources on it** (*Checkout operations*). The node's view (`NodeView.sources`, `GET /api/nodes` and `node_updated`) lists them by path (`NodeSourceView`: `{path, project: {id, name, sourceId}}`), so they are known while it is offline; Settings → Nodes shows how many there are, and `reins source list` lists them. Creating and moving a source and deleting a project publish the nodes concerned (`Nodes.publish`); renaming a project does not, so a node's view shows the old name until its next update.

## Moving a session

A session's tools run on its source's node, so moving it is re-pointing its source (`sessions/session-ownership.ts`). `POST /api/sessions/:sessionId/move {nodeId}` checks the session is idle (`sessionActivity`; otherwise 409) and, in one transaction, sets `source_id` to the target node's source for the project (409 when there is none; 404 for an unknown session). Moving to the node it is on changes nothing. Its runtime is on the server and everything is in storage, so nothing is left behind: `Sessions.move` closes its live runtime (bound to the source it left), and its next submission opens it on the target's source. The response is the session's placement view; the move broadcasts `session_updated`. `GET /api/sessions/:sessionId/move-targets` lists every node not removed as `{nodeId, name, connected, eligible, reason?}`, eligible first, each group by name; `reason` is `"current"` or `"no_source"`. A session on a removed node moves like any other, to a node holding a source of its project (its run, if the server saw one in progress, was aborted or settled as interrupted at the removal, so it is idle); until then it takes no work (*Pairing and authentication*, Removal).

Session views expose `placement: {available, removed, nodeId, nodeName, path}`: the node of the session's source, whether it is connected, whether it was removed, and the checkout's path. A removal does not broadcast `session_updated` for the node's sessions: a browser's cached view marks the node removed from the session's next update, or a reload.

**Session deletion.** Deleting a task or a project deletes its sessions' rows (and their storage) on the server, as task generation deletes its background session (session-runtime.md *Session kinds*); their live runtimes are closed first, aborting their runs (`closeSessionRuntimes` in `session-runtime/live.ts`, which closes again any a child's report reopened). The node holds nothing for a session.

## Node API

`@reins/node/node` is the node's in-process API; `connectNode` (`@reins/node/node-connection`) links it to its server over a transport and serves it there, and nothing else calls it outside tests. Tests that script a node pass a stand-in `Node` (`scriptedNode`, `@reins/node/testing`) to the same `connectNode`.

- **Lifecycle.** `startNode({reload?, execGraceMs?, execTailBytes?, dataDir?})` starts a new, independent node (its tool host's commands and partial writes are its own; no module globals) and takes no in-process server dependency; it clears what a previous run left in `partial-writes/`. `pause({timeoutMs, force})` waits for the tool host's commands (*Pausing a node*). `shutdown()` is the one teardown: refuses new commands (`Node stopped`) and kills the commands the tool host still runs (they run in process groups of their own); pause and stop the connection before it.
- **Commands** (`NodeCommands`). One method per server→node wire method, taking its params (without `epoch`) and returning its wire result: `runProcess` returns the source of the stream `process.run` opens, `listDirectory → {entries}`, `readFile → {size, source}`, `writeFile → {size}` (*Checkout operations*), `reload → {scheduled}` (*Reloading a node*), and the tool host's: `envFs → {result, source}` (the stream's bytes), `envExec` → the source of its output stream, `envExecAttach → {result, source}`, `envExecKill → {killed}`, `checkoutEnvironment` → the checkout's environment (*Tool host*). `connectNode` serves each and advertises it as a capability, with `stream.cancel`.
- **Errors.** A definite rejection throws `NodeRejection` carrying a `NodeError`: `invalid_request` (a path escaping its checkout, a program not on `PATH`, a chunk out of order, an `execId` already known, an environment too large), `not_found` (a missing checkout or file, an unknown `execId`), `unavailable` (retryable: a new `env.exec` while the node pauses; a reload with nothing to restart the node). Any other exception is sent as `internal`, non-retryable.

## When a node goes away

Sessions are on the server, so a node going away interrupts only what runs on it: the commands of its tool host. Everything else waits for it, a running tool call for a bounded time.

- **Offline or not yet connected:** submissions are admitted; a run waits for the node at its first assistant request (preparing its checkout and environment, a pause point) and at each tool call (`RemoteExecutionEnv`: file operations retried for 30 s, a command sent again while certainly not run for 90 s, after which the tool call fails). Request-now calls of routes and git (`fs.*`, `process.run`, skills) fail at once with `unavailable` (503; skills answer the server's own, `available: false`).
- **A dropped link** (a server handler reload, the network): the node redials; a short call is sent again; a command keeps running on the node, which keeps it and its output's tail for `EXEC_GRACE_MS` (60 s), and the server picks it up again by its ID and output offset (`env.execAttach`, *Tool host*).
- **A node restart** (a reload, an update, SIGTERM, a crash): a command it lost, and one killed by `force` or at the end of a drain, comes back "outcome unknown". A reload or SIGTERM first drains its commands (*Pausing a node*).
- **Removed** (*Pairing and authentication*, Removal): its sessions refuse work, their live runtimes are closed (aborting their runs; tool calls waiting for it fail) and a run in progress without a live runtime is settled as interrupted.

How a server restart pauses, suspends and resumes runs is in [session-runtime.md](session-runtime.md) *Recovery*.
