# Internal node seam

`packages/node/src/contract.ts` (`@reins/node/contract`) is the server's durable command vocabulary: the commands `node_command_outbox` stores (provision, prompt, steer, setModel, abort, pending resume, hydrate) and their typed results, plus the schemas both sides share (session configuration, prompt content, node error codes). The node does not dispatch on it: it serves each command through its own wire method and `Node` method (see *Node API*). It imports no server, Pi or browser modules; Oxlint restricts the contract's imports to `zod` and backend imports to declared node package exports. Future daemon implementation belongs elsewhere in `packages/node/src/`, not in this export. `deliveryPolicy()` classifies provision, prompt, steer and setModel as `submit-work`, matching server outbox admission; abort and pending resume remain immediate controls. The classifier does not itself deliver commands. The semantic contract alone does not guarantee delivery or offline execution. Future read-only workspace/git commands should use `request-now` and return unavailable when offline. `node-command-store.ts` owns SQLite outbox rows and transitions; `models/node-command-projection.ts` owns submission/projection and a wake hint; `models/node-command-dispatcher.ts` resolves the session's current source and owns the sole delivery path. Session creation atomically stores the session and provision command, then signals a dedicated dispatcher after commit. The signal carries no command payload; startup, node availability/reconnect wake, and a 30-second poll rescan SQLite. The dispatcher resolves the session's current source before claim and uses the internal adapter to admit provisioning without constructing Pi. Creation returns a persisted ID and its provision command ID without awaiting the dispatcher or returning a live runtime; the session is `provisioning` (see *Session placement*). Browser HTTP creation returns a session view immediately; validated prompt/steer and scripting child starts persist their input without waiting for Pi admission (unsupported remote sources still reject input). The node adapter lazily opens/reopens Pi when an addressed input or explicit pending resume arrives. Session views distinguish placement (`placement_status`) from runtime activity; negative admission and delivery exceptions are `failed`; failures are notified and removed rather than automatically retried. The start signal is a hint; the periodic scan recovers missed hints. Process startup deletes interrupted dispatches (their outcome is unknown and they are not replayed), marking an interrupted provision `provision_failed` and returning an interrupted move's session to its resting state with the reason (see *Session placement*). Handler hot reload must not reinterpret previous in-flight work. Live delivery failures are notified and removed. `stop()` clears the timer. Prompt and steer now persist validated input in `node_command_outbox` before acknowledgement, keyed uniquely by `(session_id, command_json.clientId)` via a SQLite expression index (the clientId travels only inside the command payload); a replay with the same operation/content/source returns the prior admission acknowledgement (once the input was admitted its command is deleted, and the replay is recognized from the replica's `reinsInput` and queues nothing). A different payload with that key is rejected while the input is pending. The dispatcher scans `node_command_outbox` in insertion order across all persisted operations and delivers **per session**: each session with deliverable work gets one delivery chain that sends its queued commands strictly in outbox order, one at a time (re-reading the session's current source before each), while different sessions' chains run concurrently, so a command waiting on its admission timeout (up to 120s for input) or a stalled session never delays another session. At most `MAX_CONCURRENT_SESSIONS` (16; injectable via `new NodeCommandDispatcher(state, { maxConcurrentSessions })`) chains run at once, bounding the node requests and timers a startup backlog can open; sessions beyond the cap wait for a free slot in outbox order. Queued and dispatching predecessors order work only within their session; a queued offline provision cannot stall unrelated sessions. **No double delivery:** `claimCommand` is one atomic `UPDATE` that moves a row from `queued` to `dispatching` only when no earlier row of its session is `queued` or `dispatching`, so a session never has two commands in flight regardless of which dispatcher instance (or process) claims; the in-memory chain map only avoids redundant work. A wake is a hint: a wake for a session whose chain is running, or a scan that hits the cap, rescans SQLite when a chain ends, picking up commands enqueued meanwhile. **Deferral:** a command requeued by `DeliveryDeferred` ends its session's chain and is skipped by every scan until the next external wake (a submission/availability wake, `drain()`, `start()` or the 30-second poll), so it neither spins nor holds a slot; other sessions keep delivering. **Lifecycle:** `stop()` (handler uninstall) clears the poll and stops the instance for good: no new chain or next command starts, while commands already being delivered finish, settle and notify; `dispatcherFor`/`dispatcherForInput` then create a fresh instance for the state. During a hot reload the old and new module instances share the outbox; the claim keeps them from overlapping within a session, and a waiter on one instance for work settled by the other resolves at that instance's next scan. `drain()` wakes and resolves once no chain is running. Future remote nodes: chains stay per session, but a per-node cap or fairness may be needed so one slow node cannot occupy every slot. Failed commands are removed after notification so later queued work can proceed. Provision must be admitted before its inputs; the internal node adapter interprets the command and owns readiness, lazy runtime opening and Pi admission; the transport claims and settles the command without knowing its operation. There is no input-only scan or claim lifecycle. The dispatcher scans, checks predecessor/source availability and sends one validated `NodeCommand` through the selected adapter. `node-command-transport.ts` alone claims and settles generic delivery, recording explicit negative results and exceptions as failed; stored commands are parsed strictly (`getWork`; every writer stores a `nodeCommand` payload), and one that does not parse fails its delivery like any other exception, never sent (a provision so failed makes its session `provision_failed`). Settled commands are deleted (the outbox is a queue), so no session state is read from them. The dispatcher fences inputs behind provision, while `@reins/node/node` interprets node-owned commands and lazily assembles/reopens Pi with node-local canonical storage and injected product policy; server-side `node-command-notifications.ts` handles scheduling/input-failure notifications after delivery. The adapter does not read the outbox or broadcast product events. Legacy persisted open/reopen is unsupported. The node keeps no per-command receipts: a replayed provision, prompt, steer, setModel or hydrate converges on its own state (see *Replay idempotency*). Provision scheduling changes notify through `Sessions.notifyScheduling()`, not a dispatcher-level broadcast. Eventual input failures use `node-command-notifications.ts`: only the currently connected submitting WS client registered for `(sessionId, clientId)` receives the existing error shape. Disconnected clients are not notified; failed commands are deleted after settlement, with no replay-to-UI mechanism yet. Scripting sends and child reports return on enqueue rather than Pi admission; explicit wait observes settlement (for node-owned sessions from server projections; see *Server reads projections only*). Process startup discards interrupted dispatches rather than replaying them. Explicit abort and resume remain immediate controls rather than queued behind input. Errors after enqueue surface asynchronously on the existing WS error path, not as a retraction of the acknowledgement. Queued inputs survive process loss and are recovered by the shared dispatcher scan; remote execution remains unsupported, and the only automatic retry is the requeue of submitted work whose delivery outcome is unknown on a live server (see *Session commands on the wire*). Provision establishes source admission and stores the session's frozen configuration (see *Session configuration*); the node validates a provisioned model against its registry when Pi creates the lane, so an unknown configured model fails the provision (the session is `provision_failed` and shows "Provisioning failed: …"). The outbox stores a session ID and operation, not a source. Explicit node rejections and delivery exceptions are failures and never retried; a transport outcome that is unknown (timeout, lost link) requeues submitted work, while dispatches interrupted by a server restart are deleted at startup and not replayed. Queued commands are retained when no adapter is available; the dispatcher polls for eligible commands. No external node adapter is implemented. The stored commands use a single durable `session.provision` carrying the session's frozen `configuration` (no open/reopen commands), a queued `session.setModel`, the queued move `session.hydrate` (see *Session relocation*), attachment references and `sourceSessionId` (string or null, always present); they are **not** a network protocol: no handshake, framing, correlation, ordering, delivery guarantee or serialized runtime event payload is promised. A stored command whose schema no longer parses is failed, not sent; the wire negotiates its own version in `node.hello`. For existing installations from the in-progress internal-node spike, reconcile schema changes on the affected development database before using the new code; the fresh schema adds a provision index in `030_node_command_outbox` and receipt tables in `032_node_replica_receipts` (dropped by `035_node_session_watermarks`); `032` also added `sessions.storage_owner`, which `037_drop_session_storage_owner` drops (placement is `placement_status` alone). Delivery failures are removed after notification, never automatically retried. Schema changes take effect only when the backend starts with a new database connection.

**Execution target:** the server never executes sessions. `runtimes/execution-target.ts` is a leaf seam: `SessionExecutionTarget.send(command, commandId?)` delivers one semantic command, with the outbox row ID (never sent to the node; required for submitted work — provision, prompt, steer, setModel, hydrate — which may throw `DeliveryDeferred`; a replay converges on node state, not on the ID). `installRuntimeHooks` registers the one target, `runtimes/internal-node-execution.ts` (every command over the JSON-RPC link to the session's node), and `executionTargetFor(state)` returns it. For a session at rest on the server (`placement_status = 'server'`) the target answers abort with `aborted: false` (nothing runs) and hydrates the session onto its node before any other command (normally a move is already queued ahead of the work; this covers work behind a move a restart interrupted; see *Session relocation*). The dispatcher and `executeSessionCommand` call only the resolver, so they import neither `SessionManager` nor the target implementation. Callers still validate the current source themselves. The interface exposes no live runtime and no `open`; the server holds none. Placement is the session's `placement_status` alone (`waitUntilProvisioned`, `SessionInstance.wait`, fencing, session views; see *Session placement*).

**Server reads projections only:** no live node runtime crosses to the server. `Node` (`@reins/node/node`) exposes one method per session command, `attach` and `shutdown` (see *Node API*); the in-process runtime map is reachable solely through `nodeRuntimesForTesting(node)` (`has`/`open`/`close`), a clearly marked test seam that production code must not import. Server code reads a node-owned session's state from its own projections, so it works unchanged with the node in another process:

- *Activity* (`models/node-session-activity.ts`, the one helper): `nodeSessionActivity(row)` is `running` when `activity_state` is `running` (set/cleared by the durable `session.started`/`session.settled` reports), `queued` when prompt/steer input in `node_command_outbox` is still `queued`/`dispatching` (so a run whose input the node has not admitted, or whose `started` has not arrived, is not idle), else `idle`. `activeNodeSessionIds()` applies the same rule across sessions, including sessions whose input waits behind their move onto a node. Reading activity writes nothing: a `running` that sessions at rest on the server kept from when the server still ran sessions was finished by migration `038_clear_stale_server_running`. Edge cases: an input already admitted (its command deleted from the outbox) whose `started` is still in flight reads `idle` for that gap; failed and interrupted inputs are deleted, so not pending; provision alone is not activity; a run that never settles because the node died mid-run stays `running` (session lists no longer reconcile node `running` against a runtime). Used by session views (`pendingOperation` is shown only when idle), task deletion (any non-idle node session blocks it) and `/api/health` (`activeSessions` = active sessions; `streaming` if any).
- *Wait* (`SessionInstance.wait`): a session at rest on the server runs nowhere (any input for it queued a move, making it `moving`): its transcript result is returned at once. For every other session it polls projections every 10ms. It fails at once with "Session provisioning failed: …" when the session is `provision_failed`; otherwise it tracks every input it sees pending in the outbox (`queued`/`dispatching`) and resolves once none is still pending, the session is not `running`, and every tracked input the node admitted is covered by a settlement. **Admission is proven by the replica, not by the outbox** (settled commands are deleted): an admitted prompt/steer is a `reinsInput` in the server replica whose `reinsId` is the command's clientId (`replicaInput` in `node-replica.ts`), either a transcript entry or, for a steer Pi still holds in its queue, Pi's pending entry value (`pi.pending.entry`), which awaits a run. The node delivers that commit before it answers the command (Pi's commit awaits the node outbox drain), so the replica normally holds the input by the time its command settles. A transcript entry is covered once the latest settlement was applied after it: each settlement records the replica's `harness_next_seq` (`settlement_next_seq` in `node_session_watermarks`, beside `settlement_count` and the latest status/error), and the node delivers a run's commits before its settlement, so an entry whose seq is below it was committed before that run settled. A failed input never reaches the replica (and produces a failure notification): it expects no run. The result is `transcriptResult` over the replica transcript with the latest settlement's status/error as the terminal outcome (`completed`/`failed`/`cancelled`, or `idle` with no reply), `timeout` at the deadline, and an `AbortSignal` rejects with `AbortError`. Limits: an input admitted before the wait began whose `started` has not arrived reads as settled; an admitted input whose commit the node has not delivered yet (held behind an earlier undeliverable or unready row of its outbox) reads as failed; an input admitted while an earlier run was still active can be covered by that run's settlement.
- *Abort* (`ws.ts`): a session on a node always forwards `session.abort` (no live-runtime lookup) and acknowledges; the node answers `{aborted: false}` when nothing is live. A session at rest on the server has nothing running: abort answers "Session not active".

The node runs in its own process (see *Process model* below); the server never calls `startNode()`, and `handler.install()` only starts the dispatcher, which defers submitted work until a node connection negotiates. `runtimes/internal-node.ts` is the server adapter for the internal node's connection: it serves node→server calls (below), credentials included (see *Credentials*), and injects nothing into the node; the node process (`main.ts`) opens and owns its SQLite connection. It resolves and passes the source/path/created-at/parent binding from product rows. The node itself never imports backend state or tables. `openNodeDb(path)` (`@reins/node/storage`) opens node storage and runs the node-owned versioned SQLite migrations; `startNode(db)` starts a new node over that open, migrated database (see *Node API*), and binding never runs schema setup. The node's own `migrations` table records `001_canonical_node_storage` (canonical lane/binding/outbox/receipts, including the provisioned task snapshot on the session binding row), `002_node_attachments` (image cache), `003_session_outbox` (moves pending commits into the ordered per-session outbox shared with lifecycle reports), `004_session_task` (task snapshot), `005_attachment_uploads` (rebuilds the outbox, keeping rows, IDs and its AUTOINCREMENT sequence, so it can hold `attachment` upload rows) `006_node_attachment_content` (content index for reusing cached attachments) and `007_drop_admission_receipts` (drops the per-command `admission_receipts` table; see *Replay idempotency*). New versions append named migrations; startup applies missing SQL and ledger inserts transactionally without reconstructing or comparing the full schema. Nonempty DBs without the ledger (including the earlier `user_version` experiment) and unknown migration names fail closed. Migration errors throw synchronously during node initialization before commands are accepted; no reset or automatic deletion occurs. Migrations are atomic, node-local, restart-required and do not import backend migrations. Test against in-memory or temporary files, never the user's default DB; back up node storage before deployment because discarding an old node DB makes node-owned sessions unresumable (server history/images remain readable). See [node-migrations.md](node-migrations.md) for the append-only migration workflow. The node's command methods bind and check provisioned sessions, open node canonical storage with ordered outbox delivery, and execute addressed commands. The dispatcher retains server scheduling, source lookup, claim/settle, failure notification and UI projection. `runtimes/node-execution.ts` routes immediate controls through the same target. **Loopback JSON-RPC commands:** the dispatcher and immediate controls send every node-owned command (wire methods and capabilities named after the op; see *Session commands on the wire*) through `sendInternal()` in `runtimes/internal-node.ts`, which pairs `createServerTransport` (`node-transport/server-peer.ts`) with the node half `connectNode()` (`@reins/node/node-connection`) over `createLoopbackPair()` (`@reins/node/protocol`: string frames, microtask delivery, close seen by both ends, queued frames dropped). The same hello/ready negotiation, zod wire schemas and epoch checks as a remote node apply, so values that do not survive JSON fail as `-32602` instead of leaking in-process. The wire params carry the stored `configuration` (the same `sessionConfiguration` schema) beside the binding, so a replay (which re-sends the stored command) carries the same configuration; node rejections (`NodeRejection`) return application error `-32000` whose JSON-RPC `error.data` is the NodeResult error `{code, message, retryable}` (`nodeError` in `@reins/node/protocol`); exceptions thrown by node code use the same code with `{code: "internal", retryable: false}`. The peer validates `error.data` against a per-call schema, bounds it to 8 KiB and error messages to 2048 chars (senders truncate messages and replace oversized data with `-32603`), and treats malformed or oversized error responses as a non-deferred `-32603` that closes the connection. `node-transport/commands.ts` maps the wire outcome to a `NodeResult`, so the dispatcher records the node's own code (e.g. `invalid_request`) and never sees RPC codes; other protocol failures (e.g. `-32602`) are terminal `internal` failures. For submitted work, connection loss, send failure, failed negotiation, call timeout (outcome unknown, late reply dropped), busy (`-32002`) or stale epoch (`-32003`) throw `DeliveryDeferred`: `deliverCommand` returns the row to `queued` (never `failed`) and the dispatcher replays it on the next wake/poll, safe because every submitted command converges on its own node state (see *Replay idempotency*). Immediate controls return `unavailable` to their caller instead. `stopInternalNode()` (test helper) closes the link and shuts its node down; each handler install creates its own link (handlers are per connection, never registered on the shared `Node`), and a closed link is recreated on the next command. The loopback link has no negotiation timeout or heartbeat; the local socket link has both (see *Transport*). No backend production code calls a `Node` method directly. Sessions at rest on the server are hydrated onto their node on next use (*Session relocation*). The server applies node committed writes and lifecycle reports idempotently by per-session watermarks in `node-replica.ts`; `runtimes/internal-node.ts` serves `session.committed` into it and supplies product policy; the node process passes its own database to `startNode(db)`. The node deletes outbox batches only after the server acknowledges them. Pi storage SQL is shared in `@reins/node/pi-storage`; on the server nothing writes Pi tables except replica application (and hydrates only read them).

**Intermediate seam:** `packages/node/src/runtime/build.ts` constructs Pi for sessions from node-local storage/resources/native tools and owns the runtime map; the server builds no session runtime. The node receives its session configuration (model, thinking level, task) with `session.provision` (see *Session configuration* below), renders the system prompt and checks out the task branch itself, so opening a runtime makes no server call; provider credentials are served over the link (see *Credentials* below; *Agent tools* for tools); browser events cross the link as `session.event` and run lifecycle as durable `session.started`/`session.settled` reports (below). For node-owned sessions, the node fetches attachment bytes with `attachment.fetch` (below); the node verifies their checksum and declared MIME/size once when fetched and materializes them in its SQLite attachment cache (`node_attachments`) before prompt admission, then hydrates provider input synchronously from cached bytes. The same table holds node-created tool-result images, whose rows are the only copy until their outbox upload is acknowledged, so the cache must not be evicted while an upload row names it (nothing evicts it today; rows go only with the session). Opening a runtime does not fetch historical image bytes; an uncached historical reference becomes a provider placeholder. Native Pi drive/reopen code now lives in `@reins/node/pi-runtime`; `@reins/node/runtime` creates Pi model/resource context with an injected credential store (on the node its `RemoteCredentialStore`; on the server, for its model catalog, utility asks and OAuth refresh, the server's `DbCredentialStore`), `@reins/node/host-tools` creates cwd-scoped native tools and execution environment, and `@reins/node/resources` / `@reins/node/prompt` own local discovery and slash expansion. Slash expansion now uses the session's bound source cwd rather than the project's current path. The node builder takes the immutable node session binding (created-at, parent ID and cwd) and canonical storage directly. The node verifies each command's binding against the binding stored at provision; the server resolves that binding from product rows on every send. `startNode(db)` takes no in-process server dependency. The node process is still the server process, so agent file/git work and the open-time branch checkout share its checkout and unsupported remote sources remain queued or fail closed. Replays of submitted commands converge on node state, so an unknown delivery outcome is requeued (see *Replay idempotency*). If a session binding is missing from node storage, the node returns an explicit `not_found` with "This session's node data is missing. Start a new session." before Pi admission. For submitted work (prompt, steer, setModel) the server then re-hydrates the session onto that node from its replica and sends the command once more (see *Session relocation*); only if that fails is the input marked `failed` and its submitting WS client notified (the frontend refreshes authoritative activity after the error so optimistic streaming ends). Immediate controls (abort, resumePending) return `not_found` to their caller. A binding mismatch still throws and is reported as a failure. No remote daemon or network transport exists. See `docs/plans/node-architecture.md` for ownership and recovery limits.

**Node→server calls:** the node reports commits, fetches attachment bytes and reads credentials over the same JSON-RPC link, as a remote node would; `startNode(db)` takes only its database. Method names live in `methods` (`@reins/node/protocol`; see *Wire method naming* below): `session.committed` `{epoch, sessionId, startSeq, writesJson}` → `{acknowledged: true}` is a durable report the node replays until acknowledged and the server applies by sequence watermark (see *Replay idempotency*). `writesJson` crosses as a string, byte-for-byte, because a replay of the last applied batch is compared by the hash of its exact string (a different string for that `startSeq` is rejected as divergence and stays pending). `attachment.fetch` `{epoch, sessionId, attachmentId, offset}` → `{attachment: {data, mimeType, byteSize, sha256, filename?, width?, height?} | null}` returns base64 of raw bytes `[offset, offset + 512 KiB)` so a 10 MiB upload fits 1 MiB frames; the node loops over offsets, requires consistent metadata and exact chunk lengths, then verifies total size and sha256 before caching. `attachment.store` `{epoch, sessionId, attachmentId, mimeType, sha256, byteSize, filename?, width?, height?, offset, data}` → `{stored: true} | {nextOffset}` is the reverse direction, for node-created image bytes (tool results; see *Images* under *Session events*). **The node assigns `attachmentId`** (`att_<uuid>`; the schema allows `[A-Za-z0-9_.-]`, 1–128 chars) when it references the image, and the node delivers the upload from its session outbox (below), so it is a durable report like `session.committed`, replayed until acknowledged. `data` is base64 of raw bytes `[offset, offset + 512 KiB)`, symmetric with fetch, so it fits capped frames. On every chunk the server first looks up the session's attachment under that ID with its data held: the same sha256, MIME type and size answers `{stored: true}` at once without buffering (a replay after a lost reply is idempotent), and different content under that ID is rejected (`-32000` "Attachment <id> is already stored with different content": divergence, left pending on the node like a divergent commit). Otherwise it keeps one partial upload per connection keyed by `(sessionId, attachmentId)` (at most 8; the oldest is evicted; cleared on close) holding the contiguous prefix received; a chunk whose offset is not that prefix length gets `{nextOffset: received}` (so a retried chunk is not appended twice, and an evicted or unknown upload restarts at 0), every chunk must be exactly `min(512 KiB, byteSize - offset)` bytes, and changed metadata for the key rejects. After the last chunk the server verifies the sha256, then stores through the session attachment store under exactly the node's ID (the upload MIME allowlist and 10 MiB limit apply; an ID another session holds rejects with "Attachment ID already in use"; a pruned row with the same content has its bytes restored). Identical bytes already held under another ID are stored again under the new ID, never remapped, so every transcript reference resolves as written; backend migration `034_session_attachment_node_ids` replaced the per-session `(sha256, mime_type)` uniqueness with an index for this (server-assigned uploads still dedupe by content). Mismatches and store rejections are `-32000`, `byteSize` over 10 MiB is `-32602`. Each chunk call has the 30s timeout; the node loops from `nextOffset`, bounded to twice the chunk count plus one. Frames: `createRpcPeer(socket, handlers, { maxFrameBytes })` caps each frame (default 1 MiB, `DEFAULT_MAX_FRAME_BYTES`); `createServerTransport` and `connectNode` pass the option through, the internal loopback link uses `Infinity`, so a committed batch of any size crosses in one frame, and the local socket link uses 64 MiB (see *Transport*). An outbound frame over the cap is never sent: that one call rejects with `FRAME_TOO_LARGE` (`-32004`, a local code, terminal: the dispatcher records a failure rather than requeueing) and the connection stays open. `writesJson` has no size limit; a remote (capped) transport will need chunked commits, since an oversized batch would otherwise never deliver and would block that session's later outbox rows, including lifecycle reports. Attachments ≤ 10 MiB (`MAX_ATTACHMENT_BYTES`, the upload limit; larger rejects with an explicit `-32000`). The upload MIME allowlist (`ATTACHMENT_IMAGE_MIME_TYPES`) and size limit are exported by `@reins/node/protocol` and used by both the node and the server attachment store. These methods are base protocol v1, not capabilities: the server accepts them only after `node.hello` and only with the epoch it issued (`-32003` otherwise). Handlers are injected into `createServerTransport(socket, handlers)`; `internal-node.ts` supplies them with the placement check (`nodeOwnsSession`/`nodeMayReadSession`), so the transport imports no product stores. Server application errors use `-32000` with a message only. Node side: `connectNode()` attaches its connection to the `Node` immediately (calls await negotiation) and detaches on close or failed negotiation; the newest attached connection serves calls, and attaching replays every session's pending outbox. With no attached connection, calls reject: commits, attachment uploads and lifecycle reports stay pending, and a prompt/steer needing an uncached attachment returns `unavailable`/retryable (explicit server rejections return `invalid_request`). `internalNodeFor()` recreates a closed link so server calls do not depend on a provision. Calls time out after 30s with unknown outcome; all are safe to retry.

## Process model

The server and the internal node are separate processes that meet only on the local node socket (*Transport*).

- **Server-only** (`bun run start:server`, `packages/backend/src/index.ts`): opens the product database under `REINS_DATA_DIR`, listens on HTTP and on the node socket. It never starts a node or opens node SQLite.
- **Node-only** (`bun run start:node`, `packages/node/src/main.ts`): opens only node storage (`~/.reins/node/storage.db`), starts the node and dials the socket. It never imports server code (`reins/node-implementation-isolation`) or opens the product database. Logs go to stdout/stderr with a `[node]` prefix. A node migration failure throws at startup and the process exits nonzero. `REINS_NODE_TEST_FAUX_PROVIDER` is a **test-only** hook (`src/testing/faux-provider.ts`) that registers a scripted faux model so process-level tests can drive runs in a child process; never set it in production.
- **Combined** (`bun run start`, `bun run dev`; `packages/backend/src/supervisor.ts start|dev`): spawns the server (in dev, `packages/backend/dev.ts` with handler hot reload) and the node (plus the frontend watchers in dev). Both inherit the environment, so they agree on `REINS_NODE_SOCKET`. The server exiting stops everything. The node exiting is restarted with exponential backoff (1 s doubling to 30 s, reset after 30 s of uptime); nothing watches node code, so a running node is never restarted because its code changed (node dev reload is deferred; restart it to pick up node changes). SIGTERM/SIGINT: SIGTERM to every child, SIGKILL after 8 s, exit 0. The Docker image runs `supervisor.ts start`.

**Startup ordering:** either may start first. A node started before the server finds no socket and redials with its backoff (100 ms to 5 s); a server started before the node accepts commands and defers submitted work in its outbox until a node negotiates (immediate controls return `unavailable`).

**Shutdown:** the server on SIGTERM/SIGINT exits through `exit`, removing its socket file (a SIGKILLed server leaves a stale socket that the next start removes). The node on SIGTERM/SIGINT stops redialing and closes its connection first (no new commands), then `Node.shutdown()` **aborts** active runs and closes every live runtime, bounded by 5 s, so each run settles durably (its aborted reply, commits and `session.settled` wait in the outbox and replay on the next connection), then closes the node database and exits 0. It does not wait for runs to finish: agent runs can last minutes, longer than any supervisor would wait. A node killed without a chance to shut down (SIGKILL, crash) leaves its run pending in Pi with an unknown outcome and the server's activity `running`; after restart the session continues once the pending operation is resumed (`POST /api/sessions/:id/resume`), and a prompt admitted before that waits behind it (crash recovery of `running` activity is open; see the plan).

## Node API

`@reins/node/node` is the node's in-process API; `connectNode` (`@reins/node/node-connection`) serves it over a connection and nothing else calls it outside tests.

- **Lifecycle.** `openNodeDb(path)` (`@reins/node/storage`; `:memory:` in tests) opens node storage and applies node migrations, failing on an unsupported database (see [node-migrations.md](node-migrations.md)); the caller owns the connection. `startNode(db)` starts a new node over it: every call is an independent node (its runtimes, outbox drain, event seqs, credential cache and attached connections are its own), with no module-global database or shared instance. `shutdown()` is the one teardown: it refuses new commands (`Node stopped`), aborts active runs and closes every live runtime, then waits for serialized work; close the connection before it and the database after. `main.ts` opens `~/.reins/node/storage.db`, starts one node and closes the database on exit.
- **Commands.** One method per server→node wire method, taking its params (without `epoch`) and returning its wire result: `provision → {provisioned}`, `prompt`/`steer → {inputId}`, `setModel → {modelSet}`, `abort → {aborted}`, `resumePending → {started}`, `hydrate → {hydrated}`. `connectNode` registers each as the handler of its method and advertises it as a capability; there is no command round trip, so the node never parses the outbox's command vocabulary.
- **Errors.** A definite rejection throws `NodeRejection` (`@reins/node/protocol`) carrying a `NodeError`: `not_found` (no copy of the session on this node), `invalid_request` (bad attachment, unknown model, a hydrate that does not verify), `busy` (a hydrate under an active run), `unavailable` (retryable: an attachment fetch or hydrate pull with no server). `connectNode` sends it as `-32000` with the error as `error.data` (message truncated to 2048 chars); any other exception (a binding mismatch, no pending operation to resume) is sent as `internal`, non-retryable.
- **Test seam.** `nodeRuntimesForTesting(node)` (`has`/`open`/`close`) reaches a node's live runtimes; production code must not import it.

**Extension point.** New node capabilities (future plugins included) are wire methods: a name in `methods`, strict params/result schemas in `protocol/schema.ts`, a `capability` entry for server→node methods, and a handler registered in the peer's open handler record (`createRpcPeer(socket, handlers)`), which dispatches by method name and needs no change. The server calls it only once `node.hello` negotiated the capability.

## Transport

Everything above framing (schemas, `node.hello` negotiation, epochs, outbox replay, lifecycle reports, credentials) is transport-neutral: `createRpcPeer` needs only a `WireSocket` (send a text frame, receive frames, close). The production local link is the **local Unix socket**: JSON-RPC 2.0 over a Unix domain stream socket with newline-delimited frames, restart-required. The server (`server-process.ts`) owns the listener and routes each connection to the currently installed handler (`acceptNodeConnection` → `acceptInternalNodeConnection`); the node process dials it (`connectLocalNode`, `@reins/node/local-link`). The in-memory loopback (`createLoopbackPair()`, uncapped, no hello timeout or heartbeat) is a **test utility only**: backend tests that need both sides in one process link an in-process node through `__tests__/helpers/loopback-node.ts`, which registers a lazy connector through the marked seam `setInternalNodeConnectorForTesting` (`createServerState()` does so by default). Production never registers one; `reins/server-node-process-boundary` (Oxlint) forbids non-test server code from importing `@reins/node/node`, `@reins/node/node-connection`, `@reins/node/local-link` or values from `@reins/node/storage`, and `node-dependency-boundary.test.ts` checks the same by source scan.

**Why not WebSocket locally:** Bun 1.3.9 can serve WebSocket on a Unix socket, but its WebSocket client cannot dial one (`ws+unix://` is rejected; `unix`/`socketPath` options are ignored), and loopback TCP would need its own authentication. NDJSON over the raw socket needs no HTTP upgrade and gets authentication from file permissions. Remote nodes will use WebSocket + TLS with enrollment (not built); they reuse everything above the `WireSocket`.

**Framing** (`protocol/ndjson.ts`, used by both ends): each frame is the UTF-8 of one `JSON.stringify` string followed by `\n`. `JSON.stringify` never emits a raw newline; `send` rejects a frame containing one (a `TypeError`, which closes the peer). The receiver splits chunks on the newline byte (which never occurs inside a multi-byte UTF-8 sequence), so frames split anywhere, including mid-character, are reassembled from bytes, several frames per chunk are delivered in order, and each frame is decoded whole with a fatal decoder (invalid UTF-8 closes). A partial frame that crosses the cap closes the connection immediately, so buffering is bounded by the cap. Writes the socket does not accept (Bun `write` may take fewer bytes, or none) are queued in order and flushed on `drain`; the outbound queue itself is not capped (the heartbeat closes a peer that stops reading). Closing either end, or the socket ending/erroring, closes once, drops queued bytes and calls `onclose` asynchronously on that side, which closes the peer (in-flight calls fail with outcome unknown).

**Endpoint and permissions** (`node-transport/local-socket.ts`): default `~/.reins/run/node.sock` (`defaultLocalNodeSocketPath()`, beside the node's `~/.reins/node/storage.db`, not under `REINS_DATA_DIR`, so both sides agree without configuration); `REINS_NODE_SOCKET` overrides it for both processes (set it for both, or neither); tests pass explicit temp paths. The path must be absolute and at most 103 bytes (`sun_path`). The parent directory is created 0700; an existing one must be owned by the user and not group/world-writable, else startup fails. The socket file is chmodded 0600 right after `Bun.listen` creates it (per umask; the private directory covers the gap). **Local authentication is these file permissions**: only the same OS user can connect. Remote nodes will instead require enrollment plus authenticated TLS before any method (credentials above all) is served. On startup an existing path that is not a socket fails; a socket something still accepts on fails with "Another process is already listening on the node socket"; a socket nothing accepts on is stale and removed. `stop()` closes all connections and removes the file if it is still ours (a server killed by a signal leaves it; the next start removes it as stale). The listener is separate from the browser HTTP/WebSocket server.

**One internal-node connection:** an accepted connection becomes the internal node's link only once it negotiates `node.hello`; the previous link is then closed and the dispatcher woken. Closing it fails the old connection's in-flight calls with outcome unknown (submitted work is requeued as `DeliveryDeferred`, controls return `unavailable`); the old connection's epoch is never accepted on the new one (`-32003`), and the node side rejects commands carrying an epoch it was not issued. With no negotiated connection, submitted work is deferred and waits for the next wake (the new link's negotiation wakes it). A wake that arrives while a delivery is in flight is not lost if that delivery is then deferred: the dispatcher records the wake generation each deferred attempt began in and retries it when the busy chain ends. The server delivers queued work as soon as it has answered `node.hello`, so a command can reach the node in the same read as the hello reply; the node's command handlers wait for its side of the negotiation to settle before checking the epoch (otherwise a reconnect replay could be rejected as stale). `GET /api/health` reports `internalNode.connected`; the server logs "Internal node connected"/"disconnected".

**Server handler hot reload** (dev): the listener lives in `server-process.ts`, which is never reloaded. A reload installs the new handler, then the old handler's uninstall stops its dispatcher and closes its node connection (`closeInternalNodeLink`); each bundle has its own link registry, dispatcher and node services, so the old code never serves the new link. The node process is untouched: its runs keep going (live events emitted while no connection is attached are dropped with a seq gap; commits and lifecycle reports wait in its outbox). It redials after its backoff (50–100 ms), the listener routes the connection to the new handler, negotiation wakes the new dispatcher and the node replays its outbox (idempotent by the server's sequence and lifecycle watermarks). An in-flight command on the old connection fails with outcome unknown and is requeued; work submitted between the reload and the redial is deferred; both are delivered once over the new connection (the old epoch is fenced). Tested end to end with real processes in `server-process.test.ts` (a run active across the reload finishes, a steer queued during the gap reaches it, no duplicates). `kill -USR2 <server pid>` triggers the same reload without a source change. The database is process state: `server-process.ts` opens it once at startup (`openDb`: migrations, then `recoverInterruptedDispatches`) and injects the handle into every handler bundle it loads (`setDb`), so a reload opens no second connection and never treats the old handler's in-flight (`dispatching`) commands as interrupted (tested: a reload while a command is dispatching delivers it once). Migrations therefore need a server restart; the dev watcher warns when `migrations.ts` changes.

**Node client and reconnect** (`connectLocalNode`): dials, wires the NDJSON socket synchronously on open, runs `connectNode`, and redials whenever a dial fails or the connection closes (including failed negotiation, which now closes the connection on the node side). Delays grow exponentially from 100 ms to a 5 s cap with equal jitter (uniform in [d/2, d]); the backoff resets once a connection negotiates. Each connection is a new attach: every session's pending outbox replays and the credential cache is dropped. `onStatus` reports negotiated connects and their disconnects (the node entrypoint logs them). `stop()` closes the connection and cancels redials; call it before `Node.shutdown()`.

**Hello timeout:** on the socket link both ends close a connection that has not negotiated within 10 s (`HELLO_TIMEOUT_MS`): the server so a silent client cannot hold a slot, the node so it redials instead of waiting on a server that never answers.

**Heartbeat** (peer option, usable on any transport; on for the socket link): every 10 s each side sends a `node.ping` notification (`{}`: no id, reply, epoch or session seq; handled inside the peer, never dispatched, never touching event seqs or the outbox). Any received frame counts as heard; after 3 consecutive intervals with nothing received (30-40 s) the peer is treated as dead and the connection closed. Timers are injectable (`timers`) for tests.

**Frame caps:** the socket link caps frames at 64 MiB (`LOCAL_MAX_FRAME_BYTES`), both ways and in the NDJSON buffer, instead of the peer's 1 MiB default: attachments already cross in 512 KiB chunks, and ordinary commit batches and prompts fit, while a buggy peer cannot grow a partial frame without bound. Limits that remain: a prompt whose JSON exceeds 64 MiB (possible only with many multi-MiB text blocks: 64 blocks of up to 4 Mi characters each) fails as `FRAME_TOO_LARGE`; a single committed batch over 64 MiB fails to deliver and stays pending, holding back its session's later outbox rows, as it would on any capped link. A remote link still needs chunked `session.committed` and a prompt size bound that fits its cap.

## Credentials

**The server is the sole credential holder and the sole OAuth refresher.** A node needs no credential configuration: every Pi model runtime it builds (runtime open in `runtime/build.ts`, provision's registry lookup and lane creation) reads provider credentials from the server over the attached connection through `RemoteCredentialStore` (`packages/node/src/credentials.ts`), Pi's `CredentialStore` interface. Refresh tokens never leave the server.

Node→server requests (base protocol, epoch-checked like the other node→server methods; not per session, so any negotiated connection is served — **a remote node must additionally be enrolled and authenticated before these are exposed to it**). Handlers are injected into `createServerTransport` (`readCredential`/`refreshCredential`/`listCredentials`), implemented by `runtimes/node-credentials.ts` over `DbCredentialStore` and wired in `internal-node.ts`:

- `credentials.get` `{epoch, providerId}` → `{credential}`: the stored credential or `null` (logged out; Pi then falls back to ambient auth or reports "Provider is not configured", as on a node with no credentials).
- `credentials.refresh` `{epoch, providerId}` → `{credential}`: see below. An API key or logged-out provider is returned as for `get`.
- `credentials.list` `{epoch}` → `{credentials: [{providerId, type}]}`, no secrets.

*Wire shape* (`nodeCredential` in `@reins/node/protocol`, strict): `{type: "api_key", key?, env?}` (the key and Pi's provider-scoped env, e.g. Cloudflare account IDs) or `{type: "oauth", access, expires, enterpriseUrl?, availableModelIds?, gatewayConfig?}`. `toNodeCredential` copies only `OAUTH_WIRE_FIELDS`, the non-secret OAuth fields Pi's providers read at request or catalog time: GitHub Copilot's `enterpriseUrl` (base URL) and `availableModelIds` (model filter) and Radius' `gatewayConfig`. Other providers' `toAuth` read only `access` (OpenAI Codex derives its account ID from the access token). The strict schema rejects `refresh` or any other field even if a handler returned one (`-32603`). On the node an OAuth credential carries `refresh: ""` only because Pi's type requires the field; nothing on the node reads it.

*Refresh (single refresher).* Pi resolves OAuth request auth in `resolveStoredOAuth`: a token with less than 5 minutes left is refreshed inside `credentials.modify(providerId, fn)`, whose `fn` re-checks expiry and calls the provider's `oauth.refresh`. On the server, `credentials.refresh` runs exactly that code: `createPiModelRuntime().getAuth(providerId)` against `DbCredentialStore`, whose `modify` is serialized per provider for the whole server process and persists the rotated credential before releasing. So concurrent node requests, other nodes and the server's own model catalog refresh a login at most once; a request that finds the token already refreshed (outside the window) returns the current one without refreshing. A refresh failure is `-32000` with `error.data` `{code: "unavailable", retryable: true}` and the message `OAuth refresh failed for <provider>; sign in again on the server if this persists`; a stored OAuth login with no OAuth provider on the server is `invalid_request`. Neither message carries token material; the server logs Pi's error message (provider name and reason), never credential values.

*Node store.* `RemoteCredentialStore`:

- `read` returns the cached credential when fresh, else calls `credentials.get` (concurrent reads of a provider share one call).
- `modify(providerId, fn)` is how Pi refreshes (`resolveStoredOAuth`, and the model catalog's `resolveRefreshCredential` for a strictly expired token) and how `Models.login` persists a login. Every Pi refresh `fn` returns `undefined` without side effects when there is no OAuth credential, so the store probes `fn(undefined)`: a function that still returns a credential is a login and rejects with "Credentials are managed by the Reins server: sign in on the server". Otherwise `fn` is not run again: a fresh cached OAuth credential (refreshed meanwhile) is returned, else the store calls `credentials.refresh`, shared by concurrent callers of that provider (N concurrent requests → one RPC), and returns the server's credential, which is all Pi uses from `modify` on this path.
- `list` calls `credentials.list` (not cached). `delete` rejects ("log out on the server").
- *Cache:* memory only (never node SQLite or disk), per provider, until the credential is no longer usable as-is. There is no TTL: an API key stays cached for the life of the connection; an OAuth entry stays until its token enters Pi's 5-minute refresh window (`OAUTH_MIN_VALIDITY_MS`, mirroring pi-ai's unexported `DEFAULT_OAUTH_MINIMUM_VALIDITY_MS`), when it is re-read or refreshed. Every entry is dropped when a connection **attaches** (so a reconnect re-reads), not when one detaches. Logged-out results are not cached. A result that raced an invalidation is not cached.
- *Trade-off:* a server-side logout or API key change reaches a connected node only when it reconnects (or, for OAuth, at the next refresh, which the server answers from its current store). Until then the node keeps using the credential it cached. This buys zero credential RPCs per model request on a steady link and runs that survive a brief link drop; there is no server push of credential changes.
- *No connection:* a cached credential still serves `read` (a run in progress keeps working through a dropped link while its credential stays valid). A cache miss, an OAuth token in the refresh window (`read` or `modify`), and `list` reject with "Credentials unavailable: no Reins server connection". Opening a runtime still works (Pi records the availability error), but a model request needing such a credential fails as for missing credentials until a connection is attached.

## Wire method naming

Wire methods are named for what is happening, not for what the receiver does or which side serves them. All names live in `methods` (`@reins/node/protocol`).

- Commands sent to the node are imperatives on the resource, named after their contract op: `session.provision`, `session.prompt`, `session.steer`, `session.setModel`, `session.abort`, `session.resumePending`, `session.hydrate`.
- Requests name the resource: `attachment.fetch`, `session.snapshot`, `script.execute`, `credentials.get`, `credentials.refresh`, `credentials.list`.
- Durable reports are past tense: `session.committed`, `session.started`, `session.settled`.
- Live notifications: `session.event`.
- Only connection-level methods use the `node.` prefix: `node.hello`, `node.ping` (heartbeat notification).

Server→node methods are negotiated capabilities named after the method (`capability` enum); node→server methods are base protocol.

**Session configuration (in `session.provision`):** the server resolves a session's configuration once, at creation (`createManagedSession`), and freezes it into the provision command stored in `node_command_outbox`: `configuration: {model: {provider, modelId} | null, thinkingLevel: string | null, task: {title, description, branchName} | null}`. Model: the creation override, else the `default_model` setting (its runtime type must match); thinking: the override's level, else the default's, with the row's `off` sent as null. The same model and thinking level are persisted on the server session row; a later `default_model` change never reaches an existing session, and a session created with no resolvable model stays at null (it cannot open until `session.setModel`). The task is a snapshot: task title/description edits after creation are **not** propagated to the node (the branch name is immutable). On the node (`Node.provision` in `node.ts`), provision is idempotent by **ordering**, not by one transaction:

1. When a model was resolved, it is looked up in the node's model registry first; a model the registry does not know rejects the provision with `invalid_request` (`Model not found: <provider>/<model>`) before anything is stored (no binding or lane). The dispatcher records the failure (the session becomes `provision_failed` with the reason, in the settling transaction), logs it and broadcasts `{type: "error", sessionId, error: "Session provisioning failed: …"}` to connected clients, then removes it; the session shows "Provisioning failed: …", and opening it reports its node data missing.
2. `provisionNodeSession` (`storage.ts`) stores the binding and, on first bind, the task snapshot (`sessions.task_json`, node migration `004_session_task`; NULL is a scratch session). An equal binding is a no-op (the first provision's task stands); a different one rejects. The configuration is not part of the binding: binding equality (`verify`) still compares only source, cwd, created-at and parent.
3. Unless the main lane already exists, Pi creates it (`createMainLane` in `runtime/lane.ts`): an `AgentHarness` over a `StorageBackedSession` on the node's `PiStorageAdapter`, created with just the registry model, `thinkingLevel` and no active tools, then `harness.lane("main")` and `harness.close()`. Pi writes its own lane records through the adapter, so they replicate like any Pi commit; the runtime sets its registered tools at first open. No resolved model: no lane (open fails "requires an explicit model" until `session.setModel`).
4. There is no receipt. A replay (a crash between the steps, a lost reply, a node restart) runs the steps again and each converges: the binding matches (a different one still rejects), the lane exists and is not written again. A replay whose lane exists converges even if its model has since left the registry. Provision's lane creation and runtime opening are serialized per session, because Pi's storage has no cross-harness conflict detection.

From then on Pi's lane is the **only** durable copy of the node's model selection: the node keeps no other. Opening reads the stored selection through Pi's `laneConfig` address (`storedLaneModel`), because building a harness needs a registry model first and an unknown stored model must still be reported by name.

Pi does not persist the system prompt (the harness takes it from options at every open; only model, thinking level and active tools are lane state), which is why the task snapshot lives with the binding. At every open the node, with no server call:

- checks out `task.branchName` in the binding cwd with node-local git (`runtime/git.ts`) only if the current branch differs; a git failure fails the open;
- renders the system prompt itself with `buildReinsSystemPrompt` (`@reins/node/system-prompt`, the single copy, also used by the Claude adapter and `print-reins-system-prompt.ts`); a null task is a scratch session. Fixture tests (`runtime/system-prompt.test.ts`) pin its output byte-for-byte to the pre-move server rendering;
- reads the model from Pi's lane and validates it against its model registry before building Pi: an unknown model throws `NodeModelNotFoundError`; no lane (no model was ever resolved) fails with `AgentHarness Pi runtime requires an explicit model`. Pi restores the lane's model and thinking level.

Runtime errors log node-locally (`console.error`).

**Model changes (`session.setModel`):** `{op: "session.setModel", sessionId, provider, modelId, thinkingLevel?}` → `{kind: "modelSet"}`. `Sessions.setModel` (the HTTP session model route and scripting `sessions.setModel`) keeps its server-side provider/model validation against the catalog, then for a node-owned session updates the row and enqueues the command in `node_command_outbox` in one transaction, wakes the dispatcher and broadcasts `session_updated` without waiting: the node applies it asynchronously. The HTTP route (`PUT /api/sessions/:id/model`) answers with the session view. Validation is a single catalog lookup (`findPiModel`); an unknown provider or model is `Model '<model>' not found for provider '<provider>'`. It is `submit-work` and delivered in outbox order like prompt/steer: after earlier queued commands of the session are admitted (a prompt's run may still be going; the lane change applies from Pi's next LLM turn) and before later ones; a request is never deduplicated, so the last delivered change wins. Omitting `thinkingLevel` keeps Pi's current level. The node applies it to the open runtime, or opens one if needed (validating the new model and seeding a lane Pi has not created, so a lane whose stored model is gone can be repaired), and calls the runtime's `setModel`, which persists through Pi's lane. A replay (a lost reply, a node restart) applies the same absolute selection again and returns `modelSet` (see *Replay idempotency*). A model the node's registry does not know returns `invalid_request` (`Model not found: <provider>/<model>`): the command fails, is logged, and every connected client gets `{type: "error", sessionId, error: "Model change failed: …"}` plus `session_updated` (there is no single submitting client), then the failed command is removed. The row keeps the requested model until the next settlement reports Pi's actual selection. A session at rest on the server is queued for hydration onto its node first (the lazy trigger), so the change reaches Pi's lane there. The server no longer reaches into the node's live runtime to change a model.

**Durable run lifecycle (node→server reports):** `session.started` `{epoch, sessionId, runId}` and `session.settled` `{epoch, sessionId, runId, status, error?, metadata: {model, thinkingLevel}, reply, replyError?}` → `{acknowledged: true}` are base-protocol requests, like `session.committed`. They drive durable server effects (activity `running`/`finished`, runtime model metadata, a child's report to its parent), so they are never lost with a notification.

- *Node persistence and ordering:* commits, attachment uploads and lifecycle reports share one node table, `session_outbox` (migration `003_session_outbox`; `attachment` rows since `005_attachment_uploads`), ordered by row ID and drained per session serially (`createOutboxDrain`, one per node); a row is deleted only after the awaited acknowledgement, and a failure stops that session's drain until the next commit, report, provision or attach. A commit row is inserted inside its Pi commit transaction and the harness emits `run_start`/`run_end` after that commit, so a settlement is always delivered after the transcript commits it summarizes, and run N's `settled` before run N+1's `started`. An `attachment` row (payload `{"attachmentId"}`; the bytes stay in `node_attachments` and are read at delivery, never copied into the outbox) is inserted in the same SQLite transaction that writes the cached bytes, which is the transaction that creates the reference: either the `after_tool` hook's own transaction, before Pi can commit or stage the result carrying it, or the Pi commit transaction itself (storage-adapter safety net), before that commit's row. Row IDs are AUTOINCREMENT, so every upload is delivered, and acknowledged, before any commit that can contain its reference, and the server holds the bytes under that ID before its replica applies the transcript entry. For a child session (binding `parentSessionId`) the settlement needs the final reply from an async transcript read: the node inserts the settlement at once with `ready = 0`, which holds it **and every later row of that session** in place, then fills in `reply` (or `replyError`) and marks it ready. A new node instance (`startNode(db)`) releases rows left unready by a crash as `replyError: "The node restarted before the final reply was read"`. Pi emits `started` again with the same runId on `run_resume` and in-run compaction; each is recorded and the server treats it as a replay.
- *Server idempotency:* a lifecycle watermark per session (`node_session_watermarks`, backend migration `035_node_session_watermarks`): the last applied report's `(run_id, kind)` and the sha256 of its JSON (without epoch/sessionId). The node delivers a session's reports in order and deletes each only after its acknowledgement, so the only report that can be replayed is the last one applied. `runtimes/node-session-events.ts` applies each report through `SessionInstance.startedWith()`/`settledWith()` with a watermark callback (`recordNodeLifecycle` in `node-replica.ts`) that runs **inside the same server transaction** as the activity update, metadata write and the parent steer's `node_command_outbox` insert (`enqueueSessionInput`, synchronous), so the watermark and the effects commit together. A report matching the last one (e.g. after a lost ack, even across a server restart) applies nothing and is acknowledged, so it cannot re-steer the parent or re-flip state; so does a `started` for the run that last settled (Pi re-reports `started` for a resumed run). The same key with a different payload hash is divergence: rejected with `-32000`, left pending on the node, and applied nowhere. Any other report applies. Settlements also increment `settlement_count` and keep their status/error for waits. Broadcasts and the dispatcher wake happen after commit. Because the node delivers a session's reports in order and only after the previous acknowledgement, no per-session `SessionInstance` is retained: each report uses a fresh instance, and no stale-settlement guard is needed.
- *Reply failure:* if the node cannot read a child's transcript, `reply` is null and `replyError` carries the message; the server logs it and marks the child `finished` without reporting to the parent (the pre-protocol behaviour; no misleading "Session completed."). A parent that cannot receive the report (out of scope, source unavailable) is likewise logged and leaves the child `finished`.
- *Limits:* a run that never settles because the node died mid-run leaves the session `running` until a later run (crash recovery is open). The watermark is one row per session (nothing grows per report or batch). Without installed services (`subscribeInternalNodeServices`), lifecycle reports are rejected and stay pending.

**Session events (node→server notification):** `session.event` `{epoch, sessionId, seq, event}` is a JSON-RPC notification (no `id`, never answered) carrying live UI deltas only. The peer (`createRpcPeer`) takes notification handlers (`{params, notify}`) alongside call handlers and offers `notify(method, params)`. Notifications are best effort: an unknown method, invalid params, a failing handler, a stale epoch or an out-of-order seq drops that one notification with a `console.warn` and never closes the connection (closing would fail durable in-flight calls for a lossy message); a call to a notification-only method gets `-32601`. `notify()` returns false and drops locally when closed or when the frame exceeds the peer cap; a socket failure still closes the peer. `event` is a runtime event, relayed to browsers as the node runtime projected it; the schema checks its `type` and that every image block in any `content` array (messages, tool results, partial tool results) is an attachment reference (`{type: "image", attachmentId, mimeType, byteSize, sha256?, filename?, width?, height?}`, strict), so an event carrying inline image bytes is dropped at the wire; run lifecycle is not a session event. `seq` is per session and node instance, starts at 1 and increments for every event the node emits, including ones dropped because no connection is attached (then the event is discarded without error). The node emits a session's events in occurrence order. The server transport accepts only the issued epoch, drops seqs at or below the last one seen on that connection, and passes `missed` (skipped seqs since the previous event, 0 for the first on a connection) to its `event` handler, which logs gaps; there is no replay or resync, and seqs are not compared across reconnects or node restarts. A lost event only affects live browser rendering; the transcript remains `session.committed`. `internal-node.ts` authorizes the session's placement (fencing, below) and forwards to the services injected per `ServerState` by `installRuntimeHooks()` (`runtimes/node-session-events.ts`), which broadcasts the event as received: the server no longer externalizes node event images. `onError` stays node-local.

*Images:* session events never carry image bytes. Pi holds user prompt images as references (hydrated only for providers), and tool-result images are turned into references where Pi produces them, synchronously and without the network: the node registers Pi's `after_tool` hook (`referenceToolImages` in `createAgentHarnessPiRuntime`, implemented by `runtime/tool-images.ts`), which runs after a tool executes and before Pi stages and commits its result. For each inline image block it first looks for a cached `node_attachments` row of the session with the same sha256 and MIME type (index `node_attachments_content`, migration `006_node_attachment_content`) and, if one exists, reuses its ID and writes nothing, so an image read or checkpointed repeatedly, or met again by the storage-adapter safety net, is cached and uploaded once. Reuse keeps the outbox ordering: a node-created row's upload row was appended in an earlier (or the same) transaction, so it precedes any commit that now references it, or was already acknowledged; a prompt attachment materialized by `attachment.fetch` is cached under the server's ID and has no upload row because the server already holds it. The reference then carries the cached row's metadata, which is what the server holds for that ID (filename and dimensions are hints, so the first occurrence's win and a later block's differing hints are dropped). The same bytes under another MIME type, or in another session, get their own attachment. Otherwise it assigns a new ID (`att_<uuid>`) and, in one node SQLite transaction, writes the bytes into `node_attachments` under that ID and appends an `attachment` upload row to the session outbox; it returns the reference of the prompt-image shape (`{type: "image", attachmentId, mimeType, byteSize, sha256, filename?, width?, height?}`) at once. The hook never waits on the server and never keeps bytes inline: with no connection the run proceeds normally and the upload waits in the outbox with the commits. Pi then stages and commits the reference, so the tool-result message, `tool_execution_end`, message/entry/turn/agent events and `session.committed` (hence the server replica and transcript reload) all carry it. Pi does not validate or strip image blocks on commit or replay (its `ImageContent` type requires `data`, so the hook's return is cast in that one place, as prompt references already are); compaction only serializes text. `toProviderMessagesForSession` hydrates references inside `toolResult` messages from the node cache, as it does for `reinsInput`, so the provider still receives the bytes (an uncached reference becomes the `[Image attachment missing]` text).

- *Rejection policy:* before referencing an image the node applies the server's upload rules: a MIME type outside `ATTACHMENT_IMAGE_MIME_TYPES`, empty bytes or more than 10 MiB replace the block with a text note (`[Image omitted: unsupported type <mime>]`, `[Image omitted: empty]`, `[Image omitted: larger than 10 MiB]`), with nothing cached or queued, so the model sees the note rather than the image. Every queued upload is therefore one the server accepts, and a server rejection of a queued upload (different content under the ID, an ID another session holds, a missing cache row) is a real divergence or corruption: it stays pending and, like a divergent commit, holds back that session's later outbox rows until resolved. Nothing retries it past the normal drain triggers.
- *Storage-adapter safety net:* Pi can commit a tool result without running `after_tool` (a checkpointed result it republishes for an interrupted tool on recovery; a hook cut short by abort). The node's `PiStorageAdapter` (opened by `openNodeStorage`) takes a `prepare` step that rewrites the prepared writes inside the commit transaction, before they are stored and before the commit row is recorded: `referenceInlineImages` (the hook's conversion, shared) replaces every inline image in any `content` array of any write (message entries, `retainedTail` messages, Pi's staged `pi.pending.entry` values and `pi.pending.tool_output` checkpoints) with a reference, its bytes and upload row written in the same transaction. No inline image reaches node storage or `session.committed`. A commit that fails rolls back its conversion with it; a retried Pi commit converts afresh (reusing any cached ID for the same content, otherwise new IDs; nothing orphaned), and outbox replays resend the stored, already converted `writesJson` bytes, never converting again. Reads return the stored references, which providers hydrate from the cache; Pi's in-memory copy of that one result may still hold the bytes until it is re-read, and live events built from it get the placeholder below.
- *Stray inline images in live events* (a partial result in `tool_execution_update`, sent before `after_tool` runs; Pi's in-memory copy of a result the safety net converted) are replaced in the live event only by the text block `[Image attachment unavailable]` (`sendableEvent` in `node.ts`), synchronously, so ordering and seqs are unchanged.

*History written by the server* (when it still ran sessions) keeps inline tool-result images in its transcript; a hydrate copies them verbatim (see *Session relocation*). The server no longer externalizes live event images: every live event comes from a node.

**Agent tools (node→server requests):** the server does not execute agent tools. Every tool definition lives on the node: native read/write/edit/bash (`@reins/node/host-tools`) and the Reins application tools `create_task`, `search` and `execute` (`@reins/node/reins-tools`), assembled by `buildNodeRuntime`; `NodeRuntimePolicy` has no tools field. Their names, descriptions, parameter schemas and order are the model-visible contract, pinned by a snapshot test (`runtime/reins-tools.test.ts`). Each Reins tool forwards exactly one base-protocol request, named per *Wire method naming*:

- `script.execute` `{epoch, sessionId, callId, code}` → `{ok: true, text} | {ok: false, error}`: the server runs the script in its `node:vm` sandbox against the Reins scripting API (`tools/execute.ts`). A script that throws is a completed call (`ok: false`), so its full message reaches the model as `Error: <message>` exactly as before; the tool keeps its `{success}` details.
- `script.search` `{epoch, sessionId, query}` → `{text, matchCount}`: the formatted scripting API documentation (`tools/search.ts`).
- `project.createTask` `{epoch, sessionId, title, description, branchName?, prompt?}` → `{task, sessionStarting}`: creates the task through the task model (branch, broadcast) and, with a prompt, starts a session on it fire-and-forget as before (`tools/create-task.ts`). Not folded into execute.
- `script.cancel` `{epoch, sessionId, callId}` (notification): aborts the `AbortSignal` of that in-flight script, if it belongs to the same session.

*Scope and authorization:* params name only the calling session; strict schemas reject any project/task field (`-32602`), so a node cannot widen scope. `internal-node.ts` runs the same placement check as the other node→server methods (unknown session, or one not placed on the calling node, is rejected with `-32000` before product code runs), then `runtimes/node-tool-calls.ts` (injected with the report services by `installRuntimeHooks()` as `subscribeInternalNodeServices`) derives project/task from the server's session row and builds the server-side `SessionInstance` for `sessions.*` scripts and task session starts. `internal-node.ts` therefore imports no session manager/instance. Rejections are `-32000` with a message (truncated to 2048 chars); the tool reports them as `Error: <message>`.

*Timeouts, abort and retries:* per-call timeouts are 5 min for `script.execute` (the vm bounds synchronous code to 30s, but a script may await several `sessions.wait` calls of up to 30s each), 30s for `script.search` and 60s for `project.createTask` (git branch creation). The tool's `AbortSignal` is passed to the peer call: aborting stops the node waiting immediately (late reply dropped). On abort or timeout of `script.execute` the node also sends `script.cancel`; the server aborts the script's signal, which API calls that honour it (`sessions.wait`) observe; synchronous script code and already-started effects are not interrupted. Closing the link aborts every in-flight script. `project.createTask` and `script.search` have no server-side cancellation. None of the calls is retried automatically. Transport failures become tool results, never exceptions: a timeout, abort, connection loss after sending or `-32603` means the outcome is unknown, and `execute`/`create_task` say so ("may have run, with side effects" / "the task may have been created"); no attached connection, busy, invalid params or stale epoch mean the call did not run. Results are unbounded on the uncapped internal link; over a capped transport an oversized result fails with `-32603` (unknown outcome).

## Session commands on the wire

Every server→node session command crosses the JSON-RPC link (`sendNodeCommand` in `node-transport/commands.ts`; client methods on `createServerTransport`; handlers in `connectNode`). Each is a capability of the same name, checked with the connection's epoch before the node runs anything (`-32003` otherwise). All carry the `binding` the server resolved from product rows, which the node verifies against its stored binding.

| Method | Params (besides `epoch`, `sessionId`, `binding`) | Result | Delivery | Timeout |
|---|---|---|---|---|
| `session.provision` | `configuration` | `{provisioned: true}` | outbox | 30s |
| `session.prompt`, `session.steer` | `clientId`, `content`, `sourceSessionId` (nullable) | `{inputId}` | outbox | 120s |
| `session.setModel` | `provider`, `modelId`, `thinkingLevel?` | `{modelSet: true}` | outbox | 60s |
| `session.abort` | — | `{aborted}` | immediate | 30s |
| `session.resumePending` | — | `{started}` | immediate | 60s |
| `session.hydrate` | `task`, `snapshot` | `{hydrated: true}` | outbox | 10 min |

`content` is text blocks and image **references** only (strict: at most 64 blocks, text up to 4 MiB characters, allowed image MIME types, `byteSize` ≤ 10 MiB, paired dimensions); inline bytes or other block types are `-32602`. `content` and `configuration` use the schemas the outbox stores them with (`promptContent`, `sessionConfiguration` in `@reins/node/contract`). No outbox command ID crosses the wire: the node keeps no per-command state.

*Results and errors* (`commandOutcome`): a result becomes the NodeResult value; a node rejection is `-32000` whose `error.data` is the NodeResult error, so `not_found` (session node data missing), `invalid_request` (bad attachment, unknown model), `busy` (a hydrate under an active run), `unavailable` (attachment fetch with no connection) and `internal` (node exceptions, e.g. binding mismatch or "no pending inactive operation") reach the dispatcher or caller unchanged. Other protocol failures (e.g. `-32602`) are terminal delivery exceptions. When the node did not run the command (busy, stale epoch, not negotiated) or the outcome is unknown (timeout, lost link, send failure): submitted work throws `DeliveryDeferred` and is requeued; an immediate control returns `{code: "unavailable", retryable: true}` to its caller and is never retried.

*Timeouts* bound admission, not the run: prompt/steer may fetch uncached attachments (each 512 KiB chunk its own 30s call), check out the task branch and build Pi before Pi admits, so they get 120s; setModel and resumePending may open the runtime (60s); abort waits for the aborted run to go idle (30s). A timed-out submitted command is requeued and its replay joins or answers the still-running admission.

*Replay safety* (verified by `__tests__/runtimes/internal-node-execution.test.ts`, which replays after a timeout and after Pi admitted an input the server never heard of, and by `packages/node/src/node.test.ts`, which replays provision, prompt, steer and setModel after a node restart on the same storage):

- **prompt:** Pi admission is durable: `lane.accept` commits the `reinsInput` entry keyed by `reinsId` (= the command's `clientId`). On replay (a lost reply, a node restart) `admitPrompt` finds that input (queued or as an entry) and returns it without accepting again, so there is no duplicate message or run; an in-flight admission of the same input is joined (`deduplicateAdmission`). A recovered operation is driven again only if not already active.
- **steer:** `lane.steer` commits the queued input and Pi moves it from queue to transcript in one commit, so `findAdmitted` checks the queue first, then entries, and cannot miss an input moving between them; a replay therefore never enqueues it twice. One residual: an abort discards queued steers, so if a steer's reply was lost and the user aborts before the replay, the replay re-queues that steer (a resurrection, not a duplicate).
- **setModel:** absolute (provider/model/thinking level), and the outbox orders a requeued command before later commands of its session, so re-applying it is idempotent (the replay writes the same selection to Pi's lane again).
- **provision:** converges on its binding and lane (see *Session configuration*).
- **hydrate:** converges by content (see *Session relocation*).
- **abort, resumePending:** immediate controls, never replayed. Abort with no live runtime returns `{aborted: false}` without opening Pi; with a live runtime it aborts the active run (if any) and reports whether the runtime was busy. resumePending with nothing to resume is an `internal` rejection.

*Re-entrancy:* a node serving `session.prompt`/`session.steer` calls `attachment.fetch` back over the same link before admission; the peer serves inbound requests while its own call is pending, so this does not deadlock (covered by the prompt-with-image test).

## Replay idempotency

There are no receipt tables on either side: "already applied" is derived from state, so a replay after a lost acknowledgement or a process restart (either side, no memory) is **acknowledged as success** and applies nothing twice.

**Node → server reports** (`node-replica.ts`, one `node_session_watermarks` row per session):

- *Commits:* the node records a session's batches contiguously from its `harness_next_seq` (a batch covers `[startSeq, startSeq + writes.length)`, is applied atomically and is never empty), so batches never partially overlap. Against the server's `sessions.harness_next_seq`: `startSeq` equal applies the batch and stores its start and the sha256 of its exact `writesJson`; greater is a **gap** and rejects (the batch stays pending on the node); smaller is a replay and is acknowledged without applying. A replay whose `startSeq` equals the last applied batch's is compared by hash (a mismatch is **divergence** and rejects); a batch that straddles the watermark rejects as divergence. An empty batch rejects.
- *Lifecycle reports:* the last applied report's `(runId, kind)` and payload hash; see *Durable run lifecycle* above.

**Server → node commands** converge on each command's own node state (see *Session commands on the wire*): provision (equal binding, existing lane), prompt/steer (Pi's durable `reinsId`), setModel (absolute selection), hydrate (identical copy; a different copy is replaced, see *Session relocation*). Abort and resumePending are immediate controls and never replayed. A state-based mismatch check remains: a different binding rejects.

**Divergence detection and its limits.** Detected: a different `writesJson` for the last applied batch, a batch straddling the watermark, a gap, a different payload for the last lifecycle report, a different binding, differing attachment content. Not detected (acknowledged as already applied): a replayed commit batch older than the last one (only the last batch's hash is kept), and a replayed lifecycle report older than the last one (not possible while the node delivers in order and deletes only after acknowledgement). The node no longer detects a different command replayed under an earlier command ID (commands are not keyed by ID); the server never does this, since a requeued row re-sends its stored command. Residuals: a steer whose reply was lost and that an abort discarded before the replay is re-queued by the replay (a resurrection, not a duplicate); a replayed prompt whose operation is still open on the node drives it (as a recovered operation). Upgrading to `035_node_session_watermarks` does not backfill: until a session's next applied report, a lifecycle report whose acknowledgement was lost across the upgrade would be applied again, and waits see no latest settlement for runs settled before it.

## Session placement

A session's placement is a column, `sessions.placement_status` (backend migration `036_session_placement_status`, CHECK-constrained; `037_drop_session_storage_owner` removed `move_failed` and dropped `storage_owner`), the **single source of truth** for where a session lives, with a failure's reason in `sessions.status_error`. It is written **in the same server transaction as the outbox change that causes it**; nothing derives placement from outbox rows. **The server never executes sessions.** Values (`PlacementStatus` in `session-store.ts`):

| Status | Meaning | Written by |
|---|---|---|
| `server` | at rest on the server: its server Pi tables are the canonical copy; the server never runs it, any use hydrates it onto its source's node first | default for stored rows (sessions from before nodes); a failed move of a session at rest (with `status_error`) |
| `provisioning` | its `session.provision` is queued or being delivered; server tables are the (empty) replica | `createManagedSession`, in the transaction that stores the session and queues the provision (`scheduleWork`). Every new session, including child and task sessions, starts here |
| `provisioned` | on its node, ready; server tables are its replica | provision admitted, hydrate admitted (`commitPlacement` in the settling transaction), a hydration outside the outbox succeeding (`recordHydration`); a failed move of a node-owned session (with `status_error`) |
| `provision_failed` | provisioning failed; the session never landed anywhere (`status_error`: the node's reason, e.g. `Model not found: …`) | provision failed (`commitPlacement`); an interrupted provision at startup |
| `moving` | a move's `session.hydrate` is queued or being delivered; `source_id` is the target | `queueMove` (explicit move `requestSessionMove`, lazy trigger `queueHydrationForUse`), with the hydrate row |

**Failed moves revert.** A move's hydrate command stores, server-side only, the resting state it left: `{op: "session.hydrate", targetSourceId, revertTo: {status: "server" | "provisioned", sourceId}}` (the contract schema strips `revertTo`; it never reaches the node). A failed hydrate (`commitPlacement`) or one interrupted by a restart (`recoverInterruptedDispatches`) returns the session to `revertTo.status` on `revertTo.sourceId` and records the reason in `status_error` (`revertTo` is required: a hydrate without it cannot settle or be recovered); the UI shows "Move failed: …" while the status is the resting one. A hydration outside the outbox that fails (`recordHydration`) leaves the placement as it was and records the reason. `status_error` is cleared by the next placement change (the next move being queued, a provision or hydrate admitted). A provision that settles while a move was queued behind it leaves `moving` in place.

**Readers.** `waitUntilProvisioned` (abort, resumePending) returns at once for `server` (the next command hydrates it) and `provisioned`, waits for the pending provision/hydrate for `provisioning`/`moving` (rejecting "Execution source unavailable; session provisioning queued" while it waits on an unreachable source), and rejects `provision_failed` with "Session provisioning failed: …". `SessionInstance.wait` fails the same way. Fencing (*Session relocation*) accepts node writes unless the session is `server` or `moving`. Session views expose `placement: {status, error, available, nodeId?, nodeName?}` (`available`: the session's source is on the internal node; `nodeId`/`nodeName`: the node it is on, being provisioned on or moving to, absent at rest on the server); the UI shows "Provisioning", "Provisioning · source unavailable", "Provisioning failed: …", "Moving to …" and, for `server`/`provisioned` with an error, "Move failed: …".

**The outbox is a queue.** A command is `queued`, then `dispatching` while one delivery is in flight. `deliverCommand` records the result in one transaction with the placement change (`commit` hook): an admitted command is deleted there; a failed one is marked `failed`, its failure notified (`onCommandDelivered` receives the outcome) and then deleted. Process startup (`recoverInterruptedDispatches`, once per process when `server-process.ts` opens the database, never on handler install) deletes interrupted (`dispatching`) commands and failed ones whose notification was lost, marking interrupted provisions `provision_failed` ("Provisioning was interrupted by a server restart") and returning interrupted moves to their `revertTo` ("Move was interrupted by a server restart"); queued work behind them is delivered normally (work for a session back at rest hydrates it first). Migration `039_outbox_queue_states` narrowed the table's CHECK to `queued`/`dispatching`/`failed` (rebuilt keeping every row under its rowid). Replays of admitted input are recognized from the replica: `enqueueInput` queues nothing for a clientId the replica already holds (`replicaInput`).

**Migrations.** `036_session_placement_status` set each row from its own `storage_owner` (`server` → `server`, else `provisioned`), then from its outbox: a session whose latest provision/hydrate was `failed`/`unknown` became `provision_failed`/`move_failed`, one with a pending provision `provisioning`, one with a pending hydrate `moving` (re-pointed at the hydrate's target source); it then deleted every settled (`admitted`, `failed`, `unknown`) command, keeping `queued`/`dispatching` ones, and added `node_session_watermarks.settlement_next_seq`, backfilled with the session's current `harness_next_seq` for existing settlements. `037_drop_session_storage_owner` maps `move_failed` rows by their owner (`server` → `server`, `internal-node` → `provisioned`, keeping the reason), adds `revertTo` to pending hydrates the same way (the previous source of a move already under way is unknown, so it reverts to the current, target, source: its node answers `not_found` and the next command re-hydrates), rebuilds the `placement_status` column without `move_failed` (re-added under a temporary name, copied, old column dropped, renamed) and drops `storage_owner`. `ALTER TABLE … DROP COLUMN` keeps the table, rows, indexes, triggers and foreign keys. `038_clear_stale_server_running` sets `activity_state = 'finished'` on sessions at rest on the server still marked `running` (so activity reads are pure), and `039_outbox_queue_states` rebuilds the outbox with the narrowed state CHECK.

**Terminology.** "Open" no longer names node placement: a session is provisioned (or provisioning) on its node; "open" is reserved for runtime opening on the node.

## Session relocation

A session moves between placements through the **server as the hub**. At rest, the server's copy is authoritative: a `placement_status = 'server'` session is *at rest on the server* (its server Pi tables are canonical; the server never runs it); a session on a node has an exact server replica (`session.committed`). Every move is a **hydrate** of the server's copy onto the target node: server → node, and node A → node B alike. There is **no release** and no direct node-to-node transfer: the previous owner is told nothing. Code: `models/session-ownership.ts` (state machine, preconditions, fencing, lazy trigger, explicit move), `runtimes/session-relocation.ts` (delivery), `packages/node/src/relocation.ts` and `hydrate` in `node.ts` (node side), snapshot rows and digests in `@reins/node/pi-storage`.

**State machine** (`source_id` and `placement_status`; see *Session placement*):

```
at rest on server (server) ──session.hydrate queued──▶ moving to N ──node acknowledged──▶ owned by N (provisioned)
                                                                  └─failed──▶ back at rest (server) + status_error
owned by A (provisioned, idle) ──re-pointed at B + session.hydrate queued──▶ moving to B ──node acknowledged──▶ owned by B (provisioned)
                                                                  └─failed──▶ back on A (provisioned) + status_error
```

A move in progress is `placement_status = 'moving'`, set in the transaction that queues its `session.hydrate {targetSourceId}` outbox row, with `source_id` re-pointed at the target source (`sessionLocation` reads the column). **Queueing a move** is, in one server transaction: the precondition check (for a session on a node), switching the session's `source_id` to the target node's source for the project, queueing `session.hydrate` for the target with the resting state to revert to (`revertTo`) and marking it `moving`. From that commit on the previous owner is fenced (below). The session becomes `provisioned` on the target in the transaction that settles (and deletes) the command (`deliverCommand`'s `commit` hook, `commitPlacement`); a failure returns it to `revertTo` with the reason (see *Session placement*). Moves are submitted work in outbox order, so input submitted during a move waits behind it.

**Preconditions.** A node-owned session moves only when it is idle **on the server**: not `running`, no pending input (`nodeSessionActivity`) and no other queued/dispatching command; otherwise the request is rejected with a conflict (409). Why this is enough: a node delivers a session's reports in order and `session.settled` is recorded after the run's commits, so a session the server sees as idle has a replica holding everything through its last run. Moving a session to a node it is already on or moving to reports its placement and queues nothing; moving it elsewhere while a move is under way conflicts.

**Accepted loss.** Commits the old owner made **outside a run** (for example the lane write of a `session.setModel`) that it had not delivered when the session moved are lost: the new owner hydrates the server's copy without them, and the old owner's late delivery is refused (below).

**Hydrate protocol (pull, chunked).** The server sends `session.hydrate {binding, task, snapshot}`; the binding is resolved for the target source, the task snapshot from the server's task row and `snapshot = {harnessNextSeq, rowCounts: {entries, values, lists, usage}, digest}` from the server's copy, all at delivery time (not stored with the command). The node then pulls:

- `session.snapshot {epoch, sessionId, fromSeq}` → `{summary, rows, nextSeq}` (node→server request, read-only): rows with seq ≥ `fromSeq` from `session_messages` (with the parent's harness ID instead of a row ID), `pi_values`, `pi_lists` and `pi_usage`, in (seq, table, key) order, at most 500 rows and about 4 MiB of JSON per page (a page always holds at least one seq whole and never splits one), `nextSeq` null after the last page, plus the copy's current summary. Histories the server wrote before nodes may start at seq 0. History that is not canonical AgentHarness storage (an entry without a harness ID) is refused.
- `attachment.fetch` for every attachment referenced anywhere in the rows (image blocks with an `attachmentId`). Inline images in history the server wrote before nodes (tool results) stay inline and need nothing; an attachment the server no longer holds (pruned) is skipped and providers get the missing-image placeholder, as on the server; a checksum or metadata mismatch rejects.

Every page's summary must equal the command's (else "changed during hydration"), and the pulled rows must summarize to it. Nothing is stored until then; in **one node transaction** the node binds the session (binding and task snapshot), writes every row verbatim (parents linked by harness ID, `harness_next_seq` copied), caches the attachments and recomputes the summary from what it stored; any mismatch rolls back and rejects with `invalid_request`. Pi is never involved: rows are copied, not rebuilt. The digest is a sha256 over every row's fields in snapshot order (`summarizePiSnapshot`), computed the same way on both sides.

**Replace on hydrate.** A node that already holds the session (moving back to a previous owner, which was never told it lost the session) and whose copy is not identical **replaces it wholesale**: it closes the session's idle runtime (a run still active there refuses the hydrate with `busy`), deletes everything it holds for the session (binding, Pi rows, outbox, attachment cache: `dropNodeSession`) and then pulls as above. The old copy is dropped **before** the pull, so a hydrate that fails leaves no stale copy for later commands to run on: they answer `not_found` and the server re-hydrates (*Lazy trigger*). There is no prefix/tail optimization: the whole copy is pulled again.

**Idempotency.** Hydrate converges by content, with no per-command record: a node that already holds an **identical** copy (binding and summary; a replay after a lost acknowledgement, also after a node restart, or a hydrate under another command ID) answers at once without a pull. Hydrates of one session are serialized with provision and runtime opening on the node, so a replay overlapping a slow first attempt waits and then finds the copy. A node that restarts or loses its connection mid-pull has stored nothing new and starts over on the replay. A retryable node rejection (server unreachable mid-pull) and an unknown outcome requeue the move (`DeliveryDeferred`); other rejections fail it, broadcasting `Session move failed: …` and `session_updated` to every viewer. A failed move returns the session to the resting state it left (`revertTo`): at rest on the server, or provisioned on its previous node, which was told nothing and still holds its copy (if it dropped it after a refused report, its next command answers `not_found` and re-hydrates it). The reason stays in `status_error` ("Move failed: …" in the UI) until the next placement change. A failed move does not block commands (`waitUntilProvisioned` proceeds).

**Continuity.** The node's copy starts from the copied `harness_next_seq`, so its next commit's `startSeq` equals the server's `harness_next_seq` and `applyNodeReplica` accepts it; the server's copy simply becomes the replica. The watermarks are not reset by a move: the sequence belongs to the session, not the node, and the previous owner can no longer write (fencing), so no replay from it can apply; the last batch's hash and the lifecycle watermark carry over (a new node's runs have new run IDs). Model and thinking level come from the copied Pi lane (`pi.lane.config`), not from the row; the task snapshot is taken from the server's task row at hydration. A copy with no Pi lane (a session at rest that never ran) gets the row's model as a queued `session.setModel` behind the lazy hydrate, which seeds the lane on the node.

**Lazy trigger.** The next time a session at rest on the server is used, it is hydrated onto its current source's node and the work is delivered there: `enqueueSessionInput` and `Sessions.setModel` queue `session.hydrate` ahead of the work, in the same transaction, unless one is pending (`queueHydrationForUse`). Work for a session at rest that reaches the execution target without a hydrate ahead (behind a move a restart interrupted, which returned it to rest) hydrates it first (`hydrateForDelivery`, which has no outbox row: `recordHydration` marks the session `provisioned`, or records the reason and leaves it at rest) and is then sent to the node; abort answers `aborted: false`. Sessions at rest therefore migrate one at a time, on use; viewing their history never moves them. A failed hydrate fails the work waiting on it with the same message. **Lost node data:** when the node answers `not_found` to submitted work of a session on it, the server re-hydrates it onto that node from its replica (`hydrateForDelivery`, recorded the same way) and sends the command once more.

**Fencing.** Node→server writes (`session.committed`, `session.started`/`settled`, `session.event`, `attachment.store`, `script.*`, `project.createTask`) are accepted only for a session placed on the sending node: `placement_status` neither `server` nor `moving`, and the session's source on that node (`nodeOwnsSession`). A session moved to another node, one being moved (the target has nothing to report until its hydrate settles; the previous owner was re-pointed away), or one at rest on the server rejects them with a **definite** application error: `-32000` whose `error.data` is the NodeError `{code: "not_owner", message: "Node session unavailable: <id>", retryable: false}` (`session.event` is a notification and is just dropped). Reads (`session.snapshot`, `attachment.fetch`) are allowed whenever the session's source is on the calling node (`nodeMayReadSession`), at rest or moving included, which is how a hydrating node pulls it. Today the only node is the internal one (`INTERNAL_NODE_ID`); the checks are in terms of the session's source node so they generalize. On the server nothing but replica application writes Pi tables.

**`not_owner` on the node.** When an outbox delivery (`session.committed`, `session.started`/`settled`, an `attachment` upload) is refused with `not_owner`, the node stops that drain and, serialized with the session's hydrate and runtime opening, drops the session: it aborts and closes its runtime, deletes its pending outbox rows and its whole local copy (`dropNodeSession`). It does not retry. "Inactive" is derived from absence, so no node migration is needed: until the session is hydrated there again, commands for it answer `not_found` (which, if the server routes work there again, triggers a re-hydrate). The drop is keyed to the copy the refused report came from (an in-memory copy generation bumped on every drop), so a late refusal never drops a copy hydrated after it. Agent tool calls refused with `not_owner` just fail as tool results.

**Explicit move.** `POST /api/sessions/:sessionId/move` with `{nodeId: string}` (required; `null` or a missing ID is 400: there is no release to the server) queues the move and returns the session's placement without waiting (`{status, error, available, nodeId, nodeName}`: `moving`, or `provisioned` when it is already there); 409 for a busy session (active run, pending input or undelivered work), a move elsewhere under way, or a node with no source for the session's project; 404 for an unknown session. `GET /api/sessions/:sessionId/move-targets` lists every node as `{nodeId, name, connected, eligible, reason?}`, eligible nodes first and each group in name order; an ineligible node's `reason` is `"current"` (the session is on it or moving to it) or `"no_source"` (it has no source for the session's project); `connected` is whether the internal node's link is open (other nodes report false). It is computed only on request (the UI fetches it when the move dialog opens). Session views (detail and list) carry `placement` (`{status, error, available, nodeId?, nodeName?}`: `nodeId`/`nodeName` name its source's node unless it is at rest on the server); the move and the hydrate's settlement each broadcast `session_updated`, which is how the UI follows a move to completion.

**Limits.** The node holds a hydrating session's rows and attachments in memory until its single write transaction (large histories with many inline images cost memory once); the server recomputes the full summary for every snapshot page (quadratic in pages for very large sessions). Sessions with active runs are never moved. Ownership is per node, not per copy: if a session moves A → B → A while A was offline, A's undelivered reports from its first stay are refused as `not_owner` only while the move back is under way; afterwards they meet the replica's own checks instead (a gap or divergence stays pending until the hydrate replaces A's copy, deleting them; a batch that happens to continue the replica exactly is applied). Cross-node moves with several real nodes are untested (only the internal node exists; tests simulate a second node). A stale copy on a previous owner is kept until that node is refused (`not_owner`) or the session is hydrated there again. While a session moves, session views show it as `moving` ("Moving to …").
