# Node contract

A **node** runs agent sessions: it owns the Pi runtime and the checkout the agent works in, and holds nothing durable ([ADR-015](../adr/015-server-canonical-storage-stateless-node.md)). The **server** never runs a session. It owns product state (projects, tasks, sessions, settings, credentials), **the only copy of every session's AgentHarness storage**, the durable command outbox that delivers work to nodes, and the browser UI/API. The node's Pi runtime reads and commits a session's storage on the server over the link.

This doc covers what the server and node say to each other and what each is responsible for. How the link itself works (socket, framing, JSON-RPC, negotiation, streams) is in [node-transport.md](node-transport.md); read it first.

Today there is one kind of node: a local process (`packages/node`) on the server's machine, linked over a Unix socket. Remote nodes are not built; see [the node architecture plan](../plans/node-architecture.md) for what is open. Decisions behind this design are recorded in ADRs [010](../adr/010-state-derived-idempotency.md), [012](../adr/012-ndjson-unix-socket-local-link.md)–[015](../adr/015-server-canonical-storage-stateless-node.md).

| Concern | Server (`packages/backend`) | Node (`packages/node`) |
|---|---|---|
| Session storage | The only copy: Pi tables in the server database, served over `storage.*` | None: every Pi read and commit crosses the link (`RemoteStorage`) |
| Execution | None | Pi runtime, native tools, Reins tools (which call the server), skill/resource discovery, task branch checkout |
| Commands | Durable outbox, per-session ordering | Idempotent command handlers; no per-command records |
| Credentials | Sole holder and sole OAuth refresher | Reads them over the link; caches in memory only |
| Attachments | Durable bytes for the browser and for providers | In-memory cache of bytes the server holds |

## Packages and import boundaries

The server does not depend on the node package. What both sides need lives in one shared package ([ADR-014](../adr/014-shared-protocol-and-storage-packages.md)); Pi's storage on SQLite (`PiStorageAdapter`, `packages/backend/src/pi-storage.ts`) is the server's alone:

Entry points: `@reins/node-protocol` (one barrel, `src/index.ts`) and `@reins/node-protocol/testing` (the in-memory loopback socket pair and `scriptedCommandHandlers`; tests only). Node tests run Pi over a test storage server (`packages/node/src/testing/storage-server.ts`) that keeps each session in an in-memory Pi `Storage` checked against Pi's storage conformance suite, not over the server's SQLite.

The server's own Pi model context (catalog, model validation, OAuth provider metadata, credential refreshes) is built directly from Pi with the server's credential store (`pi/factory.ts`), not from the node's runtime. The server runs no inference: every model call, task generation included (*Session kinds*), runs in a session on a node.

Boundaries (Oxlint rules in `scripts/oxlint-plugin-reins.cjs`, also checked by `node-dependency-boundary.test.ts`):

- `reins/node-import-boundary`: backend production code never imports `@reins/node` or `@reins/node/*` (exact name or `@reins/node/` prefix, so `@reins/node-protocol` is allowed), nor any package's `src/` path. There are no production exceptions. Backend tests may import `@reins/node` (they start in-process nodes).
- `reins/server-node-process-boundary`: non-test server code never imports `@reins/node/node`, `@reins/node/node-connection`, `@reins/node/local-link` or `@reins/node-protocol/testing`. No backend production code calls a `Node` method; everything crosses the link.
- `reins/node-protocol-isolation`: `packages/node-protocol` imports only `zod`, its own modules and runtime builtins.
- `reins/node-implementation-isolation`: node code never imports server code.
- No server code singles out a node ID. The seeded `internal` node row is migration data only.

## Process model

The server and the local node are separate processes that meet only on the node socket ([node-transport.md](node-transport.md)).

- **Server-only** (`bun run start:server`, `packages/backend/src/index.ts` → `server-process.ts`): opens the product database under `REINS_DATA_DIR`, listens on HTTP and on the node socket. It never starts a node.
- **Node-only** (`bun run start:node`, `packages/node/src/main.ts`): starts the node and dials the socket. It keeps no state on disk: its data directory (`REINS_NODE_DATA_DIR`, default `~/.reins`) holds only the bytes of unfinished `fs.write`s (`partial-writes/`), which it removes when it starts. Logs go to stdout/stderr with a `[node]` prefix. It announces `REINS_NODE_ID`, by default `DEFAULT_LOCAL_NODE_ID` (`"internal"`, the node row the server's migrations seed). `REINS_NODE_TEST_FAUX_PROVIDER` is a **test-only** hook (`src/testing/faux-provider.ts`) registering a scripted model for process-level tests; never set it in production.
- **Combined** (`bun run start`, `bun run dev`; `packages/backend/src/supervisor.ts start|dev`): spawns the server (in dev, `packages/backend/dev.ts` with handler hot reload), the node and, in dev, the frontend watchers. Both inherit the environment, so they agree on `REINS_NODE_SOCKET`. The server exiting stops everything. A node that exits is restarted with exponential backoff (1 s doubling to 30 s, reset after 30 s of uptime). Nothing watches node code, in `dev` either: the node runs new code only after it is restarted (see [hot-reload.md](hot-reload.md)). SIGTERM/SIGINT: SIGTERM to every child, SIGKILL after 8 s, exit 0. The Docker image runs `supervisor.ts start`.

**Startup ordering:** either may start first. A node started before the server redials with backoff (100 ms to 5 s); a server started before the node accepts commands and holds submitted work in its outbox until the node negotiates (direct calls such as abort return `unavailable`).

**Shutdown:** the server on SIGTERM/SIGINT exits through `exit`, removing its socket file. The node on SIGTERM/SIGINT stops redialing and closes its connection first (no new commands), then `Node.shutdown()` **aborts** active runs and closes every live runtime, bounded by 5 s, and exits 0. It does not wait for runs to finish: runs can last longer than a supervisor would wait. A run cut off by a shutdown or a crash is settled as interrupted by the server when the node next connects (*Crash recovery*); Pi leaves its operation pending in the server's copy, and `POST /api/sessions/:id/resume` continues it.

## The link

How the server and node exchange messages is in [node-transport.md](node-transport.md): the socket and its permissions, framing, JSON-RPC, `node.hello` and epochs, the heartbeat, frame caps, wire error codes, the method tables and naming, streams, reconnecting, hot reload and test links. This doc covers what is sent over it.

## Checkout operations

The server reads and writes a source's checkout through the node holding it, never on its own disk ([ADR-018](../adr/018-process-run-and-fs-methods.md)): **git runs on the node through one generic method, `process.run`, while the git logic (which commands, how their output is read) stays on the server**, where it hot reloads. The file browser's filesystem reads and uploads, which are not git and whose shell equivalents differ between Linux and macOS, are typed `fs.*` methods. All are negotiated, request-now node capabilities: never queued, failing at once when the node is offline. Like `skills.list`, all name the source and send the path the server resolves for it (`cwd`); the node has no sources table to check it against yet (node-owned sources are planned).

- `process.run {sourceId, cwd, streamId, argv, env?, binary?}` → `{}`, and opens a stream (node-transport.md *Streams*) of the process's stdout. `argv` is run directly, never through a shell (the server builds arguments from browser input such as paths and branch names); `env` is merged over the node's environment. The node refuses a missing checkout (`not_found`) or a program it cannot find on `PATH` (`invalid_request`, "Program not found: <name>") before answering, and spawns the process when the stream starts. The stream's end frame carries the exit (`{code, signal, stderr}`); cancelling the stream (or losing the link) kills the process. No stdin yet: no server git call writes to one.
- `fs.list {sourceId, cwd, path}` → `{entries: [{name, type}]}`: one directory, files and directories only (no symlinks), directories first, then by name case-insensitively, at most `MAX_DIRECTORY_ENTRIES`. A `path` resolving outside the checkout is `invalid_request` ("Path traversal not allowed"); a missing directory `not_found`.
- `fs.read {sourceId, cwd, streamId, path, maxBytes?}` → `{size}`, then the file's bytes (the first `maxBytes`) as a binary stream. `path` is checked as for `fs.list`; anything but a file is `not_found` ("File not found"). The node reads with `createReadStream`: a sliced `Bun.file` stream never ends for a large file in Bun 1.3.9.
- `fs.write {sourceId, cwd, path, offset, data, last}` → `{size}`: one chunk of a file (`data` base64 of at most `ATTACHMENT_CHUNK_BYTES`, so it fits a frame). `path` is checked as for `fs.list`, and naming a directory is `invalid_request`. Chunks come in order: offset 0 starts the file (creating its directories), each later chunk must start where the written bytes end (`invalid_request` otherwise), and `last` renames the file into place, replacing one there. Until then its bytes are kept in the node's data directory (`<dataDir>/partial-writes/`, named by a hash of the file's path), so an upload that never finishes leaves nothing in the checkout, not even its directories (they are created with the last chunk). The node clears `partial-writes/` when it starts: an upload cut off by a node restart cannot continue (its next chunk is out of order) and is refused. The move into the checkout is a rename, or a copy when the data directory is on another filesystem. Any other filesystem failure (a path through a file) is `invalid_request`. Uploads (`SourceModel.writeFiles`) send each file this way, one chunk at a time.

On the server, a node runs a process through `RemoteNode.spawn(argv, {sourceId, cwd, env?, binary?})`: it opens the `process.run` stream (bounded by a 10 s timeout on the node accepting it) and returns `{stdout, exited}` (`SpawnedProcess`, `spawn.ts`). Git is a `Git` (`git.ts`) built on an injected `Spawn`, so the git logic stays on the server whichever checkout it reads; the server runs no git of its own (tests use `localGit` from `__tests__/helpers/local-git.ts`). Creating a project without a base branch detects it in the project's first source on its node (`createProject`): with that node unreachable the project is not created (503).

**Which checkout a call works in** is the call's source, resolved where the call enters and handed to `ProjectModel` as a `SourceModel` (`resolveSource` in `models/sources.ts`): an agent tool's or script's calling session (`sessions.source_id`, from `sessionToolScope`); a project HTTP request works in the project's default source until the frontend picks among several (node architecture plan). Tasks have no source: a task's sessions may run in several. The source model (`models/sources.ts`) owns what reads or changes its checkout: its `git` runs on its node (`node.spawn` bound to it), as do `listFiles()` (two `git ls-files` runs merged), `listDirectory(path)` (`fs.list`, 10 s timeout), `workspace(baseBranch)` (files and diffs), `sync(baseBranch)` (fetch and fast-forward) and `listSkills()`. Tasks are not closed from git state: whether a branch looks merged depends on which checkout looks. `listDirectory` turns the node's refusals into the domain errors routes already map (`PathTraversalError` → 400, `FileNotFoundError` → 404). An unreachable node (not connected, no answer, link dropped: `RemoteNode`'s `RpcFailure` with code `"unavailable"`, from a call, a process's start, its stdout or its exit alike) reaches the router as it is, which answers 503 (`isNodeUnavailable` in `errors.ts`); models do not translate it. Task creation, reopen and deletion, task diff stats (`null` while the node is offline), spread, push, rebase, the current branch, a file at a ref (`GitTreeFileSystem`) and the diffs (`Workspace`) all go through the source's `git`. A working-tree diff shows untracked files as Git-native new files by marking them intent-to-add in a temporary copy of the index: `Git` runs that as one `sh -c` script through `process.run` (`WITH_UNTRACKED_AS_INTENT_TO_ADD` in `git.ts`: copy the index, `git add -N` each readable untracked file, run the diff, remove the copy on exit or `TERM`), so the index lives on the node and a diff costs one round trip. Patches cross as binary, byte for byte. Working-tree file content (`WorkingTreeFileSystem`, `/files/content` without a ref) reads through `fs.read` (`openStream`, 10 s timeout) in two steps, as a file at a ref does through git: the first 8 KiB for the size and the MIME type (`detectMimeTypeFromBytes`), then the whole file only if the route sends it (a binary file without `download=1` gets a placeholder). Its refusals become `WorkspaceFileNotFoundError` (404) and `InvalidWorkspacePathError` (400) (`nodeRefusal` in `errors.ts`).

## Node API

`@reins/node/node` is the node's in-process API; `connectNode` (`@reins/node/node-connection`) serves it over a connection and nothing else calls it outside tests.

- **Lifecycle.** `startNode()` starts a new, independent node (its runtimes, caches, event seqs, credential cache and connections are its own; no module globals) and takes no in-process server dependency. `attach(server)` adds a connection (the newest serves the node's server calls). `liveSessions()` lists the sessions with a run in progress (for `node.hello`). `shutdown()` is the one teardown: refuses new commands (`Node stopped`), aborts active runs and closes every live runtime; close the connection before it.
- **Commands.** One method per server→node wire method, taking its params (without `epoch`) and returning its wire result: `prompt`/`steer → {inputId}`, `setModel → {modelSet}`, `abort → {aborted}`, `resumePending → {started}`, `close → {closed}`, `listSkills → {skills}` (see *Skills*), `listDirectory → {entries}`; `runProcess` returns the source of the stream `process.run` opens (see *Checkout operations*). `connectNode` registers each as a handler and advertises it as a capability, with `stream.cancel`; `credentialsChanged` (the `credentials.changed` notification) drops the provider's cached credential.
- **Errors.** A definite rejection throws `NodeRejection` carrying a `NodeError`: `invalid_request` (bad attachment, unknown model), `busy` (a runtime running under another binding), `not_found` (a skills checkout that does not exist), `unavailable` (retryable: an attachment fetch with no server). Any other exception (no pending operation to resume, a storage failure) is sent as `internal`, non-retryable.
- **Test seam.** `nodeRuntimesForTesting(node)` (`has`/`open`/`close`) reaches a node's live runtimes; production code must not import it.

**Runtimes.** The node opens a session's runtime on the first prompt, steer, setModel or resumePending from what that command carries (binding, task branch, lane seed, runtime configuration; see *Session commands on the wire*) and keeps it in memory; opening and closing are serialized per session. A runtime open under another binding (the session moved to another source on this node) is closed and reopened when idle and refused `busy` while it runs. `close` aborts a run and closes the runtime; nothing else closes an idle one yet (idle eviction is a follow-up in the plan).

**Link loss.** Runtimes outlive a connection: a run keeps going through a redial (a server handler reload or restart). Every node→server call a run makes follows the newest connection, and **a call that was never sent waits for one**: no connection attached, or one that closed or never negotiated (`NotConnected` in `@reins/node-protocol`: the peer refuses to send on a closed connection, and a call waiting for a negotiation that fails was never sent). It waits for another connection to attach and is sent there, for up to `RECONNECT_WAIT_MS` (30 s, `startNode({reconnectWaitMs})`) in all, then fails. This applies to `storage.*`, lifecycle reports, `credentials.*` and attachment fetches and uploads (an upload restarted on a new connection resends chunks an old one may have received, which is safe: the same ID and content is acknowledged as stored). **A call that was sent is sent again only when the server recognises a repeat:** a `storage.commit` (under its `commitId`) or a lifecycle report (`session.started`, or `session.settled` under its `reportId`) whose reply was lost (outcome unknown: its connection closed or it timed out) is resent on the next connection to attach, within the same wait. Any other call in flight at a drop, and any refused call, fails as it came. A storage call that fails (past the wait, a read in flight at a drop, or refused) fails the run: Pi faults its harness on any storage error and never ends the run itself, so the node sends its `session.settled` (failed, "Session storage failed: …"; lost like any report that cannot be delivered) and ignores any later report from that runtime. The node then marks the runtime **stale**, never reuses it (nor lists it as live), and closes and reopens it from the server's copy before the session's next command; a command whose runtime went stale under it (e.g. a delivery racing a dropped link) runs once more on a fresh runtime, which is safe because every command converges on replay (*Replay idempotency*).

## Node hub (server side)

One hub per handler load (`nodes/node-hub.ts`, built by `createServerState` in `state.ts`, which each handler load's `start` (`server.ts`) calls; closed on a dev reload or process exit, after which the node redials the next load's hub; tests create one with the `createServerState()` helper). It is `state.nodes` (the `NodeHub` interface in `state.ts`) and owns: node links by node ID and the command dispatcher and its `wake()`. It calls product code directly, with the state it belongs to: `nodeHandlers` (`nodes/node-handlers.ts`) serves a node's calls (storage, reports, events, tool calls, credentials, attachments; resolved once per connection, at hello), `settleInterruptedRuns` settles interrupted runs at hello, `sessionRoute` resolves a session's node once per delivery and `onCommandDelivered` notifies settled commands. Interface: `accept(socket)`, `get(nodeId)` (a `RemoteNode`: `connected`, `request(method, input, options)` for any request-now node method, abort and resume included, `openStream(method, input, options)`; see node-transport.md *5. Hub and node API*), `credentialsChanged(providerId)` (*Credentials*), `wake()`, `start()`/`close()`. Callers of `request` choose their own timeout. Outbox delivery timeouts, the concurrency cap and the stream buffer cap are hub options (`NodeHubOptions`). No live runtime crosses to the server.

`sessionRoute` (`nodes/commands.ts`) resolves the session's source to its node, or null when the session or source is gone. The dispatcher's availability check and the send share that one resolution: the hub routes the session, checks that node is connected and sends through the route (`route.send(node, command, timeouts)`: the node's `RemoteNode` and the hub's delivery timeouts). The send builds what the command carries from the rows at send time (`sessionContext` in `nodes/commands.ts`: binding, lane seed, and the kind's runtime configuration and branch); one that cannot be built (an unusable `default_model`, an unknown kind) fails the command. A node whose link closed before the send defers it (`DeliveryDeferred`).

**Default source:** a new session is placed on the source its caller names (child and task sessions inherit the caller's), else on its project's **default source: the project's first (lowest-ID) source** (`defaultSource` in `node-store.ts`, `resolveSource` in `models/sources.ts`). A project has no path of its own: paths live on sources, and a checkout (node and path) belongs to one project (a unique index; `DuplicateSourceError`, 409). A project's first source is created with it, on the node its creator chose (`createProject` in `models/projects.ts`, through `createSource` in `models/sources.ts`; the browser form's node selector, or for a `projects.create` script the calling session's node unless it names one), after the path is checked on that node (`fs.list` of `.`: a missing directory refuses the project, an unreachable node is a 503, and the project is not kept either way). `PATCH /api/projects/:id/sources/:sourceId` moves a source's path, checked the same way (`moveSource`); `GET /api/projects/:id/sources` lists them for the edit form. Selection is policy, not a connectivity check: a session placed on a node that is not connected is created and its work waits.

**Nodes and sources:** `nodes` identifies execution hosts; `sources` binds a project to a host-local path. Sessions persist `source_id` beside `project_id` (triggers enforce agreement). **A session runs on its source's node**; that is the whole of placement. The node runs a session in its bound source path, not the project's current path.

## Command outbox

Submitted session work (`Sessions.submit` in `models/sessions.ts`: the only way to queue it, validating the session's source; callable inside a caller's transaction, it wakes the hub in a microtask, after that transaction commits) reaches nodes through the server's durable `node_command_outbox` ([ADR-010](../adr/010-state-derived-idempotency.md) explains why it needs no receipts). **A command is only that work**: prompt, steer and setModel (`nodeCommand` in `node-methods.ts`), stored in the outbox, delivered in order and replayed when the outcome is unknown. Everything else the server asks of a node, abort and resume (*Abort and resume*) included, is a direct `RemoteNode` call: sent at once, never queued or retried, failing to its caller (`unavailable` when the node is offline).

- **Storage** (`nodes/node-command-store.ts`): rows hold a session ID and the command JSON, not a source (the source is resolved at send time). States are `queued`, `dispatching` and `failed`; settled commands are deleted (the outbox is a queue), so no session state is read from it. `getNodeCommand` parses stored commands strictly, and one that does not parse fails like a delivery exception.
- **Input:** validated prompt/steer (browser WS, scripting sends, child reports) is stored before acknowledgement, keyed uniquely by `(session_id, command_json.clientId)`. A replay with the same payload returns the prior acknowledgement; a different payload under that key is rejected while pending. Once admitted its command is gone, so `enqueueInput` recognizes a replay from the session's storage (`storedInput` in `pi-session-store.ts`: a `reinsInput` with that `reinsId`) and queues nothing. Acknowledgement means stored, not admitted by Pi; later failures surface asynchronously.
- **Dispatcher** (`nodes/node-command-dispatcher.ts`): scans the outbox in insertion order and runs one **delivery chain per session** that sends that session's commands strictly in order, one at a time, re-resolving the session's source before each. Chains of different sessions run concurrently, at most `MAX_CONCURRENT_SESSIONS` (16) at once; others wait in outbox order. A session's work is attempted only while its source's node has an open link. Wakes are hints: submissions, a node negotiating, `start()` and a 30 s poll rescan SQLite; a wake arriving while a chain runs is retried when the chain ends. `stop()` (process shutdown) stops new chains; in-flight deliveries finish and settle.
- **No double delivery:** `claimCommand` is one atomic `UPDATE` moving a row from `queued` to `dispatching` only when no earlier row of its session is `queued` or `dispatching`, so a session never has two commands in flight, even if two dispatchers are accidentally started.
- **Settlement** (`deliverCommand` in `nodes/node-command-dispatcher.ts`): an admitted command is deleted; a definite rejection or delivery exception is marked `failed`, notified and deleted (never retried); an unknown outcome (`DeliveryDeferred`: timeout, lost link, send failure, busy, stale epoch, no connected node) returns the row to `queued` and ends that session's chain until the next external wake. `FRAME_TOO_LARGE` and other protocol failures (`-32602`) are terminal.
- **Failure notifications** (`onCommandDelivered` in `nodes/node-command-notifications.ts`, reached through the hub's services; each browser client keeps the inputs it submitted until they settle, `WsClient.submissions` via `observeSubmission`, so they outlive a hub reload): an input failure goes only to the currently connected WS client that submitted `(sessionId, clientId)` (the existing error shape; the frontend then refreshes activity); disconnected clients are not notified and there is no replay-to-UI. Model-change failures are broadcast to every client with `session_updated`. Scheduling changes notify through `Sessions.notifyScheduling()`.
- **Startup recovery** (`recoverInterruptedDispatches`, whenever a handler load opens the database: at process startup, and on a dev reload once the previous load stopped): every interrupted (`dispatching`) command is set back to `queued` and redelivered once its node connects; the count is logged. Its outcome is unknown, and every outbox command replays safely (see *Replay idempotency*), whether or not the node received it. The row keeps its rowid, so it stays ahead of later work for its session. Failed commands whose notification the restart lost are deleted (failures are never retried). It must never run while another dispatcher could still settle a delivery (that would put a second command of the session in flight), so a reload starts the new load only after the previous load's `stop` resolved: its links closed and its deliveries settled.

## Abort and resume

Abort and resume are not commands: `Sessions.abort(sessionId)` (the WS `abort` message) and `Sessions.resume(sessionId)` (`POST /api/sessions/:id/resume`), on the session model (`models/sessions.ts`), resolve the session's source and call its node directly (`state.nodes.get(nodeId).request`), so abort is not ordered behind queued input. Abort carries the session's `binding`; resumePending may open the runtime, so it carries the same session context outbox delivery builds (`sessionContext`), and one that cannot be built fails the call. Each is bounded by its own timeout (abort 30 s: it waits for the aborted run to go idle; resumePending 60 s: it may open the runtime). Each returns the node's answer (`{aborted}`, `{started}`) or throws `SessionCallFailed` carrying a `NodeError`: the node's own refusal, or `{code: "unavailable", message: "Node unavailable: …", retryable: true}` when the node is not connected, refused it before its handler ran (busy, stale epoch) or the outcome is unknown (timeout, lost link). Nothing is queued or retried. `session.close` is called the same way (`closeSessionOn`, *Moving a session*).

## Session commands on the wire

Every server→node session method crosses the link (outbox commands through `sessionRoute` in `nodes/commands.ts`, abort and resume through `Sessions.abort`/`resume` in `models/sessions.ts`, all as `RemoteNode.request`; handlers in `connectNode`). Each is a capability checked against the connection's epoch before the node runs anything. The server resolves what each carries from its rows on every send: the `binding` (`{sourceId, cwd, createdAt, parentSessionId}`: where the session runs and Pi's session identity), and for the methods that may open the runtime (**opening commands**: prompt, steer, setModel and resumePending; `sessionContext`) the `branch` the node checks out before it opens Pi (resolved by the session's kind: an `agent` task session's task branch; null for a scratch session or a utility kind, which the node checks nothing out for), the `lane` seed (`{model: {provider, modelId} | null, thinkingLevel: string | null}`: the row's model and thinking level, else the current `default_model` setting's; `off` is sent as null) and the `runtime` configuration (`{systemPrompt, tools?, environment}`, resolved from the session's kind; see *Session kinds*). All three are read from the rows at send time, so task edits and prompt changes reach the node the next time it opens the runtime: **a runtime already open keeps the prompt and tools it was opened with** until it is closed (a move, a node restart, a stale runtime) and reopened.

| Method | Params (besides `epoch`, `sessionId`) | Result | Delivery | Timeout |
|---|---|---|---|---|
| `session.prompt`, `session.steer` | `binding`, `branch`, `lane`, `runtime`, `clientId`, `content`, `sourceSessionId` (nullable) | `{inputId}` | outbox | 120 s |
| `session.setModel` | `binding`, `branch`, `lane`, `runtime`, `provider`, `modelId`, `thinkingLevel?` | `{modelSet: true}` | outbox | 60 s |
| `session.abort` | `binding` | `{aborted}` | direct (`Sessions.abort`) | 30 s |
| `session.resumePending` | `binding`, `branch`, `lane`, `runtime` | `{started}` | direct (`Sessions.resume`) | 60 s |
| `session.close` | none | `{closed}` | direct (`closeSessionOn`), best effort | 30 s |

`content` is text blocks and image **references** only (at most 64 blocks, text up to 4 Mi characters, allowed image MIME types, `byteSize` ≤ 10 MiB); inline bytes or other block types are `-32602`. `content` uses the contract schema the outbox stores. No outbox command ID crosses the wire: the node keeps no per-command state.

**Delivery outcomes** (`deliveryOutcome` in `nodes/commands.ts`): a validated wire result is preserved as `NodeResult.value` (`{inputId}` or `{modelSet}`), with no second success vocabulary; a node rejection reaches the dispatcher with the node's own code. When the node did not run the command or the outcome is unknown, delivery throws `DeliveryDeferred` and the command is requeued. (Abort and resume: *Abort and resume*.)

**Delivery timeouts** bound admission, not the run (`NODE_COMMAND_TIMEOUTS`, a hub option): prompt/steer may fetch uncached attachments, check out the task branch and open Pi over the server's storage before admission (120 s); setModel may open the runtime (60 s). A timed-out command is requeued and its replay joins or answers the still-running admission. Abort and resume carry their own timeouts (*Abort and resume*).

**Re-entrancy:** a node serving `session.prompt`/`session.steer` calls `attachment.fetch` and `storage.*` back over the same link before admission; the peer serves inbound requests while its own call is pending.

### Session configuration and the main lane

The server resolves a session's model and thinking level once, at creation (`createSession` in `sessions/create-session.ts`): the creation override, else the `default_model` setting (thinking: the override's level, else the default's). A `default_model` of another runtime is rejected there and when seeding a lane (`piModelSetting` in `models/model-settings.ts`). They are stored on the session row; a later `default_model` change never reaches an existing session. Session creation writes nothing else: **Pi's main lane is created by the node**, through the server's storage, the first time it opens the session's runtime, seeded from the command's `lane` (Pi's harness creates a lane that does not exist with the model it is opened with). The node validates the model against its own registry, so the server never needs to know the node's models; an unknown model rejects the command `invalid_request` (`Model not found: <provider>/<model>`), and a null seed model fails the open ("AgentHarness Pi runtime requires an explicit model") until `session.setModel`. Once the lane exists **it is the only copy of the model selection** and the seed is ignored. Pi does not persist the system prompt, so every runtime open checks out the command's branch (if any) and builds the system prompt from the command's runtime configuration (see *Session kinds* and [node-runtime.md](node-runtime.md)).

### Session kinds

A session's **kind** (`sessions.kind`, migration 046; `"agent"` unless created as another) defines how it runs: its system prompt, its tools and whether the node appends its environment. There is no per-session prompt: it comes from the kind. Kinds live in a registry on the server (`sessions/session-kinds.ts`): a name → a resolver that, given the session's row and its task's, returns what the opening commands carry: the `runtime` configuration `{systemPrompt, tools?, environment}` and the `branch` to check out (absent: none). Defining a kind is one entry (`registerSessionKind(name, kind)`, which returns its removal). Kinds are validated in code, not by the database, so a new kind needs no migration; `createSession(state, projectId, {kind})` rejects an unknown one, as does sending a command for a row whose kind is no longer registered. Only server code creates sessions of a kind; scripts can neither create nor see them.

- **`agent`** (every existing session): the server's Reins prompt (`reinsSystemPrompt` in `sessions/system-prompt.ts`: the persona and editing guidelines, session orchestration when the session is offered `execute`, and the task section for a task session or the project-assistant section for a scratch session, from the session's hierarchy), every tool (`tools` absent), the node's environment appended, and its task's branch checked out (a task session). The prompt text is product code, so it hot reloads on the server ([ADR-019](../adr/019-server-generated-system-prompt-and-session-kinds.md)).
- **Utility kinds**: a fixed system prompt, a chosen tool list (typically `[]`) and `environment: false`, so the model sees exactly the kind's prompt. **A utility kind has no side effects:** no tools, no node environment and no checkout (it names no branch, even on a task session). Background sessions (`background: true`) are the usual home for them.
  - **`task-generator`** (built in): parses freeform intent into a task's `{title, description, branch_name}` JSON, with `tools: []`. `generateTask` (`sessions/task-generator.ts`, for `POST /api/projects/:id/tasks/generate`) creates a background session of it on the request's source with the utility model (the `utility_model` setting, else `default_model`'s; neither: no session, the deterministic task), submits the user's text as a prompt and waits for settlement (`waitForSettlement`, 30 s). The session exists only for the request: whatever the outcome it is deleted (its row, cascading to its transcript, attachments and queued outbox work) and its node is told `session.close` (best effort, as for other deletions). A node that is offline (the prompt waits in the outbox), a timeout, a failed run or a reply that is not the expected JSON gives the deterministic task (the prompt as title and description, a slugged branch). A prompt already in delivery when the session is deleted may still open a runtime on the node after the close; every call it makes for the session is refused, as for any deleted session.

**On the node** (`buildNodeRuntime`): every tool is registered, and the lane's active tools are set to `runtime.tools` (absent: every registered tool), so Pi offers the model only those; a name the node does not have rejects the command `invalid_request` ("Unknown tools: …"). The system prompt is `runtime.systemPrompt`, followed, when `environment` is true, by the node's environment (`environmentPrompt` in `runtime/system-prompt.ts`): the list of the active tools, the REINS docs paths of the node's own install, the checkout's context files (AGENTS.md) and skills. These are machine-local, which is why the node renders them.

### Model changes (`session.setModel`)

`Sessions.setModel` (HTTP `PUT /api/sessions/:id/model` and scripting `sessions.setModel`) validates the provider/model against the server catalog (`findPiModel`), then updates the row and enqueues `session.setModel` in one transaction, wakes the hub and broadcasts `session_updated` without waiting. It is submit-work in outbox order: after earlier commands of the session are admitted (a running prompt picks it up from Pi's next LLM turn) and before later ones; the last delivered change wins. Omitting `thinkingLevel` keeps Pi's current level. The node applies it to the open runtime, or opens one (validating the new model, which also seeds a lane that does not exist or repairs one whose model is gone), and persists through Pi's lane. A replay re-applies the same absolute selection. An unknown model fails the command: every client gets `{type: "error", sessionId, error: "Model change failed: …"}` plus `session_updated`. The row keeps the requested model until the next settlement reports Pi's actual selection.

### Skills (`skills.list`)

The skills a session can invoke live in its source checkout on a node, so the server asks the node for them. `skills.list {epoch, sourceId, cwd}` is a negotiated server→node request (a `capability`), not a session command: no `sessionId`, no binding, no outbox. `cwd` is the source's path as the server resolves it (as in a binding; the node has no sources table). The node reads that checkout with the same discovery prompt expansion uses (`ReinsResourceLoader`: `~/.agents` plus the checkout's `.agents/skills`) and answers `{skills: [{name, description}]}`, at most `MAX_LISTED_SKILLS` (1024) entries, names up to 128 and descriptions up to 4096 characters; a checkout that does not exist is `not_found`.

`GET /api/projects/:id/skills` (`routes/skills.ts`, used for the composer's `/name` suggestions) sends `skills.list` to the node of the request's source (see *Which checkout a call works in*) (`state.nodes.get(nodeId).request`, timeout 5 s). It never queues or waits for a node: when the node is not connected, does not answer in time or refuses, it answers `{skills: [], available: false}` (200, logged at debug); otherwise `{skills, available: true}`. The frontend keeps its last known suggestions when `available` is false (`ProjectStore.fetchSkills`/`fetchLists`), so an offline node shows no error.

## Node→server calls

The node reads and commits session storage, reports run lifecycle, fetches and uploads attachments, runs Reins tools and reads credentials over the same link. Node→server handlers (`nodeHandlers`, `nodes/node-handlers.ts`) are resolved once per connection, at hello, from the node ID it announced, and fenced (see *Fencing*); the transport (`server-peer.ts`) imports no product stores: it is handed the handlers.

### Lifecycle reports

`session.started {epoch, sessionId, runId}` and `session.settled {epoch, sessionId, runId, reportId, status, error?, metadata: {model, thinkingLevel}, tipId}` → `{acknowledged: true}` drive server effects: activity `running`/`finished`, runtime model metadata and a child's report to its parent (`nodes/node-session-events.ts` → `runStarted`/`runSettled` in `sessions/session-runs.ts`; a child's final reply is read there from the report's `tipId` branch).

- The node sends a session's reports one at a time in occurrence order over the newest connection, waiting for one when none is attached (*Link loss*; `sendReport` in `node.ts`). Pi emits `run_start`/`run_end` after the commits they follow, and every commit went to the server first, so a settlement always follows the commits it summarizes. One whose reply was lost is resent on the next connection (*Link loss*), and while a session has a report still to deliver the node lists it in `liveSessions`, so the server does not settle its run as interrupted meanwhile. A report that cannot be delivered (no connection within the wait, a refusal) is logged and lost; *Crash recovery* settles its run.
- `tipId` is Pi's committed `run_end.tipId` (null for a storage fault/interruption with no trustworthy completed branch). The server projects child replies directly from that captured ancestry through `loadBranchMessages`; a delayed report cannot read a newer run's main tip. No node transcript read or reply-read promise is needed.
- Each report is applied inside one server transaction with the session's run record (`sessions/session-runs.ts`, columns on `sessions`), the activity update, the metadata write and, for a child, the parent's steer inserted into the outbox. `started` sets `run_id` (the run in progress); a `started` for the run already in progress applies nothing. `settled` clears `run_id`, increments `settlement_count` and records the latest status/error (`settlement_json`), the storage's `harness_next_seq` at that moment (`settlement_next_seq`) for waits and its `reportId` (`last_settlement_id`); a settlement whose `reportId` is the last applied one is a resend and applies nothing. Broadcasts and the hub wake happen after commit.
- A child whose settlement report is enqueued for its parent clears to idle; if the server could not project the completed branch or the parent cannot receive it (out of scope, source unavailable), the server logs it and marks the child `finished` with no report.
- Pi re-reports `started` with the same run ID in-run (compaction), which the server treats as a repeat. A run the server or node already settled (interrupted, or failed on a storage fault) may be resumed by Pi under the same run ID on the next command; its reports then apply again (a new `started` if Pi emits one, and a new settlement).

### Crash recovery

The node holds nothing that could report a lost run later, so the server settles it (`settleInterruptedRuns` in `sessions/session-runs.ts`, run by the hub when a node negotiates): every session whose source is on that node, whose activity is `running` and whose ID the hello's `liveSessions` does not list is settled as failed ("The run was interrupted: its node restarted or lost its connection to the server") through the same `settled` path as a node report, under the run ID of its last `started` report. A node lists a session while its runtime is streaming and not stale, or while it still has a lifecycle report for it to deliver. Pi leaves the run's operation pending in the server's copy; `session.resumePending` continues it, and a later prompt joins it. A node that never reconnects leaves its sessions `running`.

### `session.event`

`{epoch, sessionId, seq, emittedAt, event}` is a JSON-RPC notification carrying live UI deltas only. `emittedAt` is the node's wall clock (`Date.now()`) at emission, for latency diagnostics only (see [client-telemetry.md](client-telemetry.md) *Session bus capture*); it is forwarded to browsers and never drives behavior. `event` is a **string**: the node's single `JSON.stringify` of one runtime event, made after `sendableEvent` (`packages/node/src/session-events.ts`) replaced any image that is not an attachment reference. The server validates only the envelope (epoch, sessionId, seq, emittedAt, and `event` a string of at most `MAX_SESSION_EVENT_CHARS`, 32 MiB), fences it (see *Fencing*; the one session-row read also supplies the project) and relays the string to every connected browser without parsing it, as `{"event":<event>,"type":"event","sessionId":…,"projectId":…,"seq":…,"emittedAt":…}` (`sessionEventFrame` in `models/broadcast.ts`). The envelope fields come after the payload, so duplicate keys inside the payload cannot override them. Notifications are best effort: an unknown method, invalid params, a failing handler, a stale epoch or an out-of-order seq drops that one notification with a warning and never closes the connection. `seq` is per session and node instance, starts at 1 and counts every emitted event, including ones dropped because no connection was attached; the server drops seqs at or below the last seen on that connection, logs gaps, and forwards `seq` so browsers detect gaps too. There is no replay or resync: a lost event only affects live rendering (the transcript comes from the session's storage on the server). Event shapes, including thin `message_update`s and their keyframes, are in [node-runtime.md](node-runtime.md) *Events*. Run lifecycle is not a session event.

### Attachments

- `attachment.fetch {epoch, sessionId, attachmentId, offset}` → `{attachment: {data, mimeType, byteSize, sha256, filename?, width?, height?} | null}` returns base64 of bytes `[offset, offset + 512 KiB)`. The node loops over offsets, requires consistent metadata and exact chunk lengths, verifies size and sha256, and caches the bytes in its in-memory `AttachmentCache` (`node-attachments.ts`) before prompt admission. Provider input is hydrated from the cache; a miss (history from before the runtime opened, e.g. after a node restart) is fetched from the server then, and an attachment the server no longer holds becomes a provider placeholder. With no connection, a prompt/steer needing an uncached attachment returns `unavailable`. A session's cache entries go when its runtime closes.
- `attachment.store {epoch, sessionId, attachmentId, mimeType, sha256, byteSize, filename?, width?, height?, offset, data}` → `{stored: true} | {nextOffset}` uploads node-created image bytes. **The node assigns `attachmentId`** (`att_<uuid>`). If the session already holds that ID with the same content the server answers `{stored: true}` at once (idempotent replay); different content under that ID is rejected. Otherwise the server keeps one partial upload per connection and key (at most 8), answers `{nextOffset}` for an out-of-order chunk, verifies the sha256 after the last chunk and stores under exactly the node's ID (the upload MIME allowlist and 10 MiB limit apply; an ID another session holds rejects). Identical bytes under another ID are stored again, never remapped, so every transcript reference resolves as written.
- Limits (`MAX_ATTACHMENT_BYTES` 10 MiB, `ATTACHMENT_IMAGE_MIME_TYPES`) are exported by `fields.ts` and used by both sides. Each chunk call has a 30 s timeout.

**Images never cross in events or commits as bytes.** User prompt images are references from the start. Tool-result images are converted where Pi produces them: the node's `after_tool` hook (`runtime/tool-images.ts`) replaces each inline image with a reference before Pi stages the result, reusing a cached attachment of the session with the same sha256/MIME, else **uploading the bytes now** under a new ID (`attachment.store`) and caching them, so the server holds the bytes before any commit references them. Images outside the allowlist, empty or over 10 MiB, and images whose upload fails, become a text note (`[Image omitted: …]`). `RemoteStorage`'s `prepare` step applies the same conversion to any inline image Pi commits without the hook (recovered checkpoints, hooks cut short by abort). Stray inline images in live events (partial tool results) are replaced by `[Image attachment unavailable]` (`sendableEvent` in `session-events.ts`). It scans only events that can carry images (message snapshots on `message_start`/`message_end`, `turn_end`, `agent_end`, `entry_added`, and tool results in `tool_execution_update`/`tool_execution_end`); streaming assistant updates hold only text, thinking and tool calls and skip it. The server relays events unread, so **this node check is the only guarantee that events carry no image bytes**; a node must not skip it. Providers still receive bytes: `toProviderMessagesForSession` hydrates references through the cache.

### Agent tools

All tool definitions live on the node: native read/write/edit/bash (`@reins/node/host-tools`) and the Reins tools `create_task`, `search` and `execute` (`@reins/node/reins-tools`). Their names, descriptions, schemas and order are pinned by a snapshot test (`runtime/reins-tools.test.ts`). Each Reins tool forwards one request:

- `script.execute {epoch, sessionId, callId, code}` → `{ok: true, text} | {ok: false, error}`: the server runs the script in its `node:vm` sandbox against the scripting API (`tools/execute.ts`). 5 min timeout.
- `script.search {epoch, sessionId, query}` → `{text, matchCount}` (`tools/search.ts`). 30 s.
- `project.createTask {epoch, sessionId, title, description, branchName?, prompt?}` → `{task, sessionStarting}` (`tools/create-task.ts`). 60 s.
- `script.cancel {epoch, sessionId, callId}` (notification): aborts that script's `AbortSignal` on abort or timeout of `script.execute`; closing the link aborts every in-flight script.

Params name only the calling session; strict schemas reject project/task fields, and `nodes/node-tool-calls.ts` derives scope from the server's session row. None is retried. Transport failures become tool results: an unknown outcome says the call "may have run"; no connection, busy, invalid params or stale epoch mean it did not run.

### Credentials

**The server is the sole credential holder and the sole OAuth refresher** ([ADR-013](../adr/013-server-holds-credentials.md)). A node needs no credential configuration: every Pi model runtime it builds reads provider credentials through `RemoteCredentialStore` (`packages/node/src/credentials.ts`). Refresh tokens never leave the server.

- `credentials.get {epoch, providerId}` → `{credential}`: the stored credential or `null` (logged out; Pi then falls back to ambient auth, e.g. provider environment variables in the node's environment).
- `credentials.refresh {epoch, providerId}` → `{credential}`: runs Pi's own refresh (`getAuth`) against the server's `DbCredentialStore`, whose `modify` is serialized per provider for the process and persists the rotated credential, so concurrent nodes and the server refresh a login at most once. Failure is `-32000` with `{code: "unavailable", retryable: true}` and "OAuth refresh failed for <provider>; sign in again on the server if this persists". No message carries token material.
- `credentials.list {epoch}` → `{credentials: [{providerId, type}]}`, no secrets.
- `credentials.changed {epoch, providerId}` (server→node notification, a capability): a credential for the provider was set or deleted on the server. The routes that change credentials send it to every connected node through the hub (`state.nodes.credentialsChanged`): `PUT`/`DELETE /api/auth/api-keys/:provider`, a completed OAuth login (`/api/oauth/start` once Pi stored it) and `DELETE /api/oauth/:providerId`. A routine OAuth refresh does not send it: nodes re-read a token entering the refresh window themselves, and a notification would only discard the refreshed token the asking node is about to cache. Best effort: an offline node, or one that misses the frame, re-reads everything when it next attaches.

These are not per session, so any negotiated connection is served; **a remote node must be enrolled and authenticated before they are exposed to it.** Handlers: `nodes/node-credentials.ts`.

*Wire shape* (`nodeCredential`, strict): `{type: "api_key", key?, env?}` or `{type: "oauth", access, expires, enterpriseUrl?, availableModelIds?, gatewayConfig?}`. `toNodeCredential` copies only `OAUTH_WIRE_FIELDS`, the non-secret fields Pi's providers read at request or catalog time; the schema rejects `refresh` or any other field (`-32603`). On the node an OAuth credential carries `refresh: ""` only because Pi's type requires it.

*Node store:* `read` returns a fresh cached credential or calls `credentials.get` (concurrent reads share one call). `modify(providerId, fn)` is how Pi refreshes and how a login would persist: a function that returns a credential for no prior credential is a login and rejects ("sign in on the server"); otherwise the store returns a fresh cached OAuth credential or calls `credentials.refresh` (shared by concurrent callers). `list` calls the server; `delete` rejects. The cache is memory only, per provider, with no TTL: an API key stays for the life of the connection; an OAuth entry until it enters Pi's 5-minute refresh window (`OAUTH_MIN_VALIDITY_MS`). Every entry is dropped when a connection attaches, and a provider's entry on `credentials.changed`; logged-out results are not cached. A `credentials.*` call in flight when its provider (or the whole cache) is invalidated is not cached, and later reads do not join it, so a stale answer never outlives the change. With no connection, a cached credential still serves `read`; a miss, a token in the refresh window and `list` wait for a connection (*Link loss*), then reject with "Credentials unavailable: no Reins server connection".

### Session storage (`storage.read`, `storage.commit`)

The node's Pi runtime keeps a session's AgentHarness storage on the server ([ADR-015](../adr/015-server-canonical-storage-stateless-node.md)): `RemoteStorage` (`packages/node/src/remote-storage.ts`, Pi's `Storage`) turns every read and every commit into one of these calls, and the server serves each from a fresh `PiStorageAdapter` on its own database (`readStorage`/`commitStorage` in `nodes/node-storage.ts`). Schemas: `storageReadParams`/`storageReadResult`, `storageCommitParams`/`storageCommitResult` in `server-methods.ts`.

- `storage.read {epoch, sessionId, op, args}` → `{op, …}`: one read method of Pi's `Storage`, its arguments as `args` and its result named by `op`:

  | `op` | `args` | Result |
  |---|---|---|
  | `getEntries` | `{ids}` | `{entries}`: the entries found, in request order (Pi's `Map`) |
  | `getValue` | `{namespace, key}` | `{value: {namespace, key, value, seq} \| null}` (null: Pi's `undefined`) |
  | `scanValues` | `{namespace, key}` (key prefix) | `{values: [{namespace, key, value, seq}]}` |
  | `readList` | `{namespace, key, options?: {cursor?, order?, limit?}}` | `{elements: [{seq, value}]}` |
  | `scanBranch`, `scanBranchStructure` | Pi's `StorageBranchScan` | `{entries}` (entries, or payload-free structures) |
  | `scanEntries` | Pi's `EntryScan` | `{entries}` |
  | `scanUsage` | Pi's `UsageScan` | `{rows}` |
  | `getStats` | `{}` | `{stats: {messageCount, usage}}` |

  The node rebuilds Pi's value addresses (`value(namespace, key)`) and `Map`s from these.
- `storage.commit {epoch, sessionId, commitId, writes}` → `{firstSeq, seqs, timestamp, stats}`: Pi's `Write[]` as the node produced them, applied in one server transaction by the adapter (`PiStorageAdapter.commitOnce`), which runs Pi's `prepareStorageCommit` and `validateCommittedWrites` against the server's copy and assigns the seqs; the result is Pi's `CommitResult`. `commitId` is the node's fresh ID for the commit, kept when it is resent. The session row keeps the last applied commit's ID and result (`last_commit_id`, `last_commit_json`), written in the same transaction; a commit under that ID is answered with that result and writes nothing. Only the last commit can come again, since a session's commits go one at a time.

Reins-owned structure is strict (an unknown `op`, write kind or extra field is `-32602`); Pi's own bodies (an entry's payload, values, list elements, usage) cross as the JSON Pi's storage writes and reads, with only their envelope checked (entry `id`/`parentId`/`type`, plus `seq`/`timestamp` when stored). Results are not chunked: a read is bounded by the frame cap (64 MiB locally).

**Fencing:** reads and commits are served only when the session's source is on the calling node (see *Fencing*). Otherwise both are refused as `-32000` with `{code: "not_owner", message: "Node session unavailable: <id>", retryable: false}`. **Refusals are definite:** a read or commit Pi's storage refuses (a duplicate entry or usage ID or a missing parent: a stale or concurrent writer; an unknown branch entry; an invalid list limit) is `-32000` with `{code: "invalid_request", retryable: false}` and changes nothing. **Resends:** `RemoteStorage` sends commits one at a time in admission order, each under a fresh `commitId`; the node resends one whose reply was lost on its next connection (*Link loss*), and one still unanswered past the reconnect wait (or that timed out with no new connection) rejects with the connection's `RpcFailure`. `new RemoteStorage(sessionId, server, prepare?)` takes the node's server-call surface (`readStorage`, `commitStorage`, as the connection has them) and an optional `prepare` step that rewrites each commit's writes just before it is sent, in commit order (the node uploads inline images there; see *Attachments*). `close()` seals admission, waits for admitted commits and releases nothing on the server. Proven by Pi's `createStorageConformance` through the hub's loopback link (`__tests__/nodes/node-storage.test.ts`).

## Fencing

Every node→server call about a session (`storage.read`/`storage.commit`, `session.started`/`settled`, `session.event`, `attachment.fetch`/`attachment.store`, `script.*`, `project.createTask`) is served only when **the session's source is on the calling node** (`nodeOwnsSession` in `sessions/session-ownership.ts`). Otherwise it is refused with `-32000` and `NodeError` `{code: "not_owner", message: "Node session unavailable: <id>", retryable: false}` (events are dropped). An unknown session is refused before any product service runs. Agent tool calls refused with `not_owner` fail as tool results; a refused storage call fails the run. Credentials are not per session: any negotiated connection is served.

## Replay idempotency

There are no receipt tables on either side ([ADR-010](../adr/010-state-derived-idempotency.md)): "already applied" is derived from state, so a replay after a lost acknowledgement or a restart of either side is **acknowledged as success** and applies nothing twice.

**Node → server:** a commit or lifecycle report whose reply was lost is resent (*Link loss*). Commits and reports each go one at a time per session, so only the last applied one can come again, and the session row keeps just its ID: a commit under the last `commitId` is answered with its recorded result (see *Session storage*); otherwise Pi's sequence check refuses a stale or duplicate writer. *Lifecycle reports:* a `started` for the run already in progress (a resend, or Pi's in-run compaction) applies nothing; a settlement under the last applied `reportId` applies nothing, and any other settlement applies (a second settlement for the same run is a resumed run, so the run ID cannot tell a resend). *Attachments:* the same content under the same ID is acknowledged; different content rejects.

**Server → node commands** converge on Pi's state in the server's copy:

- **prompt:** Pi admission is durable (`lane.accept` commits the `reinsInput` keyed by `reinsId` = the command's `clientId`). A replay finds that input and returns it; an in-flight admission of the same input is joined. A recovered operation is driven again only if not already active.
- **steer:** `lane.steer` commits the queued input and Pi moves it from queue to transcript in one commit, so checking the queue first, then entries, cannot miss it. Residual: an abort discards queued steers, so a steer whose reply was lost and which an abort discarded before the replay is re-queued (a resurrection, not a duplicate).
- **setModel:** an absolute selection, re-applied.
- **abort, resumePending, close** are not commands: direct calls to the session's node, never replayed (*Abort and resume*). Abort with no live runtime returns `{aborted: false}` without opening Pi; resumePending with nothing to resume is an `internal` rejection; close with no open runtime returns `{closed: false}`.

Verified by `__tests__/integration/command-replay.test.ts` (replay after a timeout, after Pi admitted an input the server never heard of, and after a server restart interrupted a delivery), `__tests__/server-process.process-test.ts` (real processes, `bun run test:process`: a server killed mid-delivery, a node frozen across a handler reload or a server restart, a run and queued input across a handler reload, a node killed and a server restarted mid-run), `__tests__/nodes/node-hub.test.ts` (a commit reply lost across a hub replacement) and `packages/node/src/node.test.ts`.

## Server reads projections only

Server code reads a node's sessions from its own tables, so it works unchanged with the node in another process:

- **Activity** (`models/session-activity.ts`): `sessionActivity(row)` is `running` when `activity_state` is `running` (set/cleared by lifecycle reports), `queued` when prompt/steer input for the session is still `queued`/`dispatching` in the outbox, else `idle`. `activeSessionIds()` applies the same rule across sessions. Reading writes nothing. Used by session views (`pendingOperation` only when idle), task deletion (any non-idle session blocks it) and `/api/health` (`activeSessions`, `streaming`). Gap: an admitted input whose `started` has not arrived reads `idle`.
- **Wait** (`waitForSettlement` in `sessions/session-runs.ts`, behind `SessionInstance.wait` and `api.sessions.wait`): polls projections every 10 ms: it tracks every input it sees pending in the outbox and resolves once none is pending, the session is not `running`, and every tracked input the node admitted is covered by a settlement. **Admission is proven by the session's storage** (settled commands are deleted): an admitted input is a `reinsInput` whose `reinsId` is the command's clientId, either a transcript entry or a steer Pi still holds (`pi.pending.entry`). Pi commits it before the node answers the command. An entry is covered once the latest settlement was applied after it (`settlement_next_seq` above its seq). A failed input never reaches storage and expects no run. The result is the transcript's final reply with the latest settlement's status/error (`completed`/`failed`/`cancelled`, or `idle` with no reply), `timeout` at the deadline; an `AbortSignal` rejects with `AbortError`. Limits: an input admitted before the wait began whose `started` has not arrived reads as settled; an input admitted while an earlier run was active can be covered by that run's settlement.
- **Abort** (`ws.ts`, through `Sessions.abort`): always calls `session.abort` on the session's node; the node answers `{aborted: false}` when nothing is live.

## Moving a session

A session runs on its source's node, so moving it is re-pointing its source (`sessions/session-ownership.ts`). `POST /api/sessions/:sessionId/move {nodeId}` checks the session is idle **on the server** (not `running`, no pending input and no other queued/dispatching command; otherwise 409) and, in one transaction, sets `source_id` to the target node's source for the project (409 when there is none; 404 for an unknown session). Moving to the node it is on changes nothing. Every commit of its last run went to the server, so nothing is left behind. The previous node is told `session.close` (`closeSessionOn` in `sessions/session-ownership.ts`: only if it is connected, 30 s timeout, failures logged; best effort, not awaited): it aborts a run and closes the runtime. From the update on, its calls for the session are refused (*Fencing*), and the session's next command opens it on the target. The response is the session's placement view; the move broadcasts `session_updated`. `GET /api/sessions/:sessionId/move-targets` lists every node as `{nodeId, name, connected, eligible, reason?}`, eligible first, each group by name; `reason` is `"current"` or `"no_source"`.

Session views expose `placement: {available, nodeId, nodeName}`: the node of the session's source and whether it is connected.

**Session deletion.** Deleting a task or a project deletes its sessions' rows (and their storage) on the server, as task generation deletes its background session (*Session kinds*); the caller reads each session's node first and tells it `session.close` afterwards (`sessionsOnNodes`, `closeDeletedSessions` in `sessions/session-ownership.ts`; best effort, not awaited). The node holds nothing else for a session, so there is nothing to track: a node that is not connected, or misses the close, keeps a runtime whose every call for the session is refused (the session is unknown) until the node restarts.
