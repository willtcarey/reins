# Internal node seam

`packages/node/src/contract.ts` is the isolated `@reins/node/contract` export of a separately buildable node package. It contains a versioned semantic vocabulary for session provision, prompt, steer, abort, pending resume, typed results and observations. It imports no server, Pi or browser modules; Oxlint restricts the contract's imports to `zod` and backend imports to declared node package exports. Future daemon implementation belongs elsewhere in `packages/node/src/`, not in this export. `deliveryPolicy()` classifies provision, prompt and steer as `submit-work`, matching server outbox admission; abort and pending resume remain immediate controls. The classifier does not itself deliver commands. The semantic contract alone does not guarantee delivery or offline execution. Future read-only workspace/git commands should use `request-now` and return unavailable when offline. `node-command-store.ts` owns SQLite outbox rows and transitions; `models/node-command-projection.ts` owns submission/projection and a wake hint; `models/node-command-dispatcher.ts` resolves the session's current source and owns the sole delivery path. Session creation atomically stores the session and provision command, then signals a dedicated dispatcher after commit. The signal carries no command payload; startup, node availability/reconnect wake, and a 30-second poll rescan SQLite. The dispatcher resolves the session's current source before claim and uses the internal adapter to admit provisioning without constructing Pi. Creation returns a persisted ID and scheduling projection without awaiting the dispatcher or returning a live runtime. Browser HTTP creation returns a session view immediately; validated prompt/steer and scripting child starts persist their input without waiting for Pi admission (unsupported remote sources still reject input). The node adapter lazily opens/reopens Pi when an addressed input or explicit pending resume arrives. Session views distinguish provision scheduling from runtime activity; negative admission is `failed`, transport/exception ambiguity is `unknown`, and neither can automatically replay. The start signal is a hint; the periodic scan recovers missed hints. Only process database initialization marks orphaned dispatching rows unknown: handler hot reload must not mark previous in-flight work unknown. `stop()` clears the timer. Prompt and steer now persist validated input in `node_command_outbox` before acknowledgement, keyed uniquely by `(session_id, command_json.clientId)` via a SQLite expression index (the clientId travels only inside the command payload); a replay with the same operation/content/source returns the prior admission acknowledgement. A different payload with that key is rejected. The single command dispatcher scans `node_command_outbox` in insertion order across all persisted operations. An unresolved earlier command fences only its session; a queued offline provision or unknown admission cannot stall unrelated sessions. Provision must be admitted before its inputs; the internal node adapter interprets the command and owns readiness, lazy runtime opening and Pi admission; the transport claims and settles the command without knowing its operation. There is no input-only scan or claim lifecycle. The dispatcher scans, checks predecessor/source availability and sends one validated `NodeCommand` through the selected adapter. `node-command-transport.ts` alone claims and settles generic delivery, recording an explicit negative result as failed and exceptions (including malformed stored commands) as unknown. The dispatcher fences inputs behind provision, while `@reins/node/node` interprets node-owned commands and lazily assembles/reopens Pi with node-local canonical storage and injected product policy; server-side `node-command-notifications.ts` handles scheduling/input-failure notifications after delivery. The adapter does not read the outbox or broadcast product events. Legacy persisted open/reopen is unsupported. Provision has an atomic node-side receipt; prompt/steer receipts follow Pi admission non-atomically, so absence of a receipt cannot resolve an unknown outcome. Provision scheduling changes notify through `Sessions.notifyScheduling()`, not a dispatcher-level broadcast. Eventual input failures use `node-command-notifications.ts`: only the currently connected submitting WS client registered for `(sessionId, clientId)` receives the existing error shape. Disconnected clients are not notified; the failure remains in the outbox, and no replay-to-UI mechanism exists yet. Scripting sends and child reports return on enqueue rather than Pi admission; explicit wait still observes runtime settlement. Process startup marks interrupted dispatches `unknown` and blocks later inputs in that session; without an atomic Pi admission receipt, interrupted sends cannot be replayed safely. Explicit abort and resume remain immediate controls rather than queued behind input. Errors after enqueue surface asynchronously on the existing WS error path, not as a retraction of the acknowledgement. Queued inputs survive process loss and are recovered by the shared dispatcher scan; remote execution and automated unknown reconciliation remain unsupported. Provision only establishes source admission: model validation and Pi construction happen on the first addressed command, so an invalid configured model leaves provision admitted but the input outcome unknown and later inputs fenced. A durable node-side receipt for safe replay is still missing. The outbox stores a session ID and operation, not a source. Without Pi-side durable admission keyed by command ID, dispatch failures and interrupted dispatch remain `unknown` rather than retried. Queued commands are retained when no adapter is available; the dispatcher polls for eligible commands. No external node adapter is implemented. Semantic contract v3 uses a single durable `session.provision` (no open/reopen commands), attachment references and `sourceSessionId`; it is **not** a network protocol: no handshake, framing, correlation, ordering, delivery guarantee or serialized runtime event payload is promised. Change schema meaning with a version bump; negotiate incompatible versions closed when transport exists. For existing installations from the in-progress internal-node spike, reconcile schema changes on the affected development database before using the new code; the fresh schema defines `storage_owner` in `032_node_replica_receipts` and a provision index in `030_node_command_outbox`. Unknown outcomes remain fenced, never automatically retried. Schema changes take effect only when the backend starts with a new database connection.

`handler.install()` acquires the `@reins/node/node` instance via `startNode()` (releasing its lease on uninstall) before the dispatcher drains work. Overlapping handler installs on the same node SQLite connection reuse a live node/runtime cache; old in-flight server-handler work can finish without closing an active Pi run. `runtimes/internal-node.ts` is the server bootstrap: it injects the node SQLite connection, exact replica delivery callback, and an in-process product-policy preparer; it resolves and passes the source/path/created-at/parent binding from product rows. The node itself never imports backend state or tables. `startNode()` initializes the node SQLite schema and returns a running node; `send()` binds and checks provisioned sessions, opens node canonical storage with ordered pending-commit delivery, and executes addressed commands. The dispatcher retains server scheduling, source lookup, claim/settle, failure notification and UI projection. `runtimes/node-execution.ts` routes immediate controls through the same instance. Legacy server-owned sessions continue through `legacy-session-execution.ts` and server SQLite. The server applies node committed writes and receipts in `runtimes/pi/node-storage.ts`; the node deletes outbox batches only after that callback succeeds. Pi storage SQL is shared in `@reins/node/pi-storage`, with a server-only writer guard in `runtimes/pi/storage-adapter.ts`.

**Intermediate seam:** `packages/node/src/runtime/build.ts` constructs Pi for new node-owned sessions from node-local storage/resources/native tools and owns the runtime map; backend `SessionManager.open()` now rejects node-owned sessions. Its old builder/registry path still serves existing server-owned sessions. Server `prepare()` supplies model/settings, credentials, task checkout, custom DB tools, prompt formatter, lifecycle and observer as in-process JS values/closures. For node-owned sessions, the server supplies attachment bytes through a separate async callback; the node verifies their checksum and declared MIME/size once when fetched and materializes them in its disposable SQLite cache before prompt admission, then hydrates provider input synchronously from cached bytes. Opening a runtime does not fetch historical image bytes; an uncached historical reference becomes a provider placeholder. Native Pi drive/reopen code now lives in `@reins/node/pi-runtime`; `@reins/node/runtime` creates Pi model/resource context with an injected credential store, `@reins/node/host-tools` creates cwd-scoped native tools and execution environment, and `@reins/node/resources` / `@reins/node/prompt` own local discovery and slash expansion. The server still invokes these modules in-process and passes product credential and attachment adapters; it holds only legacy server-owned live runtime instances in `ServerState.sessions`. Slash expansion now uses the session's bound source cwd rather than the project's current path. The node builder takes the immutable node session binding (created-at, parent ID and cwd) and canonical storage directly. The legacy server builder resolves those fields from the product row. The server bootstrap still verifies the binding against product identity before opening the runtime; model, auth, attachment and tools remain product-dependent. This is not independently runnable node Pi: product credentials, tools, lifecycle, browser events and image bytes cross an in-process seam, not a serializable protocol. Files/git still execute in the server process and unsupported remote sources remain queued or fail closed. Node provision receipts are durable, but prompt/steer admission receipts are not atomic with Pi and `unknown` input cannot be replayed; no remote daemon or network transport exists. See `docs/plans/node-architecture.md` for ownership and recovery limits.
