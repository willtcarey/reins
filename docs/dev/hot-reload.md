# Dev Reload

Under `bun run dev`, the server's **app** hot reloads: its HTTP/browser handlers, product services, the session runtime code **and the node hub**. **The process** is the OS process, which lives until a restart; **the app** is the server's swappable code and what it builds (routes, ws handlers, the node hub and links, the node bundle, models): a dev reload replaces the app, production starts one. A reload closes every node's connection and each node redials the new app; tool calls in flight ride through the redial, a bash command picking its output up again ([ADR-020](../adr/020-reloadable-node-hub.md)). **Sessions run on the server** in runtimes the process keeps across reloads (*Sessions on the server*): a reload neither pauses nor interrupts a run, and a running runtime keeps its code until it is idle. The node reloads only when asked (*Reloading the node*, [ADR-021](../adr/021-explicit-node-reload.md)). The process's own code (the process-owned sources below: `ServerProcess`, the open sessions and the database connection included) needs the process restarted, which the dev server does by itself, the node running on (*Restarting the server*); the protocol needs the server and node restarted together.

## What triggers what

| Edit or request | What happens | Runs | The node and its commands |
|---|---|---|---|
| App source (`packages/backend/src`, not process-owned; `@reins/telemetry`), or `kill -USR2 <server pid>` | **App reload** (*What reloads*) | Go on, never paused | Keeps running; its link drops and it redials the new app; a running command goes on and is picked up |
| Process-owned source (`process-owned.json`, or the list itself), or `kill -HUP <server pid>` | **Server restart**, once the new code builds (*Restarting the server*) | Paused, suspended, resumed by the next process | Keeps running; its link drops and it redials; a running command goes on and is picked up |
| Node source (`packages/node`): `bun run node:reload`, `api.nodes.reload()` | **Node reload** (*Reloading the node*) | Go on; tool calls wait for the node | Restarted once no command runs |
| `supervisor.ts`, `@reins/node-protocol` | Nothing but a warning for the protocol: **restart `bun run dev`** (*What requires restart*) | Suspended and resumed | Stopped and started again: commands are cut off |

## Ownership

| Lifetime | What lives there | Who may keep a reference to it |
|---|---|---|
| **Process** (until a restart; the process-owned sources below) | `ServerProcess` (`state.ts`): the database connection (`db`, opened once by `database.ts`: file, pragmas; each app migrates it, none closes it), `broadcast` (sends a frame to every browser connection; the process registers the sockets on open and close, so they outlive apps), `sessions` (`OpenSessions`: live runtimes, openings, submission chains, event seqs, the pause gate, the idle sweep), `credentialLocks` (the credential store's per-provider locks), `app` and `registerApp(app)` (the current app, a plain property: undefined between apps), `frontendDir`, `nodeSocket`. Also the HTTP server and the dev watcher | Anyone: each app (`AppState.process`), every session runtime, whichever app built it |
| **App** (one start to its stop; `server.ts`, replaced as a whole on every reload) | `AppState`: `process` plus its own node hub (`nodes`, connections and announced builds), `/nodes/link` endpoint (`nodeLinks`), node bundle (`nodeBundle`) and the node socket listener; what it offers sessions (`App`, `app.ts`: `node()` and the Reins tools), registered with the process from its start to its stop; its routes, ws handlers, models and module state (the stores' `getDb()` and open sessions, set from `process.db` and `process.sessions` at each start) | The app's own code: routes, ws handlers, models, the hub. **Never a session runtime**: it reads the current app per call, `process.app` |
| **Open session** (opened on use to its idle close; `session-runtime/`) | A live runtime (`OpenSession` in `OpenSessions.live`): its AgentHarness, storage (`PiStorageAdapter` on `process.db`), model runtime and credential store (over `process.credentialLocks`), attachment cache and tools, built by one app's code and kept on it until closed. **Reaches directly**, with its own code: storage, attachments and credentials on the process, its events (`process.broadcast`), its run lifecycle (the session row on `process.db`, `session_updated` through `process.broadcast`) and a child's report to its parent (the parent's runtime through `process.sessions`, opened with this runtime's code if needed). **Through the app** (`process.app`, at each call; none in the gap): its node (`node()`) and the Reins tools | The process's `OpenSessions` only; an app calls it through `SessionRuntime` |
| **Request** (one HTTP request, browser message, tool call or script) | `Models` (`models/models.ts`) and what they build (a `Broadcast`, a credential store, `Sessions`, `Nodes`, `ProjectModel`) | That request's code |

**The rule:** a session runtime may keep the `ServerProcess`, never an `AppState` or an `App`; everything it needs of an app it reads from `process.app` at each call, and handles there being none (a reload's gap; session-runtime.md *Reaching the current app*). The types enforce it where practical: a runtime is opened and built from a `ServerProcess` only (`openSessionRuntime`, `buildSessionRuntime`'s `RuntimeOpening`), and `App` hands out nothing session-bound to keep (its tool methods take the session ID; a runtime asks for its node again at each call). An app's routes, ws handlers and models take the `AppState` and reach the process through `state.process`; nothing copies a process field into the app's state.

**Process-owned sources** (`packages/backend/src/process-owned.json`, relative to `src/`): `index.ts`, `server-process.ts`, `dev-build.ts`, `dev-watch.ts`, `process-state.ts`, `database.ts`, `logger.ts`. They import at runtime only each other, `@reins/node-protocol`, third-party packages and builtins (types from anywhere, with `import type`); the process owner reaches app code only by importing the app's entry (`server.ts`) dynamically. Oxlint's `reins/process-owned-imports` enforces it from the same list. In dev the app is a separate bundle: a process-owned module importing app code (`app-globals.ts`, `node-store.ts`, `models/*`) would run a second copy of it, with its own module state. App code may import a process-owned module only for what keeps no state (`logger.ts`): the app's bundle gets its own copy.

`server.ts` exports one function, `start(process, {recoverRuns})`, and the process owner calls it with its `ServerProcess`. `start` makes the process's database the one the stores' `getDb()` returns, with the process's open sessions the session store derives running sessions from (`injectProcessState`) and prepares it (`prepareDatabase` in `app-globals.ts`: migrations), builds the app's state (`createAppState` in `state.ts`: a new hub and `/nodes/link` endpoint around the process), binds the node socket (`process.nodeSocket`), registers what it offers sessions (`process.registerApp(createApp(state))`), resumes the runs a previous process left running when it is the process's first app (`recoverRuns`, session-runtime.md *Recovery*) and returns the app's `fetch` and browser `message` handlers (state bound in) and `stop`. `stop` unregisters the app (`process.app` is undefined until the next one; scripts it runs for sessions are aborted) and closes the hub, listener and `/nodes/link` sockets at once (closing the links ends their calls). It does not close the database: the process owns it ([ADR-029](../adr/029-sessions-on-the-server-nodes-host-tools.md)).

The process owner orchestrates: at startup it creates the `ServerProcess` (`createServerProcess`) and starts the first app; on a reload it imports the new app, awaits the running app's `stop`, then starts the new one; at exit it stops the running app (its listener removes the socket file). Its WebSocket handlers are generic: a socket whose upgrade data carries handlers (`UpgradeData` in `state.ts`; a remote node's `/nodes/link`) is driven by them and belongs to the app that upgraded it, which closes it on `stop`; the process registers only the rest (browser sockets, `/ws`) as browser connections, which outlive reloads. So a change to the node hub or transport reloads like any other server code. The HTTP server's `maxPayloadLength` is the remote link's frame cap (16 MiB). Only one listener can bind the socket. Between the two apps, HTTP requests get 503 (a `/nodes/link` dial too: the node redials) and browser messages an error ("Server reloading"); it lasts as long as opening the database. Requests already in flight finish on the app they started on.

**App module state is lost on a reload.** Anything an app keeps in module scope or in its state starts empty in the next app: OAuth logins in progress (`routes/oauth.ts`, docs/tech-debt.md), the session kinds registered at run time beyond the built-in ones (`registerSessionKind`), each node's announced build (the hub's, learned again at the node's redial), the node bundle (built again). Keep what must outlive an app in the database or, when it cannot be, in the `ServerProcess` (a restart-only change).

## What a reload does to the node link

Closing the previous hub closes every node connection; the app's `stop` also closes its `/nodes/link` sockets, negotiated or not. Each node sees its connection close and redials (100 ms backoff); the new listener, or the new app's `/nodes/link`, accepts it and the new hub negotiates a new connection, judging the node's build against the new app's node bundle at once (a node on another build is told to update, ADR-025). Nothing is handed over: every call that was in flight on the old connection ends with outcome unknown, and each kind recovers as it does after any dropped link ([node-transport.md](node-transport.md) *When things go wrong*):

- **Session runs** are on the server and keep running; their tool calls ride through the redial: a file operation is sent again, a command keeps running on the node and is picked up again by its ID (`pi.execAttach`; `NodeDirClient`, node-contract.md *Shell commands*). A call made during the gap finds no app to reach its node through and waits, as for an offline node.
- **`execute`** runs on the server, not over the link: a script the stopped app was running for a session is aborted and fails that one tool call with "may have run"; a Reins tool call made during the gap is not run ("the server is reloading, try again").
- **Request-now calls and streams** of routes and git (skills, `fs.*`, `process.run`) fail to their caller with `unavailable`.
- **A submission** is answered by the app that took it (its ack or its error, to the socket that sent it); one cut off by the reload gap is resent by the browser under the same `clientId`, and converges.

Every app uses the process's database connection. A reload runs migrations on it again (only pending ones apply, so a new migration takes effect on the next reload).

## Sessions on the server

Sessions run on the server ([ADR-029](../adr/029-sessions-on-the-server-nodes-host-tools.md)): submitted work goes to a session's runtime (`session-runtime/`; [session-runtime.md](session-runtime.md)). What follows is how runtimes live across reloads (in full: session-runtime.md *What the process keeps*, *Reaching the current app*).

- **The process owns the runtimes** (`ServerProcess.sessions`, an `OpenSessions` created in `process-state.ts`, typed in `state.ts`): live runtimes by session ID with their last activity, the openings in progress (concurrent opens of one session share one), live event seqs (per session, for the life of the process), each session's submission chain and the pause gate. An app opens a runtime with its own code (`openSessionRuntime` in `session-runtime/live.ts`, from the session's rows) and puts it in the map; a runtime keeps the code it was built with.
- **A runtime keeps the `ServerProcess`, never the app** (*Ownership*): its storage, attachments and credentials are on the process (`process.db`, `process.credentialLocks`), its events go out through `process.broadcast`, and what it needs of an app (its node, the Reins tools: `App`) it reads from `process.app` at each call. Its run lifecycle it applies itself, with its own code, on the process's database and broadcast, a child's report steering its parent's runtime through `process.sessions`: no app is involved. During the reload gap `process.app` is undefined and nothing waits for it: a node call waits as for an offline node, a Reins tool call is not run, and run lifecycle is applied as at any time. Two surfaces cross between code of different apps, `App` (a runtime calls an app) and `SessionRuntime` (an app calls a runtime): an incompatible change to either, or to `ServerProcess` and the process-owned sources, needs a restart. Errors crossing them are classified by fields (`outcome`, an error's `name`), never by class: each app has its own classes.
- **Idle runtimes are closed:** the process's sweep (every 30 s) closes a runtime idle 3 minutes and not streaming. When an app registers, runtimes earlier apps built are closed at once if idle and marked `retired` otherwise; a retired one is closed once idle, and an open meanwhile reopens it on the new code once it is idle (it keeps running its old code until then). A runtime an old runtime's code opens while a newer app is current (its child report to a parent) is retired from the start (`APP_CODE`, session-runtime.md *What the process keeps*).
- **What a reload does to a run:** nothing it can see. Tool calls ride through the node's redial (`NodeDirClient`, node-contract.md *Shell commands*); a script the stopped app was running for it is aborted and comes back "may have run". A reload recovers nothing: runtimes never left memory.
- **What a restart does:** SIGTERM/SIGINT, and a restart of the server alone (*Restarting the server*), pause every run at its next pause point (bounded by 3 s, then forced) and suspend it (`suspendSessions`), and the next process's first app resumes it (session-runtime.md *Recovery*); a crash cuts runs off wherever they are, and the next start resumes them the same way. Every node's link drops with the process and each node redials the next one; a bash command in flight goes on on the node and the resumed run picks it up again (session-runtime.md *Recovery*, Bash across a restart).

## What reloads

- Every local source under `packages/backend/src` the app reaches, the node hub and transport (`nodes/`) included, except the process-owned sources (*Ownership*).
- `@reins/telemetry` source used by the app.
- The session runtime (`session-runtime/`), the Reins system prompt (`sessions/system-prompt.ts`) and session kinds (`sessions/session-kinds.ts`): new runtimes are built by the new code; a runtime open at the reload keeps the code it was built with (and its kind's prompt) until it is closed, at once when idle, else as soon as it goes idle, and the session's next submission opens it on the new code.
- `kill -USR2 <server pid>` rebuilds and reloads without changing files.

`buildDevBundle` (`dev-build.ts`) bundles every local source and reloadable workspace package. Third-party dependencies, builtins and **`@reins/node-protocol` stay external**, one module instance for the process. The protocol stays external because the server and the node must change it together: the server keeps the protocol it started with until both restart, so a protocol edit never applies on one side only.

Bundled source retains its own `import.meta` locations. Each process builds into `.dev-build/<pid>/`, removed on exit; stale directories are removed at startup. A failed build/import leaves the previous app running; if the new app fails to start (e.g. the socket cannot be bound), nothing serves (503) until the next reload, and nodes redial until an app listens. Reloads are debounced by 100 ms. Test and fixture files are ignored.

## Restarting the server

The server process can be restarted alone: the supervisor gives it `REINS_SERVER_RESTART_EXIT_CODE` (`SERVER_RESTART_EXIT_CODE`, 75, in `supervisor.ts`), and a server exiting with it is started again at once while the node and the frontend watchers keep running. Any other server exit still stops everything. Before exiting it does what SIGTERM does (`exitProcess` in `server-process.ts`): pause every run at its next pause point (bounded by 3 s), suspend the sessions, leave the node's commands running, and close its links and the socket listener on `exit`. The next process resumes the runs (session-runtime.md *Recovery*) and the node redials it, so a bash command running through the restart is picked up again and its run gets the real result (session-runtime.md *Recovery*, Bash across a restart). The browser's socket drops and reconnects; HTTP is refused for the second or two the new process takes to listen.

It is asked for two ways, each checked first: the new process code must build (`checkBuilds` in `dev-build.ts`: `index.ts` and everything it reaches, the app's sources and the workspace packages included, in memory). A build error is logged and the running server kept.

- **In dev, a process-owned edit** (`dev-watch.ts`): debounced with other edits (100 ms), a run of the watcher in which a process-owned source's contents differ from what the process started with restarts it rather than reloading the app. Saving a file unchanged restarts nothing. A broken edit keeps the server running and reloads nothing until an edit that builds, which then restarts it with every change since. (Bun's `fs.watch` may report only the first of several files written at once, so the watcher compares contents rather than trusting events' file names.)
- **By hand**, `kill -HUP <server pid>` (the supervisor logs `started server (pid N)`), in dev or `start`: restart without a source change.

Run alone (`bun packages/backend/dev.ts`, `bun run start:server`), the server is not given the code: a process-owned edit is only warned about, and SIGHUP keeps its default (the process dies without suspending).

What the check cannot catch (a process that builds but throws at startup) exits with another code and stops everything, as a broken full restart would. The restart picks up the code on disk, `@reins/node-protocol` included: so once a protocol source has changed since the server started, a process-owned edit is warned about instead of restarting the server alone (*What requires restart*).

## What requires restart

The watcher logs a warning rather than half-applying a change it cannot apply alone:

- **The process-owned sources** without a supervisor to restart the server (*Restarting the server*; with one, the server restarts by itself). They are (*Ownership*; `process-owned.json`, which `server-process.ts` reads as `PROCESS_OWNER_SOURCES`): the process owner (`index.ts`, `server-process.ts`, `dev-build.ts`, `dev-watch.ts`), `process-state.ts` (the process's `ServerProcess`: open sessions, credential locks, the current app), `database.ts` (the connection the process opens) and `logger.ts`, and the surfaces between the process, runtimes and apps (`ServerProcess`, `App`, `SessionRuntime`, `OpenSessions` in `state.ts`) when a change breaks them: a runtime built by an older app calls the new one through them. `state.ts` itself reloads; the watcher cannot tell a breaking change, so restart after one with `kill -HUP <server pid>`.
- **The supervisor** (`supervisor.ts`, which spawns the server and the node): restart `bun run dev`. The watcher does not warn about it (no app imports it).
- `@reins/node-protocol`: **restart `bun run dev`**, the server and node together, especially for a version or required-field change. The link is on **protocol version 16**: a server and node of different versions refuse each other's hello, so tool calls wait until both run the same version (a node bundle is told to update instead, ADR-025). The schemas are strict, so a field change without a version bump would otherwise refuse calls as invalid params, a terminal failure. Restarting only the server would start it on the new protocol while the node keeps the old one, so after a protocol edit the watcher no longer restarts the server for process-owned edits either (it warns): restart `bun run dev`.

A server restart (by the supervisor or a full one) drops links the same way a reload does (each node redials the next process, 100 ms backoff, and tool calls ride through), and suspends its runs for the next process to resume (*Sessions on the server*). See [node-contract.md](node-contract.md) *When a node goes away* and [session-runtime.md](session-runtime.md) *Recovery*.

## Reloading the node

`packages/node/src` is not watched: reloading on every save would cut off the tool calls in flight on the node, including those of the agent that saved. Reload the node when you are ready ([ADR-021](../adr/021-explicit-node-reload.md); node-contract.md *Reloading a node*):

```sh
bun run node:reload                 # the local node; --force, or a node ID, as arguments
```

or from an agent's `execute` script, `await api.nodes.reload()` (the calling session's node), or `POST /api/nodes/:nodeId/reload`. The node first checks that its new code builds and refuses with the error if not. Otherwise the call returns at once: it does not wait for the reload, so an agent can reload the node it runs on. The node then exits once no command (a bash call) is running on it, and the supervisor starts it again at once. Sessions run on the server, so no run is paused: a running command finishes and its result reaches the run first; a command started meanwhile is refused and sent again by the server once the node is back, and any other tool call waits for the node and runs on the new code. A command that runs long holds the reload up for up to 60 s; then the reload is cancelled (logged by the node, naming the command) and the command runs on, unless `force` cuts it off (it comes back "outcome unknown"). A bash call running `bun run node:reload` is a command too, but it ends as soon as the reload answers, so it does not hold it up. A node run on its own (`bun run start:node`) has nothing to restart it and refuses: restart it yourself.

A node restart interrupts only the tool calls in flight on it: a command it lost comes back to the model as "outcome unknown" (node-contract.md *Shell commands*).

## Tests

`supervisor.process-test.ts` reloads a supervised node over HTTP while a run is in flight on the server: the node restarts at once and the run's tool call runs once on the new process, nothing paused. `server-process.process-test.ts` (`bun run test:process`) kills a node mid-run (the run goes on), stops a server with SIGTERM mid-run (paused and suspended; the next process resumes it and its tool call runs once), kills one mid-request (the next process asks it again), and reloads a real dev server with `SIGUSR2` mid-run (the run goes on, never paused, while the node redials the new app, and a browser socket opened before the reload submits after it) and mid-command (the link drops, the node redials and the command, which ran on, completes through it, once). `integration/session-across-reload.test.ts` replaces the app under a session running on the server mid-tool-call (the node redials the new hub; its run continues and settles through the new app) and holds a reload's gap open (a bash call waits and runs on the next app's link, a Reins tool call is not run, and a run's lifecycle is applied at once, with no app; a runtime opened by another app's code is retired), and `process-state.test.ts` covers the idle sweep, retiring on a new app, and the current app property. `nodes/node-hub.test.ts` covers a new connection superseding a node's old one (its call in flight ends with outcome unknown). `dev-watch.test.ts` covers the watcher on a miniature source tree: an app edit reloads, a process-owned edit (written with others at once) restarts once, a broken one keeps the process until an edit that builds, no supervisor means a warning, and a protocol edit stops process-owned restarts. `supervisor.test.ts` restarts a server exiting with the restart code alone (the node not restarted) and stops everything on another exit; `supervisor.process-test.ts` restarts a real dev server (SIGHUP, so no checkout file is touched: a dev instance may run from it) while a bash command runs on its node: the node is never restarted, the command runs once and the resumed run gets its real result.

## Usage

```sh
bun run dev                         # supervised server, node and frontend watchers
bun packages/backend/dev.ts         # server only, app reload enabled
bun run start:node                  # separate node; restart it after node edits (it cannot reload itself)
bun run node:reload                 # reload the supervised node after node edits
kill -HUP <server pid>              # restart the supervised server alone (process-owned edits do it by themselves)
```

For protocol changes, work in a separate worktree and test against isolated ports, databases and sockets, then restart the server and node together at a deliberate idle point.
