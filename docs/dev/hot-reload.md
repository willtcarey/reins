# Dev Reload

Under `bun run dev`, the server's **app** hot reloads: its HTTP/browser handlers, product services and the session runtime code. **The process** is the OS process, which lives until a restart; **the app** is the server's swappable code and what it builds (routes, ws handlers, models, the node bundle): a dev reload replaces the app, production starts one. **The node hub and its links are the process's** ([ADR-029](../adr/029-sessions-on-the-server-nodes-host-tools.md), amending [ADR-020](../adr/020-reloadable-node-hub.md)): a reload leaves every node linked, and nodes redial only when the process restarts. **Sessions run on the server** in runtimes the process keeps across reloads (*Sessions on the server*): a reload neither pauses nor interrupts a run, and a running runtime keeps its code until it is idle. The node reloads only when asked (*Reloading the node*, [ADR-021](../adr/021-explicit-node-reload.md)). The process's own code (the process-owned sources below: `ServerProcess`, the hub, the open sessions and the database connection included) and the protocol require a restart.

## Ownership

| Lifetime | What lives there | Who may keep a reference to it |
|---|---|---|
| **Process** (until a restart; the process-owned sources below) | `ServerProcess` (`state.ts`): the database connection (`db`, opened once by `database.ts`: file, pragmas; each app migrates it, none closes it), `broadcast` (sends a frame to every browser connection; the process registers the sockets on open and close, so they outlive apps), `nodes` (the node hub, `nodes/node-hub.ts`: every node's link, its epoch and announced build) and `nodeLinks` (`/nodes/link`'s WebSockets, `nodes/node-link.ts`), `sessions` (`OpenSessions`: live runtimes, openings, submission chains, event seqs, the pause gate, the idle sweep), `credentialLocks` (the credential store's per-provider locks), `app(signal?)` and `registerApp(app)` (the current app), `frontendDir`. Also the HTTP server, the local node socket listener (`nodes/local-socket.ts`, bound once by `server-process.ts`) and the dev watcher | Anyone: each app (`AppState.process`), every session runtime, whichever app built it, and the hub |
| **App** (one start to its stop; `server.ts`, replaced as a whole on every reload) | `AppState`: `process` plus its node bundle (`nodeBundle`); what it offers process-owned code (`App`, `app.ts`: `hub`, the hub's questions, `nodes/hub-app.ts`; run lifecycle; the Reins tools), registered with the process from its start to its stop; its routes (`/nodes/link`'s included, which upgrades through `process.nodeLinks`), ws handlers, models and module state (the stores' `getDb()`, set from `process.db` at each start) | The app's own code: routes, ws handlers, models. **Never a session runtime or the hub**: they reach the current app per call, `(await process.app(signal)).…` |
| **Open session** (opened on use to its idle close; `session-runtime/`) | A live runtime (`OpenSession` in `OpenSessions.live`): its AgentHarness, storage (`PiStorageAdapter` on `process.db`), model runtime and credential store (over `process.credentialLocks`), attachment cache, tools (its node: `process.nodes`), built by one app's code and kept on it until closed | The process's `OpenSessions` only; an app calls it through `SessionRuntime` |
| **Request** (one HTTP request, browser message, tool call or script) | `Models` (`models/models.ts`) and what they build (a `Broadcast`, a credential store, `Sessions`, `Nodes`, `ProjectModel`) | That request's code |

**The rule:** a session runtime and the node hub may keep the `ServerProcess`, never an `AppState` or an `App`; everything they need of an app they reach through `process.app()` at each call. The types enforce it where practical: a runtime is opened and built from a `ServerProcess` only (`openSessionRuntime`, `buildSessionRuntime`'s `RuntimeOpening`), the hub is created with `process.app` only (`createNodeHub`), and `App` hands out nothing to keep (its tool and lifecycle methods take the session ID, its hub methods the node ID; a runtime's node is `process.nodes.get(id)`). An app's routes, ws handlers and models take the `AppState` and reach the process through `state.process` (`state.process.nodes`); nothing copies a process field into the app's state.

**Process-owned sources** (`packages/backend/src/process-owned.json`, relative to `src/`): `index.ts`, `server-process.ts`, `dev-build.ts`, `process-state.ts`, `database.ts`, `logger.ts`, `nodes/node-hub.ts`, `nodes/server-peer.ts`, `nodes/node-streams.ts`, `nodes/node-link.ts`, `nodes/local-socket.ts`. They import at runtime only each other, `@reins/node-protocol`, third-party packages and builtins (types from anywhere, with `import type`); the process owner reaches app code only by importing the app's entry (`server.ts`) dynamically. Oxlint's `reins/process-owned-imports` enforces it from the same list. In dev the app is a separate bundle: a process-owned module importing app code (`db.ts`, `node-store.ts`, `models/*`) would run a second copy of it, with its own module state. App code may import a process-owned module only for what keeps no state (`logger.ts`, `requestOrigin`): the app's bundle gets its own copy (the dev-build test checks the hub is not among them).

`server.ts` exports one function, `start(process, {recoverRuns})`, and the process owner calls it with its `ServerProcess`. `start` makes the process's database the one the stores' `getDb()` returns (`setDb`) and prepares it (`prepareDatabase` in `db.ts`: migrations), builds the app's state (`createAppState` in `state.ts`: the node bundle around the process), registers what it offers process-owned code (`process.registerApp(createApp(state))`), resumes the runs a previous process left running when it is the process's first app (`recoverRuns`, session-runtime.md *Recovery*) and returns the app's `fetch` and browser `message` handlers (state bound in) and `stop`. `stop` unregisters the app (session and hub calls wait for the next one; scripts it runs for sessions are aborted). It closes no node link and not the database: the process owns them ([ADR-029](../adr/029-sessions-on-the-server-nodes-host-tools.md)).

The process owner orchestrates: at startup it creates the `ServerProcess` (with its hub and `/nodes/link` endpoint, `createServerProcess`), binds the local node socket (handing each connection to `process.nodes.accept`) and starts the first app; on a reload it imports the new app, awaits the running app's `stop`, then starts the new one; at exit it stops the listener (removing the socket file) and closes the links. Its WebSocket handlers are generic: a socket whose upgrade data carries handlers (`UpgradeData` in `state.ts`; a remote node's `/nodes/link`, whose handlers `process.nodeLinks` creates) is driven by them; the process registers the rest (browser sockets, `/ws`) as browser connections. Both kinds are the process's and outlive reloads. The HTTP server's `maxPayloadLength` is the remote link's frame cap (16 MiB). Between the two apps, HTTP requests get 503 (a new `/nodes/link` dial too: the node redials), browser messages an error ("Server reloading"), and what the hub asks of an app (a hello's key, refusal and build, telling browsers) waits for the next one; it lasts as long as opening the database. Requests already in flight finish on the app they started on.

**App module state is lost on a reload.** Anything an app keeps in module scope or in its state starts empty in the next app: OAuth logins in progress (`routes/oauth.ts`, docs/tech-debt.md), the session kinds registered at run time beyond the built-in ones (`registerSessionKind`), the node bundle (built again). Keep what must outlive an app in the database or, when it cannot be, in the `ServerProcess` (a restart-only change).

## What a reload does to the node link

Nothing. The hub, its links and their epochs are the process's, so no node sees its connection close: calls and streams in flight go on, and session runs' tool calls are not even resent. What changes is the app the hub asks: a hello arriving in the gap (a node that dropped for its own reasons) waits for the next app, whose rows and node bundle answer it (`ready`, `update` or a refusal); browsers are told of a link gained or lost through the current app.

- **`execute`** runs on the server, not over the link: a script the stopped app was running for a session is aborted and fails that one tool call with "may have run"; one called during the reload gap waits for the next app.
- **A submission** is answered by the app that took it (its ack or its error, to the socket that sent it); one cut off by the reload gap is resent by the browser under the same `clientId`, and converges.
- **A node's build** is judged at its hello, against the app that answered it: a node linked on the previous app's build keeps its link (shown as it was then) and is told to update at its next hello, after the next process restart or its own redial.

Every app uses the process's database connection. A reload runs migrations on it again (only pending ones apply, so a new migration takes effect on the next reload).

## Sessions on the server

Sessions run on the server ([ADR-029](../adr/029-sessions-on-the-server-nodes-host-tools.md)): submitted work goes to a session's runtime (`session-runtime/`; [session-runtime.md](session-runtime.md)). What follows is how runtimes live across reloads (in full: session-runtime.md *What the process keeps*, *Reaching the current app*).

- **The process owns the runtimes** (`ServerProcess.sessions`, an `OpenSessions` created in `process-state.ts`, typed in `state.ts`): live runtimes by session ID with their last activity, the openings in progress (concurrent opens of one session share one), live event seqs (per session, for the life of the process), each session's submission chain and the pause gate. An app opens a runtime with its own code (`openSessionRuntime` in `session-runtime/live.ts`, from the session's rows) and puts it in the map; a runtime keeps the code it was built with.
- **A runtime keeps the `ServerProcess`, never the app** (*Ownership*): its storage, attachments and credentials are on the process (`process.db`, `process.credentialLocks`), its events go out through `process.broadcast`, its node is the process's hub's (`process.nodes.get`), and what it needs of an app (run lifecycle, the Reins tools: `App`) it reaches through `process.app()` at each call. During the reload gap a call waits for the next app (`APP_WAIT_MS`, 30 s), then fails. Two surfaces cross between code of different apps, `App` (a runtime or the hub calls an app) and `SessionRuntime` (an app calls a runtime): an incompatible change to either, or to `ServerProcess` and the process-owned sources, needs a restart. Errors crossing them are classified by fields (`outcome`, an error's `name`), never by class: each app has its own classes; the hub's questions are answered as values (`HubApp`).
- **Idle runtimes are closed:** the process's sweep (every 30 s) closes a runtime idle 3 minutes and not streaming. When an app registers, runtimes earlier apps built are closed at once if idle and marked `retired` otherwise; a retired one is closed once idle, and an open meanwhile reopens it on the new code once it is idle (it keeps running its old code until then).
- **What a reload does to a run:** nothing it can see. Its node stays linked; a script the stopped app was running for it is aborted and comes back "may have run". A reload recovers nothing: runtimes never left memory.
- **What a restart does:** SIGTERM/SIGINT pause every run at its next pause point (bounded by 3 s, then forced) and suspend it (`suspendSessions`), and the next process's first app resumes it (session-runtime.md *Recovery*); a crash cuts runs off wherever they are, and the next start resumes them the same way. Every node's link drops with the process and each node redials the next one; a bash command in flight goes on on the node and the resumed run picks it up again (session-runtime.md *Recovery*, Bash across a restart).

## What reloads

- Every local source under `packages/backend/src` the app reaches, except the process-owned sources (*Ownership*; the node hub and transport among them).
- `@reins/telemetry` source used by the app.
- The session runtime (`session-runtime/`), the Reins system prompt (`sessions/system-prompt.ts`) and session kinds (`sessions/session-kinds.ts`): new runtimes are built by the new code; a runtime open at the reload keeps the code it was built with (and its kind's prompt) until it is closed, at once when idle, else as soon as it goes idle, and the session's next submission opens it on the new code.
- `kill -USR2 <server pid>` rebuilds and reloads without changing files.

`buildDevBundle` (`dev-build.ts`) bundles every local source and reloadable workspace package. Third-party dependencies, builtins and **`@reins/node-protocol` stay external**, one module instance for the process. The protocol stays external because the server and the node must change it together: the server keeps the protocol it started with until both restart, so a protocol edit never applies on one side only.

Bundled source retains its own `import.meta` locations. Each process builds into `.dev-build/<pid>/`, removed on exit; stale directories are removed at startup. A failed build/import leaves the previous app running; if the new app fails to start, nothing serves (503) until the next reload, and node links wait for an app (a hello fails after `APP_WAIT_MS` and is redialed). Reloads are debounced by 100 ms. Test and fixture files are ignored.

## What requires restart

The watcher logs a restart-required warning rather than half-reloading:

- **The process-owned sources** (*Ownership*; `process-owned.json`, which `server-process.ts` reads as `PROCESS_OWNER_SOURCES`): the process owner (`index.ts`, `server-process.ts`, `dev-build.ts`), `process-state.ts` (the process's `ServerProcess`: open sessions, credential locks, the hub, the current app), `database.ts` (the connection the process opens), `logger.ts` and the node hub and transport (`nodes/node-hub.ts`, `server-peer.ts`, `node-streams.ts`, `node-link.ts`, `local-socket.ts`), and the surfaces between the process, runtimes and apps (`ServerProcess`, `App`, `HubApp`, `NodeHub`, `SessionRuntime`, `OpenSessions` in `state.ts`) when a change breaks them: a runtime built by an older app, and the hub, call the new one through them. `state.ts` itself reloads; the watcher cannot tell a breaking change, so restart after one. A change to what the hub asks of an app (`nodes/hub-app.ts`: keys, refusals, the build rule, telling browsers) reloads.
- **The supervisor** (`supervisor.ts`, which spawns the server and the node): restart `bun run dev`. The watcher does not warn about it (no app imports it).
- `@reins/node-protocol`: **restart the server and node together**, especially for a version or required-field change. The link is on **protocol version 12**: a server and node of different versions refuse each other's hello, so tool calls wait until both run the same version (a node bundle is told to update instead, ADR-025). The schemas are strict, so a field change without a version bump would otherwise refuse calls as invalid params, a terminal failure.

A server restart drops every link (each node redials the next process, 100 ms backoff, and tool calls ride through), and suspends its runs for the next process to resume (*Sessions on the server*). See [node-contract.md](node-contract.md) *When a node goes away* and [session-runtime.md](session-runtime.md) *Recovery*.

## Reloading the node

`packages/node/src` is not watched: reloading on every save would cut off the tool calls in flight on the node, including those of the agent that saved. Reload the node when you are ready ([ADR-021](../adr/021-explicit-node-reload.md); node-contract.md *Reloading a node*):

```sh
bun run node:reload                 # the local node; --force, or a node ID, as arguments
```

or from an agent's `execute` script, `await api.nodes.reload()` (the calling session's node), or `POST /api/nodes/:nodeId/reload`. The node first checks that its new code builds and refuses with the error if not. Otherwise the call returns at once: it does not wait for the reload, so an agent can reload the node it runs on. The node then exits once no command (a bash call) is running on it, and the supervisor starts it again at once. Sessions run on the server, so no run is paused: a running command finishes and its result reaches the run first; a command started meanwhile is refused and sent again by the server once the node is back, and any other tool call waits for the node and runs on the new code. A command that runs long holds the reload up for up to 60 s; then the reload is cancelled (logged by the node, naming the command) and the command runs on, unless `force` cuts it off (it comes back "outcome unknown"). A bash call running `bun run node:reload` is a command too, but it ends as soon as the reload answers, so it does not hold it up. A node run on its own (`bun run start:node`) has nothing to restart it and refuses: restart it yourself.

A node restart interrupts only the tool calls in flight on it: a command it lost comes back to the model as "outcome unknown" (node-contract.md *Tool host*).

## Tests

`supervisor.process-test.ts` reloads a supervised node over HTTP while a run is in flight on the server: the node restarts at once and the run's tool call runs once on the new process, nothing paused. `server-process.process-test.ts` (`bun run test:process`) kills a node mid-run (the run goes on), stops a server with SIGTERM mid-run (paused and suspended; the next process resumes it and its tool call runs once), kills one mid-request (the next process asks it again), and reloads a real dev server with `SIGUSR2` mid-run: the run goes on, never paused, the node never redials, and a browser socket opened before the reload submits after it. `integration/session-across-reload.test.ts` replaces the app under a session running on the server mid-tool-call (the node's link stays open and is never redialed; its run continues and settles through the new app), `nodes/hub-app.test.ts` covers links across a reload and a hello in the gap (served, refused or told to update by the next app, against its build), and `process-state.test.ts` covers the idle sweep, retiring on a new app and waiting for an app during the gap. `nodes/node-hub.test.ts` covers a new connection superseding a node's old one (its call in flight ends with outcome unknown). `dev-build.test.ts` checks the app's bundle carries no copy of the hub.

## Usage

```sh
bun run dev                         # supervised server, node and frontend watchers
bun packages/backend/dev.ts         # server only, app reload enabled
bun run start:node                  # separate node; restart it after node edits (it cannot reload itself)
bun run node:reload                 # reload the supervised node after node edits
```

For protocol changes, work in a separate worktree and test against isolated ports, databases and sockets, then restart the server and node together at a deliberate idle point.
