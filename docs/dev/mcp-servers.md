# MCP Servers

Remote MCP servers the user adds in Settings ([features/mcp-servers.md](../features/mcp-servers.md)): their storage, the OAuth client, and the connections the server keeps to them. Agents reach their tools only through `execute`: the system prompt names the servers, `api.mcp.tools` finds a server's tools and `api.mcp.call` calls one (*Exposing tools to agents*).

The client side is `@modelcontextprotocol/sdk` (backend dependency): its `Client`, the streamable HTTP and legacy SSE client transports, and its OAuth `auth()` (discovery, dynamic client registration, PKCE, code exchange, refresh). Reins implements the parts the SDK leaves to an application: where OAuth state is kept, where the user is sent, and the connections' lifetime.

`transport` is a column with one value, `http`, ready for stdio. It and a secret's `kind` have no `CHECK`, so a new value needs no table rebuild. `name` is unique and an identifier (`^[a-z][a-z0-9-]{0,31}$`): the namespace of the server's tools later.

## Connections

`McpConnections` (`mcp/connections.ts`) keeps at most one connection per server, shared by every caller. The model calls it; nothing else should.

- **On demand.** A call (`listTools`, `callTool`, `test`) connects first if needed; concurrent callers share one attempt (`connecting`). A caller's `signal` stops its own wait, not the shared attempt.
- **What it reads.** At each connection it reads the row and the secrets from the store: a change is picked up by closing the connection (`disconnect`, which the model calls when a change affects the connection, on sign-in, sign-out and removal).
- **Transports.** Streamable HTTP first; when the server refuses its first POST with a 4xx other than 401/403 (what a legacy server answers), the HTTP+SSE transport. A wrong URL path is refused the same way (404), so when the fallback fails too, the failure is the streamable HTTP one with the fallback's after it (`The server answered HTTP 404: … (and as a legacy HTTP+SSE server: …)`); a fallback that needs sign-in is `needs_sign_in`.
- **Status** (`status(row, signedIn)`, the row and whether it holds tokens as the model read them for its view): `disabled` and `needs_sign_in` (OAuth without tokens) come from the configuration and win; then the connection: `connected`, `connecting`, the last failure (`error {message}` or `needs_sign_in`), else `not_connected`.
- **Failures.** A request that finds its MCP session gone (HTTP 404: the server restarted) was not run: the connection is dropped and the request runs once on a new one. The server's own JSON-RPC errors (unknown tool, invalid params), a timeout and the caller's abort leave the connection open and reach the caller as the SDK's `McpError`/the abort reason. Anything else (unreachable, HTTP errors, an `UnauthorizedError`) drops the connection, records the failure and throws `McpServerUnavailableError {status}`; the next call connects again.
- **Tool list.** Listed once per connection (all pages) and cached on it; `notifications/tools/list_changed` (the client's `listChanged` handler) lists it again at once. Callers share the listing, and a caller's `signal` stops only its own wait: a caller that gives up (a search past its deadline) leaves the listing to finish for the next one. `toolCount` is the last count, for views.
- **Timeouts.** Connecting 15 s; a request 60 s unless `callTool` is given `timeoutMs` (`McpConnectionOptions`; tests pass their own through `createAppState(…, {mcp})`). Cancellation through `signal` sends `notifications/cancelled`.
- **Idle.** A connection no call used for 5 minutes is closed (`not_connected`; its tool cache goes with it).
- **Background refresh.** A timer refreshes the OAuth tokens of servers nobody uses (*OAuth*, *Background refresh*). It runs at most a minute after the app starts (a reload starts it again), then each hour (`tokenRefreshCheckMs`). `close()` stops it.
- **Changes** call the `changed(serverId)` callback the app gives it (`createAppState`): a new `Models` publishes the server (`mcpServers.get(id).publish()`), skipping one removed meanwhile.
- **Layering.** It is below the models: it imports the store, never `models/`. `status(row, signedIn)` takes what its caller read. A call for a server whose row is gone (removed since the model found it) throws a plain `Error`; the not-found error the routes translate is the model's (`McpServerNotFoundError`).

### Where connections live

On the app, not the process: `createAppState` creates the `McpConnections`, the app's `stop` closes it (`close()`: every connection closed, nothing connects again on it), and the next app connects again on demand. Nothing about a connection needs to outlive an app: what must (credentials, a sign-in in progress) is in the database. hot-reload.md *Ownership*.

- A reload or restart closes every MCP connection, and a call in flight fails. The next use reconnects, which costs one `initialize` round trip.
- In exchange, the connection manager is app code: it hot reloads, and `ServerProcess` knows nothing about MCP. Connections on the process would survive a reload, but their code would change only on a restart.
- A sign-in in progress is in the database (the hash of its `state`, its callback URL and start time on the row, its PKCE verifier and any client it registered among the secrets), not in app memory as provider OAuth keeps its logins. So a reload during a sign-in, frequent in dev, does not lose it.

## OAuth

`McpOAuthProvider` is the SDK's `OAuthClientProvider` over the store, in one of three modes:

- **`sign-in`** (`startMcpSignIn`, `POST /api/mcp-servers/:id/sign-in`): Reins first sends an unauthenticated `initialize` to read the server's `WWW-Authenticate` (resource metadata URL and scope, as the transport would; a server that needs no authentication accepts it, and the session it opened is ended with a `DELETE`, best effort), records the sign-in on the row (`beginMcpSignIn`: the SHA-256 of a random `state`, the callback URL, the time), then runs `auth()`: discovery (cached as `discovery`), the client (the server's `client_information` when registered for this callback URL, else one an earlier sign-in registered for it, else a new registration, kept as `sign_in_client_information`; a pre-registered client, `oauth_client_id` with its `client_secret`, is used as configured), the PKCE verifier (`code_verifier`), and the authorization URL, which the route returns. It hands out no tokens, so `auth()` starts an authorization rather than refreshing. The scope is the row's `oauth_scope`, else the server's.
- **`callback`** (`finishMcpSignIn`, `GET /oauth/mcp/callback`): the model finds the sign-in by the hash of `state`, refuses one older than 15 minutes or answered with `error`, and runs `auth()` with the code, keeping what the exchange gives in memory. On success one transaction makes the tokens, the client they were issued to and the sign-in's callback URL the server's (`completeMcpSignIn`). The sign-in record, verifier and registered client are removed whatever happened, the connection is replaced, and a background `test` connects so the page shows the result. The callback page closes its window.
- **`connection`**: the transports' provider. It only reads the credentials, and gives its tokens without their refresh token, so the transport's own `auth()` (after a 401 that the connection's refresh did not fix, or a 403 for scope) never refreshes outside the lock (*Refreshes are serialized*). When `auth()` asks to redirect, it only marks `signInRequired` (and saves no verifier, so a sign-in in progress stays valid). The transport then throws `UnauthorizedError`: `needs_sign_in`.
- **`refresh`** (`refreshMcpTokens`, under the lock): a refresh of the tokens its caller read. It writes the credentials only while the stored tokens are still those (`holdsTokens`). A sign-out, a sign-in or another refresh during its request wins: its result is dropped (`superseded`). A refusal (`invalid_grant`, the SDK's `invalidateCredentials('tokens')`) deletes the tokens (`signed_out`). Its `outcome` says which.

**A sign-in never changes the server's credentials until it completes.** The server's tokens were issued to its client, and a refresh must present that client. If a sign-in replaced the client when it started (a new registration from another origin), an abandoned sign-in would make the next refresh fail and sign the server out. Also, the SDK invalidates credentials when an exchange fails (`all` on `invalid_client`, `tokens` on `invalid_grant`). In the `sign-in` and `callback` modes this drops only the sign-in's own client and the discovery cache, so a bad code does not sign out a working server.

**The sign-in window** (`_signIn` in `mcp-servers-section.ts`) is opened blank in the click, before `POST …/sign-in` answers: Safari and Firefox block a `window.open` that runs after an await. The answer sends it to the authorization URL (its `opener` set to null first); a failure closes it. When the browser blocks even that (`open` returns null), the waiting banner's *Open the sign-in page* link is the way in.

The callback is a page for the browser, so it is outside `/api` (`API.mcpOAuthCallback`, `/oauth/mcp/callback`). Its URL is the origin the browser used to reach Reins (`requestOrigin`, as for node install scripts: `X-Forwarded-Proto`/`X-Forwarded-Host`, else the request) plus that path. It is stored with the sign-in (`sign_in_redirect_url`), so the exchange presents the same one, and becomes `oauth_redirect_url` when it completes. A registered client records its `redirect_uris`: a sign-in from another origin registers again.

A script has no browser request: `api.mcp.signIn` takes the origin from the agent (`callbackOrigin`), else the origin of the latest completed sign-in (`latestMcpRedirectUrl`: the server's own, else any server's), else `http://localhost:<REINS_PORT>`. When the user's browser cannot reach that URL, the page it lands on still carries the `code` and `state` in its address: `api.mcp.finishSignIn(url)` passes them to `McpServers.finishSignIn`, as the callback route does.

**Refreshes are serialized** per server (`McpRefreshLock`, one for each `McpConnections`). With rotating refresh tokens, each refresh token works once: a second refresh with it fails `invalid_grant` and signs the server out. Each refresh under the lock first checks whether the refresh before it made it unnecessary. A refresh does not hold the lock against a sign-in or a sign-out: its writes check that the tokens did not change meanwhile (the `refresh` mode).

- **A connection's** (`oauthConnectionFetch`, the transports' `fetch`). The transport refreshes once per request refused 401, so concurrent requests after an expiry would each refresh. Instead, a 401 from the MCP server refreshes under the lock, unless the stored access token is no longer the one refused (another refresh or a sign-in replaced it): it is then used. The request is sent again with the new token. Only when that fails does the 401 reach the transport. The MCP server's requests are those to the server URL's origin that carry a bearer token: that covers the legacy SSE transport's message endpoint (another path), and leaves out the transport's own OAuth requests to an authorization server on the same origin (a client's credentials, Basic or in the form, never a bearer token).
- **Background refresh** (`refreshAgedMcpTokens`, from the timer in *Connections*). Many authorization servers expire a refresh token that is not used for some days, so a server not used for a while would need a new sign-in. Each enabled OAuth server whose tokens were issued more than a day ago (`tokenRefreshAgeMs`: the `updated_at` of its `tokens` secret, `mcpTokensAgeSeconds`; a sign-in and each refresh set it) is refreshed under the lock, when its tokens include a refresh token. A refusal deletes the tokens (as above) and publishes the server (`needs_sign_in`). Any other failure (unreachable, a server error) keeps the tokens, and the next check tries again. A disabled server is not contacted. No refresh extends an absolute lifetime that the authorization server sets.

Not done: refreshing before the access token expires (an expired token costs one 401), token revocation at the authorization server on sign-out, per-project servers, stdio, elicitation, resources and prompts.

## Exposing tools to agents

Agents reach MCP tools only through `execute`, in two steps: the system prompt names the servers, and `api.mcp.tools(server, query)` finds the tools of one. No MCP tool becomes a direct tool of the model, because:

- the model's tool definitions and the system prompt then do not grow with each server (Vercel has 238 tools);
- a tool a server adds is found at the next lookup; direct tool definitions are fixed for a turn and would need a fresh list before each run;
- a server that is slow or down delays only the lookup of its own tools, not every run;
- one script can call many tools without a model round trip for each.

`search` does not list MCP tools. The agent picks the server from the prompt, so MCP tools are never ranked against API functions, and `search` never waits for a server.

- **The system prompt** (`reinsSystemPrompt`, `sessions/system-prompt.ts`) has an *MCP servers* section when the session is offered `execute` and a server is enabled: each server's name and its `instructions` (multi-line, continued under its line), and how to find and call its tools. Not its status, which changes during a session (a lookup reports it). `SessionModel.context` reads the enabled servers into the kind's context (`SessionKindContext.mcpServers`) when the runtime opens, so a server added or changed reaches a session the next time its runtime opens, as task edits do. `instructions` (column renamed from `description` by migration `059`, at most 4000 characters) is the user's own text: what the server is for and how to use it (for a gateway such as executor, the integrations behind it). Reins does not use the `instructions` a server may send at `initialize`: few send them (executor does not; CircleCI's are 5.5k characters, too many for every prompt), and they cannot change during a connection, while a gateway's integrations do. The form and `api.mcp.add`/`update` say that it goes into every prompt.
- **`api.mcp.tools(server, query?)`** (`scripting/mcp.ts`, `mcpToolDocs` in `scripting/mcp-tool-docs.ts`) returns documentation, not data: the matching tools as a TypeScript interface (`interface VercelTools { list_deployments(args: {…}): Promise<McpToolResult> }`), the format `search` uses for API functions. A tool's title and description are its JSDoc, with *Read-only.* or *Destructive.* from its annotations; its `inputSchema` is its `args` (optional when nothing is required), each argument with its description; an `outputSchema` types `structuredContent`. A name that is not an identifier is quoted (`"search-issues.v2"(…)`). The JSON Schema renderer covers what servers send: `type` arrays, `enum`, `const`, `anyOf`/`oneOf`, `allOf`, `$ref` into `$defs`/`definitions` (a recursive one is `unknown`), `additionalProperties`, `nullable`; deeper than 6 levels is `unknown`.
- **Matching** uses `searchFunctions`' rules (`rankByTerms`, `scripting/term-search.ts`): each word of the query is a substring, scored by where it is found (name 10, title 5, argument names 3, description 1); the tools that match every word, else, for several words, those that match the most. A plural word also matches its singular (`deployments` finds `get_deployment`). The first 10 matches are documented and the others named. Without a query, a server of at most 10 tools is documented whole, a larger one only names its tools. When none match, the answer names every tool.
- **`api.mcp.call(server, tool, args?, timeoutMs?)`** returns the `CallToolResult` as it is, with `ctx.signal`. A failure the tool reports is a result with `isError`, not a throw, so its content reaches the script. Images and large results go through the limits of `execute`.
- A script names a tool with `api.mcp.call(server, tool, args)`, not a method for each tool: server and tool names with hyphens or dots would make those awkward.

The seam is `McpServers` on the call's `Models` and the `McpServerModel` it finds: `listTools({signal})` → `McpTool[]` (`name`, `title`, `description`, `inputSchema`, `outputSchema`, `annotations`), read from the connection's list (*Connections*), else by connecting and listing; `callTool(name, args, {signal, timeoutMs})` → the SDK's `CallToolResult`; both throw `McpServerUnavailableError` (`status`) when the server is disabled, needs sign-in or is down. The tool list is not stored: a stored list would help only when the server cannot be used, and then its tools cannot be called either.

Not done: a maximum age for the connection's tool list, for a server that does not send `list_changed` on a busy connection.
