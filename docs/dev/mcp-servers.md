# MCP Servers

The MCP servers the user adds in Settings ([features/mcp-servers.md](../features/mcp-servers.md)), remote ones and stdio ones run on a node, and those a project's `.mcp.json` defines (*Repo servers*, whose stdio commands run only once the user turns them on, *Allowed commands*): their storage, the OAuth client, and the connections the server keeps to them (the Reins server is always the MCP client). Agents reach their tools only through `execute`: the system prompt names the servers, `reins.tools.search` finds their tools and `reins.tools.call` calls one, by IDs of `mcp__<server>__<tool>` (*Exposing tools to agents*).

MCP is a built-in **extension** ([server-sdk.md](server-sdk.md)): its backend part is `packages/backend/src/extensions/mcp/`, registered by `extensions/built-in.ts` (`registerMcp`), and it uses only the server SDK (`@reins/sdk/server`), its own modules and npm packages (lint: `reins/backend-extension-boundary`). Its frontend part is `packages/frontend/src/extensions/mcp/` ([reins-sdk.md](reins-sdk.md) *The MCP extension's frontend part*).

The client side is `@modelcontextprotocol/sdk` (backend dependency): its `Client`, the streamable HTTP and legacy SSE client transports and Reins' own stdio transport over a node process (the server's `transport` picks one), and its OAuth `auth()` (discovery, dynamic client registration, PKCE, code exchange, refresh). Reins implements the parts the SDK leaves to an application: where OAuth state is kept, where the user is sent, and the connections' lifetime.

**A server is remote or stdio**, a union told apart by `transport` (`McpTransportKind`) in its fields, rows and views: `McpRemoteFields`/`McpRemoteRow`/`McpRemoteServerView` (`http`, streamable HTTP, the default with a `url`, or `sse`, legacy HTTP+SSE; `url`, `authKind` (`none` by default) and its auth kind's fields; the view's secrets only as `has…`, and `signedIn`) or `McpStdioFields`/`McpStdioRow`/`McpStdioServerView` (`command`, `args`, `cwd`; its environment a secret, `env`, the view's only as `envNames`). Neither has the other's fields: code that needs one kind's narrows on `transport` (the OAuth code takes only `McpRemoteRow`, `McpStdio.start` only `McpStdioRow`). The table is flat, with a kind's columns empty for the other (a stdio server's `url` `""` and `auth_kind` `none`); only the store's `toRow` and `fieldValues` know it. `validMcpServerFields` (`validRemoteFields`, `validStdioFields`) checks and trims each kind's fields. A change keeps the server's kind unless it gives `transport`; changing the kind starts from the new kind's defaults (so `url` or `command` must be given) and drops the old kind's secrets. The input is the shape of the `mcpServers` entries of Claude's and Cursor's configs (`command`, `args`, `env`, `cwd`), so an entry can be copied over with a `name`. A change gives `env` whole: a name left out is removed, a value given as null keeps the stored one (`mergedEnv`; Settings sends a blank field so). It has no `CHECK`, so a new value needs no table rebuild; a new secret kind is a new key. `name` is unique and an identifier (`^[a-z][a-z0-9-]{0,31}$`): the namespace of the server's tools later.

### Rows and secrets

A server's row is in MCP's database and its secrets are in the host's secret storage, so a change to both is not one transaction (ADR-033). The store and the model order the writes so that a half-done change does no harm:

- **Removal** deletes the server's secrets (`keys("servers/<id>/")`), then its row: a stop between them leaves a server without credentials (it needs sign-in or a header value again, and can be removed again), never secrets that no server owns.
- **Creation** inserts the row, then its secrets; a secret that cannot be stored deletes the server again.
- **A change** updates the row first (a name taken by another server then changes nothing), then its secrets. A sign-in's completion stores the client and the tokens, then the callback URL on the row. Ending a sign-in clears the row's record, then deletes its verifier and registered client.
- Server IDs are never used again (`AUTOINCREMENT`), so a key left behind could never become another server's.

## Connections

`McpConnections` (`connections.ts`) keeps at most one connection per remote server, shared by every caller, and one per stdio server and calling session (its process), shared by that session's calls. The model calls it; nothing else should. *Stdio servers* says what differs for stdio.

- **On demand.** A call (`listTools`, `callTool`, `test`) connects first if needed; concurrent callers share one attempt (`connecting`). A caller's `signal` stops its own wait, not the shared attempt.
- **What it reads.** At each connection it reads the row and the secrets from the store: a change is picked up by closing the connection (`disconnect`, which the model calls when a change affects the connection, on sign-in, sign-out and removal).
- **Transports.** The server's `transport` picks one, in `transportFor` (the one place a kind becomes a transport): `http`, streamable HTTP (the default); `sse`, the legacy HTTP+SSE transport; `stdio`, `NodeProcessTransport` (*Stdio servers*). There is no fallback from one to the other: a wrong URL path is refused with the same 404 as a legacy server would give, so a fallback hid the real failure. A streamable HTTP server refusing the first POST with a 4xx other than 401/403 (a legacy server answers 404 or 405) fails with the HTTP error and a hint to set the transport to SSE. A change to `transport` closes the connection; it does not sign out.
- **Status** (`status(row, signedIn)`; whether a repo server may run is `McpRepoGate.block`'s, which `connection()` and a stdio server's kept tool list ask first), the row and whether its OAuth tokens are usable, `mcpSignedIn`, as the model read them for its view) says whether agents can use the server, and if not, why. It is calculated at each read: `disabled` (the user's own servers; a repo server is `off`, the gate's); else `needs_sign_in` for OAuth without usable tokens (none, or an expired access token without a refresh token); else the last recorded failure (`error {message}` or `needs_sign_in`); else `ready`. The connection is not part of it: it is opened on demand, and a server is `ready` before its first use and after an idle close. An access token that expires shows at the next read; nothing is pushed for it.
- **Failures.** A request that finds its MCP session gone (HTTP 404: the server restarted) was not run: the connection is dropped and the request runs once on a new one. The server's own JSON-RPC errors (unknown tool, invalid params), a timeout and the caller's abort leave the connection open and reach the caller as the SDK's `McpError`/the abort reason. Anything else (unreachable, HTTP errors, an `UnauthorizedError`) drops the connection, records the failure and throws `McpServerUnavailableError {status}`; the next call connects again.
- **Tool list.** Listed once per connection (all pages) and cached on it; `notifications/tools/list_changed` (the client's `listChanged` handler) only clears the cache: the next caller lists again. Callers share the listing, and a caller's `signal` stops only its own wait: a caller that gives up (a search past its deadline) leaves the listing to finish for the next one. No count or list is kept for views: Settings lists the tools when the user expands them.
- **Timeouts.** Connecting 15 s; a request 60 s unless `callTool` is given `timeoutMs` (`McpConnectionOptions`; tests pass their own through `testMcp(options)`, an `McpOptions`). Cancellation through `signal` sends `notifications/cancelled`.
- **Idle.** A connection no call used for 5 minutes is closed (its tool cache goes with it). The status does not change.
- **Background refresh** is not the connections': `McpTokenRefresher` (*OAuth*, *Background refresh*) shares their refresh lock, which `startMcp` makes.
- **Changes** call the `changed(serverId)` callback that `startMcp` gives it only when the status changes with no change to the server: a failure is recorded, a connection clears a recorded failure, or a background refresh signs the server out. The extension then publishes the server (`servers.get(id).publish()`), skipping one removed meanwhile. Connecting, closing and idle closes are not told. `disconnect` is not either: its callers (the model's changes, sign-in, sign-out, removal and `test`) publish the server themselves.
- **Layering.** It is below the models (it is given `McpStdio` to start a stdio server's process, and the refresh lock): it uses the store, never `servers.ts` or `server.ts`. `status(row, credentials)` takes what its caller read. A call for a server whose row is gone (removed since the model found it) throws a plain `Error`; the not-found error the routes translate is the model's (`McpServerNotFoundError`).

### Stdio servers

A stdio server is a command run on a node; the Reins server is its MCP client, over the process's stdin and stdout. It is global (every session may use it), but each session runs its own process.

- **Where it runs: in the calling session's checkout.** A stdio server runs a process for each session that uses it, on the session's node, with the session's checkout (its source's path) as its directory; a relative `cwd` is inside the checkout, an absolute or `~/…` one is used as it is (`processCwd`). This is what the `mcpServers` entries of Claude Code and Cursor expect, where each session or window starts its own process in its project: many servers act on their working directory (filesystem, git, language-server bridges, framework servers, a project's `.env`), and a process shared across checkouts would act on one checkout for every session, or keep one browser or scratchpad for them all. The tool provider passes the caller's `sessionId` down (`Placement`); `McpStdio.start` reads the session's node and path (`reins.sessions.get`). A call with no session (another extension's `reins.tools.call`, the routes) is refused: `McpServerSessionRequiredError` ("runs in the calling session's checkout, and this call has no session"; 400 on the routes, which say to use it from a session first). Its connection is the session's own: one per (server, session) (`Entry.sessionId`, keyed `<id>:<session>`), shared by that session's calls; the key on the node is `mcp:<server>:<session>`.
- **The process.** `NodeProcessTransport` (`stdio.ts`): `start` spawns `[command, ...args]` (argv, no shell: the program is looked up on the node's `PATH`) with `reins.nodes.spawn(node, …, { key, cwd, env })` and the default `ifRunning` (`replace`), then reads its `lines`; each line is a JSON-RPC message (`JSONRPCMessageSchema`) for `onmessage`, blank lines are skipped. `send` writes the message as a JSON line. A line that is not JSON-RPC stops the process (its stdout is the protocol's, and cannot be trusted after one). The process's end (its exit, a stop, a line too long, its node losing it) gives `onerror` and `onclose`, with `endReason`: how it ended, and the last 2000 characters of its stderr (`stderrTail()`), so "Program not found", a crash's message or a stack trace is in the failure the caller and Settings see. `close` stops the process (SIGTERM to its group, then SIGKILL). `env` is added to the node's environment.
- **Starting.** Connecting starts the process and runs `initialize` within `stdioConnectTimeoutMs` (60 s: `npx -y` may download the server first), then lists its tools at once and keeps the list (below). A spawn the node refuses (no such program or directory, the node away) is a failure like any other: recorded in the server's status, and the session's next call starts again.
- **The tool list is kept** in `mcp_tool_lists` (by server and the node it ran on), written at each connection's listing and again on `notifications/tools/list_changed` (a stdio connection lists again at once, rather than only clearing its cache), unless the server changed meanwhile (the entry's generation). While the session has no process running, `listTools` answers from the latest list of any session, without starting one, so a search answers while processes are idle, in a new session, after a reload, and in Settings (*Tools*). **Before its first start there is no list, and a search in a session starts it there**, within the search's deadline, as a remote server's first search connects: the search waits at most its deadline, and a start that outlives it goes on and keeps its list for the next search. The alternative, a search that never starts a process, would leave a new server's tools unfindable until something called a tool by an ID the agent cannot know. A call reads the list to resolve its ID, then starts the session's process. One list for all sessions assumes a server lists the same tools in every checkout, which most do; a server whose tools depend on the project shows the latest session's until the session's own process lists.
- **Status** is one per server, as a remote server's: `disabled`, `ready`, or `error {message}` from the latest failed start or request in any session (with the stderr tail), cleared by the next success in any session (`McpConnections.failures`). `ready` says the server can be used, not that a process runs: one is started on demand. Settings cannot test a stdio server (it has no session: its menu has no *Test*); an agent's `reins.mcp.test` starts its own session's process afresh. The system prompt stays one line per server.
- **Lifecycle.** An idle close (5 minutes without a call from that session) stops the session's process; the tool list stays. `disconnect` (a change, disabling, removal) stops every session's process through its handle. A change to `command`, `args`, `cwd`, `env`, the transport or the name restarts them (each session's next call starts its process as changed) and, except for the name, forgets the tool lists, as the tools may differ. Removal and a rename also stop and forget whatever is kept under the old keys on every node (`McpStdio.forget`: `reins.nodes.processes()`, then `reins.nodes.stop(node, key)`), so no record is left behind. A process that exits while no call is in flight records no failure: the session's next call starts it again. Turning the extension off stops its processes through the host (ADR-039). Each session that uses a server has a process until it idles: a node runs at most 64 processes, git's included.
- **Not reattached after a reload yet.** A reload or restart lets go of keyed processes (the host's), and the next app's `McpStdio` stops those an earlier app let go of (at its start: every `mcp:*` record not `running` in this app), before its first spawn, so a server nobody uses again does not run on. The next call starts the process again and initializes it. Reattaching (`ifRunning: "attach"`, resuming without `initialize` unless `lostBytes`) is a later task: it needs the client's state across the reload (the negotiated protocol version and capabilities, kept beside the tool list) and a client that skips `initialize` on a resumed process.
- **Secrets.** `env` values are stored only in the host's secret storage (`servers/<id>/env`), go to the node only in the spawn request (which neither side logs, and of which the host keeps only an HMAC), and are never in views (`envNames` only), the extension's database, the `processes` records or the logs. A program's arguments are not secret: they are in its process's command line on the node.

### Where connections live

On the app, not the process: each registration of the extension (one for each app, `createAppState`) creates its `McpConnections`, and its disposer, which the app's `stop` awaits, closes them (`close()`: every connection closed, nothing connects again on it). The next app connects again on demand. Nothing about a connection needs to outlive an app: what must (credentials, a sign-in in progress) is in the database. hot-reload.md *Ownership*.

- A reload or restart closes every MCP connection, and a call in flight fails. The next use reconnects, which costs one `initialize` round trip (a stdio server's process is started again: *Stdio servers*).
- In exchange, the connection manager is app code: it hot reloads, and neither `ServerProcess` nor `AppState` knows about MCP. Connections on the process would survive a reload, but their code would change only on a restart.
- A sign-in in progress is in the database (the hash of its `state`, its callback URL and start time on the row, its PKCE verifier and any client it registered among the secrets), not in app memory as provider OAuth keeps its logins. So a reload during a sign-in, frequent in dev, does not lose it.

### Repo servers

A project's `.mcp.json` (the `mcpServers` shape) defines its repo servers. They are rows of `mcp_servers` with the project's `project_id`, one per project and name: the row holds what is the user's (the switch, the OAuth state, the values of its variables, `variables`, all secrets but the switch) and the entry as last read in any session of the project (`repo_json`, `McpRowFields.repo`; its kind's columns follow it, an HTTP entry's `auth_kind` `oauth`). So the existing connections, OAuth and tool lists work for them unchanged.

- **Reading.** `McpRepoServers.read(sessionId)` reads `<checkout>/.mcp.json` through the session's node (`reins.nodes.readFile`) when the session's runtime opens: the prompt section calls it first (`mcpPromptSection`), so a change to the file reaches a session the next time it opens, as the prompt does; nothing watches the file. A session that never read one reads it at its first lookup (`ofSession`). What it read is kept for it (`mcp_repo_reads`: `RepoFile` as JSON), so each session uses its own checkout's entries; a node that cannot read it now leaves the session's last read. Browsers are told (`mcp_repo_changed {projectId}`) only when the read changed something.
- **Entries.** `parseRepoConfig`: `type` `http`/`sse`, or a `url` without a `command`, is HTTP (`url`, `headers`); `type` `stdio`, or a `command`, is stdio (`command`, `args`, `env`, `cwd`, a relative directory inside the checkout). Skipped, with the reason: a name that is not `MCP_SERVER_NAME_PATTERN` (it names the tools), an unknown `type`, both or neither of `command` and `url`, fields of the wrong type, a `cwd` outside the checkout. Not valid JSON, or no `mcpServers` object: the file is `invalid` and the session has no repo servers.
- **Which servers a session has**: the user's own and its file's (`McpServers.forSession`), never a repo server with the name of one of the user's own: `sessionServers` and the session's list skip that entry at each use (a skipped entry with the reason in the list), so a repository cannot stand in for a server the user trusts by its name, and adding or removing one of their own takes effect at once; the tool provider and the prompt use it. `find` (`reins.mcp`) and `list` (Settings) have only the user's own. A call without a session (another extension) has only the user's own.
- **HTTP entries.** `${VAR}`/`${VAR:-default}` in header values expand when connecting (`repoHeaders`, `connections.ts`) from the user's values for the project (`variables`), else their default, never from the Reins server's environment: an HTTP entry runs without being turned on, so a file could otherwise send any of the server's variables (API keys) to any URL. A variable with neither fails the connection, saying so. The OAuth state is the row's, so per project and name. Not signed in, a repo server connects without OAuth (no client is registered at each attempt), and a 401 is `needs_sign_in`; the user signs in from the session's list (the same `signIn`). A read whose URL, transport or headers differ from the row's signs the user out (`adopt`: the OAuth secrets and a sign-in in progress deleted, the connection closed).
- **Stdio entries** run per session as the user's own do (*Stdio servers*), each session the version its own read has (`McpStdio.start`, `entryFor`), under the key `mcp:<project>/<name>:<session>`. `${VAR}` in env values expands from the user's values, else the node's environment (read with `reins.nodes.run`, base64 so any value comes back whole), else the default; one with none fails the start. A session's read that changes its entry stops that session's process (`disconnectSession`).
- **The switch** is the only field `update` takes for a repo server (`updateRepo`); `remove` refuses one (the file defines it). `publish` tells `mcp_repo_changed` instead of `mcp_server_updated`, as Settings' list is the user's own.

### Allowed commands

A repo server runs only when its switch is on and, for a stdio entry, when the exact command its session read (`stdioVersion`: command, args, cwd, env names; not env values) is one the user allowed for its project ([ADR-040](../adr/040-repo-mcp-commands-run-only-when-allowed.md)).

- **One place decides** (`McpRepoGate.block(row, sessionId)`, `repo-gate.ts`): null, it may run; else `off`, whose `message` is what agents are told (connections pass it on in `McpServerUnavailableError` and know nothing of `.mcp.json`). Connections ask it before any connection and before a stdio server's kept tool list is given, so nothing starts and no tool is listed; the prompt section, tool search and the session's list ask it too, so the list and agents agree. Off has one meaning for agents, whatever made it off (a repo server's switch, a command not allowed or changed, or one of the user's own servers disabled): the server is listed under the prompt's servers that are off, is not searched, and a call or a search of that server alone fails saying it is disabled and where the user turns it on (agents are told "disabled", the word their prompt uses). Nothing is recorded and no one is told: the agent decides whether to tell the user, who turns it on with `/mcp`.
- **The allowed commands** are in the host's secret storage, `allowed/<project>/<name>/<hash>` (the command and when), so a row written into the extension's database allows nothing. Turning a server on adds its command; the commands of other branches stay, and none is taken out: off stops every command of it. `McpRepoGate.changed` says another command of it is allowed, not the session's (the list's "its command changed").
- **The toggle** (`allow {id, allowed, sessionId}` → `McpRepoSwitch.set`): on, the switch on and, for a stdio server, the command as the session read it (`McpStore.repoEntry`) allowed; off, the switch off, so nothing of it runs for the project. A change of the switch closes its connections. No session is told. Idempotent: two browsers answering at once agree. `update` refuses every field of a repo server, `enabled` included.
- **Only the routes turn servers on.** `McpRepoSwitch` is made in `startMcp` and given to `registerMcpRoutes` alone, and `allow` refuses a request that is not a browser's (`HttpCall.browser`, 403). `McpContext`, `reins.mcp`, the tool provider and the prompt hold `McpRepoGate`, which only answers.
- **The frontend part** (`session-servers.ts`): `/mcp` opens `mcp-servers` (`{ source, sessionId }`, one tab per checkout: its key is the source, as the file is the checkout's) in the Inspector for the shown session; nothing opens it by itself. The mounted list follows the session shown when it is on the same checkout (its toggles act for that session, and its **Tools** asks `tools {id, sessionId}`, which starts a stdio server in that session's checkout) and closes with the Inspector's other tabs on a switch of checkout. The view mounts two sections. Each is headed by where its servers come from: the project's name, and Global. First `<mcp-repo-servers>` (`repo-servers-list.ts`) with the session: its `sessionServers` (with the session's `projectId`; none for a session of no project: the section draws nothing; with no server, a line says why: no file, an invalid file, not read yet, an empty file), each server drawn by `mcpServerCard` (`server-card.ts`, which the Settings page's `<settings-mcp-servers-section>` uses too: name and badges, Sign in, the switch, the command or URL, the status dot and label, Tools with descriptions cut by `ClampedTexts`, the error, the sign-in notice with its link, `openSignInWindow`/`showSignInPage`), with its own details (env and header names, "its command changed" (`changed`), the variables' fields) and Sign out. Then `<mcp-own-servers>` (`own-servers-list.ts`), over an `McpServersStore` of its own (the Settings page's store, loaded at mount, disposed with the view): the user's own servers, each drawn by `mcpServerCard` as Settings draws it (the switch, `update {enabled}`; Sign in and Sign out; Tools, the kept list for a stdio server), without Settings' menu, with **Edit in Settings** (`reins.settings.show()`) for adding, editing and removing. Nothing speaks of approval: a server not turned on is just off. There is no project-wide list: a session's list is where its servers are. There are no warnings by kind of command: a list of runners and their pinning rules would need constant upkeep.

## OAuth

`McpOAuthProvider` is the SDK's `OAuthClientProvider` over the store, in one of three modes:

- **`sign-in`** (`startMcpSignIn`, the `signIn` method, `POST /api/extensions/mcp/signIn`): Reins first sends an unauthenticated `initialize` to read the server's `WWW-Authenticate` (resource metadata URL and scope, as the transport would; a server that needs no authentication accepts it, and the session it opened is ended with a `DELETE`, best effort), records the sign-in on the row (`beginMcpSignIn`: the SHA-256 of a random `state`, the callback URL, the time), then runs `auth()`: discovery (cached as `discovery`), the client (the server's `client_information` when registered for this callback URL, else one an earlier sign-in registered for it, else a new registration, kept as `sign_in_client_information`; a pre-registered client, `oauth_client_id` with its `client_secret`, is used as configured), the PKCE verifier (`code_verifier`), and the authorization URL, which the route returns. It hands out no tokens, so `auth()` starts an authorization rather than refreshing. The scope is the row's `oauth_scope` as it is, else the server's (its challenge, else its resource metadata) plus `offline_access` when the authorization server lists it (`defaultScope`). MCP servers do not list `offline_access`, since it is the authorization server's, and some authorization servers (Vercel's) issue a refresh token only for it: without it, the sign-in ends when the first access token expires. `defaultScope` runs discovery itself and saves it for `auth()`.
- **`callback`** (`finishMcpSignIn`, `GET /extensions/mcp/oauth/callback`): the model finds the sign-in by the hash of `state`, refuses one older than 15 minutes or answered with `error`, and runs `auth()` with the code, keeping what the exchange gives in memory. On success the tokens, the client they were issued to and the sign-in's callback URL become the server's (`completeSignIn`; not one transaction, *Rows and secrets*). The sign-in record, verifier and registered client are removed whatever happened, the connection is replaced, and a background `test` connects so that a failure shows at once. The callback page closes its window.
- **`connection`**: the transports' provider. It only reads the credentials, and gives its tokens without their refresh token, so the transport's own `auth()` (after a 401 that the connection's refresh did not fix, or a 403 for scope) never refreshes outside the lock (*Refreshes are serialized*). When `auth()` asks to redirect, it only marks `signInRequired` (and saves no verifier, so a sign-in in progress stays valid). The transport then throws `UnauthorizedError`: `needs_sign_in`.
- **`refresh`** (`refreshMcpTokens`, under the lock): a refresh of the tokens its caller read. It writes the credentials only while the stored tokens are still those (`holdsTokens`). A sign-out, a sign-in or another refresh during its request wins: its result is dropped (`superseded`). A refusal (`invalid_grant`, the SDK's `invalidateCredentials('tokens')`) deletes the tokens (`signed_out`). Its `outcome` says which.

**A sign-in never changes the server's credentials until it completes.** The server's tokens were issued to its client, and a refresh must present that client. If a sign-in replaced the client when it started (a new registration from another origin), an abandoned sign-in would make the next refresh fail and sign the server out. Also, the SDK invalidates credentials when an exchange fails (`all` on `invalid_client`, `tokens` on `invalid_grant`). In the `sign-in` and `callback` modes this drops only the sign-in's own client and the discovery cache, so a bad code does not sign out a working server.

**The sign-in window** (`_signIn` in `mcp-servers-section.ts`) is opened blank in the click, before `POST …/sign-in` answers: Safari and Firefox block a `window.open` that runs after an await. The answer sends it to the authorization URL (its `opener` set to null first); a failure closes it. When the browser blocks even that (`open` returns null), the waiting banner's *Open the sign-in page* link is the way in.

The callback is a page for the browser, so it is one of the extension's pages, outside `/api` (`reins.http.pagePath(CALLBACK_PATH)`, `/extensions/mcp/oauth/callback`). Its URL is the origin the browser used to reach Reins (the `signIn` call's `origin`, as for node install scripts: `X-Forwarded-Proto`/`X-Forwarded-Host`, else the request) plus that path. It is stored with the sign-in (`sign_in_redirect_url`), so the exchange presents the same one, and becomes `oauth_redirect_url` when it completes. A registered client records its `redirect_uris`: a sign-in from another origin registers again.

A script has no browser request: `reins.mcp.signIn` takes the origin from the agent (`callbackOrigin`), else the origin of the latest completed sign-in (`latestMcpRedirectUrl`: the server's own, else any server's), else `http://localhost:<REINS_PORT>`. When the user's browser cannot reach that URL, the page it lands on still carries the `code` and `state` in its address: `reins.mcp.finishSignIn(url)` passes them to `McpServers.finishSignIn`, as the callback route does.

**Refreshes are serialized** per server (`McpRefreshLock`, one for each `McpConnections`). With rotating refresh tokens, each refresh token works once: a second refresh with it fails `invalid_grant` and signs the server out. Each refresh under the lock first checks whether the refresh before it made it unnecessary. A refresh does not hold the lock against a sign-in or a sign-out, so that neither waits for a slow authorization server: its writes check that the tokens did not change meanwhile (the `refresh` mode). The secret storage is async, so a sign-out or a sign-in that lands between that check and the write is not excluded: in that short window the refresh's tokens can win. This is accepted (ADR-033).

- **A connection's** (`oauthConnectionFetch`, the transports' `fetch`). The transport refreshes once per request refused 401, so concurrent requests after an expiry would each refresh. Instead, a 401 from the MCP server refreshes under the lock, unless the stored access token is no longer the one refused (another refresh or a sign-in replaced it): it is then used. The request is sent again with the new token. Only when that fails does the 401 reach the transport. The MCP server's requests are those to the server URL's origin that carry a bearer token: that covers the legacy SSE transport's message endpoint (another path), and leaves out the transport's own OAuth requests to an authorization server on the same origin (a client's credentials, Basic or in the form, never a bearer token).
- **Background refresh** (`McpTokenRefresher`, one for each app, from `startMcp`; its disposer stops it). A timer runs at most a minute after the app starts (a reload starts it again), then each hour (`tokenRefreshCheckMs`). Many authorization servers expire a refresh token that is not used for some days, so a server not used for a while would need a new sign-in. Each enabled OAuth server whose tokens were issued more than a day ago (`tokenRefreshAgeMs`: the row's `oauth_tokens_issued_at`, `getTokens`; storing tokens, at a sign-in and each refresh, sets it) is refreshed under the lock, when its tokens include a refresh token. A refusal deletes the tokens (as above) and publishes the server (`needs_sign_in`). Any other failure (unreachable, a server error) keeps the tokens, and the next check tries again. A disabled server is not contacted. No refresh extends an absolute lifetime that the authorization server sets.

Not done: refreshing before the access token expires (an expired token costs one 401), token revocation at the authorization server on sign-out, elicitation, resources and prompts, and reattaching stdio servers after a reload (*Stdio servers*): a spawned process kept under a key outlives a reload, and the next app's client could attach to it (`ifRunning: "attach"`, `reattached`) and resume without initializing again, starting again only when output was lost (`lostBytes`) or the process ended ([ADR-039](../adr/039-node-processes.md)).

## Exposing tools to agents

Agents reach MCP tools only through `execute`, in two steps: the system prompt names the servers, and `reins.tools.search(query, { filters: { server } })` finds their tools ([server-sdk.md](server-sdk.md) *Agents and `reins.tools`*); another extension finds and calls them with `reins.tools.search` and `reins.tools.call` (*Tools on the SDK*). No MCP tool becomes a direct tool of the model, because:

- the model's tool definitions and the system prompt then do not grow with each server (Vercel has 238 tools);
- a tool a server adds is found at the next lookup; direct tool definitions are fixed for a turn and would need a fresh list before each run;
- a server that is slow or down delays only the lookup of its own tools, not every run;
- one script can call many tools without a model round trip for each.

`search` does not list MCP tools, so they are never ranked against API functions, and `search` never waits for a server.

- **The system prompt section** (`mcpPromptSection`, `prompt.ts`, through `reins.prompt`) is given when the session is offered `execute` and has any server: how to find and call the tools, then each server that is on with its `instructions` (multi-line, continued under its line; a repo server's line says it is from the `.mcp.json`), then the servers that are off, under "Disabled (you can ask the user to turn these on):", by name only (where each is from is the user's concern: both kinds are turned on with `/mcp`). With none on, the header says so instead of how to find tools. Not its status, which changes during a session (a lookup reports it). It is read when a session's runtime opens, so a server added or changed reaches a session the next time its runtime opens, as task edits do. It follows the Reins section, task included. `instructions` (column renamed from `description` by migration `059`, at most 4000 characters) is the user's own text: what the server is for and how to use it (for a gateway such as executor, the integrations behind it). Reins does not use the `instructions` a server may send at `initialize`: few send them (executor does not; CircleCI's are 5.5k characters, too many for every prompt), and they cannot change during a connection, while a gateway's integrations do. The form and `reins.mcp.add`/`update` say that it goes into every prompt.
- **One tool provider** (`mcpToolProvider`, `tools.ts`, titled "MCP servers"), registered with `reins.tools`.
  - **IDs** (`mcpToolIds`): local IDs are `<server>__<tool>`, so agents see `mcp__<server>__<tool>` (the host adds the extension's prefix, [server-sdk.md](server-sdk.md) *What an extension contributes*). A server's name has no `_`, so the server is found from the store without a connection. The tool's name is the MCP server's, not Reins', so MCP cleans it: its characters outside `[a-zA-Z0-9_-]` become `_`. A local ID longer than `reins.tools.maxLocalIdLength` (64 less `mcp__`), or one that two of a server's tools would share, is cut and ends with `_` and 8 hex characters of the SHA-256 of the tool's name, so it stays the same while the server's tools do. The host never changes an ID.
  - **Server names.** Treating `-` and `_` as the same cannot make two server names equal: a name is `^[a-z][a-z0-9-]{0,31}$`, with no `_`. So saving a server needs no check for that.
  - **Search.** The filter `{ server }` limits it to that server (by name, any case); an unknown name fails with the servers there are (`McpServerNotFoundError`), and a server that cannot be used fails with its status. Other filter keys are not MCP's and are left alone. Without `server`, every enabled server is searched at the same time; one that is off is left out silently (the prompt names it), one that fails is left out, and when nothing matched, the search fails naming the servers that could not be searched. Tools are matched with `reins.tools.match`.
  - **Call.** The host gives MCP the local ID of an `mcp__…` ID. A local ID without `__`, or whose `<server>` is no server, fails (`Unknown tool mcp__…: there is no MCP server …`). For a server, its tool list is read (*Connections*: from the connection's cache, else by connecting and listing) and the ID resolved against it: an ID of none of its tools fails (`Unknown tool …: <server> has no such tool`). The result is the server's `CallToolResult`, with the script's signal and `timeoutMs`. A failure the tool reports is a result with `isError`, not a throw; a server that cannot be used throws `McpServerUnavailableError`.

The seam below is `McpServers` and the `McpServerModel` it finds: `listTools({signal, sessionId})` → `McpTool[]` (`name`, `title`, `description`, `inputSchema`, `outputSchema`, `annotations`), read from the connection's list (*Connections*), else by connecting and listing; `callTool(name, args, {signal, timeoutMs, sessionId})` → the SDK's `CallToolResult` (`sessionId`: the caller, whose process a stdio server's call runs in); both throw `McpServerUnavailableError` (`status`) when the server is disabled, needs sign-in or is down. A remote server's tool list is not stored: a stored list would help only when the server cannot be used, and then its tools cannot be called either. A stdio server's is (*Stdio servers*): its process is stopped when idle, and starting it again costs a process and its start-up.

Not done: a maximum age for the connection's tool list, for a server that does not send `list_changed` on a busy connection.
