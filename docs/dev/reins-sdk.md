# The Reins SDK

> New to the extension system? Read [extensions-overview.md](extensions-overview.md) first: the glossary and how the parts fit.

The Reins SDK is the API through which built-in frontend extensions get everything they use: a source's files, opening views in the workspace, live projects, tasks and sessions with their actions, nodes, their own server routes and messages, and the contribution points for views, message decorators, commands, sidebar sections and Settings pages. An extension gets it as the argument of its register function, `registerFileViewer(reins)`, as a VS Code extension gets its `activate(context)`: an SDK object of its own, which knows the extension, as the server SDK is built per backend extension ([server-sdk.md](server-sdk.md)). It is the "Reins-owned seam" stage of [extension-architecture.md](extension-architecture.md) (*Interface maturity*): an explicit interface with Reins values, used by built-in code and by the frontend parts of extensions outside Reins, which the app imports from the server ([extension-loading.md](extension-loading.md), ADR-038). It has no compatibility promise yet; see *Not built yet*.

## Where it lives

**The SDK, `@reins/sdk`** (`packages/sdk/src/index.ts`, the SDK package `packages/sdk`, which added extensions depend on; `@reins/sdk/server` is its other entry): what features import. Today `index.ts` is all of it: every type a feature may use (`ReinsSdk` and its capabilities, `ExtensionInfo` and `ExtensionRegistration`, `Source`, `View`, `ViewRenderer` and its presentations (`PanePresentation`), `MountedView`, `WorkspaceContext`, `PaneContext`, `InlineContext`, `MessageDecorator`, `Projects` with `Project`, `ProjectCreation` and `ProjectChanges`, `Tasks` with `Task`, `Activity`, `Sessions` with `Session`, `SessionCreation`, `SessionSummary`, `SessionQuery` and `SessionMoveTarget`, `Nodes` with `NodeSummary`, `CurrentView` and its `Subject`s, `Sidebar` and its `SidebarSection`, `Command` and its `CommandContext`, `SettingsPage` and `Mounted`, `Http` with `HttpApi`, `HttpMethod`, `HttpCallArgs` and `HttpOutput`, `RequestOptions`) and a few pure helpers (`sameSource`). It names no views: a view's name is registered at runtime, and the feature that registers it defines its parameters' type (`FileView` and `FileViewerMode` in `components/file-viewer/file-viewer.ts`, `FileReferenceView` in the file references extension, `DiffFileTreeView` with the diff file tree). Types only, through `ViewTypes`: the SDK's interface is empty, and each feature adds its view beside its register function (`declare module "@reins/sdk" { interface ViewTypes { file: FileView } }`). `views.register`, `workspace.open` and decorators' views are checked against it (`KnownView`), so a feature that opens another's view gets it wrong only by failing typecheck. At runtime nothing reads it: any name registers and opens, so an extension without TypeScript, or one that knows no other extension's types, works the same (tested with a plain JavaScript extension in `__tests__/helpers/`). App code that takes any view (the registry, the Inspector, decorations) uses `View`. It imports only its own modules (`./`, lint: `reins/sdk-isolation`); code that runs (such as event emitters features listen to) can join the types there. Its values are Reins values: never Lit templates, marked tokens, HTML, stores, routes or transport types. The DOM values are the element the app gives a view or a Settings page to `mount` into and the `Node` an inline view's `original()` returns (ADR-030): the app gives features elements, and never takes markup or templates from them. Each member's comment states its behavior (lifecycle, ordering, what is synchronous); keep them accurate when the app changes.

**`@reins/sdk/lit`** (`packages/sdk/src/lit/index.ts`): for a Lit extension, its custom elements in a registry of its own bundle's (`defineElement`, `createElement`, `ScopedElement` with Lit's `creationScope`, `mountElement`). An extension bundles it, so each bundle and each reload gets a new registry; it imports only `lit`, which the page provides (lint: `sdk-isolation` with `allow: ["lit"]`). Built-in features do not use it.
**The SDK host** (`packages/frontend/src/sdk-host/`): the app's side of the SDK, which features never import.

- **`create-sdk.ts`** — `createReinsSdk(extension, host, { scope? })`, which builds the frozen SDK object of one extension (`ExtensionInfo`: its `name`, `label`, optional `description` and `icon`) over what every extension's SDK shares (`SdkHost`): the app's state (`app`, an `SdkBacking`: `files`, `views`, `decorators`, `commands`, `settingsPages`, `sidebar`; `AppStore` in the app), its `sessions`, `projects`, `tasks` and `nodes`, the server (`http`, whose `extension(name)` is `@reins/client`'s, and `socket`, the WebSocket client's `subscribe` and `onConnection`) and the workspace's containers (`containers`, `SdkContainers`: one `Container` for each `ContainerId`, whose `open(view)` is what `workspace.open(view, { in })` does there, so the SDK only looks the container up; `inspector` is `AppStore.inspector` itself, whose `closeView(view)` is `workspace.close(view)` (the user's close of the view's tab, by key; a pinned tab stays), and `main` a `MainArea`, which also has `current()`, the view shown and what it is about, and `subscribe(listener)`, the view or its subject changing; its `open(view)` goes to the view's route and throws for a view it cannot show; in the app `RoutedMainArea` (`routing/main-area.ts`), as `AppStore` does not route: over `app.views`, the `app-workspace` `app-shell` shows (`current()`, null on a page without one) and the browser's history, its `changed()` telling `subscribe`'s listeners when `current()` changed, which `app-shell` calls after its own render and on `app-workspace`'s `main-view-change`, dispatched after each of its renders). It adds no state of its own: what is the extension's (its routes, its messages, its Settings page) is found by its name. With a `scope` (an added extension's name), every mount it registers draws into a `display: contents` element with `SCOPE_ATTRIBUTE`, where the extension's scoped stylesheet applies ([extension-loading.md](extension-loading.md) *Styles*).
- **`sessions.ts`** — `SdkSessions`, the SDK's `sessions` over the app's stores (`SessionCache`, `ProjectsStore`, `SessionOperations`): its operations, and its live lists and actions (*Capabilities*).
- **`projects.ts`** — `SdkProjects`, `SdkTasks` and `SdkNodes`, the SDK's `projects`, `tasks` and `nodes` over `ProjectsStore`.
- **`sidebar-sections.ts`** — `SidebarSections` (`AppStore.sidebar`), the sidebar's sections and the user's arrangement of them: `register` (the SDK's `sidebar.registerSection`), `registeredBy(extension)`, `arrangement()` (each section in the user's order with `visible`), `shown()`, `load()`, `setVisible(id, visible)`, `move(id, by)` and `subscribe` (*The sidebar*).
- **`commands.ts`** — `CommandRegistry`, the registered commands and running them: `register` (the SDK's `commands.register`), `registeredBy(extension)` (*Extensions*), `list()` (by name), `invocation(text)` (the command a message runs and its `args`), `run(invocation)` and `subscribe`. Whatever runs a command (today the composer; a command palette later) runs it with `run`, which gives it only its `args`.
- **`view-registry.ts`** — `ViewRegistry`, the registered view renderers: `register` (the SDK's `views.register`), `registeredBy(extension)`, `rendererFor(view)` for containers, `keyOf(view)` (a view's identity, for the Inspector and the main area), `titleOf(view, context)` (its pane's title, null without a pane or when it throws) and `subscribe` (a renderer registered or gone).
- **`settings-pages.ts`** — `SettingsPages`, the extensions' Settings pages: `register(extension, page)` (the SDK's `settings.register`, which gives it its extension; a second while it has one throws), `pages()` (each `{ extension, settings }`, by label), `page(name)` (null for an extension without one) and `subscribe`.
- **`decorators.ts`** — `DecoratorRegistry`, the registered message decorators: `registerDecorator` (the SDK's `messages.registerDecorator`), `registeredBy(extension)` (a count: decorators have no names), `bind(source)` for messages, and `subscribe`; and `BoundDecorators`, every decorator bound to a source (the context they decorate in, filled in; not a filter), which splits prose, plain text and inline code into plain runs and pieces (`InlinePiece`: a view, its inline presentation and its `InlineContext`).

**The extension system** (`packages/frontend/src/extension-system/`, as the server's `backend/src/extension-system/`; [extensions-overview.md](extensions-overview.md)):

- **`extensions.ts`** — `Extensions` (`app-shell`'s), which frontend parts run, as the server's report says, as the server's `Extensions` decides which extensions run there: `sync(report)` activates and disposes them through the host ([extension-loading.md](extension-loading.md) *In the browser*).
- **`host.ts`** — `ExtensionHost` (`AppStore.extensionHost`), the boundary between the frontend extensions and the app, as the server's `ExtensionHost` is: `activate(extension, sdk)` calls its register function and records it (*Extensions*), `list()` (each `FrontendExtension`: its `ExtensionInfo`, `status`, `error` and what it has registered now) and `subscribe`.

The registries and the Inspector are app state on `AppStore` (`views`, `decorators`, `commands`, `settingsPages`, `sidebar`, `inspector`, with no `open` of its own: the SDK opens views through its containers), next to `files`. The view mount, `<reins-view-mount>` (`ViewMount`, `components/view-mount.ts`), is the app's side of the mount lifecycle, for views (*Contribution points*) and for an extension's Settings page and icon (*Settings pages*); features only see it as their target.

## Access

[ADR-030](../adr/030-the-reins-sdk-and-how-views-mount.md) records this choice.

- **`app-shell` builds an SDK for each extension and gives it to its register function.** The built-in extensions are `BUILT_IN_EXTENSIONS` (`extensions/built-in.ts`, the one place that lists them, as the backend's `extensions/built-in.ts`): each an `ExtensionRegistration`, its `name`, `label`, optional `description` and `icon`, and its `register`. `app-shell` (`components/app.ts`) holds one `SdkHost` (`AppStore`, `new SdkSessions(this.appStore)`, `SdkProjects`, `SdkTasks` and `SdkNodes` over its `ProjectsStore`, `main` over its `app-workspace` and the router, the app's `api` and its WebSocket client). Its `Extensions` activates each extension the server's report has on, in order (*Activation*), with `createReinsSdk(extension, host)` (`AppStore.extensionHost.activate`, which calls its register function and records it, *Extensions*); in its `connectedCallback` it creates the file browser's `FileBrowserStore` with an SDK of its own (`file-browser`, not registered: an overlay of `app-shell`'s); it disposes them when it disconnects. The extension never names itself: its name is in its registration. An extension with a backend part has the same name there (`mcp`), which is where its routes and messages are; the others' `http.call` reaches no method (a 404). Only `app-shell` holds SDK objects.
- **App code uses the app's state, not the SDK.** `app-workspace` gives the Inspector `app.views` and shows `app.inspector`; `chat-panel` gets `app.decorators` and gives its messages `bind(source)`, and gets `app.commands` for its composer; the settings page shows `app.settingsPages` and its Sidebar section `app.sidebar` (through `SettingsStore.sidebarSections`); `session-sidebar` draws `app.sidebar.shown()` and the rail's badge from `ProjectsStore.activitySummary`; `app-workspace` registers the diff file tree into `app.views` (*Views over the app's state*).
- **A feature uses only what it is given.** It imports `@reins/sdk` and its own modules, never a path into the SDK package or `sdk-host/`, `AppStore`, `ProjectFiles`, `SessionCache`, the app's HTTP client (`models/api.ts`, `@reins/client`), its WebSocket client (`models/ws-client.ts`) or another feature's internals (lint: `reins/features-through-sdk`, configured in `.oxlintrc.json` for the feature files and all of `extensions/`). `@reins/sdk` is a `tsconfig.json` `paths` alias to `../sdk/src/index.ts`, which `tsc`, `bun build` and `bun test` resolve. An added extension bundles it (types, and helpers such as `sameSource`); the app provides it Lit only (extension-loading.md *Provided libraries*).
- **A register function takes the SDK** and returns a disposer. A view is a mount function, not an element; a feature that draws with its own custom element (the file viewer) defines it like any other (`@customElement`), and its mount gives the element what it uses (the file viewer gets `files`).
- **This is a boundary between modules, not a security boundary.** A later added extension is a separate bundle, so it has no path to the app's modules; it still runs in the page.

The file browser has no contribution point for overlays: `app-shell` creates its `FileBrowserStore`, mounts it (`<file-browser>`, `<file-search>`) and opens it on the `open-in-browser`, `open-file-browser` and `open-file-search` events. **In tests**, `testSdk(options)` (`__tests__/helpers/reins-sdk.ts`) builds an SDK as `app-shell` does, for `options.extension` (`test` by default), typed by its type argument (`testSdk<McpApi>(…)`), over a files API that knows a source, real registries, an `open` that records what reaches it (`opened`), the views shown in the main area (`shownViews`; the app's `RoutedMainArea` over a history kept in `mainHistory`, its entries, so a test sees entries added and replaced; `options.current` is the one shown at first, and showing one makes it the main area's, about nothing), and sessions that record theirs (`sessionCalls`; `options.sessions` replaces an operation, such as one that fails). Requests go to `fetch` (`mockFetch`), and messages and the connection come from its `client` (`StubClient`: `fireMessage`, `fireConnection`). Projects, tasks and sessions are the app's (`SdkProjects`, `SdkTasks`, `SdkSessions`' lists and actions) over a real `ProjectsStore` (`projectsStore`) and session cache (`sessions`), which a test fills; `showMain(current)` changes what the main area shows and tells `workspace.onDidChange`'s listeners. `registerInboxPage(reins)` (`__tests__/helpers/inbox-page.ts`) is an example extension page (a repository's notifications inbox, keyed by repository, about a project), only in tests; `sidebar` is the sidebar's sections, their arrangement kept by `options.sidebarLayout` (`memoryLayout()` records what is saved; none by default). `sdkFor(extension)` builds another extension's SDK over the same app, `settingsPages` is the registry, and `extensionHost` (`ExtensionHost` over its registries) activates extensions there (`__tests__/extension-system/host.test.ts` tests attribution; `__tests__/models/stores/extensions-store.test.ts` the section's merge). `SessionActions` is tested on its own over the app's stores (`__tests__/sdk-host/sessions.test.ts`). Tests give it to register functions and check the registries; nothing is installed, so nothing is cleared after each test.

Bun tests have no DOM, and Lit's DOM shim has no children. `testDom(element)` and `testElement()` (`__tests__/helpers/test-dom.ts`) give an element what mounting a view uses: `childNodes`, `append`, `replaceChildren`, `remove`, `isConnected` (`setConnected` also runs its callbacks) and an `ownerDocument` whose `createElement` makes such elements, a defined custom element as its own class.

## The MCP extension's frontend part

The MCP extension ([mcp-servers.md](mcp-servers.md)) has a backend part, registered through the server SDK ([server-sdk.md](server-sdk.md)), and a frontend part in `extensions/mcp/`: its registration (`index.ts`, `registerMcp`, which registers its Settings page), the page's store (`mcp-servers-store.ts`, `McpServersStore`, over `reins.http` typed by `McpApi`, `reins.onMessage` and `reins.onReconnect`; `isMcpMessage` tells its messages apart) and its element (`mcp-servers-section.ts`, `<settings-mcp-servers-section>`). The page's mount creates the store and the element, and loads the servers; its dispose removes them. It also registers the `mcp-servers` view, `<mcp-repo-servers>` (`repo-servers-list.ts`: a session's repo servers with their toggles), and `/mcp` (`session-servers.ts`; mcp-servers.md *Allowed commands*). Both lists draw each server with `mcpServerCard` (`server-card.ts`). It reaches its routes, its messages and Settings only through the SDK (lint: `reins/features-through-sdk`). What it still uses of the app:

- **The app's UI kit**: `StoreController` (`controllers/`), `Loadable` (`helpers/`), `ui/icons.ts`, `ui/confirm-dialog.ts`, `ui/dialog.ts`, `ui/popover-menu.ts` and `showToast` (`ui/toast.ts`), and the app's Tailwind classes. A plugin with its own UI would bring its own; a shared kit, or theme tokens (*Not built yet*), would need to be published with the SDK.
- **The backend's types** (`@backend/extensions/mcp/…`, type only): the extension's own, from its backend part.

## Capabilities

- **`files`** — a source's files (`Files`). It is `ProjectFiles` (`models/stores/project-files.ts`, application lifetime on `AppStore`) itself: the SDK adds no layer. A `Source` is `{ nodeId, path }`: any directory on a node, whether or not a session works there. The app reads it by its node and path (the node file routes, `/api/nodes/:nodeId/files…?root=`) and tries every read: a listing the server refuses for its node (offline, removed) is empty, and is loaded again when the node list (the app's `NodesStore`, the one the settings page shows) says the node connected or disconnected. Features never see a route or availability. `listing(source)` is synchronous, loads on first ask, and is cached for the two sources asked for last (the viewed session's and the file browser's), so another project's listing is dropped once you leave it. After the change signal or the node coming back, `subscribe` listeners are told and the next ask reloads it: a listing nobody asks for again costs no request. It is empty while the node is offline or removed, and keeps its `data` array when a reload finds the same files. `nodeName(source)` names a source's node; `subscribe` hears any listing change and node names changing, and a feature that shows a listing asks again on it; `onFilesChanged` says a source's files may have changed (debounced; for sources sessions work in, from their tool calls and turns); `read` is uncached; `contentUrl` is a file's own URL; `upload(source, files, {folder, onProgress})` writes files into a folder of the source (`POST /api/nodes/:nodeId/files/upload`) and then announces its files changed at once; `nodeName(source)` is the name of its node (null until known), for views that show a file of another node than the viewed session's.
- **`sessions`** — sessions by ID (`SdkSessions`). It follows the agents' `reins.sessions` (the server SDK's `sessions`, backend `sdk-host/sessions.ts`) where the two do the same thing: the same names, arguments and errors, in the SDK's camelCase. `get(sessionId)` answers from `SessionCache` when the app has the session (with its placement), which the server's messages keep current, so it resolves at once without a request; only a session the app has not loaded is asked of the server (`SessionCache.loadDetail`, `GET /api/sessions/:id`, which also fills the cache). It gives a `Session` with its `projectId` (null for a session of no project, which Reins features may start), `taskId` (null for an assistant conversation), `parentSessionId`, `name`, `source` (its placement's node and path) and `activity` (`running`, `unread` or null). As agents' `reins.sessions.get` (in `execute`), it rejects for a session the server does not have, with the server's message. The Recent section takes each row's activity from it, so a session just opened shows read at once, as in Projects, rather than once its backend part answers again (an answer that may come before the server saved the change). `create({ projectId, taskId?, source?, title?, model?, prompt? })` creates a session (`ProjectsStore.createSession`, `POST /api/projects/:id/sessions` with those options; without them, a new conversation of the project's assistant in its default source with the default model; `source`, a node and path, any directory there, checked on its node when no session used it yet) and resolves with its ID. The server rejects a task of another project, a location on an unknown node or that is not a directory there, a model its catalog does not have and a blank title. A `prompt` is then submitted as its first message (`SessionOperations.submit`), shown at once in its conversation (an optimistic entry, as the composer's), and `create` resolves once Pi admitted it; a refused prompt rejects `create` with the server's message (the session exists without it, and its conversation shows the error). Creating does not show the session: `workspace.open({ view: "session", sessionId }, { in: "main" })` does. `send(sessionId, message)`, as agents' `reins.sessions.send`, steers the session with the message as the user (`SessionOperations.submit(sessionId, "steer", …)`, `POST /api/sessions/:id/steer`): an idle session starts work on it and a running one takes it into its work (session-runtime.md *Session orchestration*). Its conversation shows it at once, as the composer's; `send` resolves once Pi admitted it, not when the work ends, and a refusal rejects it with the server's message and shows in the conversation. It gives nothing back, as agents' `send` does. `compact(sessionId, instructions?)` is the server's manual compaction (agents' `reins.sessions.compact` takes `{ instructions }` instead) (`SessionOperations.compact`, in order with the session's other commands; session-runtime.md *Manual compaction*): it resolves once the compaction started, and the conversation shows it as automatic compaction (its indicator, the summary; a failure is the conversation's error, from `compaction_end`). Operations that reach the server reject with an Error whose message is the server's. `create` is not the agents' `start`: `start` creates a session in the caller's project and task with a required prompt and a parent, and a browser has no caller; the model is `model: { provider, modelId, thinkingLevel }` here, as the HTTP body and `start` have it.
  - **Live lists.** `list(query?)` gives the sessions the app has that the query asks for (`SessionQuery`: `projectId`, null for no project; with it `taskId`, null for the assistant's conversations; `archived`, left out otherwise), pinned first, then the latest changed (`compareSessionListItems`), each a `SessionSummary` (its project, task, parent, name, first message, times, message count, `activity`, `pinned`, `archived`, `startedBy`, `source`, `nodeName`, `nodeRemoved`). It is synchronous, read from `SessionCache` (only entries loaded enough to list, never background sessions), so it can be read while drawing; `onDidChange(listener)` says which sessions changed (*Change events*). What the app has: every session with activity (the activity snapshot, `GET /api/sessions/activity`), the sessions of no project, and what a query loads the first time it names it: `{ projectId }` loads the project (`ProjectsStore.ensureLoaded`: its tasks and its assistant's conversations), `{ projectId, taskId }` that task's sessions (`fetchTaskSessions`, once). Summaries are kept per cache entry, so an unchanged session is the same object. The actions (`setUnread`, `setPinned`, `setArchived`, `setName`) work on any session: one no list loaded has its details loaded first (`ProjectsStore.withSession`), so a section that lists sessions from elsewhere (Recent, from its backend part) can act on them.
  - **Actions**, for a session of any project or none, shown at once and put back when the server refuses (rejecting with its message): `setUnread(id, unread)` (`PATCH /api/sessions/:id/activity`; a running session cannot be marked unread), `setPinned`, `setArchived`, `setName` (`PATCH /api/sessions/:id/metadata`), `moveTargets(id)` and `move(id, source)` (`/move-targets`, `/move`). They are `ProjectsStore`'s cross-project methods over the functions `project-store.ts` exports (`setSessionUnread`, `updateSessionMetadata`, `loadMoveTargets`, `moveSession`), which `ProjectStore` uses too. The agents' `reins.sessions` (in `execute`) has `setName`, `setPinned` and `setArchived` of the same names.
- **`projects`** — `list()` (by name: `id`, `name`, `activity` from its sessions, `baseBranch`, `defaultSource`), `onDidChange` (*Change events*), `create({ name, source, baseBranch? })`, `update(id, { name?, baseBranch?, defaultSource? })` and `remove(id)` (`SdkProjects` over `ProjectsStore`).
- **`tasks`** — `list(projectId)` (synchronous: empty until the project's tasks load, which asking starts), `loaded(projectId)`, `onDidChange` (*Change events*), `create(projectId, request)` (Reins writes the task, `POST /api/projects/:id/tasks/generate`), `update(projectId, taskId, changes)` and `remove(projectId, taskId)` (`SdkTasks`). A `Task` has its `branchName`, `closed`, `updatedAt`, `sessionCount`, `diffStats` and `activity`.
- **`nodes`** — `list()`, every node not revoked (`id`, `name`, `connected`), from the server: the project form's node choice.
- **`ui`** — the host's own dialogs for its things, so every extension that acts on one asks the user the same way (`SdkUi`, `sdk-host/ui.ts`). **`renameSession(sessionId)`** asks for the session's new name in the app's `inputDialog` (`ui/input-dialog.ts`): its name now, its first message as the placeholder ("Empty session" without one), and "Leave blank to use the first message.". It saves through `sessions.setName`, a blank name as none, and resolves true once saved, false when cancelled; a failed save is toasted and the dialog stays open. A session the app has not loaded (one Recent lists) is loaded first; one the server does not have rejects. Projects (for any of its rows, on `rename-session`) and Recent (its row menu) rename through it. In tests, `setInputHostForTesting(answerer)` answers the dialog.
- **`workspace.onDidChange(listener)`** — the main area's view or what it is about changed (another route, or a session's details loaded): read `current()` again. A sidebar section follows the shown session and project with it. Listeners hear every change of the subject, also the file a session's Changes review scrolls to, which can change many times a second; so a listener that draws only some subjects keeps what it drew and draws again only when they change (Projects keeps the shown project and session, Recent the shown session, and the Inspector's Changes tree takes another diff only for another session).
- **Change events.** `projects`, `tasks` and `sessions` each have `onDidChange(listener)`, which says what changed, not the data: the listener reads again. `projects.onDidChange({ projectIds })`: projects added, removed, or whose `Project` differs (a name, a session starting to run so its activity changes). `tasks.onDidChange({ projectIds })`: projects whose tasks (or whether they loaded) differ, and every `task_updated` of a project not loaded (`ProjectsStore.onTasksUpdated`), whose tasks may have changed with nothing to read yet. `sessions.onDidChange({ sessionIds, projectIds })`: sessions whose `SessionSummary` differs, appeared or went (background ones never), with the projects they were or are in (null: none), so a session that moved names both. Each is told once a microtask (`ChangeFeed`, `sdk-host/change-feed.ts`), and only for a change its reads show: the host compares what the reads give before and after (`Snapshot`, as JSON; for sessions, each summary when its cache entry changes), so a session's model or loaded details tell nothing. Projects and tasks are compared a microtask after the `ProjectsStore` changed, and only while someone listens. An element keeps its listeners while on the page with `SubscriptionsController(host, source, subscribe)` (`controllers/subscriptions-controller.ts`, reactive-controllers.md: subscribes on connect and when the source changes, stops on disconnect). It is how a Lit element holds the events; nothing in the SDK needs it: each event returns a `Disposer`, which an extension in another framework calls when its view goes (in React, the cleanup of a `useEffect`), filtering by the IDs it shows.
- **`workspace.open(view, { in? })`** — shows a view in a container: `"inspector"` (the default) or `"main"`. Each container says what opening does.
  - **`"main"`**, the main area, shows one view at a time, the page of a route, so opening a view there is navigation: a history entry, and Back returns to the view before (`RoutedMainArea.open`, `routing/main-area.ts`; ADR-037). It shows any view whose renderer has a `pane` presentation, the same one the Inspector shows (*Contribution points*), in the chat pane's place, with `container: "main"` in its context, and throws for a view without one (`The "<name>" view has no pane presentation, so the main area cannot show it`). Nothing limits which views go there: the file viewer's `file` view opens there as it opens in the Inspector. The same view as the one shown (its name and its renderer's `key`) replaces its history entry instead of adding one, and the page is given the new view in place (`update`); opening exactly the route shown gives the page a new view object too, as an open. The host derives the route from the view: `#/view/<name>?<parameters>` (frontend-architecture.md *Routing*), so a reload, Back or a link shows the same view; a route whose renderer is not registered (yet) shows *Page unavailable* and mounts the page when it registers. The app's own views keep their routes: `session` (`SessionView`, `{ view: "session", sessionId }`, declared by `app-workspace`, registered by app code with `session-changes` as the session's two tabs: its Chat, and its Changes at `#/session/:id/changes`), `new-session` (`NewSessionView`, `{ view: "new-session", projectId, taskId }`, either null, declared by `components/new-session-page.ts`: the new session page, frontend-architecture.md *Routing*; a registered pane, `registerNewSessionPage(app.views, app)`, which `app-shell` registers, keyed by its project and task) and `project-history` (`ProjectHistoryView`, `{ view: "project-history", projectId }`, declared by `components/project-history.ts`: the project's full-screen History page, outside the workspace, which `current()` answers null for). On a phone, opening a view there brings the workspace's main page forward (`AppWorkspace.revealMain`), also for the view already shown.
- **`workspace.current()`** — the main area's view now and its `subject`: the things it is about, most specific first, as `Subject`s (`{ type, id }`). The kinds are open, as views are: `SubjectTypes` maps each `type` to its ID's type, and is empty in the SDK. The code whose views are about a kind adds it with `declare module "@reins/sdk" { interface SubjectTypes { … } }`: `components/session-views.ts` adds `project` (number), `task` (number) and `session` (string) beside `SessionView`, and `components/file-viewer/file-viewer.ts` adds `file` (`FileSubject`: `{ source, path }`, whole without another subject, on any node) beside `FileView`, and a command that reads them (`/compact`, `/new`) relies on that, as a decorator relies on the view it names. The view gives its subject from what it holds, so it can be read synchronously; what it does not hold, a command asks for (`/new` gets the shown session's source with `sessions.get`). `app-workspace.current()` asks the shown tab's mounted view: a session's tabs give its session, then its task (none for an assistant conversation), then its project, from the session's details in `SessionCache`, and only the session while they are loading. For any view it asks the mounted view, `MountedView.subject()` (through its `<reins-view-mount>`, `ViewMount.subject()`), when asked: the new session page gives the task and project chosen on it, nothing before one is chosen; the `file` view gives its file; a session's Changes gives the file its review is on first; a page without `subject`, or not mounted yet, is about nothing, and a throw is logged as nothing. On a page that is not a view (settings, a project's history, no session) it is null. `workspace.currentSubject(type)` is the ID of the first subject of that type, or null. `onDidChange` hears a subject change when the host next checks: after the main area renders, or when the view says it with `context.subjectChanged()` (`PaneContext`), such as the review on another file as it scrolls. The host then asks `subject()` again (`followShownView`) and tells listeners only if `current()` differs (`RoutedMainArea.changed`). Only the main area's views are asked, so the Inspector's context's `subjectChanged` does nothing; its focused tab can be asked the same way later.
  - **`"inspector"`**: `Inspector.open` (`AppStore.inspector`). The same view (`ViewRegistry.keyOf`: its name and its renderer's `key`) open there is focused and replaced, otherwise it opens after the others. A view about a source names it in its parameters (`file`, `file-reference`), so `open` needs no source, and opening works while no workspace is on screen (settings, History). On a phone the workspace on screen moves to the Inspector page (it listens to `Inspector.onOpen`).

- **`http.call(method, input?, options?)`** — calls a method of the extension's backend part's HTTP API (its `reins.http.handle` methods; server-sdk.md *What an extension contributes*): `POST /api/extensions/<name>/<method>` with `input` as the JSON body. It resolves with the method's output, undefined for a method without one, and rejects as `@reins/client` does (`ReinsHttpError`: the server's message, `status` and `body`; 400 for input the method's schema refuses). It is `@reins/client`'s `extension(name).call`, which only the host calls. **Typed by the contract:** the register function names its backend part's API type, `registerMcp(reins: ReinsSdk<McpApi>)` (`McpApi`, `typeof mcpApi`, imported as a type from the backend part's `api.ts`), and `call` then takes only that API's method names, with each one's input (required when it has one) and resolves with its output, from the schemas' `static` types (`HttpCallArgs`, `HttpOutput`). The frontend imports only the type, so a call goes by the method's name: there are no paths to know at runtime. `ReinsSdk` without an API (the default) calls any name untyped. The host builds every SDK the same way (`createReinsSdk<A>`); `A` only types `call`.
- **`onMessage(listener)`** — the extension's own WebSocket messages (its backend part's `broadcast`, sent as `{ type: "extension", extension, message }`), each `message` as it was sent; no other extension's. The extension tells its kinds apart (MCP: `isMcpMessage`).
- **`onReconnect(listener)`** — the server connection came back after it was lost (not its first connect). Messages sent meanwhile are lost, so a store kept current from them loads again: MCP's store lists its servers again once it has loaded them.

## Contribution points

- **`views.register(name, renderer)`** — how a view name can be shown, by presentation (ADR-030). The renderer is typed by the name's `ViewTypes` entry; the app trusts it at runtime. `key(view)`, optional, is what tells views of the name apart (the file viewer's: source and path, so lines and mode only move within a tab); without it the name has one view. Every container keeps a mount for one identity: a view of another key is mounted anew, so `update` only ever gets the same view opened again (a session's Chat never moves to another session). `tabOf`, optional (`{ type, parameter }`, a `SubjectTypes` kind and the name of the view's parameter holding its ID), makes the view one of the main area's tabs of that kind of subject: while the main area shows it, the host shows a tab for each renderer that is a tab of the same kind, its view made with the same ID in its own parameter (`ViewRegistry.tabsFor`), the app's renderers first, then extensions' in registration order, in its toolbar and as a phone's swipe pages, and choosing one opens its view (a history entry). A session's Chat and Changes are such tabs; an extension adds a tab to every session by registering a view with `tabOf: { type: "session", parameter: … }`. A container that keeps a mounted view hidden (the main area's tabs not shown) tells it with `MountedView.setVisible(false)`, at once for one mounted hidden, and `setVisible(true)` when it shows it again; a view without it is treated as shown, and one that only matters on screen (the chat marking its session read, the review loading) uses it. A view without a renderer is keyed by its name. Each presentation is a mount function: `mount(target, view, context)` draws into `target`, an element the app made, and returns `{ update?(view, context), dispose?() }`. Any framework can do that (React `createRoot`, Svelte and Vue `mount`, Solid `render`); no feature has to define a custom element. Every open sets a new view object, so a view given a new one in `update` shows it afresh (the file viewer reads its file again and reveals its lines); a view without `update` is disposed and mounted again instead. After `dispose` the app empties the target, and it never mounts a target twice without a dispose between. Two presentations exist: **`pane`**, a view as a block of its own in any container (an Inspector tab, the main area's page, later a modal; one presentation for all of them, ADR-037; context `PaneContext`: the `container` it is in, so a view can fit its actions or layout to it, and `subjectChanged()`; what it shows is in the view, and what the main area is about is `workspace.current()`), which also gives its `title(view, context)` (a tab's title; in the main area the browser tab's title, `<title> · REINS` after the activity count, and the phone's header), `description(view, context)` (a tab's tooltip) (the file viewer's are its file's name and its path: a title needs no node, and the view says its source), an optional `width` (the Inspector's width in px while the view is shown there, which other containers ignore, 320 when left out, until the user resizes it for that view name; the Changes tab asks for 240 and `file` for 640) and `icon`, a presentation of its own that draws the tab's icon into a 14 px box the app gives it, in the tab's `currentColor`, with the same lifecycle as a view (the app has no list of icons; the built-ins draw theirs from `ui/icons.ts` with `paneIcon`), an optional `toolbar`, a presentation of its own with the same lifecycle that draws the view's controls in the host's toolbar in place of its title (only the main area shows it, for now; the host keeps the sidebar button, the connection status and its menu, and on a wide screen shows its toolbar for a view only when it gives one, so a view without one fills the main area); its `subject?()` (on what `mount` returns) says what it is about for `workspace.current()` when the main area shows it; and **`inline`** (in place of a piece of message text; context `InlineContext`, *Messages* below). `popover` is meant to be another key later. Containers show `pane`: a view without one shows in the Inspector as unavailable and is refused by the main area. A name has one renderer; registering a second renderer or a renderer without a presentation throws. A view uses the SDK its register function was given (the `file` view's mount gives its file viewer `reins.files`). A view about something fixed names it in its parameters (`file` and `file-reference` carry their `source`); the context is for views that follow the viewed session.
- **The view mount.** One element, `<reins-view-mount>` (`ViewMount`, `components/view-mount.ts`), runs the lifecycle of everything an extension draws with a mount function: the Inspector renders one per tab with the renderer's `pane` and one per tab icon, the main area one for each of its tabs (`data-main-shown` on the shown one, `.visible` false on the others, filling the chat pane's place), messages one per decorated piece, and Settings one for an extension's page and one for its icon. It mounts into itself once it is on the page and has a presentation (`Mountable`: a view's presentation, or a Settings page or icon, which take no view), with its view and context when it has them, updates the view when they change (properties set together apply once), mounts again for a new presentation, and disposes when it leaves the page; a moved element disposes before it mounts again. Its children until it mounts are the fallback (a piece's original text), put back after a dispose. **Failures stay in it:** a throw from `mount` or `update` disposes what was mounted and puts the fallback back (and logs the error), or, without a fallback, shows *Failed to load: …* in its place; a throw from `dispose` is logged. So one extension's failing view leaves the Inspector, a message or Settings working.
- **`messages.registerDecorator(decorator)`** — finds pieces of completed message text and names the view shown in place of each, in its `inline` presentation (ADR-030). `decorate(text, context)` returns spans (`start`, `end`, `view`), `decorateCode(code, context)` optionally names the view of a whole inline-code span, and `onChange(listener)` says when what it decorates from changed. Decorators have no lifecycle of their own: the view does. An inline view controls its piece completely: it may draw the text (`context.original()`, a new copy of what the app draws without a view, such as `<code>app.ts</code>`), change it or draw something else; `context.text` is the piece's original text and `context.code` whether it was a whole inline-code span. File references are the `file-reference` view (`{ source, path, startLine?, endLine? }`), whose inline mount draws the original text in a control (`role="button"`) that opens the file with `workspace.open`. A piece has one view: where decorators overlap, the earlier registered wins, and a span whose view has no inline presentation leaves its text alone. Decorating is synchronous, from what the decorator has; the app decorates again after `onChange` or a view registration (`DecoratorRegistry` bumps a generation and tells its subscribers, so `app.decorators.bind(source)` returns a new `BoundDecorators` and messages parse again), and returns the same object otherwise, so rendered messages keep their HTML. The app applies decorators: `models/decorated-html.ts` walks marked's tokens for Markdown (never code blocks, HTML, links or images) and splits user messages' plain text into segments, both rendering a `<reins-view-mount data-piece="N">` around each piece's original text, and `InlineViewsController` (`controllers/inline-views-controller.ts`) gives each view mount its piece after the render. Messages still streaming are not decorated, and the stored message, copied Markdown, provider history and compaction input never see decorations. The original text stays until a view mounts, and when none can.
- **`commands.register(command)`** — what a message that starts with `/name` does instead of being sent. A `Command` has a `name` (lowercase letters, digits and hyphens; another name throws, as does a second command of a name), a `description` (its suggestion's line) and `run(context)`. Its `CommandContext` is only `args`, the message after the name, trimmed: a command reads what it acts on from the SDK (`workspace.currentSubject`), not from where it was run, so a command palette can run it from any page. It reads before its first `await`, as by then the user may have gone to another page, and throws when what it needs is not there (`/compact` where no session is shown). The composer (`chat-composer`) recognizes a command with `CommandRegistry.invocation(text)` and runs it with `CommandRegistry.run`: the trimmed message must start with `/name` of a registered command, then whitespace or its end, so `/compacting` and `please /compact` are text, as is a `/name` no command has (skills expand it on the server). There a command wins over a skill of its name; elsewhere in a message a skill works as before. The composer is busy until `run` settles, then clears the text, or shows the rejection's message under it and keeps the text. Attachments in the draft stay. Suggestions (`<slash-suggest>`, `models/slash-suggestions.ts`) list commands, under their own heading and before skills, only when `/` starts the message, and hide the skill of a command's name there. They show every command: a command cannot say beforehand that it cannot run. Commands are frontend only: the server has no command registry, and a command does its work through capabilities (`sessions`).

## The sidebar

[ADR-035](../adr/035-the-sidebar-is-a-stack-of-sections.md) records this design.

- **`sidebar.registerSection({ id, title?, mount })`** adds a part of the sidebar's body and returns its disposer. `id` is lowercase letters, digits and hyphens, one section to an ID (another throws): it is what the user's order and switches remember. `title` is its heading, which the host draws above it and Settings → Sidebar names it by (the ID without one). `mount(target)` draws into an element the host made and returns `{ dispose? }`, a Settings page's lifecycle, in a `<reins-view-mount>` (*The view mount*): mounted while the section is shown, disposed when it is turned off, the sidebar collapses or leaves the page, or the registration is disposed; a throw shows in its place. A section draws only itself and reads what it shows from the SDK (`sessions`, `projects`, `tasks`, `workspace.subscribe`).
- **Height.** Each section is as tall as its content, and the sidebar's body is its one scroller: a section has no scroll area of its own, so a long list makes the sidebar longer, not a box that scrolls inside it.
- **The host owns the frame** (`components/session-sidebar.ts`, `<session-sidebar .app>`): its header (search, Settings, collapse), the collapsed rail and its badge (from `ProjectsStore.activitySummary`, every session's activity, not from any section), the phone's sessions page, and where sections are. A section cannot choose its place, add to the header or the rail, or badge anything.
- **The user owns the order.** `SidebarSections` shows the sections in the user's `order`, then those it does not name in registration order, without those in `hidden`; so the built-ins' order in `BUILT_IN_EXTENSIONS` (Recent, Projects) is the default, and a newly registered section appears at the end, on. The arrangement is the server's `sidebar_sections` setting (`{ order, hidden }`, by ID; `SidebarLayoutStorage` over `GET`/`PUT /api/settings`), loaded on each connect and when Settings → Sidebar is shown. `move(id, by)` and `setVisible(id, visible)` change it at once and store the whole order of the sections registered now, keeping the IDs of sections not registered now after them; a change that cannot be stored is put back and rejects. Settings → Sidebar (`components/settings/sidebar-section.ts`, `<settings-sidebar-section>`) lists `arrangement()` with up and down buttons and a switch for each, and toasts a failed change.
- **The built-in sections** are two extensions that import only the SDK, the app's UI kit and its generic Lit controllers (lint: `reins/features-through-sdk`). Recent sessions (`extensions/recent-sessions/recent-sessions.ts`, one file) is the Recent section, the frontend part of an extension with a backend part, which decides what is recent (server-sdk.md *The Recent sessions extension*): `RecentSessions` holds the rows its `list` method answers (`{ id, name, firstMessage, project, task, updatedAt, activity }`, 8 of them) and asks again, once, 250 ms after sessions, tasks or projects change and on reconnect (a change during a request asks again after it); a row shows its title, "Project · Task" and activity, is marked when it is the one shown, and opens its session with `workspace.open({ view: "session", sessionId }, { in: "main" })`; its menu (`rowActions`) copies the ID, marks it read or unread, renames it (`ui.renameSession`) and archives it, then asks again. `<sidebar-recent>` keys its rows by session, and they spring to their new places (`ui/spring-reorder.ts`). Projects (`extensions/sidebar/projects/`) is the project tree, moved there from `components/` and given SDK values (`Project`, `Task`, `SessionSummary`) instead of stores: `projects-section.ts` (`<sidebar-projects>`: the projects by name, Other sessions, Add project, the task form, task details and project form dialogs, and the tree's events), `project-tree.ts` (`ProjectExpansion`: only the current project expanded, *the expansion rule* in its comment and [features/sidebar.md](../features/sidebar.md)), and `sidebar-project`, `task-list`, `task-list-item`, `session-list-item`, `delegate-popover` and the dialogs, each listening, through a `SubscriptionsController` (`controllers/subscriptions-controller.ts`), for only what it shows: the section for project changes, sessions of no project and the main area; a `sidebar-project` and its `task-list` for session and task changes naming their project. It still uses the app's event factories (`components/events.ts`), `location-dialog` and `activity-dot`.

## Settings pages

- **`settings.register({ mount })`** gives the extension a page of Settings and returns its disposer. An extension has one at a time: a second registration throws until the first is disposed. `mount(target)` draws into an element the host made and returns `{ dispose? }`, the views' lifecycle without `update`: not a view and not a presentation. The extension draws everything on the page under the host's header, its own headings included (MCP draws its server list). `settings.show()` goes to the extension's own page (`#/settings/extensions/<name>`, a new history entry, through the host's `showSettings`), for a view that links to it (MCP's list in a session, *Edit in Settings*).
- **The host owns Settings** (`components/settings/page.ts`): its sidebar, routes and page frame. Each extension with a page is one row (its registration's `label`; on a phone its `description` too), under the nav's *Extensions* heading, after the host's own list of every extension (*All extensions*), by label; the host's general sections (Models, Nodes, Sidebar) come before the heading. Its page (`#/settings/extensions/<name>`) shows a header (label, description) and then what the extension mounts. The route takes any extension name (`[a-z][a-z0-9-]*`); one without a page (not registered, or not yet) shows *No settings for "<name>"*, not an error. The registry is `AppStore.settingsPages`, which the settings page subscribes to, so a page registered or disposed while it is shown appears or goes.
- **Lifecycle.** The page is a `<reins-view-mount>` without a view (*Contribution points*, *The view mount*): it mounts once it is on the screen and disposes when it leaves (another settings page, leaving Settings, or the registration's disposer). The extension loads its own data when mounted (MCP lists its servers). A throw from `mount` is shown in its place (*Failed to load: …*); one from `dispose` is logged. Neither reaches the rest of Settings.
- **The extension's icon** (`ExtensionInfo.icon`, optional, a `mount` with the same lifecycle) is drawn before the row's label in a 14 px `<reins-view-mount>`, clipped so that a failure's message stays in its box. The host's own rows and MCP have none.

## Views over the app's state

The Inspector's Changes tab is the **`diff-file-tree` view**, registered with `views.register` like any view, but by app code: `app-shell` registers it into `app.views` for the app's lifetime (`registerDiffFileTree` in `components/changes/diff-file-tree.ts`, given the registry, an SDK's `workspace` and the app's sessions' diffs, `AppStore.diffs`).

- **Each session's diff is app state, one per session while a view uses it** (`SessionDiffs`, `models/stores/session-diffs.ts`, as `SessionCache` or `ProjectFiles` are). `use(sessionId)` gives the session's `SessionDiff` (`files`, a `DiffStore`; `review`, a `CodeReviewStore`; `source`, `projectId`, `taskId`) and a release; the last release disposes it. An entry scopes its own `DiffStore` and `CodeReviewStore` once the session's details and its task's branch are known (from `SessionCache` and `ProjectsStore`), so it fetches once; it refreshes the diff when the files API says its checkout's files may have changed, and reloads its review on `code_review_updated` and on reconnect. What it shows (branch or uncommitted changes, `DiffStore.diffMode`) is the entry's: the session's, back to branch once the entry is dropped. The tree, the session's Changes and its toolbar use the same entry, so they agree and fetch once; no view shares another view's store.
- **Its only privilege is scope.** App code may use the app's stores; features may not (lint: `reins/features-through-sdk`). The SDK, the registry, the Inspector and the view mount treat it as any view, and nothing refuses or tells apart its name.
- **It follows the main area, as an extension would**: the mount uses the changes of `workspace.currentSubject("session")`, again on each `onDidChange` (releasing the last), none for a view about no session, with a `FileTreeState` (folders closed) for each session. It highlights `currentSubject("file")` when that file is in the session's checkout, so it highlights the file the review is on and any view about one of its files. A file chosen in it opens `{ view: "session-changes", sessionId, file }` in the main area: the view shown by key, so in place. A new view or context changes nothing (its `update` does nothing).
- **The session's views pin it** (`Inspector.pin` in `models/inspector.ts`): each Chat or Changes mount pins the tab, and its dispose releases it, so the tab is there, first and not closable, while a session is shown and closes on a page that is not one. The Inspector knows nothing of it. Pinning is not in the SDK yet: no extension needs it.
- **Not a plugin seam.** Diffs and review are not SDK capabilities, so a feature cannot make this view; one that wants a summary of the session's changes would need a capability designed for it.

The session's **Chat and Changes** are app code too: `registerSessionViews(app.views, app)` (`components/session-views.ts`), which `app-shell` registers for the app's lifetime. Each finds its session from its own view, and neither shares a store with the other or with the workspace. `session` (`#/session/:id`) and `session-changes` (`#/session/:id/changes`, `?file=` for the file it is opened at) are both `tabOf: { type: "session", parameter: "sessionId" }`, keyed by session; their panes pass on `setVisible`.
- **Chat** creates `<session-chat-pane>` (the conversation, `chat-panel`) over its own `ActiveSessionStore` for the view's session (a new one when an update brings another session), refreshed on reconnect (`registerReconciler`), with the session's project loaded for its parent and running children. It gives the session, then its task and project from the session's details.
- **Changes** creates `<session-changes-pane>` (`review-diff-panel`) over its session's diff (`app.diffs.use(view.sessionId)`; an update to another session swaps them). It gives the file its review is on (`active-file-change`, kept in the pane), then the session, its task and its project from the session's details, and calls `context.subjectChanged()` when the file changes. A view with `file`, each time it is opened, reveals it (`ReviewDiffPanel.reveal`, a new object each open).
- **Their shared `toolbar`** is `<session-toolbar>` (the files button and the branch), over the changes of its view's session.

The main area's **new session page** is another: the `new-session` view's `pane`, registered by `app-shell` (`registerNewSessionPage(app.views, app)`, `components/new-session-page.ts`) for the app's lifetime, so it opens from anywhere (`/new`, the sidebar). Its mount creates `<new-session-page>` over `AppStore` and gives it each new view (its pickers replace the URL, which gives a new view); its `key` is the project and task, so opening it again for them is in place, and its `subject` is the task and project chosen on it. Its URL stays its own (`#/new?project=&task=`). It is no tab, so it shows alone.

## Extensions

What the host knows of each frontend extension, which Settings' Extensions section shows beside the backend's report (server-sdk.md *What the host knows of each extension*; [features/extensions.md](../features/extensions.md)).

- **Activation.** `app-shell` activates each extension of `BUILT_IN_EXTENSIONS` that the server's report does not have turned off, through `Extensions` (`extension-system/extensions.ts`, [extension-loading.md](extension-loading.md) *In the browser*), with `AppStore.extensionHost.activate(extension, createReinsSdk(extension, host))`, which calls its register function. A throw is logged and recorded (`status: "failed"`, `error`: its message), and the next extension still loads; what it registered before the throw is removed. The disposer `activate` returns runs the extension's, then removes everything made through its SDK that is still there (registrations and listeners: `createReinsSdk` records each one's disposer, `sdkDisposers(sdk)`), and removes it from the list. A part turned off is disposed so, and is not in the list.
- **Added extensions' frontend parts** are activated the same way by `Extensions`, from the server's report, on each connect and each `extensions_changed`, and disposed and imported again when their files or generation change.
- **Attribution.** Each registration is recorded with the extension whose SDK made it: `createReinsSdk` passes the extension's name to `ViewRegistry.register`, `DecoratorRegistry.registerDecorator`, `CommandRegistry.register` and `SidebarSections.register` (an optional last argument the SDK's own interfaces do not have, so an extension cannot claim another's name), and `SettingsPages` keys pages by extension already. App code that registers into the registries directly (the diff file tree) is no extension's. Each registry answers `registeredBy(extension)` from what is registered now, so a disposed registration is gone from the record.
- **`list()`** gives each activated extension in order, with `registrations`: `views`, `commands` and `sidebarSections` (names), `decorators` (a count) and `settingsPage`. `subscribe` hears an extension activated or gone, and any registration made or disposed in the five registries (a rearranged sidebar too).
- **The section's model** is `ExtensionsStore` (`models/stores/extensions-store.ts`, owned by `SettingsStore`): it loads the backend's report (`api.installedExtensions.list()`, `GET /api/installed-extensions`) and merges it with `Extensions.list()` by name (`extensions`, each an `ExtensionSummary`: the frontend's label, description and icon, else an added one's manifest's, else the app's info on the built-in (`BUILT_IN_EXTENSION_INFO`: every built-in's label and description, those with only a backend part too; a test checks that none is missing), else the name; which `parts` it has running; `enabled`; `disabled` when it is off, else `failed` when either part failed, with `problems` saying why). `setEnabled`, `reload` and `remove` ask the server (`api.installedExtensions`). An extension may have one part. When the report cannot be loaded, the frontend parts are still listed and `backendError` says why. The section shows a card for each, and each card opens Reins' page about the extension, `#/settings/extensions/<name>/details` (frontend-architecture.md *Routing*), not the extension's own page.

## Not built yet

Left out for now (added extensions load, and any extension can be turned off: [extension-loading.md](extension-loading.md)):

- **Theme tokens** — an extension that does not use the app's Tailwind classes cannot match the app's styling: there are no published colors, spacing or type tokens (CSS custom properties) for it. An added extension's views are in the light DOM, where the app's styles reach them, and its own stylesheet is scoped to them ([extension-loading.md](extension-loading.md) *Styles*); but the app's UI kit (icons, dialogs, toasts) is not in the SDK. Planned: [extension-design-tokens-and-ui-kit.md](../plans/extension-design-tokens-and-ui-kit.md) (tokens as CSS custom properties; host-drawn dialogs and toasts as SDK actions; a provided `@reins/ui` library of web components).
- **Settings contributions** — an extension draws its own Settings page, and cannot add to the host's pages (Models, Nodes) or to a page shared by several extensions (a "Connections" page). That would take declared settings: the backend part declares fields with a schema (as bb's `settings.define`), the host stores the values and draws them, in slots that host pages name, so they look and save like their neighbours; a mount only as the escape hatch. Pages made of several contributions would bring parts (a title, an order) back, keyed by the host page's slot rather than by extension. It also serves an extension with simple settings and no frontend part. Design it with a first real case.
- **Namespacing** — view names and decorator identity per extension (`"<plugin>:<name>"`); today names are plain strings, and nothing stops two features from taking the same one but `register` throwing.
- **Versioning** — no compatibility promise; the SDK changes with the app. A manifest's `sdk` range is checked against `packages/sdk`'s version, nothing more.
- **Further capabilities** — opening the file browser is still the `open-in-browser` event, not an SDK call; diffs, review and overlays are not capabilities, a view cannot say that its title changed (the host asks again after the main area renders), and the file viewer does not read `context.container` yet (it offers *Open in file browser* in the main area too), and `sessions` reads no messages and does not observe a session's conversation.
- **Sidebar** — a section has no header actions, badges or collapse of its own, and cannot contribute to the rail; the Projects section has no filter box yet; its dialogs (new task, task details, project form, rename, move) are its own components rather than host actions (`projects.edit(id)` and the like) that any section could ask for. `sidebar_sections` is one arrangement for every browser, not one per device.
- **Commands elsewhere** — commands run only from the composer: there is no command palette, no keyboard shortcut and no argument completion.
