# The Reins SDK

The Reins SDK is the API through which built-in frontend features get everything they use: a source's files, opening views in the workspace, and the contribution points for views and message decorators. A feature gets it as the argument of its register function, `registerFileViewer(reins)`, as a VS Code extension gets its `activate(context)`. It is the "Reins-owned seam" stage of [extension-architecture.md](extension-architecture.md) (*Interface maturity*): an explicit interface with Reins values, used by built-in code. It is not a plugin system yet; see *Not built yet*.

## Where it lives

`packages/frontend/src/reins-sdk/`:

- **`contract.ts`** — the contract, imported as `reins-sdk/contract`: every type a feature may use (`ReinsSdk` and its capabilities, `Source`, `View` with `viewKey`, `ViewRenderer` and its presentations, `MountedView`, `WorkspaceContext`, `InlineContext`, `MessageDecorator`) and a few pure helpers (`sameSource`, `viewKey`). It imports nothing (lint: `reins/sdk-contract-isolation`), so it can become a types package. Its values are Reins values: never Lit templates, marked tokens, HTML, stores, routes or transport types. The DOM values are the element the app gives a view to `mount` into and the `Node` an inline view's `original()` returns (ADR-030): the app gives features elements, and never takes markup or templates from them. Each member's comment states its behavior (lifecycle, ordering, what is synchronous); keep them accurate when the app changes.
- **`sdk.ts`** — `createReinsSdk(app)`, which builds the frozen SDK object over the app's state (`SdkBacking`: `files`, `views`, `decorators`, `open`; `AppStore` in the app). It adds no state of its own.
- **`view-registry.ts`** — `ViewRegistry`, the registered view renderers: `register` (the SDK's `views.register`), `rendererFor(view)` for containers, and `subscribe` (a renderer registered or gone).
- **`decorators.ts`** — `DecoratorRegistry`, the registered message decorators: `registerDecorator` (the SDK's `messages.registerDecorator`), `bind(source)` for messages, and `subscribe`; and `BoundDecorators`, every decorator bound to a source (the context they decorate in, filled in; not a filter), which splits prose, plain text and inline code into plain runs and pieces (`InlinePiece`: a view, its inline presentation and its `InlineContext`).

The registries and the Inspector are app state on `AppStore` (`views`, `decorators`, `inspector`, and `open(view, container)`), next to `files`. The view mount, `<reins-view-mount>` (`ViewMount`, `components/view-mount.ts`), is the app's side of the view lifecycle (*Contribution points*); features only see it as their target.

## Access

[ADR-030](../adr/030-the-reins-sdk-and-how-views-mount.md) records this choice.

- **`app-shell` builds the SDK and gives it to the built-ins.** `app-shell` (`components/app.ts`) builds one with `createReinsSdk(this.appStore)`. In its `connectedCallback` it calls the register functions with it and creates the file browser's `FileBrowserStore` with it; it disposes them when it disconnects. Only `app-shell` holds the SDK object.
- **App code uses the app's state, not the SDK.** `app-workspace` gives the Inspector `app.views` and shows `app.inspector`; `chat-panel` gets `app.decorators` and gives its messages `bind(source)`; `app-workspace` registers the diff file tree into `app.views` (*Views over the app's state*).
- **A feature uses only what it is given.** It imports `reins-sdk/contract` (types and pure helpers) and its own modules, never `reins-sdk`, another path into `reins-sdk/`, `AppStore`, `WorkspaceStore`, `ProjectFiles`, `SessionCache` or another feature's internals (lint: `reins/features-through-sdk`, configured in `.oxlintrc.json` for the feature files and all of `extensions/`). `reins-sdk/contract` is a `tsconfig.json` `paths` alias, which `tsc`, `bun build` and `bun test` resolve.
- **A register function takes the SDK** and returns a disposer. A view is a mount function, not an element; a feature that draws with its own custom element (the file viewer) defines it like any other (`@customElement`), and its mount gives the element what it uses (the file viewer gets `files`).
- **This is a boundary between modules, not a security boundary.** A later external extension is a separate bundle, so it has no path to the app's modules; it still runs in the page.

The built-in features:

| Feature | Register function | Uses |
|---|---|---|
| File viewer (the `file` view's pane, also shown by the file browser) | `registerFileViewer(reins)` in `components/file-viewer/file-viewer.ts` | `files`, `views.register` |
| File references in messages (the `file-reference` view and its decorator) | `registerFileReferences(reins)` in `extensions/message-file-references/message-file-references.ts` | `files`, `views.register`, `messages.registerDecorator`, `workspace.open` |
| Diff file tree (the Inspector's `diff-file-tree` view, the Changes tab): app code over the app's stores, *Views over the app's state* | `registerDiffFileTree(app.views, stores)` in `components/changes/diff-file-tree.ts`, by `app-workspace` while connected | the view registry |
| File browser and file search | none: `app-shell` creates its `FileBrowserStore` (`models/stores/file-browser-store.ts`) with the SDK | `files`, `workspace.open` |

The file browser has no contribution point for overlays: `app-shell` creates its `FileBrowserStore`, mounts it (`<file-browser>`, `<file-search>`) and opens it on the `open-in-browser`, `open-file-browser` and `open-file-search` events. It shows its file in a `<file-viewer>` it renders itself, not through the view registry: both are file code.

**In tests**, `testSdk(options)` (`__tests__/helpers/reins-sdk.ts`) builds an SDK as `app-shell` does, over a files API that knows a source, real registries, and an `open` that records what reaches it (`opened`). Tests give it to register functions and check the registries; nothing is installed, so nothing is cleared after each test.

Bun tests have no DOM, and Lit's DOM shim has no children. `testDom(element)` and `testElement()` (`__tests__/helpers/test-dom.ts`) give an element what mounting a view uses: `childNodes`, `append`, `replaceChildren`, `remove`, `isConnected` (`setConnected` also runs its callbacks) and an `ownerDocument` whose `createElement` makes such elements, a defined custom element as its own class.

## Capabilities

- **`files`** — a source's files (`Files`). It is `ProjectFiles` (`models/stores/project-files.ts`, application lifetime on `AppStore`) itself: the SDK adds no layer. A `Source` is `{ nodeId, path }`; the app works out how to reach it (today the project file routes, through the project of the sessions placed on it) and whether its node is connected, from `SessionCache`, so features never see a project ID or availability. `listing(source)` is synchronous, loads on first ask, and is cached for the two sources asked for last (the viewed session's and the file browser's), so another project's listing is dropped once you leave it. After the change signal or the node coming back, `subscribe` listeners are told and the next ask reloads it: a listing nobody asks for again costs no request. It is empty while the node is offline, and keeps its `data` array when a reload finds the same files. `subscribe` hears any listing change, and a feature that shows a listing asks again on it; `onFilesChanged` says a source's files may have changed (debounced); `read` is uncached; `contentUrl` is null for an unknown source.
- **`workspace.open(view, { in? })`** — shows a view in a container (only `"inspector"` exists): `AppStore.open`. A view with the same `viewKey` that is open is focused and replaced, otherwise it opens after the others. A view about a source names it in its parameters (`file`, `file-reference`), so `open` needs no source, and opening works while no workspace is on screen (settings, History). On a phone the workspace on screen moves to the Inspector page (it listens to `Inspector.onOpen`).

## Contribution points

- **`views.register(name, renderer)`** — how a view name can be shown, by presentation (ADR-030). Each presentation is a mount function: `mount(target, view, context)` draws into `target`, an element the app made, and returns `{ update?(view, context), dispose?() }`. Any framework can do that (React `createRoot`, Svelte and Vue `mount`, Solid `render`); no feature has to define a custom element. Every open sets a new view object, so a view given a new one in `update` shows it afresh (the file viewer reads its file again and reveals its lines); a view without `update` is disposed and mounted again instead. After `dispose` the app empties the target, and it never mounts a target twice without a dispose between. Two presentations exist: **`pane`** (the Inspector's tabs; context `WorkspaceContext`, the viewed session's source), which also gives the tab's `title(view)`, `description(view)` and `icon`, a presentation of its own that draws the tab's icon into a 14 px box the app gives it, in the tab's `currentColor`, with the same lifecycle as a view (the app has no list of icons; the built-ins draw theirs from `ui/icons.ts` with `paneIcon`), and **`inline`** (in place of a piece of message text; context `InlineContext`, *Messages* below). `popover` is meant to be another key later. A container offers a presentation: the Inspector shows `pane`, and a view without one shows there as unavailable. A name has one renderer; registering a second renderer or a renderer without a presentation throws. A view uses the SDK its register function was given (the `file` view's mount gives its file viewer `reins.files`). A view about something fixed names it in its parameters (`file` and `file-reference` carry their `source`); the context is for views that follow the viewed session.
- **The view mount.** One element, `<reins-view-mount>` (`ViewMount`, `components/view-mount.ts`), runs the lifecycle wherever a view is shown: the Inspector renders one per tab with the renderer's `pane`, and messages one per decorated piece. It mounts into itself once it is on the page and has a presentation, a view and a context, updates the view when they change (properties set together apply once), mounts again for a new presentation, and disposes when it leaves the page; a moved element disposes before it mounts again. Its children until it mounts are the fallback (a piece's original text), put back after a dispose.
- **`messages.registerDecorator(decorator)`** — finds pieces of completed message text and names the view shown in place of each, in its `inline` presentation (ADR-030). `decorate(text, context)` returns spans (`start`, `end`, `view`), `decorateCode(code, context)` optionally names the view of a whole inline-code span, and `onChange(listener)` says when what it decorates from changed. Decorators have no lifecycle of their own: the view does. An inline view controls its piece completely: it may draw the text (`context.original()`, a new copy of what the app draws without a view, such as `<code>app.ts</code>`), change it or draw something else; `context.text` is the piece's original text and `context.code` whether it was a whole inline-code span. File references are the `file-reference` view (`{ source, path, startLine?, endLine? }`), whose inline mount draws the original text in a control (`role="button"`) that opens the file with `workspace.open`. A piece has one view: where decorators overlap, the earlier registered wins, and a span whose view has no inline presentation leaves its text alone. Decorating is synchronous, from what the decorator has; the app decorates again after `onChange` or a view registration (`DecoratorRegistry` bumps a generation and tells its subscribers, so `app.decorators.bind(source)` returns a new `BoundDecorators` and messages parse again), and returns the same object otherwise, so rendered messages keep their HTML. The app applies decorators: `models/decorated-html.ts` walks marked's tokens for Markdown (never code blocks, HTML, links or images) and splits user messages' plain text into segments, both rendering a `<reins-view-mount data-piece="N">` around each piece's original text, and `InlineViewsController` (`controllers/inline-views-controller.ts`) gives each view mount its piece after the render. Messages still streaming are not decorated, and the stored message, copied Markdown, provider history and compaction input never see decorations. The original text stays until a view mounts, and when none can.

## Views over the app's state

The Inspector's Changes tab is the **`diff-file-tree` view**, registered with `views.register` like any view, but by app code: `app-workspace` registers it into `app.views` while it is connected (`registerDiffFileTree` in `components/changes/diff-file-tree.ts`, given the registry and its `DiffStore`, `CodeReviewStore` and `FileTreeState`). Its `pane` mount creates a `<diff-file-tree>` over those stores.

- **Its only privilege is scope.** App code may use the app's stores; features may not (lint: `reins/features-through-sdk`). The SDK, the registry, the Inspector and the view mount treat it as any view, and nothing refuses or tells apart its name.
- **It follows the stores itself.** The tree subscribes to the diff, the review and the tree state, so a new view or context changes nothing (its `update` does nothing). The diff review's active file, which the tree highlights, is in `DiffStore` (`activeFile`, `setActiveFile`, cleared when the project changes). A click on a file is still the `file-select` event, which `app-workspace` hears on the Inspector.
- **A new `WorkspaceStore` registers it again**, so the Inspector gets a new `pane` and the view mount mounts the tree again over the new stores.
- **The Inspector keeps the tab first and not closable** (`models/inspector.ts`): that is the container's layout, not the view's.
- **Not a plugin seam.** Diffs and review are not SDK capabilities, so a feature cannot make this view; one that wants a summary of the session's changes would need a capability designed for it.

## Not built yet

Deliberately left out until there are external extensions:

- **Activation** — loading, ordering, failure state and disposal of extensions; today `app-shell` calls the built-in register functions directly.
- **An SDK for each extension** — a loader would call an external extension's register function with an SDK object of its own (its namespace, its disposal), and the extension would keep `reins-sdk/contract` external when it is bundled. Today `app-shell` builds one SDK for the built-ins, and the contract is a `tsconfig` alias.
- **Namespacing** — view names and decorator identity per extension (`"<plugin>:<name>"`); today `ViewParameters` is a closed interface (exported, so a later package can augment it).
- **A types package** — `contract.ts` is ready to move, but is not published.
- **Versioning** — no compatibility promise; the contract changes with the app.
- **A loader** — no discovery, bundles or manifests ([pinned-plugin-apps.md](../plans/pinned-plugin-apps.md)).
- **Further capabilities** — opening the file browser is still the `open-in-browser` event, not an SDK call; diffs, review, sessions and overlays are not capabilities.
