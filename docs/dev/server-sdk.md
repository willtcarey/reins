# The Server SDK

The server SDK is what a backend extension gets from the server: the backend's match of the frontend's Reins SDK ([reins-sdk.md](reins-sdk.md), ADR-030). An extension's register function takes it and returns a disposer. It is the "Reins-owned seam" stage of [extension-architecture.md](extension-architecture.md) (*Interface maturity*): an explicit interface with Reins values, which built-in code uses. It is not a plugin system yet: see *Not built yet*.

An **extension** is code that contributes to Reins only through an SDK. It can have a backend part (this SDK) and a frontend part (the Reins SDK). The MCP servers ([mcp-servers.md](mcp-servers.md)) are the first built-in extension, and automations (triggers that wake sessions, *The automations extension* below) the second.

## Where it lives

```
packages/backend/src/
  sdk/server/index.ts     # @reins/sdk/server: types only
  extensions/             # the host
    host.ts               #   ExtensionHost: the registrations of one app, each with its extension, each extension's SDK object, and its report (`list`)
    services.ts           #   ServiceRunner: one registered service's instances, restarts and state
    sessions.ts           #   ExtensionSessions: reins.sessions of one extension, over the app's sessions
    nodes.ts              #   ExtensionNodes: reins.nodes, over the app's nodes
    built-in.ts           #   BUILT_IN_EXTENSIONS: the one place that imports a built-in extension (its name, migrations and register function)
    tool-docs.ts          #   api.tools.search's answer and the matching (`tools.match`)
    mcp/                  #   the MCP extension (backend part)
    automations/          #   the automations extension (backend only)
  scripting/tools.ts      # api.tools.search / api.tools.call
  routes/extensions.ts    # GET /api/extensions (the host's report), /api/extensions/:extension/:method and /extensions/:extension/*
packages/frontend/src/extensions/mcp/   # the MCP extension (frontend part)
```

- **An extension's module** gives a `ServerExtension`: `{ migrations?, register }` (MCP: `mcp` in `extensions/mcp/index.ts`). `built-in.ts` adds its name (`ExtensionRegistration`).
- **`@reins/sdk/server`** (`sdk/server/index.ts`) is a `tsconfig.json` `paths` alias, in the backend and in each package that typechecks backend sources (frontend, client, CLI). It is types only. It imports only its own modules and the type of `bun:sqlite`'s `Database`, which its own `Database` interface extends (lint: `reins/server-sdk-isolation`). Each member's comment states its behavior (lifecycle, order, errors): keep them accurate when the host changes.
- **The boundary** (lint: `reins/backend-extension-boundary`): a backend extension (`extensions/<name>/`) imports only `@reins/sdk/server`, its own modules and npm packages. Nothing outside it imports it, except `extensions/built-in.ts` (its registration) and its frontend part (frontend `extensions/<name>/`, for its types). Tests are not checked. It does not import `bun:sqlite`, not even types: it uses the database it is given, typed by the SDK's `Database`, and opens none itself. When an extension needs something that the SDK does not give, add it to the SDK: do not make an exception.
- **This is a boundary between modules, not a security boundary.** An extension runs in the server process.

## Lifecycle

- **`createAppState`** (`state.ts`) builds the app's `ExtensionHost` (`AppState.extensions`), giving it the app (`() => state`, read when an extension registers, as the node hub reads it), and registers each extension of `BUILT_IN_EXTENSIONS`, in order. For each, the host first gets its directory and database from the process (`ServerProcess.extensionData`, *Data and database*) and applies its pending migrations, then calls its register function with an SDK object of its own (`ServerSdk`: its `name`, `dataDir` and `db`, and what it registers is recorded as its). Tests give `createAppState` their own list (`extensions`) and a handler for failures (`onExtensionError`; by default they are logged).
- **A failed migration** (or a database that cannot be opened) is reported as the extension's error, and the extension does not register in that app; Reins and the other extensions go on. The failed migration is rolled back, those before it stay applied, and the next app (a reload, a restart) tries it again.
- **The app's `stop`** (`server.ts`) awaits `extensions.dispose()`: first every extension's services are stopped, all at once (*Services*), then each extension's disposer, the last registered first, then the removal of all it registered, also what its disposer forgot. A disposer can return a promise (MCP closes its connections).
- **A hot reload** builds a new app, so each extension is registered again on its new code, its new migrations applied first. The old app's `stop` has stopped its services before the new app starts them again. What must outlive an app is in its database or directory.
- **Server shutdown** (SIGTERM, SIGINT, a restart of the server alone) suspends the runs, then awaits the app's `stop` (at most 10 s, `exitProcess` in `server-process.ts`), so the services stop and the extensions are disposed before the process exits.
- **Removal:** Reins never deletes an extension's directory (nor its database). An extension no longer registered leaves them as they are.
- **A register function that throws** is reported, and what it registered before the throw is removed. The other extensions still register.
- **Each registration returns its own disposer** (`Disposer`), as in the frontend.

## What an extension contributes

- **Tools** (`tools.register(provider)`). An extension has one `ToolProvider` at a time (registering a second while it has one throws). A provider has a `title`, `search(query, { filters, signal }) → Tool[]` and `call(localId, args, { signal, timeoutMs }) → ToolResult`, which throws for an ID that is none of its tools. A `Tool` is `{ id, name, title?, description?, inputSchema, outputSchema?, annotations? }`, with JSON Schema. `tools.match(query, tools)` ranks as the core does (*Agents and `api.tools`*).
  - **A provider gives local IDs; agents see final IDs.** The final ID is `<extension>__<local ID>`: the host adds the extension's name and `__` to each tool a search finds (`ExtensionHost.searchTools`), and `api.tools.search` documents the final IDs. A local ID is `[a-zA-Z0-9_-]+`, at most `tools.maxLocalIdLength` characters (64 less the prefix), so that a final ID can also be a model's tool name later. It must be unique among the extension's tools and stable: a duplicate is the extension's error. A tool whose ID breaks these rules is left out of the search's answer and reported as the extension's error (logged): the host never changes an ID.
  - **Why the host prefixes IDs.** In Reins, tools are found on demand: there is no registry of tools, unlike bb and Pi, which register tools before a call. The prefix lets the host route a call without a map, also for an ID from before a reload or from an earlier run, and it makes collisions between extensions impossible. Extension names have no `_`, so the first `__` always splits an ID correctly.
  - **The core asks the providers at each search and each call.** A search asks all of them at the same time. A provider that throws is shown in its place, and the others still answer. A query that starts with an extension's prefix reaches that extension without it (an agent that searches for a final ID it has). A call splits its ID at the first `__` and gives the local ID to that extension's provider. An ID without `__`, of no extension or of one without a provider, or whose local ID is not `[a-zA-Z0-9_-]+`, is `UnknownToolError`: no provider is asked.
- **System prompt sections** (`prompt.register(contribution)`). A contribution gets a `PromptContext` (`session` `{ id, projectId, taskId }`, `projectId` null for a session of no project, its `task`, and the `tools` the model is offered, null for every tool) and returns text or null, possibly async. The core asks when a session's runtime opens (`SessionModel.context`, through `App.promptSections` of the current app). Only the Reins agent kind gets the sections: they follow the whole Reins section (task included), in the order of registration. A throw is reported, and the session opens without that section.
- **Scripting functions** (`scripting.register({ functions, types? })`): an extension's own `api.<namespace>` in `execute`, documented by `search`. A `ScriptFunction` is the core's `defineFunction` shape with JSON Schema (`parameters` must be an object schema; its properties are the positional arguments). `execute` gets the params and a `ScriptContext` (`sessionId`, `projectId` (null for a session of no project), `taskId`, `signal`). `types` are named schemas that `search` shows by name. A registration's functions share one namespace, which must not be a core namespace or another registration's (that throws). `scriptingApi(extensions)` (`scripting/api-registry.ts`) gives the core's functions and types plus the extensions'. `runScript` and `search` use it.
- **HTTP** (`reins.http`). **`http.handle(api, handlers)`**: the extension's API, a contract (`HttpApi`) of methods by name (`[a-zA-Z][a-zA-Z0-9_]*`), each with an optional `input` and `output` schema, and a handler for each. A method is `POST /api/extensions/<name>/<method>` with its input as the JSON body: the host checks it against `input` (400 `{ error: "Invalid input: <path>: <message>" }`, and the handler is not called), calls the handler with `{ input, signal, origin }` (`origin`: the origin the browser used, from `X-Forwarded-*`, for callback URLs), and answers its return value as JSON, or 204 for a method without `output`. A thrown Error with a numeric `status` (400–599) is answered with it and `{ error }` (MCP's `RouteError`); any other throw is logged and answered 500 with its message, as for core routes. A method name the extension already handles throws; a method no extension handles, or a request that is not POST, is a JSON 404. `input` must be a TypeBox schema for now, as the host checks it with TypeBox's `Value` (another JSON Schema is refused at registration). The schemas' `static` types type the handlers (`HttpHandlers`) and the frontend's `reins.http.call` (reins-sdk.md *Capabilities*): keep the contract in a module of schemas only (MCP's `api.ts`, `mcpApi`), whose type the frontend part imports. A view type that a schema cannot say exactly keeps its TypeScript type with `Type.Unsafe<T>(schema)`. **`http.page(path, handler)`**: a page the browser goes to itself (an OAuth callback), `GET /extensions/<name><path>` (a URL pattern), whose handler gets a `PageRequest` (`req`, `url`, decoded `params`, `origin`) and returns any `Response`; a path no page matches is a text 404. **`http.pagePath(path)`**: a page's path from the root, to build its URL. `routes/extensions.ts` asks the app's host at each request. `@reins/client` calls the methods with `client.extension(name).call(method, input?)`.

- **Services** (`services.register({ name, start })`): the extension's long-running work, in the host's lifecycle (*Services*).
- **Sessions** (`reins.sessions`): starting sessions, messaging them, reading them and hearing when the runs of those it started end (*Sessions*).
- **Nodes** (`reins.nodes`): running a command on a node (*Nodes*).

## Sessions

`reins.sessions` (`Sessions` in the SDK; `ExtensionSessions` in `extensions/sessions.ts`, which the host builds for each extension in `sdkFor` and gives it as it is (its state in `#` fields; the host gives it the way to add a settlement listener, as it keeps them), an adapter over the server's `createSession`, `Sessions.submit`, `Sessions.compact` and `Sessions.getContext`, as scripting's `api.sessions` is) lets an extension work through sessions: an automation that wakes a session up, or starts a hidden session of its own in a directory that is no project's. The extension acts as no session, so it names where a session works.

- **`get(sessionId)`** → `SessionInfo`: `id`, `source` (`{ id, nodeId, path }`), `projectId` and `taskId` (null for none), `parentSessionId`, `name`, `background`, `running` (its run is in progress now, `sessionActivity`), `startedBy` (the extension that started it, or null), `archivedAt` (null when not archived), `lastRunId` (the latest ended run's ID, `settlement_json.operationId`, null before the first: a new one after a `send` means the run that took the message ended, as Pi handles accepted steering before a run's end), `createdAt`, `updatedAt`. Any session, not only the extension's. Rejects for an unknown one ("Session not found: <id>").
- **`start({ source?, projectId?, taskId?, prompt, model?, background?, title? })`** → its ID, once Pi admitted the prompt (not when the run ends). `source` is a source ID or `{ nodeId, path }` (`ensureSource`: a directory no session used yet is checked on its node); without it, a project's session inherits as `createSession` does (its task's latest session's source, else the project's default source). With neither a source nor a project it refuses: a session of no project names where it works ([ADR-034](../adr/034-sources-without-projects.md)). `background: true` makes a session the browser never shows (backend-architecture.md *Tools*). It checks a blank prompt, then creates the session as every client does (`Sessions.create`, the same checks and messages as HTTP and scripts): refusals keep nothing (no source or project, an unknown project, task (or one of another project), source or node, a path that is not a directory there, and an offline node for a new one, a model the catalog does not have, a blank title). A first prompt the session refuses (its node was removed) rejects `start`, and the session stays, to be prompted again with `send` or moved.
- **`send(sessionId, message)`** → resolves once admitted. It steers, as `api.sessions.send` does: a running session takes the message into its work, an idle one starts a run with it (session-runtime.md *Submission and ordering*). It does not look at whether the session is busy: the extension decides that, with `get`. Any session. Rejects for an unknown session, a blank message and what submission refuses (a removed node).
- **`compact(sessionId, { instructions? })`** → resolves once the compaction started (`Sessions.compact`, session-runtime.md *Manual compaction*: in the session's order, its runtime opened if needed), not when it ends: the session reads `running` until then. Any session. Rejects for an unknown session ("Session not found: <id>"), a running one and one with nothing to compact (`CompactionRefusedError`'s messages). Pi already compacts near the context limit: this is for an extension's own lower limit (an automation's `compactAboveTokens`).
- **`contextUsage(sessionId)`** → `{ usedTokens, contextWindow, measurement: "exact" | "estimated" }` or null: the session's context occupancy, as the browser's context meter reads it (`Sessions.getContext`, session-runtime.md *Events*, "Context occupancy"), null without a known model. Rejects for an unknown session. The smallest read the automations extension needed to decide whether to compact; it gives neither the compaction threshold nor the usage's history.
- **Content** (`MessageContent`, `send`'s message and `SessionStart.prompt`): a string, or blocks in order, each a string (visible) or `{ text, hidden?, label? }`. Every block is a text block of the input, and the model gets them all, the hidden ones a blank line after the visible ones (`providerInput` in `pi-runtime.ts`: a provider can join text blocks with nothing between them), with nothing else (not the label, nor that the user sees them collapsed). Reins marks where the hidden blocks begin in the input's metadata (`metadata.details: { label, start }`; `SessionSubmission.details`). The chat shows the visible blocks in the bubble and the hidden ones collapsed under it, opened from the origin label ("sent from <extension>", else "Details"), with the label at their top (`UserMessage.visibleContent` and `details` in the frontend's `models/message.ts`). The session list's first message is the first block (`content[0]`). Refused: hidden blocks before a visible one, no visible block, a blank block, a label on another block than the first hidden one, or one that is blank or over 80 characters. An extension says in the hidden blocks what the model needs to know about them (automations: that a command's output is not the user's words).
- **Metadata** (`MessageMetadata`, on `send`'s options and `SessionStart.metadata`): the extension's own data on a message, any plain JSON object of at most 64 KiB, kept in the input's `metadata` (`SessionSubmission.metadata`) and not given to the model. Refused: Reins' keys (`sourceExtension`, `sourceSessionId`, `details`), and anything that is not plain JSON (a `Date`, a class instance), naming where. Nothing reads an extension's keys yet: they are there for its own parts later (a frontend decorator, a reader of the transcript).
- **Attribution.** A session an extension starts records it (`sessions.source_extension`, migration 063; `SessionView.sourceExtension`, scripting's `source_extension`), and every input it submits carries `metadata.sourceExtension: <name>` beside the existing `metadata.sourceSessionId`. The chat shows "sent from <name>" under a user message with it, and the session list's subtitle "from <name>". Unlike a session update (`sourceSessionId`), the content reaches the model as it is, like a user's: the extension is trusted code of the server, configured by the user.
- **`onSettled(listener)`** → `Disposer`. Each time a run of **a session this extension started** ends, once its end is recorded (`runSettled` in `sessions/session-runs.ts`, after the row and the broadcast), the listener gets `{ sessionId, status: "completed" | "failed" | "cancelled", result, error }`: `result` is the final reply's text on the run's branch (`finalReply`, null without one) for a completed run, `error` why a run failed or was cancelled. Only the extension's own sessions, so an automation records its runs' results without holding a promise across reloads. A runtime applies its run's end with no app, then tells the current app (`App.sessionSettled`, optional, through `ExtensionHost.sessionSettled`): a run that ends during a reload's gap (no app) is not told, nor one a process exit cut off before its end was applied (session-runtime.md *Recovery*); the extension reads what it missed with `get`. A listener that throws or rejects is the extension's error (logged, kept in its report). The host counts each extension's listeners (`registrations.settlementListeners`).

## Nodes

`reins.nodes` (`Nodes` in the SDK; `ExtensionNodes` in `extensions/nodes.ts`, an adapter over the `Nodes` model and its `NodeHost`, as scripting's `api.nodes.run` is) lets an extension run a command on a node: a check that a service runs on a schedule, for example.

- **`run(node, command, { cwd?, timeoutMs?, signal? })`** → `{ exitCode, output, truncated }` (`CommandResult`): bash on the node, as the node's user, with nothing confined (as a session's commands are). `node` is an ID (stable: keep this one) or a name (any case); an extension has no session, so there is no `"current"`. `cwd` is absolute, `~/…` or relative to the node's home (the default). `output` is stdout and stderr together, at most the first 16 MiB (`MAX_SCRIPT_BYTES`: it is held in the server's memory), `truncated` when there was more.
- **A failing command resolves** with its exit code. `run` **rejects** for a blank command, a `timeoutMs` outside 1 to 600 000 (10 min; 30 s by default; longer than a script's 30 s, as no agent waits for it), an unknown or removed node ("Node not found: <node> (the nodes: …)"), one that is not connected now ("Node unavailable: …": it does not wait for the node), the timeout ("Command timed out after <ms> ms on …") and the signal (an `AbortError`). Give a service's `signal`, so that a reload or a shutdown kills the command.

## The automations extension

The second built-in (`extensions/automations/`, backend only; user doc [features/automations.md](../features/automations.md)). It shows the SDK's sessions, nodes, services, database and HTTP together: no core code knows it.

- **A trigger, a target and a message.** An automation is a row (`automations`, migration `001_automations`) made by `api.automations.create` or `POST …/create`. Its trigger is a schedule (`trigger = 'schedule'`) or a command checked at an interval (`'command'`: `command`, `node`, `cwd`, `timeout_ms`; the interval is `schedule`). Its target is a session it messages (`target = 'session'`: from a script, the calling session, `ScriptContext.sessionId`), a hidden session of its own (`'own'`: `sessions.start` with `background: true` at its first delivery, in the calling session's source by default with no project, then `send`), or a new session at each delivery (`'new'`: `sessions.start`, shown in the browser unless `background`, its ID only in its run). A `'new'` delivery is skipped while a session an earlier one started still runs (`previousEnded`), for a schedule and a command alike, so the next check does not hand out what it still works on. `once` cancels it after its first delivery.
- **Every delivery is a `send`** (*Attribution*): a running session takes it into its run. The message is sent as it was given; what the model needs beside it goes in a hidden block (`automationDetails`): which automation sent it and when (not its trigger: the session it messages most likely made it), how to cancel it, and a command's output in a fence marked untrusted (`untrustedOutput`, at most 16 000 characters), as the extension's messages reach the model as a user's do and the output can carry other people's text.
- **A schedule is skipped only while the run its previous message started still runs.** After each send the extension stores the session's `lastRunId` (`last_send_*`). At the next due time it skips when the session is `running` and its `lastRunId` has not changed: no run has ended since that message was admitted, so the run that took it is still going. Work of anyone else in progress gets the message. A command's firing is never skipped.
- **The scheduler** is one service (`scheduler`) whose loop ticks at once and then every 30 s (the *Services* pattern), with the service's signal. Each tick reads the active rows from the database, so a reload or restart loses nothing; and as the next time is computed from the tick that ran it, a delivery missed while Reins was down happens once, at the first tick. A due automation's `next_run_at` is moved before anything is sent or run, so a failure does not repeat at each tick. A command check runs outside the serial chain (`Automations.checking`: one per automation at a time), so a slow command holds up no other automation; its result is applied in the chain. A target session that `get` finds archived (`archivedAt`) or not found cancels the automation; an own session that is gone is replaced at the next delivery.
- **Run history** (`automation_runs`, the latest 200 of each): `sent`, `skipped` or `failed` (the send was refused, or the check could not run) for a target session, whose runs the extension does not hear (it did not start that session); `running`, then `completed`, `failed` or `cancelled` from `onSettled` with the final reply as `output`, for an own session (messages that joined one run share its end). A run still `running` at a later delivery while its session is idle is `lost` (its end came during a reload's gap). A command's firing records its `exit_code` and `check_output`; checks that did not fire are only counted (`checks`, `last_check_at`). Ticks, check results and settlements are handled one at a time (`Automations.serial`), so a settlement always finds the run its `start` recorded.
- **Compaction:** after a completed run, an own session with `compact_above_tokens` reads `contextUsage`; above the threshold the run is marked `compaction = 'pending'`, and the next tick that finds the session idle calls `compact` (with `COMPACTION_INSTRUCTIONS`). Not in the settlement listener itself: the runtime is still busy applying the run's end there, and `compact` refuses a busy session.
- **A message is optional for a command trigger** (`message` null): its output is then the visible message (`messageOf`; "`<command>` succeeded." for none), and the details say it is a command's output, not the user's words. A schedule needs one.
- **The prompt section** (`prompt.ts`, `reins.prompt`, for agents offered `execute`): when to make an automation ("tell me when this deploys") and end the turn rather than wait or poll, which trigger to use, and to run a command that ends within a few minutes itself.
- **Schedules** (`schedule.ts`): intervals (`5m`, `every 1h30m`, at least 1 minute) are parsed by the extension; `daily HH:MM`, `weekdays HH:MM` and five-field cron expressions go to [croner](https://github.com/hexagon/croner) (no dependencies, IANA timezones, local times kept across offset changes). The timezone is checked with `Intl`.
- **Surfaces:** `api.automations.create`, `cancel`, `list`, `runs`, `replaceSession` (`scripting.ts`) and the same as HTTP methods (`api.ts`, `routes.ts`: `create` takes `target: { session } | { own: { source, … } }` and a command's `node`, as there is no calling session; `cancel` records "Cancelled by the user"). No frontend part yet.
- **Tests:** `__tests__/extensions/automations/` on the fake model, a loopback node and a fake clock (`helpers/automations-extension.ts`: `startAutomations(reins, { now, pollMs })`, its scheduler ticking once at start and then when the test calls `tick`; `idle` waits for the checks a tick started).

## Services

A service is long-running work of an extension (a timer, polling, a queue) that the host starts and stops, so that no extension keeps its own `setInterval` across reloads. `reins.services.register({ name, start })` returns a `Disposer`. The host gives nothing specific to scheduling: the service does what it likes in `start`.

- **`start(context)`** gets `{ signal, logger, fail }` and returns, or resolves to, `{ stop?() }` (or nothing). `logger` is the server's log, each line prefixed `[<extension>:<service>]`. `signal` aborts when the host stops the instance, before it calls `stop`.
- **Names** are lowercase letters, digits and hyphens, unique among the extension's services (a second registration of a name throws). There is never more than one instance of a service in the server process: the host starts the next instance only after the last one stopped (except after a stop that did not end, below).
- **When it starts:** after the extension registered (its storage opened, its migrations applied, its register function returned). A service registered later starts at once. A failed extension (storage, migration or register stage) starts none: what it registered is removed.
- **When it stops:** the host aborts `signal`, waits for a `start` still in progress, then calls `stop`: when its registration is disposed, when the extension is disposed (the app's `stop`: a dev reload, a shutdown) and after a crash. Its services stop before the extension's disposer runs, as they may use what it closes. **The wait is bounded: 5 s** (`STOP_TIMEOUT_MS` in `services.ts`), then the host reports `Service <name> did not stop within 5 s` as the extension's error and goes on, so a stuck service cannot hold up a reload or a shutdown. After a reload the new app starts it again on its new code. A `stop` that throws is reported.
- **A crash** is a `start` that throws or rejects, or `context.fail(error)` after `start` returned (a loop that cannot go on). The host reports it as the extension's error (`Service <name> crashed: …`), stops the instance as above and starts a new one after a backoff: 1 s, doubling, at most 5 min, and back to 1 s when the crashed instance had run for a minute (`healthy`). Only an instance's first `fail` counts; a `fail` after it was stopped is nothing. A crashed instance whose stop did not end in time leaves the service `failed`: the host starts no other in that app, as the old one may still run. A promise the service leaves rejected without `fail` is not seen by the host.
- **Status:** the host records each service's state (`ServiceView` in `services.ts`): `starting`, `running`, `restarting` (with `nextAttemptAt`), `stopped` (the host stopped it) or `failed` (above), with `since` (when it entered that state), `restarts` (how many times the host started it again after a crash) and `lastError` (`{ message, at }`). The host's report gives it (`ExtensionView.services`, *What the host knows*). It goes with the app, as the extension's errors do: a reload starts the count again.
- **End everything with the signal.** The host has no timers of its own to give: a service passes `signal` to each thing that waits or listens, so the abort ends them all and it needs no `stop`. A `setInterval` it clears itself is the leak to avoid: a forgotten `clearInterval` keeps the old code's timer running after each reload, beside the new one, and the host cannot see it. For polling, a loop that waits between ticks:

  ```ts
  import { setTimeout as sleep } from "timers/promises";

  reins.services.register({
    name: "poll",
    start: ({ signal, fail }) => {
      void (async () => {
        while (!signal.aborted) {
          await poll(signal);
          await sleep(5_000, undefined, { signal });
        }
      })().catch(fail);
    },
  });
  ```

  A slow `poll` delays the next one and never overlaps it. A throw from `poll` reaches `fail`: a crash, restarted with backoff. The `AbortError` at the stop reaches `fail` too, but the host ignores a `fail` after it aborted the signal. Not `for await` over `timers/promises`' `setInterval`: it does not overlap either, but after a slow tick it runs the ticks it missed one after another. `fetch(url, { signal })`, `addEventListener(type, listener, { signal })` and `Bun.spawn({ signal })` end the same way. Keep `stop` for what takes no signal (a connection to close).
- **Later:** a child process (`{ command, args, node? }`) as another kind of service, under the same lifecycle and status. A service is a definition the host runs (`ServiceRunner`), so another kind is another way to start and stop an instance.

## What the SDK gives an extension

- **`dataDir`** and **`db`**: the extension's own directory and database (*Data and database*). No extension has access to the main database.
- **`migrations`** (on the `ServerExtension`, not the SDK object): its database's schema, applied by the host (*Data and database*).
- **`secrets`**: the extension's secret storage (*Secrets*).
- **`broadcast(message)`**: to every browser, as `{ type: "extension", extension: <name>, message }` (`ServerMessage`'s `extension` member; the frontend's `InboundMessage` has it too). The extension's frontend part tells its messages apart.
- **`logger`**: the server's log.

## Data and database

- **A directory for each extension:** `<data dir>/extensions/<name>/` (`resolveDataDir()`: `REINS_DATA_DIR`, else `.reins/` under the working directory), absolute, as `reins.dataDir`. The extension writes its files only there.
- **A SQLite database for each extension:** `db.sqlite` in its directory, as `reins.db`, opened as the main database is (`openDatabase` in `database.ts`: WAL, foreign keys). A separate file, not prefixed tables in the main database: an extension cannot read or break the core's tables or another extension's, and its data can be moved, backed up or reset alone (ADR-032).
- **The process owns them** (`openExtensionData` in `database.ts`, `ServerProcess.extensionData`, process-owned): the directory is created and the database opened at the extension's first registration, and kept for the life of the process, so every app (each dev reload) gets the same connection, as with the main database. Neither the host nor the extension closes it.
- **Migrations:** `ServerExtension.migrations`, `[{ id, up(db) }]`, oldest first. Before each registration the host applies, in order, those not recorded in the extension's database (its table `reins_migrations`: `id`, `applied_at`), each with its record in one transaction. IDs must be unique non-empty strings (else the extension does not load). `up` is synchronous. Never change a migration that has shipped: add one.
- **The guard:** `reins.db` is the extension's only database (its secrets are in the host's store, *Secrets*) (the host test checks that it is not the main one), and lint keeps an extension from importing `bun:sqlite`, so it cannot open one itself.
- **The type:** an extension names its database `Database` from `@reins/sdk/server`. Today it is an interface that extends `bun:sqlite`'s `Database` and adds nothing, so the extension must run in the Bun server process and use Bun's API (`query`, `exec`, `transaction`). As no extension imports Bun's type, Reins can give the interface its own members later.
- **MCP** keeps its servers in its database (its `001_servers`); core migration `060` copied the rows the main database had there and dropped them ([mcp-servers.md](mcp-servers.md) *Modules*). Its secrets are in the host's store; its `002_host_secrets` dropped its own secrets table (ADR-033).

## Secrets

`reins.secrets` (`SecretStorage`) is a store that the host owns and scopes to each extension, as VS Code's `SecretStorage` is (ADR-033):

- **`get(key)`** (the value, or undefined), **`set(key, value)`**, **`delete(key)`** (nothing for a key it does not have) and **`keys(prefix?)`** (the keys in order, those that start with `prefix`; the prefix is matched as characters, not as a `LIKE` pattern). A key is a string of 1 to 256 characters that the extension chooses; another key, or a value that is not a string, rejects. The extension names its values (MCP: `servers/<id>/<kind>`) and finds a record's values with `keys(prefix)`.
- **Scoped:** an extension sees only its own keys. Two extensions can use the same key.
- **Where:** the main database's table `extension_secrets` (`extension`, `key`, `value`, `updated_at`; core migration `061`), through `extension-secrets-store.ts`. Each value is encrypted with the server's key (AES-256-GCM, `crypto.ts`), the one the core keeps its provider credentials with. The extension never handles ciphertext. `get` rejects for a value the host cannot decrypt (the key changed). Values stay when the extension is no longer registered, as its directory does.
- **Async:** every method returns a promise, though the implementation is synchronous SQLite today, so that a keychain could hold the values later without a change to the contract.
- **Not in the extension's transactions:** a secret's write and a write to `reins.db` cannot be one transaction. The extension orders them so that a half-done change does no harm: MCP deletes a server's secrets before its row, and deletes a server again when its secret cannot be stored at creation.
- **The host** builds each extension's store (`secretStorage(name)` in `host.ts`) and checks keys there.

## What the host knows of each extension

The host records every registration with the extension whose SDK made it (each list it keeps has the extension's name: providers, prompt contributions, scripting registrations, HTTP methods, pages), and keeps a record of each extension of the app: its migrations, its storage once opened, what stopped it and its later errors. **`ExtensionHost.list()`** reports them, in the order of registration, as `ExtensionView`s:

- **`status`**: `loaded`, or `failed` with **`failure`** `{ stage, message }`: `storage` (its directory or database could not be opened), `migration` or `register` (its register function threw). A failed extension has registered nothing. A later on/off switch would add `disabled`. Services have their own status (`services`, below), which does not change the extension's.
- **`errors`**: what the extension reported after it loaded (a tool ID left out of a search, a prompt contribution that threw), `{ message, at }`, the latest last, at most 10. `onError` still gets each one. Errors from disposal are not kept: the record goes with the app.
- **`registrations`**: what it has registered now, read from the host's lists, so a disposed registration (its own disposer, or the app's `stop`) is gone: `tools` (its provider's `title`, or null; no tool count, which would ask the provider and could go to the network), `promptSections` (how many), `settlementListeners` (how many `reins.sessions.onSettled` listeners), `scriptFunctions` (names), `httpMethods` (names) and `pages` (paths from the root).
- **`services`**: its services now, in the order of registration, each a `ServiceView` (*Services*): a disposed one is gone.
- **`storage`** (null when it could not be opened): `dataDir`, `databaseBytes` (`db.sqlite` and its WAL file), `migrations` (`applied`, `{ id, appliedAt }` from `reins_migrations` in order, and `pending`: the declared ones not applied, such as a failed one and those after it) and `secrets` (how many it keeps: neither keys, which can name the user's things, nor values).

**`GET /api/extensions`** (`routes/extensions.ts`) answers `list()` of the current app. It is the host's route, not under an extension's prefix (an extension's methods are `/api/extensions/<name>/<method>`, one segment deeper, so they cannot clash). `@reins/client` calls it with `client.extensions.list()`. Settings' Extensions section shows it, merged with the frontend parts ([reins-sdk.md](reins-sdk.md) *Extensions*, [features/extensions.md](../features/extensions.md)).

## Agents and `api.tools`

- **`api.tools.search(query, filters?)`** (`scripting/tools.ts`) returns documentation: each provider's matching tools as a TypeScript interface keyed by final ID (`toolSearchDocs`, `extensions/tool-docs.ts`), grouped by provider in the order of registration, with a `ToolResult` declaration. In each provider, the first 10 are documented and the others named. Without a query, a provider with more than 10 tools only names them. A provider's error is shown in its place. Results of different providers are not ranked against each other.
- **Matching** (`matchTools`, also `tools.match`): each word of the query is a substring of the ID and name (weight 10), title (5), argument names (3) or description (1). The tools that match every word, else, for several words, those that match the most. A plural word also matches its singular. A query that is a tool's ID or name (any case) puts that tool first. With the host's removal of the prefix, a query that is a tool's final ID, its local ID or its name (`mcp__vercel__list_deployments`, `vercel__list_deployments`, `list_deployments`) finds it first. An empty query keeps all.
- **Filters** are a plain object that the core gives to every provider without change (`{}` when none is given). Each provider decides what its keys mean, and what it does with keys it does not know. A provider tells agents its filters in its prompt section.
- **`api.tools.call(id, args?, timeoutMs?)`** takes the final ID and returns the `ToolResult` (a failure the tool reports is a result with `isError`), with the script's signal.
- **`search` lists API functions only** (the `api.tools` functions among them). It never lists the tools and never waits for an extension.

## Tests

`__tests__/extensions/host.test.ts` tests the host through a test extension (`helpers/test-extension.ts`: a provider of fixed tools that records its searches and calls) and `createAppState({ extensions })`: tool searches and calls through `execute`, scripting functions and `search`, HTTP methods (input checks, outputs, statuses) and pages, prompt sections, the extension's directory and database (not the main one), its migrations (once each, in order; a failing one rolled back and only its extension left out), broadcast, secrets (by key, scoped to the extension, encrypted in the main database, kept across apps), the report (`GET /api/extensions`: a loaded extension's registrations and storage, a failed migration or register function, secrets only counted, a disposed registration gone, later errors kept), and the lifecycle. `__tests__/extensions/sessions.test.ts` tests `reins.sessions` on the fake model with a loopback node: a background session started on a location of no project (its prompt attributed, `onSettled` told its final reply), sends from two extensions to a running and an idle session (attributed to each; only the starting extension told, a failed run told as failed), the refusals (nothing kept; a session whose first prompt is refused kept), unknown sessions, `compact` and `contextUsage`, and the listener count in the report. Tests get each extension's data in a temporary directory of their own (`testExtensionData`, `extensionDb(name)` in `helpers/test-db.ts`), removed after the test. `__tests__/extensions/nodes.test.ts` tests `reins.nodes.run` with a loopback node: by ID and name, `cwd`, the exit code and output, the signal, and the refusals (the node host's output limits and home are tested through scripting, `__tests__/scripting/nodes.test.ts`). `__tests__/extensions/services.test.ts` tests services through `createAppState` and `GET /api/extensions`, with Bun's fake timers for the backoff and the stop timeout: a service starts once after registration, a loop on the signal (the pattern above) ends at the stop with no crash reported, stops on its disposer and on the host's reload path (one app's `extensions.dispose()`, then the next app), a stop that hangs is given up after 5 s, a crash restarts with backoff (reset after a healthy minute), a crash whose stop hangs is `failed`, and a failed extension starts none. `__tests__/extensions/tool-docs.test.ts` tests the documentation and the matching. MCP's own tests are in `__tests__/extensions/mcp/` ([mcp-servers.md](mcp-servers.md) *Tests*).

## Not built yet

See [backend-extensions.md](../plans/completed/backend-extensions.md) *Not in this plan*: a loader (discovery, packages, manifests, building an extension while the server runs), direct model tools, permissions, trust and sandboxing, versioning, and dependencies between extensions. Settings that an extension declares with a schema, which the host stores and draws (as bb's `settings.define`), possibly on the host's own pages, are a possible later addition; today an extension's frontend part draws its own Settings page ([reins-sdk.md](reins-sdk.md) *Settings pages*, *Not built yet*). A known gap: `reins.db` is `bun:sqlite`'s `Database` (behind the SDK's `Database` interface, which extends it), which an extension outside the server process could not use; the SDK's `Database` would get Reins-owned members, not Bun's, with the loader. Neither does the host check, when a migration was removed or changed, that the database's record still matches the list.

**Direct model tools and their names.** When tools are given to the model directly (not through `api.tools`), an extension tool may declare a short name with no prefix (`record_todo`, not `todos__record_todo`). The prefix is needed only because `api.tools` finds tools on demand, so the host has no list of names before a call. A direct tool must be declared before the session starts, because the model gets its definition in the request. So the host can keep a map from short name to owner, as bb and Pi do. It refuses a short name that a built-in tool or another extension already has, and shows that as a problem of the extension that registered second. It does not choose silently. The prefixed ID stays the tool's stable ID, so `api.tools.call` reaches it the same way.
