# The Server SDK

The server SDK is what a backend extension gets from the server: the backend's match of the frontend's Reins SDK ([reins-sdk.md](reins-sdk.md), ADR-030). An extension's register function takes it and returns a disposer. It is the "Reins-owned seam" stage of [extension-architecture.md](extension-architecture.md) (*Interface maturity*): an explicit interface with Reins values, which built-in code uses. It is not a plugin system yet: see *Not built yet*.

An **extension** is code that contributes to Reins only through an SDK. It can have a backend part (this SDK) and a frontend part (the Reins SDK). The MCP servers ([mcp-servers.md](mcp-servers.md)) are the first built-in extension.

## Where it lives

```
packages/backend/src/
  sdk/server/index.ts     # @reins/sdk/server: types only
  extensions/             # the host
    host.ts               #   ExtensionHost: the registrations of one app, and each extension's SDK object
    built-in.ts           #   BUILT_IN_EXTENSIONS: the one place that imports a built-in extension (its name, migrations and register function)
    tool-docs.ts          #   api.tools.search's answer and the matching (`tools.match`)
    mcp/                  #   the MCP extension (backend part)
  scripting/tools.ts      # api.tools.search / api.tools.call
  routes/extensions.ts    # /api/extensions/:extension/:method and /extensions/:extension/*
packages/frontend/src/extensions/mcp/   # the MCP extension (frontend part)
```

- **An extension's module** gives a `ServerExtension`: `{ migrations?, register }` (MCP: `mcp` in `extensions/mcp/index.ts`). `built-in.ts` adds its name (`ExtensionRegistration`).
- **`@reins/sdk/server`** (`sdk/server/index.ts`) is a `tsconfig.json` `paths` alias, in the backend and in each package that typechecks backend sources (frontend, client, CLI). It is types only. It imports only its own modules and the type of `bun:sqlite`'s `Database`, which its own `Database` interface extends (lint: `reins/server-sdk-isolation`). Each member's comment states its behavior (lifecycle, order, errors): keep them accurate when the host changes.
- **The boundary** (lint: `reins/backend-extension-boundary`): a backend extension (`extensions/<name>/`) imports only `@reins/sdk/server`, its own modules and npm packages. Nothing outside it imports it, except `extensions/built-in.ts` (its registration) and its frontend part (frontend `extensions/<name>/`, for its types). Tests are not checked. It does not import `bun:sqlite`, not even types: it uses the database it is given, typed by the SDK's `Database`, and opens none itself. When an extension needs something that the SDK does not give, add it to the SDK: do not make an exception.
- **This is a boundary between modules, not a security boundary.** An extension runs in the server process.

## Lifecycle

- **`createAppState`** (`state.ts`) builds the app's `ExtensionHost` (`AppState.extensions`) and registers each extension of `BUILT_IN_EXTENSIONS`, in order. For each, the host first gets its directory and database from the process (`ServerProcess.extensionData`, *Data and database*) and applies its pending migrations, then calls its register function with an SDK object of its own (`ServerSdk`: its `name`, `dataDir` and `db`, and what it registers is recorded as its). Tests give `createAppState` their own list (`extensions`) and a handler for failures (`onExtensionError`; by default they are logged).
- **A failed migration** (or a database that cannot be opened) is reported as the extension's error, and the extension does not register in that app; Reins and the other extensions go on. The failed migration is rolled back, those before it stay applied, and the next app (a reload, a restart) tries it again.
- **The app's `stop`** (`server.ts`) awaits `extensions.dispose()`: each extension's disposer, the last registered first, then the removal of all it registered, also what its disposer forgot. A disposer can return a promise (MCP closes its connections).
- **A hot reload** builds a new app, so each extension is registered again on its new code, its new migrations applied first. What must outlive an app is in its database or directory.
- **Removal:** Reins never deletes an extension's directory (nor its database). An extension no longer registered leaves them as they are.
- **A register function that throws** is reported, and what it registered before the throw is removed. The other extensions still register.
- **Each registration returns its own disposer** (`Disposer`), as in the frontend.

## What an extension contributes

- **Tools** (`tools.register(provider)`). An extension has one `ToolProvider` at a time (registering a second while it has one throws). A provider has a `title`, `search(query, { filters, signal }) → Tool[]` and `call(localId, args, { signal, timeoutMs }) → ToolResult`, which throws for an ID that is none of its tools. A `Tool` is `{ id, name, title?, description?, inputSchema, outputSchema?, annotations? }`, with JSON Schema. `tools.match(query, tools)` ranks as the core does (*Agents and `api.tools`*).
  - **A provider gives local IDs; agents see final IDs.** The final ID is `<extension>__<local ID>`: the host adds the extension's name and `__` to each tool a search finds (`ExtensionHost.searchTools`), and `api.tools.search` documents the final IDs. A local ID is `[a-zA-Z0-9_-]+`, at most `tools.maxLocalIdLength` characters (64 less the prefix), so that a final ID can also be a model's tool name later. It must be unique among the extension's tools and stable: a duplicate is the extension's error. A tool whose ID breaks these rules is left out of the search's answer and reported as the extension's error (logged): the host never changes an ID.
  - **Why the host prefixes IDs.** In Reins, tools are found on demand: there is no registry of tools, unlike bb and Pi, which register tools before a call. The prefix lets the host route a call without a map, also for an ID from before a reload or from an earlier run, and it makes collisions between extensions impossible. Extension names have no `_`, so the first `__` always splits an ID correctly.
  - **The core asks the providers at each search and each call.** A search asks all of them at the same time. A provider that throws is shown in its place, and the others still answer. A query that starts with an extension's prefix reaches that extension without it (an agent that searches for a final ID it has). A call splits its ID at the first `__` and gives the local ID to that extension's provider. An ID without `__`, of no extension or of one without a provider, or whose local ID is not `[a-zA-Z0-9_-]+`, is `UnknownToolError`: no provider is asked.
- **System prompt sections** (`prompt.register(contribution)`). A contribution gets a `PromptContext` (`session` `{ id, projectId, taskId }`, its `task`, and the `tools` the model is offered, null for every tool) and returns text or null, possibly async. The core asks when a session's runtime opens (`SessionModel.context`, through `App.promptSections` of the current app). Only the Reins agent kind gets the sections: they follow the whole Reins section (task included), in the order of registration. A throw is reported, and the session opens without that section.
- **Scripting functions** (`scripting.register({ functions, types? })`): an extension's own `api.<namespace>` in `execute`, documented by `search`. A `ScriptFunction` is the core's `defineFunction` shape with JSON Schema (`parameters` must be an object schema; its properties are the positional arguments). `execute` gets the params and a `ScriptContext` (`sessionId`, `projectId`, `taskId`, `signal`). `types` are named schemas that `search` shows by name. A registration's functions share one namespace, which must not be a core namespace or another registration's (that throws). `scriptingApi(extensions)` (`scripting/api-registry.ts`) gives the core's functions and types plus the extensions'. `runScript` and `search` use it.
- **HTTP** (`reins.http`). **`http.handle(api, handlers)`**: the extension's API, a contract (`HttpApi`) of methods by name (`[a-zA-Z][a-zA-Z0-9_]*`), each with an optional `input` and `output` schema, and a handler for each. A method is `POST /api/extensions/<name>/<method>` with its input as the JSON body: the host checks it against `input` (400 `{ error: "Invalid input: <path>: <message>" }`, and the handler is not called), calls the handler with `{ input, signal, origin }` (`origin`: the origin the browser used, from `X-Forwarded-*`, for callback URLs), and answers its return value as JSON, or 204 for a method without `output`. A thrown Error with a numeric `status` (400–599) is answered with it and `{ error }` (MCP's `RouteError`); any other throw is logged and answered 500 with its message, as for core routes. A method name the extension already handles throws; a method no extension handles, or a request that is not POST, is a JSON 404. `input` must be a TypeBox schema for now, as the host checks it with TypeBox's `Value` (another JSON Schema is refused at registration). The schemas' `static` types type the handlers (`HttpHandlers`) and the frontend's `reins.http.call` (reins-sdk.md *Capabilities*): keep the contract in a module of schemas only (MCP's `api.ts`, `mcpApi`), whose type the frontend part imports. A view type that a schema cannot say exactly keeps its TypeScript type with `Type.Unsafe<T>(schema)`. **`http.page(path, handler)`**: a page the browser goes to itself (an OAuth callback), `GET /extensions/<name><path>` (a URL pattern), whose handler gets a `PageRequest` (`req`, `url`, decoded `params`, `origin`) and returns any `Response`; a path no page matches is a text 404. **`http.pagePath(path)`**: a page's path from the root, to build its URL. `routes/extensions.ts` asks the app's host at each request. `@reins/client` calls the methods with `client.extension(name).call(method, input?)`.

## What the SDK gives an extension

- **`dataDir`** and **`db`**: the extension's own directory and database (*Data and database*). No extension has access to the main database.
- **`migrations`** (on the `ServerExtension`, not the SDK object): its database's schema, applied by the host (*Data and database*).
- **`secrets`**: the extension's secret storage (*Secrets*).
- **`broadcast(message)`**: to every browser, as `{ type: "extension", extension: <name>, message }` (`ServerMessage`'s `extension` member; the frontend's `InboundMessage` has it too). The extension's frontend part tells its messages apart.
- **`logger`**: the server's log.

## Data and database

- **A directory for each extension:** `<data dir>/extensions/<name>/` (`resolveDataDir()`: `REINS_DATA_DIR`, else `.reins/` under the working directory), absolute, as `reins.dataDir`. The extension writes its files only there.
- **A SQLite database for each extension:** `db.sqlite` in its directory, as `reins.db`, opened as the main database is (`openDatabase` in `database.ts`: WAL, foreign keys). A separate file, not prefixed tables in the main database: an extension cannot read or break the core's tables or another extension's, and its data can be moved, backed up or reset alone (ADR-032).
- **The process owns them** (`openExtensionData` in `database.ts`, `ServerProcess.extensionData`, process-owned): the directory is created and the database opened at the extension's first registration, and kept for the life of the process, so every app (each dev reload) gets the same connection, as with the main database. Neither the host nor the extension closes it.
- **Migrations:** `ServerExtension.migrations`, `[{ id, up(db) }]`, oldest first. Before each registration the host applies, in order, those not recorded in the extension's database (its table `reins_migrations`: `id`, `applied_at`), each with its record in one transaction. IDs must be unique non-empty strings (else the extension does not load). `up` is synchronous. Never change a migration that has shipped: add one.
- **The guard:** `reins.db` is the extension's only database (its secrets are in the host's store, *Secrets*) (the host test checks that it is not the main one), and lint keeps an extension from importing `bun:sqlite`, so it cannot open one itself.
- **The type:** an extension names its database `Database` from `@reins/sdk/server`. Today it is an interface that extends `bun:sqlite`'s `Database` and adds nothing, so the extension must run in the Bun server process and use Bun's API (`query`, `exec`, `transaction`). As no extension imports Bun's type, Reins can give the interface its own members later.
- **MCP** keeps its servers in its database (its `001_servers`); core migration `060` copied the rows the main database had there and dropped them ([mcp-servers.md](mcp-servers.md) *Modules*). Its secrets are in the host's store; its `002_host_secrets` dropped its own secrets table (ADR-033).

## Secrets

`reins.secrets` (`SecretStorage`) is a store that the host owns and scopes to each extension, as VS Code's `SecretStorage` is (ADR-033):

- **`get(key)`** (the value, or undefined), **`set(key, value)`**, **`delete(key)`** (nothing for a key it does not have) and **`keys(prefix?)`** (the keys in order, those that start with `prefix`; the prefix is matched as characters, not as a `LIKE` pattern). A key is a string of 1 to 256 characters that the extension chooses; another key, or a value that is not a string, rejects. The extension names its values (MCP: `servers/<id>/<kind>`) and finds a record's values with `keys(prefix)`.
- **Scoped:** an extension sees only its own keys. Two extensions can use the same key.
- **Where:** the main database's table `extension_secrets` (`extension`, `key`, `value`, `updated_at`; core migration `061`), through `extension-secrets-store.ts`. Each value is encrypted with the server's key (AES-256-GCM, `crypto.ts`), the one the core keeps its provider credentials with. The extension never handles ciphertext. `get` rejects for a value the host cannot decrypt (the key changed). Values stay when the extension is no longer registered, as its directory does.
- **Async:** every method returns a promise, though the implementation is synchronous SQLite today, so that a keychain could hold the values later without a change to the contract.
- **Not in the extension's transactions:** a secret's write and a write to `reins.db` cannot be one transaction. The extension orders them so that a half-done change does no harm: MCP deletes a server's secrets before its row, and deletes a server again when its secret cannot be stored at creation.
- **The host** builds each extension's store (`secretStorage(name)` in `host.ts`) and checks keys there.

## Agents and `api.tools`

- **`api.tools.search(query, filters?)`** (`scripting/tools.ts`) returns documentation: each provider's matching tools as a TypeScript interface keyed by final ID (`toolSearchDocs`, `extensions/tool-docs.ts`), grouped by provider in the order of registration, with a `ToolResult` declaration. In each provider, the first 10 are documented and the others named. Without a query, a provider with more than 10 tools only names them. A provider's error is shown in its place. Results of different providers are not ranked against each other.
- **Matching** (`matchTools`, also `tools.match`): each word of the query is a substring of the ID and name (weight 10), title (5), argument names (3) or description (1). The tools that match every word, else, for several words, those that match the most. A plural word also matches its singular. A query that is a tool's ID or name (any case) puts that tool first. With the host's removal of the prefix, a query that is a tool's final ID, its local ID or its name (`mcp__vercel__list_deployments`, `vercel__list_deployments`, `list_deployments`) finds it first. An empty query keeps all.
- **Filters** are a plain object that the core gives to every provider without change (`{}` when none is given). Each provider decides what its keys mean, and what it does with keys it does not know. A provider tells agents its filters in its prompt section.
- **`api.tools.call(id, args?, timeoutMs?)`** takes the final ID and returns the `ToolResult` (a failure the tool reports is a result with `isError`), with the script's signal.
- **`search` lists API functions only** (the `api.tools` functions among them). It never lists the tools and never waits for an extension.

## Tests

`__tests__/extensions/host.test.ts` tests the host through a test extension (`helpers/test-extension.ts`: a provider of fixed tools that records its searches and calls) and `createAppState({ extensions })`: tool searches and calls through `execute`, scripting functions and `search`, HTTP methods (input checks, outputs, statuses) and pages, prompt sections, the extension's directory and database (not the main one), its migrations (once each, in order; a failing one rolled back and only its extension left out), broadcast, secrets (by key, scoped to the extension, encrypted in the main database, kept across apps), and the lifecycle. Tests get each extension's data in a temporary directory of their own (`testExtensionData`, `extensionDb(name)` in `helpers/test-db.ts`), removed after the test. `__tests__/extensions/tool-docs.test.ts` tests the documentation and the matching. MCP's own tests are in `__tests__/extensions/mcp/` ([mcp-servers.md](mcp-servers.md) *Tests*).

## Not built yet

See [backend-extensions.md](../plans/completed/backend-extensions.md) *Not in this plan*: a loader (discovery, packages, manifests, building an extension while the server runs), direct model tools, permissions, trust and sandboxing, versioning, and dependencies between extensions. Settings that an extension declares with a schema, which the host stores and draws (as bb's `settings.define`), possibly on the host's own pages, are a possible later addition; today an extension's frontend part draws its own Settings page ([reins-sdk.md](reins-sdk.md) *Settings pages*, *Not built yet*). A known gap: `reins.db` is `bun:sqlite`'s `Database` (behind the SDK's `Database` interface, which extends it), which an extension outside the server process could not use; the SDK's `Database` would get Reins-owned members, not Bun's, with the loader. Neither does the host check, when a migration was removed or changed, that the database's record still matches the list.

**Direct model tools and their names.** When tools are given to the model directly (not through `api.tools`), an extension tool may declare a short name with no prefix (`record_todo`, not `todos__record_todo`). The prefix is needed only because `api.tools` finds tools on demand, so the host has no list of names before a call. A direct tool must be declared before the session starts, because the model gets its definition in the request. So the host can keep a map from short name to owner, as bb and Pi do. It refuses a short name that a built-in tool or another extension already has, and shows that as a problem of the extension that registered second. It does not choose silently. The prefixed ID stays the tool's stable ID, so `api.tools.call` reaches it the same way.
