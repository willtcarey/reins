# The Server SDK

> New to the extension system? Read [extensions-overview.md](extensions-overview.md) first: the glossary and how the parts fit.

The server SDK is what a backend extension gets from the server: the backend's match of the frontend's Reins SDK ([reins-sdk.md](reins-sdk.md), ADR-030). An extension's register function takes it and returns a disposer. It is the "Reins-owned seam" stage of [extension-architecture.md](extension-architecture.md) (*Interface maturity*): an explicit interface with Reins values, which built-in code uses, and which extensions outside Reins use too: Reins loads their built files from a directory and reloads them ([extension-loading.md](extension-loading.md), ADR-038). It has no compatibility promise yet: see *Not built yet*.

An **extension** is code that contributes to Reins only through an SDK. It can have a backend part (this SDK) and a frontend part (the Reins SDK). The MCP servers ([mcp-servers.md](mcp-servers.md)) are the first built-in extension, automations (triggers that wake sessions, *The automations extension* below) the second, Recent sessions the third, OpenAI images (image models, *Images* below) the fourth and Secrets (*The secrets extension* below) the fifth.

## Where it lives

```
packages/sdk/src/server/index.ts  # @reins/sdk/server: types only (the SDK package, packages/sdk)
packages/backend/src/
  sdk-host/               # the SDK's capabilities, one implementation for every caller (*One layer*)
    declaration.ts        #   Caller, CallContext, sdkMethod (a ScriptMethod's declaration), bind, notForScripts, signalOf
    namespaces.ts         #   CORE_NAMESPACES: the core's namespaces, in the order search lists them
    tools.ts sessions.ts projects.ts nodes.ts images.ts ui.ts models.ts reviews.ts
                          #   each a ScriptNamespace: its methods' schemas, descriptions and implementations
    projection.ts         #   ApiContext, ScriptFunction: a namespace as a script's functions (argument checks, search's view)
    scripts.ts            #   API_FUNCTIONS, DOMAIN_TYPES, scriptingApi, searchFunctions, referencedTypes, buildApiObject
    schema-formatter.ts schema-utils.ts term-search.ts   # search's rendering and matching
  extension-system/       # the system: the app's extensions and the host
    host.ts               #   ExtensionHost: the boundary between extension instances and the server: connect(name, storage)
                          #     → { sdk, start, disconnect }, what each one registered, and how the server reads it
    extension-sdk.ts      #   createExtensionSdk: one connection's ServerSdk, its secrets
    backend.ts            #   startBackend: storage → migrations → connect → register(sdk) → start
    services.ts           #   ServiceRunner: one registered service's instances, restarts and state
    extensions.ts package.ts report.ts manifest.ts
                          #   the app's extensions (records, states, operations), added ones' packages, the report (extension-loading.md)
    tool-docs.ts          #   reins.tools.search's answer and the matching (`tools.match`)
  extensions/             # the built-in extensions, and only them
    built-in.ts           #   BUILT_IN_EXTENSIONS: the one place that imports a built-in extension (its name, migrations and register function)
    built-in-names.ts     #   every built-in's name, either part (BuiltInExtensionName)
    mcp/                  #   the MCP extension (backend part)
    automations/          #   the automations extension (backend only)
    recent-sessions/      #   the Recent sessions extension (backend part: which sessions are recent)
    openai-images/        #   the OpenAI images extension (backend only: endpoints.json and the image provider)
  tools/execute.ts        # runScript: a script's vm, with reins (buildApiObject) and text()/image()
  tools/search.ts         # searchScriptApi: search's answer
  routes/extensions.ts    # GET /api/installed-extensions (the host's report), /api/extensions/:extension/:method and /extensions/:extension/*
packages/frontend/src/extensions/mcp/   # the MCP extension (frontend part)
```

- **An extension's module** gives a `ServerExtension`: `{ migrations?, register }` (MCP: `mcp` in `extensions/mcp/index.ts`). `built-in.ts` adds its name (`BuiltInBackendPart`).
- **`@reins/sdk/server`** (`packages/sdk/src/server/index.ts`) is part of the SDK package, `@reins/sdk` (`packages/sdk`), which an added extension depends on; in this repository a `tsconfig.json` `paths` alias, in the backend and in each package that typechecks backend sources (frontend, client, CLI). It is types only. It imports only its own modules and the type of `bun:sqlite`'s `Database`, which its own `Database` interface extends (lint: `reins/server-sdk-isolation`). Each member's comment states its behavior (lifecycle, order, errors): keep them accurate when the host changes.
- **The boundary** (lint: `reins/backend-extension-boundary`): a backend extension (`extensions/<name>/`) imports only `@reins/sdk/server`, its own modules and npm packages. Nothing outside it imports it, except `extensions/built-in.ts` (its registration) and its frontend part (frontend `extensions/<name>/`, for its types). Tests are not checked. It does not import `bun:sqlite`, not even types: it uses the database it is given, typed by the SDK's `Database`, and opens none itself. When an extension needs something that the SDK does not give, add it to the SDK: do not make an exception.
- **This is a boundary between modules, not a security boundary.** An extension runs in the server process.

## Lifecycle

- **`createAppState`** (`state.ts`) builds the app's `Extensions` (`AppState.extensions`), giving it the app (`() => state`, read at each SDK call, as the node hub reads it); it makes and owns the app's `ExtensionHost` (`extensions.host`, which the core reads) and starts its extensions (`Extensions.start`): it records each built-in and starts each extension of `BUILT_IN_EXTENSIONS`, in order, except one the user turned off (extension-loading.md *The record*). Starting one (`startBackend`, backend.ts) gets its directory and database from the process (`ServerProcess.extensionData`, *Data and database*), applies its pending migrations, connects it to the host (`ExtensionHost.connect`: an SDK object of its own, `ServerSdk`, with its `name`, `dataDir` and `db`; what it registers through it is recorded as its), calls its register function with that SDK, then starts its services. Tests give `createAppState` their own list (`extensions`, then the only built-ins in the test helper) and a handler for failures (`onExtensionError`; by default they are logged).
- **A failed migration** (or a database that cannot be opened) is reported as the extension's error, and the extension does not register in that app; Reins and the other extensions go on. The failed migration is rolled back, those before it stay applied, and the next app (a reload, a restart) tries it again.
- **The app's `stop`** (`server.ts`) first, while its node links are open, stops the extensions' processes without a key and lets go of the keyed ones (`AppState.processes.release()`, *Nodes*), then awaits `extensions.dispose()`: first every extension's services are stopped, all at once (*Services*), then each extension's disconnection, the last recorded first: its disposer, then the removal of all it registered, also what its disposer forgot. A disposer can return a promise (MCP closes its connections).
- **A hot reload** builds a new app, so each extension is registered again on its new code, its new migrations applied first. The old app's `stop` has stopped its services before the new app starts them again. What must outlive an app is in its database or directory.
- **Server shutdown** (SIGTERM, SIGINT, a restart of the server alone) suspends the runs, then awaits the app's `stop` (at most 10 s, `exitProcess` in `server-process.ts`), so the services stop and the extensions are disposed before the process exits.
- **Removal:** Reins never deletes an extension's directory (nor its database). An extension no longer registered leaves them as they are.
- **A register function that throws** is reported, and what it registered before the throw is removed. The other extensions still register.
- **Each registration returns its own disposer** (`Disposer`), as in the frontend.
- **Added extensions** start the same way, in the background as the app's state is created (`Extensions.start`; `Extensions.loaded` settles when they are in); one can be unloaded alone (its connection disconnected: its services stopped, its disposer awaited, all it registered removed) and loaded again, which is how it reloads ([extension-loading.md](extension-loading.md)).
- **Turning one off** (any extension, `Extensions.setEnabled`) unloads it the same way and records it `disabled`; it does not start in the next apps until it is turned on. After each operation on one extension (turning it off or on, reloading or removing it), and once an app's extensions are in (`Extensions.start`), the host stops the kept processes of every extension not loaded (*Nodes*). The records and their states: extension-loading.md *Loading in the server*.
- **A service registered while the register function runs waits**: the connection starts services once register returns (`connection.start()`); one registered later starts at once.

## What an extension contributes

- **Tools** (`tools.register(provider)`), and every extension's tools to use (`tools.search`, `tools.call`, *Tools on the SDK*). An extension has one `ToolProvider` at a time (registering a second while it has one throws). A provider has a `title`, `search(query, { filters, signal, sessionId }) → Tool[]` and `call(localId, args, { signal, timeoutMs, sessionId }) → ToolResult`, which throws for an ID that is none of its tools. `sessionId` is the session whose script searches or calls, as a script method's `ScriptContext` has it; null when an extension searches or calls itself (`reins.tools`). The provider looks up what else it needs (`reins.sessions.get`: its project, task and `source.nodeId`, the node its tools run on), so the core passes one ID, not a copy of the session's row. A provider may answer per node, and later refuse or hide tools per session; MCP takes it and does not read it yet (its servers are all HTTP, the user's). A `Tool` is `{ id, name, title?, description?, inputSchema, outputSchema?, annotations? }`, with JSON Schema. `tools.match(query, tools)` ranks as the core does (*Agents and `reins.tools`*).
  - **A provider gives local IDs; agents see final IDs.** The final ID is `<extension>__<local ID>`: the host adds the extension's name and `__` to each tool a search finds (`ExtensionHost.searchTools`), and `reins.tools.search` documents the final IDs. A local ID is `[a-zA-Z0-9_-]+`, at most `tools.maxLocalIdLength` characters (64 less the prefix), so that a final ID can also be a model's tool name later. It must be unique among the extension's tools and stable: a duplicate is the extension's error. A tool whose ID breaks these rules is left out of the search's answer and reported as the extension's error (logged): the host never changes an ID.
  - **Why the host prefixes IDs.** In Reins, tools are found on demand: there is no registry of tools, unlike bb and Pi, which register tools before a call. The prefix lets the host route a call without a map, also for an ID from before a reload or from an earlier run, and it makes collisions between extensions impossible. Extension names have no `_`, so the first `__` always splits an ID correctly.
  - **The core asks the providers at each search and each call.** A search asks all of them at the same time. A provider that throws is shown in its place, and the others still answer. A query that starts with an extension's prefix reaches that extension without it (an agent that searches for a final ID it has). A call splits its ID at the first `__` and gives the local ID to that extension's provider. An ID without `__`, of no extension or of one without a provider, or whose local ID is not `[a-zA-Z0-9_-]+`, is `UnknownToolError`: no provider is asked.
- **Image models** (`images.registerProvider(provider)`): an `ImagesProvider` for agents' `reins.images` (*Images*).
- **System prompt sections** (`prompt.register(contribution)`). A contribution gets a `PromptContext` (`session` `{ id, projectId, taskId }`, `projectId` null for a session of no project, its `task`, and the `tools` the model is offered, null for every tool) and returns text or null, possibly async. The core asks when a session's runtime opens (`SessionModel.context`, through `App.promptSections` of the current app). Only the Reins agent kind gets the sections: they follow the whole Reins section (task included), in the order of registration. A throw is reported, and the session opens without that section.
- **Script methods** (`scripting.register({ namespace, methods, types? })`): an extension's own `reins.<namespace>` in `execute`, documented by `search`. It is a `ScriptNamespace`, the declaration the core's namespaces use (*One layer*): each method a `ScriptMethod` (`description`, `params` (`[{ name, schema, optional? }]`, the positional arguments), `returns`, `tags`, `run(context, ...args)`), its `context` a `ScriptContext` (`sessionId`, the calling session, whose project, task and node `reins.sessions.get` gives; and `signal`), as a script's session is always the caller. The params' schemas must be TypeBox schemas: the host checks a script's arguments with them before `run` (*Scripts*). `types` are named schemas that `search` shows by name. The namespace must not be a core namespace or another registration's (that throws). An extension types `run` from its declaration with a one-line helper (`scriptMethod` in `mcp/scripting.ts`), as the core does with `sdkMethod`. `scriptingApi(extensions)` (`sdk-host/scripts.ts`) gives the core's functions and types plus the extensions'. `runScript` and `search` use it.
- **HTTP** (`reins.http`). **`http.handle(api, handlers)`**: the extension's API, a contract (`HttpApi`) of methods by name (`[a-zA-Z][a-zA-Z0-9_]*`), each with an optional `input` and `output` schema, and a handler for each. A method is `POST /api/extensions/<name>/<method>` with its input as the JSON body: the host checks it against `input` (400 `{ error: "Invalid input: <path>: <message>" }`, and the handler is not called), calls the handler with `{ input, signal, origin }` (`origin`: the origin the browser used, from `X-Forwarded-*`, for callback URLs), and answers its return value as JSON, or 204 for a method without `output`. A thrown Error with a numeric `status` (400–599) is answered with it and `{ error }` (MCP's `RouteError`); any other throw is logged and answered 500 with its message, as for core routes. A method name the extension already handles throws; a method no extension handles, or a request that is not POST, is a JSON 404. `input` must be a TypeBox schema for now, as the host checks it with TypeBox's `Value` (another JSON Schema is refused at registration). The schemas' `static` types type the handlers (`HttpHandlers`) and the frontend's `reins.http.call` (reins-sdk.md *Capabilities*): keep the contract in a module of schemas only (MCP's `api.ts`, `mcpApi`), whose type the frontend part imports. Define a method's input and output in the contract itself: the frontend takes their types from it (`HttpOutput<RecentSessionsApi["list"]>`, `@reins/sdk`) and the backend with TypeBox's `Static`, so the module exports no type of its own beyond the contract's (Recent sessions' `api.ts`). A view type that a schema cannot say exactly keeps its TypeScript type with `Type.Unsafe<T>(schema)`. **`http.page(path, handler)`**: a page the browser goes to itself (an OAuth callback), `GET /extensions/<name><path>` (a URL pattern), whose handler gets a `PageRequest` (`req`, `url`, decoded `params`, `origin`) and returns any `Response`; a path no page matches is a text 404. **`http.pagePath(path)`**: a page's path from the root, to build its URL. `routes/extensions.ts` asks the app's host at each request. `@reins/client` calls the methods with `client.extension(name).call(method, input?)`.

- **Services** (`services.register({ name, start })`): the extension's long-running work, in the host's lifecycle (*Services*).
- **Sessions** (`reins.sessions`): starting sessions, messaging them, reading and changing them, waiting for them and hearing when the runs of those it started end (*Sessions*).
- **Nodes** (`reins.nodes`): the nodes, and files and commands on them (*Nodes*).
- **Projects and tasks** (`reins.projects`, `reins.tasks`): reading, creating and changing them (*Projects and tasks*).
- **Images, UI, models and code reviews** (`reins.images`, `reins.ui`, `reins.models`, `reins.reviews`): the same methods agents have in `execute` (*One layer*); `reviews` refuses an extension, which has no session.

## One layer: the SDK, bound to a caller

Each capability is implemented once, in `sdk-host/`, as SDK methods over the models (ADR-036). An extension's `reins.<namespace>` and an agent's `reins.<namespace>` in `execute` are the same methods, under the same object name, bound to a different **caller** (`Caller` in `declaration.ts`):

- **A script's caller is its session** (`{ kind: "session", session, signal }`): defaults are its own (`"current"` IDs, its project, task, source, node and model), what it starts is its child when it says so, what it sends is a session update from it (`sourceSessionId`), and every call gets the script's signal.
- **An extension's caller is the extension** (`{ kind: "extension", name }`): it acts as no session, so it names what a script may leave out (a node, a project, a source), `"current"` is refused ("… names the calling session, and an extension has none"), and what it starts and sends records it (`sourceExtension`). Its options may carry a `signal`.
- **One declaration.** Each method callable from scripts is a `ScriptMethod` (`@reins/sdk/server`), declared once beside its implementation with `sdkMethod` (`declaration.ts`): its `description`, its `params` (`[{ name, schema, optional? }]`, the positional arguments, TypeBox schemas), its `returns` schema, `tags` for `search`, and `run(context, ...args)`, whose arguments are typed by the params' schemas and whose result by `returns` (`__tests__/sdk-host/type-safety-check.ts`). A namespace is a `ScriptNamespace` (`{ namespace, methods, types? }`); `CORE_NAMESPACES` (`namespaces.ts`) lists the core's. The SDK's interfaces (`Sessions`, `Nodes`, …) are written in `packages/sdk/src/server/index.ts` (types only), and the host's SDK object is checked against them: `bind(namespace.methods, context)` gives methods typed by the declaration, so a declaration that drifts from the interface does not compile.
- **`toScript`**: a method whose script form differs from its result says so: `tools.search` gives an extension the matching tools (`ToolSearchGroup[]`) and a script their TypeScript documentation (`returns` documents the script's form).
- **Async everywhere**: every method returns a promise, for both callers.
- **Errors** are the same for both: "Session not found: <id>", "Project not found: <id>", "Task not found: <id>", "Node not found: …".

### Scripts: what they may call, and how

- **Only what is declared.** `services`, `http`, `prompt`, `db`, `secrets`, `broadcast`, `logger`, the registrations (`tools.register`, `images.registerProvider`, `scripting.register`) and `sessions.onSettled` are extensions' only: they are not `ScriptMethod`s, so scripts never see them.
- **Fields and options for extensions only** are marked in the schema with `scripts: false` (`notForScripts`): `signal` (`SignalSchema`), `sessions.start`'s `background` and `metadata`, `sessions.send`'s `metadata`, `ui.openFile`'s `sessionId`. `search` leaves them out, and a script that gives one is refused; a trailing argument left with no field for scripts (`send`'s options) is not a script's argument at all. Only trailing arguments may be dropped so (the projection throws otherwise), as a script's arguments are positional.
- **The projection** (`projection.ts`, `scriptFunctions(namespace, contextOf)`) makes each method a function of a script's `reins` (`ScriptFunction`: what `search` documents, and `call(args, ctx)`). `contextOf` maps the script's `ApiContext` (`session`, `models`, `signal`) to the method's context: the core's `scriptCallContext`, an extension's `ScriptContext`. `buildApiObject` (`scripts.ts`) puts them on the script's `reins` (`runScript`), and `searchScriptApi` (`tools/search.ts`) renders them (`schema-formatter.ts`): positional params, `Promise<…>` returns, descriptions as doc comments and `@param` tags, named types by name (a named type made optional keeps its name: `sameSchema`, `schema-utils.ts`).
- **Argument checks** happen before `run`, with the declared schemas (TypeBox `Value.Check`): a missing required argument, a wrong type ("reins.tools.call: options: Expected object"), more arguments than declared ("reins.tools.call takes at most 3 arguments (id, args, options)"), and a field an object schema does not have ("reins.sessions.list: options has no field \"project_id\" (its fields: projectId, …)"): a misspelt or renamed option is an error, not ignored. A script's `Uint8Array` is another realm's class; the check takes it as bytes and gives the method the server's.

### Tools on the SDK

`reins.tools.search(query, { filters?, signal? })` and `reins.tools.call(id, args?, { timeoutMs?, signal? })` are the operations `reins.tools.*` gives scripts (*Agents and `reins.tools`*): an extension finds and calls every extension's tools, MCP servers' included, and its own, by their final IDs. `search` resolves to each provider's group (`{ title, tools }`, the tools with final IDs, or `{ title, error }`), in the order of registration; `call` to the `ToolResult`, rejecting for an unknown ID ("Unknown tool: …") and what the provider throws. A script's search is the same groups as TypeScript documentation (`toolSearchDocs`).

## Sessions

`reins.sessions` and `reins.sessions` (`Sessions` in the SDK; `SESSIONS` in `sdk-host/sessions.ts`, over the `Sessions` model: `create`, `submit`, `waitForSettlement`, `compact`, `getContext`, `setModel`, `updateMetadata`) start sessions, message them, read and change them and wait for them. The extension's object adds `onSettled`, whose listeners the host keeps.

- **A session** (`SessionInfo`, `Session` in `search`): `id`, `source` (`{ id, nodeId, path }`), `projectId` and `taskId` (null for none), `parentSessionId`, `name`, `firstMessage` (its first input's text as lists show it, null before it has one), `messageCount`, `model` (`{ provider, modelId, thinkingLevel }`, null before it has one), `background`, `running` (its run is in progress now, `Sessions.running`), `unread` (not running, and its last run ended with something the user has not opened: `activity_state = 'finished'`, the browser's amber dot), `pinned`, `archived`, `startedBy` (the extension that started it, or null), `lastRunStartedAt` (when its latest run started, the one in progress else the newest that ended, from Pi's records: `readPendingPiOperation`, `readNewestRunResult`; a message steered into a running run does not change it), `lastRunId` (the latest ended run's ID, `settlement_json.operationId`, null before the first: a new one after a `send` means the run that took the message ended, as Pi handles accepted steering before a run's end), `createdAt`, `updatedAt`. Any session can be read, of any project.
- **`get(sessionId)`**, **`current()`** (a script's own; an extension is refused) and **`entries(sessionId, query?)`** (its transcript's messages and tool calls, `listSessionEntries`, with `createdAt`).
- **`list(query?)`**: from a script, by default the sessions the browser lists (not archived, not background) of its project (a session of no project: the sessions of no project on its source), pinned first, then the latest change; `projectId`, `taskId` (`"current"`, or null for those of no task), `since`, `search`, `minMessages`, `background`, `limit` (1 to 200) and `offset` narrow it. From an extension without `projectId`: those of every project and of none, the latest change first (`updated_at`, `listSessions` with `projectId: "any"`, `orderBy: "latest"`), 50 at a time unless `limit` says otherwise, paged with `offset`, so a reader that filters (Recent leaves out closed tasks' sessions) reads on until it has enough. A `limit` or `offset` out of range rejects.
- **`start(prompt, options?)`** → `{ sessionId }`, once Pi admitted the prompt (not when the run ends). `prompt` is `MessageContent`. From a script, `options.parentSessionId` is required (`"current"`: a child, which reports back; null: independent), and what it leaves out is the caller's: its project, its task in its own project (in another project none unless `taskId` names one of it), its source (in another project the source a session of it inherits), its model; a child more than 3 deep is refused. From an extension, `source` (a source ID or `{ nodeId, path }`: `ensureSource`, a directory no session used yet is checked on its node) or `projectId` is needed: without a source, a project's session inherits as `createSession` does (its task's latest session's source, else the project's default source); with neither, it refuses ([ADR-034](../adr/034-sources-without-projects.md)). `model` (`{ provider, modelId, thinkingLevel? }`), `title`; for extensions only `background` (a session the browser never shows, backend-architecture.md *Tools*) and `metadata`. It checks a blank prompt, then creates the session as every client does (`Sessions.create`, the same checks and messages as HTTP): refusals keep nothing (no source or project, an unknown project, task (or one of another project), source or node, a path that is not a directory there, and an offline node for a new one, a model the catalog does not have, a blank title). A first prompt the session refuses (its node was removed) rejects `start`, and the session stays, to be prompted again with `send` or moved.
- **`send(sessionId, message, options?)`** → resolves once admitted. It steers: a running session takes the message into its work, an idle one starts a run with it (session-runtime.md *Submission and ordering*). It does not look at whether the session is busy: the caller decides that, with `get`. Any session. Rejects for an unknown session, a blank message and what submission refuses (a removed node).
- **`wait(sessionId, timeoutMs?)`** → `{ sessionId, status, result, error }` once the session is at rest, at most `timeoutMs` (0 to 30 000, 10 000 by default); a script cannot wait for its own session.
- **`compact(sessionId, { instructions? })`** → resolves once the compaction started (`Sessions.compact`, session-runtime.md *Manual compaction*: in the session's order, its runtime opened if needed), not when it ends: the session reads `running` until then. Rejects for an unknown session ("Session not found: <id>"), a running one and one with nothing to compact (`CompactionRefusedError`'s messages). Pi already compacts near the context limit: this is for a caller's own lower limit (an automation's `compactAboveTokens`).
- **`contextUsage(sessionId)`** → `{ usedTokens, contextWindow, measurement: "exact" | "estimated" }` or null: the session's context occupancy, as the browser's context meter reads it (`Sessions.getContext`, session-runtime.md *Events*, "Context occupancy"), null without a known model.
- **`setModel(sessionId, provider, modelId, thinkingLevel?)`**, **`setName(sessionId, name | null)`**, **`setPinned`**, **`setArchived`** → the session after.
- **Content** (`MessageContent`, `send`'s message and `SessionStart.prompt`): a string, or blocks in order, each a string (visible) or `{ text, hidden?, label? }`. Every block is a text block of the input, and the model gets them all, the hidden ones a blank line after the visible ones (`providerInput` in `pi-runtime.ts`: a provider can join text blocks with nothing between them), with nothing else (not the label, nor that the user sees them collapsed). Reins marks where the hidden blocks begin in the input's metadata (`metadata.details: { label, start }`; `SessionSubmission.details`). The chat shows the visible blocks in the bubble and the hidden ones collapsed under it, opened from the origin label ("sent from <extension>", else "Details"), with the label at their top (`UserMessage.visibleContent` and `details` in the frontend's `models/message.ts`). The session list's first message is the first block (`content[0]`). Refused: hidden blocks before a visible one, no visible block, a blank block, a label on another block than the first hidden one, or one that is blank or over 80 characters. An extension says in the hidden blocks what the model needs to know about them (automations: that a command's output is not the user's words).
- **Metadata** (`MessageMetadata`, on `send`'s options and `SessionStart.metadata`): the extension's own data on a message, any plain JSON object of at most 64 KiB, kept in the input's `metadata` (`SessionSubmission.metadata`) and not given to the model. Refused: Reins' keys (`sourceExtension`, `sourceSessionId`, `details`), and anything that is not plain JSON (a `Date`, a class instance), naming where. Nothing reads an extension's keys yet: they are there for its own parts later (a frontend decorator, a reader of the transcript).
- **Attribution.** A session an extension starts records it (`sessions.source_extension`, migration 063; `SessionView.sourceExtension`, scripts' `startedBy`), and every input it submits carries `metadata.sourceExtension: <name>` beside the existing `metadata.sourceSessionId`. The chat shows "sent from <name>" under a user message with it, and the session list's subtitle "from <name>". Unlike a session update (`sourceSessionId`), the content reaches the model as it is, like a user's: the extension is trusted code of the server, configured by the user.
- **`onSettled(listener)`** → `Disposer`. Each time a run of **a session this extension started** ends, once its end is recorded (`runSettled` in `sessions/session-runs.ts`, after the row and the broadcast), the listener gets `{ sessionId, status: "completed" | "failed" | "cancelled", result, error }`: `result` is the final reply's text on the run's branch (`finalReply`, null without one) for a completed run, `error` why a run failed or was cancelled. Only the extension's own sessions, so an automation records its runs' results without holding a promise across reloads. A runtime applies its run's end with no app, then tells the current app (`App.sessionSettled`, optional, through `ExtensionHost.sessionSettled`): a run that ends during a reload's gap (no app) is not told, nor one a process exit cut off before its end was applied (session-runtime.md *Recovery*); the extension reads what it missed with `get`. A listener that throws or rejects is the extension's error (logged, kept in its report). The host counts each extension's listeners (`registrations.settlementListeners`).

## Projects and tasks

`reins.projects`/`reins.projects` and `reins.tasks`/`reins.tasks` (`PROJECTS`, `TASKS` in `sdk-host/projects.ts`, over the project and task stores and `ProjectModel.tasks()`): any project or task, by its ID.

- **`ProjectInfo`** `{ id, name, baseBranch, defaultSourceId, createdAt, lastOpenedAt }`; `projects.list()`, `get(id)` (rejects "Project not found: <id>"), `current()` (a script's project, null for a session of no project; an extension is refused) and `create(name, path, baseBranch?, nodeId?)` (an extension names the node; a script's defaults to its own).
- **`TaskInfo`** `{ id, projectId, title, description, branchName, baseCommit, status, closedAt, createdAt, updatedAt }` (`closedAt` null while it is open; reopening clears it); `tasks.get(id)` (rejects "Task not found: <id>"), `update(id, { title?, description?, baseCommit? })`, `close`, `reopen` take a task of any project; `list(status?, projectId?)`, `create(title, description, branchName?, projectId?)` work in a project, the script's by default (a session of no project, and an extension, must name one: tasks belong to projects); `current()` is a script's task.

## Nodes

`reins.nodes`/`reins.nodes` (`NODES` in `sdk-host/nodes.ts`, over the `Nodes` model and its `NodeHost`): the nodes, and files and commands on any of them, nothing confined (as a session's commands are). A node is named by its ID (stable: keep this one) or its name (any case); a script may say `"current"`, its session's node, also the default of `get` and `reload`, which an extension must name.

- **`list()`**, **`get(node?)`** (with its sources), **`reload(node?, force?)`**, **`readFile(node, path, { binary? })`**, **`writeFile(node, path, content)`**, **`copy(fromNode, fromPath, toNode, toPath)`** ([features/scripting.md](../features/scripting.md) *Files and commands on any node*), each with an extension's `signal` in its options.
- **`run(node, command, { cwd?, timeoutMs?, env?, signal? })`** → `{ exitCode, output, truncated }` (`CommandResult`): bash on the node. `cwd` is absolute, `~/…` or relative to the node's home (the default). `env` (names `[A-Za-z_][A-Za-z0-9_]*`) is added to the node's environment for the command (Pi's exec `env`, sent in `pi.exec`'s options): a value given there needs no quoting and is not in the command's text or its process's arguments, which is how a secret reaches a command (`printf '%s\n' "KEY=$KEY" >> .env`, *The secrets extension*). `output` is stdout and stderr together, at most the first 16 MiB (`MAX_SCRIPT_BYTES`: it is held in the server's memory), `truncated` when there was more. A failing command resolves with its exit code. `run` **rejects** for a blank command, a `timeoutMs` out of range (a script's: 1 to 30 000; an extension's: 1 to 600 000, as no agent waits for it; 30 s by default), an unknown or removed node ("Node not found: <node> (the nodes: …)"), one that is not connected now ("Node unavailable: …": it does not wait for the node), the timeout ("Command timed out after <ms> ms on …") and the signal (an `AbortError`). An extension gives a service's `signal`, so that a reload or a shutdown kills the command. It runs as `bash -c` (stderr joined to stdout), to its end, on the node's one process primitive (node-contract.md *Processes*), as git does.
- **`spawn(node, command, { cwd?, env?, maxLineBytes?, signal?, key?, ifRunning? })`** → a `NodeProcess`, **for extensions only** (not a `ScriptMethod`, so scripts' `reins.nodes` does not have it; checked by `checkSpawn` in `sdk-host/nodes.ts`, started and kept by the app's `Processes`, `models/processes.ts`, as the owner `extension:<name>`, through `extension-system/extension-processes.ts`): a long-running process on the node, as an MCP client runs a stdio server. `command` is argv (an array: no shell) or a string (`/bin/sh -c`). It resolves once the process runs, and gives `id`, `nodeId`, `pid`, `key`, `reattached`, `previous` and `lostBytes` (below), `lines` (stdout as whole lines; a line over `maxLineBytes`, 8 MiB by default, stops it and throws) or `chunks` (raw; one of the two, read once, and keep reading: stdout nobody reads fails it at 64 MiB), `write(data)` (resolves once the process has taken the bytes, in order; at most 16 MiB not yet taken), `closeInput()`, `stderrTail()` (the last 64 KiB characters, to say why it failed), `onStderr(listener)`, `exited` (`{ code, signal, error?, detached? }`, never rejects, only for a real end; `error` when a line was too long, stdout was not read or its node no longer has it; `detached` when the host let go of it) and `stop()` (stdin closed, SIGTERM to its process group, SIGKILL after 3 s; resolves with `exited`). The shape wraps an MCP SDK `Transport`: `start` reads `lines` into `onmessage`, `send` is `write(JSON.stringify(message) + "\n")`, `close` is `stop`, `exited` gives `onclose` (and `onerror` with its `error`). It rejects for a blank command, an environment variable name that is not `[A-Za-z_][A-Za-z0-9_]*`, `maxLineBytes` out of range, a key that is not 1 to 256 characters, `ifRunning` without a key, an unknown, removed or disconnected node, a directory or program the node does not have, and a node already running as many processes as it may (64). **A dropped link does not end it** (node-contract.md *Processes*): the handle attaches again on the node's next link, within the node's grace period (60 s), reading on from where it was, and resends its writes. **It ends** when it exits, is stopped, its `signal` aborts or its node restarts. **Without a key** the extension's unloading stops it (its connection's disconnection stops every process it started, one still starting too: a disposer, a reload, turning it off). **With a key** ([ADR-039](../adr/039-node-processes.md)) the process is the host's: a key is unique per extension and node (`mcp:<server>`, `dev:<project>`, `lsp:<source>`); the host records (extension, node, key, process ID, pid, output offset, an HMAC of the command, `cwd` and `env` under the server's key, how it ended) in the main database (`processes`, migration 066, under its owner, `extension:<name>`; `process-store.ts`), not the extension's, as it must find them when the extension's code does not load. **`ifRunning: "replace"`** (the default) stops a process kept under the key, resolving once it has ended, and starts a fresh one; **`"attach"`** gives a handle on it (`reattached: true`, reading from where the extension's handles had read it to), or starts one when there is none, it ended (`previous` says how: its exit, or lost with its node, as for a replace that finds it gone), or its hash differs from the one given (`reattached: false`). Calls on one key are taken one at a time, so concurrent attaches share one process, and an app has **one handle per process**: a call that finds the process an earlier call of this app started gets that call's handle (with its `reattached`, `signal` and `maxLineBytes`), which its users share. `lostBytes` counts output the node no longer kept when the handle attached, or attached again after a link down (its tail is 8 MiB): a reader of whole messages starts again, a log view shows a gap. On an unload or the app's stop (a reload, a restart) the host **lets go of** keyed processes (`exited` resolves `detached`; their output offset recorded), before the extension's disposer runs, so a disposer that stops its handles stops none of them: do not stop a keyed process you mean to keep. Once the extension is not loaded (turned off, removed, or its code not loading after a reload or a restart), the host stops its kept processes and forgets them (one on a node away is stopped when the node connects within its grace period; past it, the node stopped it). **`processes()`** → `ProcessInfo[]` (`{ key, nodeId, pid, state, exit?, startedAt }`, `state` `running` in this app, `detached` or `ended`), before any spawn, in key order. **`stop(node, key)`** stops the process kept under the key without a handle and forgets the key; resolves with how it ended, or null for a key with nothing kept (on a node away it is only forgotten, with an exit saying so). Records do not expire: one goes when its key is used again, stopped, or its extension not loaded. After a crash, the recorded offset is the last let-go's: output since then is read again. **`env`** goes to the node only in the start request, which neither side logs, and the node keeps nothing of it, nor does the host (only the hash): a secret may go there (ADR-013, ADR-039), never in the command's text. **Why not scripts:** a process outlives the call that starts it, and a script's work ends with it; a session's own background processes need the session-owned lifecycle in docs/TODO.md (*Background processes on a session*).

## The automations extension

The second built-in (`extensions/automations/`, backend only; user doc [features/automations.md](../features/automations.md)). It shows the SDK's sessions, nodes, services, database and HTTP together: no core code knows it.

- **A trigger, a target and a message.** An automation is a row (`automations`, migration `001_automations`) made by `reins.automations.create` or `POST …/create`. Its trigger is a schedule (`trigger = 'schedule'`) or a command checked at an interval (`'command'`: `command`, `node`, `cwd`, `timeout_ms`; the interval is `schedule`). Its target is a session it messages (`target = 'session'`: from a script, the calling session, `ScriptContext.sessionId`), a hidden session of its own (`'own'`: `sessions.start` with `background: true` at its first delivery, in the calling session's source by default with no project, then `send`), or a new session at each delivery (`'new'`: `sessions.start`, shown in the browser unless `background`, its ID only in its run). The sessions it starts are in `project_id` when it is set (a script's `project`: `"this"`, an ID or null; by default the calling session's project for `'new'`, none for `'own'`). It is not a reference: the project is the core's, so a deleted project makes each `start` fail, recorded as a failed run. A `'new'` delivery is skipped while a session an earlier one started still runs (`previousEnded`), for a schedule and a command alike, so the next check does not hand out what it still works on. `once` cancels it after its first delivery.
- **Every delivery is a `send`** (*Attribution*): a running session takes it into its run. The message is sent as it was given; what the model needs beside it goes in a hidden block (`automationDetails`): which automation sent it and when (not its trigger: the session it messages most likely made it), how to cancel it, and a command's output in a fence marked untrusted (`untrustedOutput`, at most 16 000 characters), as the extension's messages reach the model as a user's do and the output can carry other people's text.
- **A schedule is skipped only while the run its previous message started still runs.** After each send the extension stores the session's `lastRunId` (`last_send_*`). At the next due time it skips when the session is `running` and its `lastRunId` has not changed: no run has ended since that message was admitted, so the run that took it is still going. Work of anyone else in progress gets the message. A command's firing is never skipped.
- **The scheduler** is one service (`scheduler`) whose loop ticks at once and then every 30 s (the *Services* pattern), with the service's signal. Each tick reads the active rows from the database, so a reload or restart loses nothing; and as the next time is computed from the tick that ran it, a delivery missed while Reins was down happens once, at the first tick. A due automation's `next_run_at` is moved before anything is sent or run, so a failure does not repeat at each tick. A command check runs outside the serial chain (`Automations.checking`: one per automation at a time), so a slow command holds up no other automation; its result is applied in the chain. A target session that `get` finds archived (`archived`) or not found cancels the automation; an own session that is gone is replaced at the next delivery.
- **Run history** (`automation_runs`, the latest 200 of each): `sent`, `skipped` or `failed` (the send was refused, or the check could not run) for a target session, whose runs the extension does not hear (it did not start that session); `running`, then `completed`, `failed` or `cancelled` from `onSettled` with the final reply as `output`, for an own session (messages that joined one run share its end). A run still `running` at a later delivery while its session is idle is `lost` (its end came during a reload's gap). A command's firing records its `exit_code` and `check_output`; checks that did not fire are only counted (`checks`, `last_check_at`). Ticks, check results and settlements are handled one at a time (`Automations.serial`), so a settlement always finds the run its `start` recorded.
- **Compaction:** after a completed run, an own session with `compact_above_tokens` reads `contextUsage`; above the threshold the run is marked `compaction = 'pending'`, and the next tick that finds the session idle calls `compact` (with `COMPACTION_INSTRUCTIONS`). Not in the settlement listener itself: the runtime is still busy applying the run's end there, and `compact` refuses a busy session.
- **A message is optional for a command trigger** (`message` null): its output is then the visible message (`messageOf`; "`<command>` succeeded." for none), and the details say it is a command's output, not the user's words. A schedule needs one.
- **The prompt section** (`prompt.ts`, `reins.prompt`, for agents offered `execute`): when to make an automation ("tell me when this deploys") and end the turn rather than wait or poll, which trigger to use, and to run a command that ends within a few minutes itself.
- **Schedules** (`schedule.ts`): intervals (`5m`, `every 1h30m`, at least 1 minute) are parsed by the extension; `daily HH:MM`, `weekdays HH:MM` and five-field cron expressions go to [croner](https://github.com/hexagon/croner) (no dependencies, IANA timezones, local times kept across offset changes). The timezone is checked with `Intl`.
- **Surfaces:** `reins.automations.create`, `cancel`, `list`, `runs`, `replaceSession` (`scripting.ts`) and the same as HTTP methods (`api.ts`, `routes.ts`: `create` takes `target: { session } | { own: { source, … } }` and a command's `node`, as there is no calling session; `cancel` records "Cancelled by the user"). No frontend part yet.
- **Tests:** `__tests__/extensions/automations/` on the fake model, a loopback node and a fake clock (`helpers/automations-extension.ts`: `startAutomations(reins, { now, pollMs })`, its scheduler ticking once at start and then when the test calls `tick`; `idle` waits for the checks a tick started).

## The secrets extension

The fifth built-in (`extensions/secrets/`, with a frontend part, `packages/frontend/src/extensions/secrets/`; user doc [features/secrets.md](../features/secrets.md)). It uses only the SDKs: no host code knows it, and no host seam was added for it but `nodes.run`'s `env`.

- **A request returns at once.** `reins.secrets.request({ names, purpose?, descriptions? })` (`scripting.ts`, the calling session from `ScriptContext.sessionId`) checks the names (`[A-Za-z_][A-Za-z0-9_]*`, unique, 1 to 50; descriptions only of names asked for), stores a row in `requests` (migration `001_requests_and_secrets`), broadcasts `{ type: "changed" }` and returns `{ requested, next }`: `next` tells the agent to end its turn. Nothing waits: the run may end, be aborted or the server restart, and the request stays.
- **The user answers in the session.** The frontend part follows `workspace.onDidChange` and opens `{ view: "secrets-request", requestId }` in the Inspector, once per request in each browser, when the main area shows the requesting session (`currentSubject("session")`); it reads the open requests (`requests`) again on each broadcast and reconnect, so a reloaded page and other browsers follow. The form posts the values to `submit` (`api.ts`), the only place values cross; `cancel` ends a request.
- **Submit** (`Secrets.submit`): exactly the request's names, each value one non-empty line of at most 16 KiB with no NUL (else 400, and the request stays open); a request being answered refuses a second answer (404). Each value goes into `reins.secrets` under `values/<handle>` (a handle is `sec_` and 24 random bytes, base64url), then the session is woken (`sessions.send`): visible "The user entered NAME.", and a hidden block (`Secret handles`) with each name's handle and how to use it. Only then are the `secrets` rows written and the request deleted; a send that fails deletes the values again and keeps the request. Cancel sends "The user cancelled the request for NAME: nothing was stored."
- **Use by handle.** `reins.secrets.get(handle)` gives the value and records `last_used_at`; an unknown or deleted handle rejects. Whoever has a handle reads the value, so a session reads only what it was given; there is no list for agents. The agent gives the value to a command as `env` (`nodes.run`), never in its text. The model sees a value only if a script returns or prints it: there is no redaction yet.
- **Deletion:** the `expiry` service deletes the secrets whose last use (or storage, when never used) is more than 7 days old (`KEEP_UNUSED_MS`), every 10 minutes; the Settings page lists the open requests (Cancel) and the stored secrets by name, without values or handles (`stored`), and deletes one (`remove`). The value is deleted before its row.
- **The prompt section** (`prompt.ts`, agents offered `execute`): one line, that `reins.secrets.request` is there for sensitive values and the chat is not. How to use it (one request for all known names, end the turn, give values as `env`, never read the file back) is in the `request` and `get` descriptions (`scripting.ts`), which `search("secrets")` gives.
- **Tests:** `__tests__/extensions/secrets/` on the fake model and a loopback node, a fake clock (`startSecrets(reins, { now, sweepMs })`); the frontend's in `frontend/src/__tests__/extensions/secrets/` (the opening rule, the form).

## The Recent sessions extension

The third built-in (`extensions/recent-sessions/`, with a frontend part, `packages/frontend/src/extensions/recent-sessions/`; user doc [features/sidebar.md](../features/sidebar.md)). It owns what "recent" means, so no core code knows it: the core gives only `sessions.list`, `projects.get` and `tasks.get`.

- **Its one method, `list({ limit })`** (`api.ts`, `recentSessionsApi`, `limit` 1 to 50): the `limit` sessions with the latest activity (`updatedAt`: a run ending, a rename; opening one changes nothing), each as the sidebar draws it: `{ id, name, firstMessage (the frontend shows the name, else the first message), project (its name, or null), task (its title, or null), updatedAt, activity ("running", "unread" or null) }`.
- **A closed task puts its sessions away** (`recentSessions` in `index.ts`): a session of a closed task is left out unless a run started in it after the task closed (`lastRunStartedAt` later than `closedAt`), or the task is reopened. A run going when the task closed (an agent closing its own task) ends after it, which changes `updatedAt`, but does not bring the session back, as it does not mark it unread (`runStartedBeforeTaskClosed` in `sessions/session-runs.ts`). It reads `sessions.list` 50 at a time until it has `limit` (at most 500 read), and each project and task once per answer.
- **Liveness is the frontend part's** (reins-sdk.md *The sidebar*): it asks again after the browser hears sessions, tasks or projects change. The backend part broadcasts nothing.
- **Tests:** `__tests__/extensions/recent-sessions/` through the HTTP route; the SDK's reads in `__tests__/extension-system/sessions.test.ts`.

## Services

A service is long-running work of an extension (a timer, polling, a queue) that the host starts and stops, so that no extension keeps its own `setInterval` across reloads. `reins.services.register({ name, start })` returns a `Disposer`. The host gives nothing specific to scheduling: the service does what it likes in `start`.

- **`start(context)`** gets `{ signal, logger, fail }` and returns, or resolves to, `{ stop?() }` (or nothing). `logger` is the server's log, each line prefixed `[<extension>:<service>]`. `signal` aborts when the host stops the instance, before it calls `stop`.
- **Names** are lowercase letters, digits and hyphens, unique among the extension's services (a second registration of a name throws). There is never more than one instance of a service in the server process: the host starts the next instance only after the last one stopped (except after a stop that did not end, below).
- **When it starts:** after the extension registered (its storage opened, its migrations applied, its register function returned). A service registered later starts at once. A failed extension (storage, migration or register stage) starts none: what it registered is removed.
- **When it stops:** the host aborts `signal`, waits for a `start` still in progress, then calls `stop`: when its registration is disposed, when the extension is disposed (the app's `stop`: a dev reload, a shutdown) and after a crash. Its services stop before the extension's disposer runs, as they may use what it closes. **The wait is bounded: 5 s** (`STOP_TIMEOUT_MS` in `services.ts`), then the host reports `Service <name> did not stop within 5 s` as the extension's error and goes on, so a stuck service cannot hold up a reload or a shutdown. After a reload the new app starts it again on its new code. A `stop` that throws is reported.
- **A crash** is a `start` that throws or rejects, or `context.fail(error)` after `start` returned (a loop that cannot go on). The host reports it as the extension's error (`Service <name> crashed: …`), stops the instance as above and starts a new one after a backoff: 1 s, doubling, at most 5 min, and back to 1 s when the crashed instance had run for a minute (`healthy`). Only an instance's first `fail` counts; a `fail` after it was stopped is nothing. A crashed instance whose stop did not end in time leaves the service `failed`: the host starts no other in that app, as the old one may still run. A promise the service leaves rejected without `fail` is not seen by the host.
- **Status:** the host records each service's state (`ServiceView` in `services.ts`): `starting`, `running`, `restarting` (with `nextAttemptAt`), `stopped` (the host stopped it) or `failed` (above), with `since` (when it entered that state), `restarts` (how many times the host started it again after a crash) and `lastError` (`{ message, at }`). The host's report gives it (`ExtensionView.services`, *What the host knows*). It goes with the app, as the extension's errors do: a reload starts the count again.
- **End everything with the signal.** The host has no timers of its own to give: a service passes `signal` to each thing that waits or listens, so the abort ends them all and it needs no `stop`. A `setInterval` it clears itself is the leak to avoid: a forgotten `clearInterval` keeps the old code's timer running after each reload, beside the new one, and the host cannot see it. For polling, a loop that waits between ticks:

  ```ts
  import { setTimeout as sleep } from "timers/promises";

  reins.services.register({
    name: "poll",
    start: ({ signal, fail }) => {
      void (async () => {
        while (!signal.aborted) {
          await poll(signal);
          await sleep(5_000, undefined, { signal });
        }
      })().catch(fail);
    },
  });
  ```

  A slow `poll` delays the next one and never overlaps it. A throw from `poll` reaches `fail`: a crash, restarted with backoff. The `AbortError` at the stop reaches `fail` too, but the host ignores a `fail` after it aborted the signal. Not `for await` over `timers/promises`' `setInterval`: it does not overlap either, but after a slow tick it runs the ticks it missed one after another. `fetch(url, { signal })`, `addEventListener(type, listener, { signal })` and `Bun.spawn({ signal })` end the same way. Keep `stop` for what takes no signal (a connection to close).
- **Later:** a child process (`{ command, args, node? }`) as another kind of service, under the same lifecycle and status. Until then a service starts one with `reins.nodes.spawn` and its `signal`. A service is a definition the host runs (`ServiceRunner`), so another kind is another way to start and stop an instance.

## What the SDK gives an extension

- **`dataDir`** and **`db`**: the extension's own directory and database (*Data and database*). No extension has access to the main database.
- **`migrations`** (on the `ServerExtension`, not the SDK object): its database's schema, applied by the host (*Data and database*).
- **`secrets`**: the extension's secret storage (*Secrets*).
- **`broadcast(message)`**: to every browser, as `{ type: "extension", extension: <name>, message }` (`ServerMessage`'s `extension` member; the frontend's `InboundMessage` has it too). The extension's frontend part tells its messages apart.
- **`logger`**: the server's log.

## Data and database

- **A directory for each extension:** `<data dir>/extensions/<name>/` (`resolveDataDir()`: `REINS_DATA_DIR`, else `.reins/` under the working directory), absolute, as `reins.dataDir`. The extension writes its files only there.
- **A SQLite database for each extension:** `db.sqlite` in its directory, as `reins.db`, opened as the main database is (`openDatabase` in `database.ts`: WAL, foreign keys). A separate file, not prefixed tables in the main database: an extension cannot read or break the core's tables or another extension's, and its data can be moved, backed up or reset alone (ADR-032).
- **The process owns them** (`openExtensionData` in `database.ts`, `ServerProcess.extensionData`, process-owned): the directory is created and the database opened at the extension's first registration, and kept for the life of the process, so every app (each dev reload) gets the same connection, as with the main database. Neither the host nor the extension closes it.
- **Migrations:** `ServerExtension.migrations`, `[{ id, up(db) }]`, oldest first. Before each registration the host applies, in order, those not recorded in the extension's database (its table `reins_migrations`: `id`, `applied_at`), each with its record in one transaction. IDs must be unique non-empty strings (else the extension does not load). `up` is synchronous. Never change a migration that has shipped: add one.
- **The guard:** `reins.db` is the extension's only database (its secrets are in the host's store, *Secrets*) (the host test checks that it is not the main one), and lint keeps an extension from importing `bun:sqlite`, so it cannot open one itself.
- **The type:** an extension names its database `Database` from `@reins/sdk/server`. Today it is an interface that extends `bun:sqlite`'s `Database` and adds nothing, so the extension must run in the Bun server process and use Bun's API (`query`, `exec`, `transaction`). As no extension imports Bun's type, Reins can give the interface its own members later.
- **MCP** keeps its servers in its database (its `001_servers`); core migration `060` copied the rows the main database had there and dropped them ([mcp-servers.md](mcp-servers.md) *Modules*). Its secrets are in the host's store; its `002_host_secrets` dropped its own secrets table (ADR-033).

## Secrets

`reins.secrets` (`SecretStorage`) is a store that the host owns and scopes to each extension, as VS Code's `SecretStorage` is (ADR-033):

- **`get(key)`** (the value, or undefined), **`set(key, value)`**, **`delete(key)`** (nothing for a key it does not have) and **`keys(prefix?)`** (the keys in order, those that start with `prefix`; the prefix is matched as characters, not as a `LIKE` pattern). A key is a string of 1 to 256 characters that the extension chooses; another key, or a value that is not a string, rejects. The extension names its values (MCP: `servers/<id>/<kind>`) and finds a record's values with `keys(prefix)`.
- **Scoped:** an extension sees only its own keys. Two extensions can use the same key.
- **Where:** the main database's table `extension_secrets` (`extension`, `key`, `value`, `updated_at`; core migration `061`), through `extension-secrets-store.ts`. Each value is encrypted with the server's key (AES-256-GCM, `crypto.ts`), the one the core keeps its provider credentials with. The extension never handles ciphertext. `get` rejects for a value the host cannot decrypt (the key changed). Values stay when the extension is no longer registered, as its directory does.
- **Async:** every method returns a promise, though the implementation is synchronous SQLite today, so that a keychain could hold the values later without a change to the contract.
- **Not in the extension's transactions:** a secret's write and a write to `reins.db` cannot be one transaction. The extension orders them so that a half-done change does no harm: MCP deletes a server's secrets before its row, and deletes a server again when its secret cannot be stored at creation.
- **The host** builds each extension's store (`secretStorage(name)` in `extension-sdk.ts`) and checks keys there.

## What the host knows of each extension

The host records every registration with the extension whose SDK made it (each list it keeps has the extension's name: providers, prompt contributions, scripting registrations, HTTP methods, pages, services, listeners), and `Extensions` keeps a record of each extension of the app: where it came from, its state (its storage and migrations once opened, what stopped it) and its later errors. **`Extensions.list()`** reports them, in the order their records were made (one turned off or on again moves to the end), as `ExtensionView`s (`describe`, report.ts):

- **`status`**: `loaded`, `loading` (an added extension being imported), `disabled` (turned off: nothing registered, no storage open), or `failed` with **`failure`** `{ stage, message }`: an added extension's `manifest` or `load` (a file it names is missing, or its module could not be imported or is not an extension), then `storage` (its directory or database could not be opened), `migration` or `register` (its register function threw).
- **`frontendFailure`**: an added extension's frontend part's failure as a browser last reported it (`{ message, at }`, the message with the stack), or null (extension-loading.md *In the browser*).
- **`source`**, **`manifest`**, **`build`** and **`backendPart`** (`ExtensionOrigin`): where it came from (`{ kind: "built-in" }` or `{ kind: "path", path }`), an added extension's manifest (`label`, `description`, `version`, `icon`) and its files (`id`, their hash, and its frontend part's `script` URL), null for built-ins; and whether it has a backend part (not a built-in with only a frontend part, which the host records `loaded` with nothing on the server; extension-loading.md). A failed extension has registered nothing. Services have their own status (`services`, below), which does not change the extension's.
- **`errors`**: what the extension reported after it loaded (a tool ID left out of a search, a prompt contribution that threw), `{ message, at }`, the latest last, at most 10. `onError` still gets each one. Errors from disposal are not kept: the record goes with the app.
- **`registrations`**: what it has registered now, read from the host's lists, so a disposed registration (its own disposer, or the app's `stop`) is gone: `tools` (its provider's `title`, or null; no tool count, which would ask the provider and could go to the network), `promptSections` (how many), `settlementListeners` (how many `reins.sessions.onSettled` listeners), `scriptFunctions` (names), `httpMethods` (names) and `pages` (paths from the root).
- **`services`**: its services now, in the order of registration, each a `ServiceView` (*Services*): a disposed one is gone.
- **`storage`** (null when it could not be opened): `dataDir`, `databaseBytes` (`db.sqlite` and its WAL file), `migrations` (`applied`, `{ id, appliedAt }` from `reins_migrations` in order, and `pending`: the declared ones not applied, such as a failed one and those after it) and `secrets` (how many it keeps: neither keys, which can name the user's things, nor values).

**`GET /api/installed-extensions`** (`routes/extensions.ts`) answers `list()` of the current app. It is the host's route, not under an extension's prefix (an extension's methods are `/api/extensions/<name>/<method>`, one segment deeper, so they cannot clash). `@reins/client` calls it with `client.installedExtensions.list()`. Settings' Extensions section shows it, merged with the frontend parts ([reins-sdk.md](reins-sdk.md) *Extensions*, [features/extensions.md](../features/extensions.md)).

## Images

Core has the registry and the agent surface; every image provider is an extension's. `reins.images.registerProvider(provider)` registers an extension's `ImagesProvider` (`models(signal)` gives its model IDs; `generate(model, request, signal)` gives `ImageBlock[]`), one at a time. The host keeps them in `imageProviders`, by extension name.

- **IDs:** agents see `<extension>__<model>`, split at the first `__`, as tool IDs are. A provider's own ID has no whitespace and may hold `/` (`william-pc/Qwen-Image`).
- **`images.list()` and `images.generate`** (`sdk-host/images.ts`, `reins.images` and `reins.images` alike): `list()` asks every provider at once (a throw fails the list). `generate(prompt, { model?, images?, size?, count?, parameters? })` uses the first listed model when there is no `model`, and gives `{ model, images }`. `images` takes what `image()` takes (`collectImages`), so an earlier result can be edited.
- **Script output** (`tools/script-output.ts`, `runScript` in `tools/execute.ts`): `text(value)` and `image(...items)` are globals of the script's vm, adding blocks in call order; the return value comes last (left out when undefined). The images are fitted (`fitImage`, as `read`'s) once the script ended, one at a time: Bun has crashed when many resizer workers were cut off at once. `ScriptExecuteResult` has `content` only when the script used them, and keeps `text` for a runtime of older code (session-runtime.md *Reaching the current app*). The `after_tool` hook stores the images as attachments.
- **The openai-images extension** (`extensions/openai-images/index.ts`, user doc [features/images.md](../features/images.md)) reads `endpoints.json` in its data directory at each call, checked with a TypeBox schema. It has no database, HTTP API or Settings page. Its tests use a fake server (`helpers/fake-openai-images.ts`).
- **Not yet:** a direct model tool, an adapter to Pi's `ImagesModels`, and a Settings page for endpoints (docs/TODO.md).

## Agents and `reins.tools`

- **`reins.tools.search(query, { filters? })`** (`sdk-host/tools.ts`; `reins.tools.search` gives the same groups as data, *Tools on the SDK*) returns documentation: each provider's matching tools as a TypeScript interface keyed by final ID (`toolSearchDocs`, `extension-system/tool-docs.ts`), grouped by provider in the order of registration, with a `ToolResult` declaration. In each provider, the first 10 are documented and the others named. Without a query, a provider with more than 10 tools only names them. A provider's error is shown in its place. Results of different providers are not ranked against each other.
- **Matching** (`matchTools`, also `tools.match`): each word of the query is a substring of the ID and name (weight 10), title (5), argument names (3) or description (1). The tools that match every word, else, for several words, those that match the most. A plural word also matches its singular. A query that is a tool's ID or name (any case) puts that tool first. With the host's removal of the prefix, a query that is a tool's final ID, its local ID or its name (`mcp__vercel__list_deployments`, `vercel__list_deployments`, `list_deployments`) finds it first. An empty query keeps all.
- **Filters** are a plain object that the core gives to every provider without change (`{}` when none is given). Each provider decides what its keys mean, and what it does with keys it does not know. A provider tells agents its filters in its prompt section.
- **`reins.tools.call(id, args?, { timeoutMs? })`** takes the final ID and returns the `ToolResult` (a failure the tool reports is a result with `isError`), with the script's signal (an extension's `reins.tools.call` takes its own `signal`).
- **`search` lists API functions only** (the `reins.tools` functions among them). It never lists the tools and never waits for an extension.

## Not built yet

See [backend-extensions.md](../plans/completed/backend-extensions.md) *Not in this plan*. The loader is built ([extension-loading.md](extension-loading.md): a directory on disk, a manifest naming built files, reloads); git sources, node parts and versioning beyond the manifest's `sdk` range are not. Also not: direct model tools, permissions, trust and sandboxing, versioning, and dependencies between extensions. Settings that an extension declares with a schema, which the host stores and draws (as bb's `settings.define`), possibly on the host's own pages, are a possible later addition; today an extension's frontend part draws its own Settings page ([reins-sdk.md](reins-sdk.md) *Settings pages*, *Not built yet*). A known gap: `reins.db` is `bun:sqlite`'s `Database` (behind the SDK's `Database` interface, which extends it), which an extension outside the server process could not use; the SDK's `Database` would get Reins-owned members, not Bun's, if extensions ever ran in another process (external ones run in the server's, ADR-038). Neither does the host check, when a migration was removed or changed, that the database's record still matches the list.

**Direct model tools and their names.** When tools are given to the model directly (not through `reins.tools`), an extension tool may declare a short name with no prefix (`record_todo`, not `todos__record_todo`). The prefix is needed only because `reins.tools` finds tools on demand, so the host has no list of names before a call. A direct tool must be declared before the session starts, because the model gets its definition in the request. So the host can keep a map from short name to owner, as bb and Pi do. It refuses a short name that a built-in tool or another extension already has, and shows that as a problem of the extension that registered second. It does not choose silently. The prefixed ID stays the tool's stable ID, so `reins.tools.call` reaches it the same way.
